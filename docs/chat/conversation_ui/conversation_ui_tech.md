## Database Schema

No draft table or migration. `composerDraft.store` and the build draft map live only in renderer memory. Save to Notes creates an ordinary row in the existing profile-scoped `notes` table; it stores the captured body, without a chat foreign key or synchronization with later transcript changes.

## IPC Channels

- `note:create` through `window.api.notes.create({ title, body })` returns the existing `NoteData`; main resolves the active profile. See [Notes channels](../../notes/notes/notes_tech.md#ipc-channels).
- Copy uses `navigator.clipboard.writeText`; draft edits and the curtain have no IPC. Attachment preparation and run dispatch keep their existing channels.

## Services & Key Methods

### Draft ownership

- `composerDraftKey` serializes a tuple of profile ID (or null) and `dashboard`, `agent:<id>` or `chat:<id>`. `useComposerDraftKey` derives it from the active profile and entry identity. Agent-page drafts do not reuse the dashboard's null-chat buffer.
- `useComposerDraftStore.update` merges a field patch and skips unchanged identities. `useComposerDraftField` subscribes to one field and binds its setter to the originating key, so typing does not rerender the workspace and an awaited operation cannot write into a newly visible composer.
- Each draft contains text, note ID/title references, files with upload/error/token state, new-chat `modeSelection`, ordered `pendingAgentIds` and `pendingMcpIds`, plus `sending`. Mode intent is `auto`, `none` or a live mode ID. Null agent intent uses the entry page's seed; an empty list preserves explicit removal.
- `beginSend(key)` synchronously acquires the draft's preparation lock; `endSend(key)` releases it in `finally`. A component-local ref used to reset on remount, allowing a return to the entry page to dispatch the same preparation twice. The lock belongs to the draft, not all composers.
- `ChatInput.clearComposer` compares the submitted text by value and note/file lists by identity before clearing them in the source key. `ChatWorkspace.handleNewChat` similarly resets only unchanged mode/agent/MCP intent after `startNewChat` returns true. Changed fields and in-flight file state remain available.
- `useNewChatFlow.startNewChat` returns true after calling `startRun`, false after preparation failure/guard cancellation and best-effort orphan cleanup. Missing deferred files are a failure rather than a successful send with silently omitted paths. `useChatComposer.submit` returns false for missing chat cache or empty content; attachment-only active sends are valid. These outcomes mean dispatch, not successful run completion.
- `useChatAttachments` keeps a monotonically assigned upload token in the draft. Completion/failure/finally update the source only while that token matches. Navigation/unmount preserves it; explicit clear invalidates it. Destination capability/scope is validated on send so loading queries cannot discard a restored attachment.

### Message context actions

- `MessageBubble` marks each rendered body with `data-message-markdown`. The source is the exact string the body renders: attachment tags stripped on the assistant path and nested code fences repaired on both, so Copy text and Save to Notes never carry a model's broken nesting or its zero-width escapes. Labels, metadata and cursors are outside the source payload. Structured turns expose each rendered text body independently.
- `MessageStream` attaches `useMessageContextMenu` to the transcript container. `messageContextText(root, target, selection, point?)` returns empty text, and the hook opens no menu, unless the selection meets all of these: it is non-collapsed, both range endpoints are inside the container, the range intersects the right-click target, and `selection.toString()` is not blank. When `point` is given, it must also fall inside one of `range.getClientRects()`, each stretched vertically by half of the target's computed `line-height` minus `font-size`; the rects cover the glyphs while the highlight fills the line, so a click between two selected lines would otherwise miss. The hook passes `point` only when `clientX` or `clientY` is non-zero, treating a zero pair as a keyboard-opened menu. There is no fallback to the closest body. When the target's closest marked body is inside the container and `range.toString()` matches its `textContent` (both trimmed), the body's `data-message-markdown` source is returned. Any other selection returns `selection.toString()` as plain text. The comparison uses the range and not the selection because Chromium's `Selection.toString()` inserts layout line breaks between blocks.
- `MessageContextMenu` captures text before focus changes and renders a fixed portal clamped eight pixels inside the viewport. Each opening has an identity; completion from an older action cannot close a newer menu.
- `useSaveMessageNote` uses the first nonempty line, removes a leading one-to-six-hash heading marker, caps the title at 80 characters and falls back to Chat excerpt. Its returned callback captures profile identity synchronously at the gesture, before React Query schedules the mutation. The mutation checks identity before existing Notes create IPC and after completion, returning no note for a changed profile and invalidating `['notes']` only for the unchanged profile. The caller navigates to the returned note only while its menu is mounted. Inside that guard it calls `setSidebarTab('notes')` and `setRevealNoteId`, then `setActiveNoteId` and `setActiveView('note-detail')`. `NoteItem` scrolls the row into view once and clears the reveal intent.
- A synchronous action ref prevents duplicate Copy/Save calls; both controls disable while pending. Failures remain in a retryable alert. Dismissal does not cancel an already requested note write.

### Nested code fences

- **Entry.** `src/renderer/src/utils/nestedFences.ts:repairNestedFences(markdown, { streaming })`. Called by `MessageBubble` for both roles and by `collectFileRefSources` in `src/renderer/src/components/chat/fileRefs.tsx`. Without `streaming` it repairs the whole text.
- **Parser.** A module-level `unified().use(remarkParse).use(remarkGfm)`, the parser `react-markdown` renders the bubble with. `unified` and `remark-parse` are direct dependencies pinned to exact versions, and the lockfile holds one copy of each, shared with `react-markdown`. Keep it that way: two copies could parse a reply two ways, and the repair would be aimed at a tree the bubble does not render.
- **Gate, before any parse.** Text with no triple backtick returns at once. Otherwise it is split on `\r\n`, `\r` or `\n` with the break sequences kept aside, so the parser's line numbers index the lines and the output rejoins with the original endings. `mayHoldNesting` then walks the backtick fence lines, with blockquote markers, list markers and indentation stripped first, and tracks the width of the fence it is inside. A zero-width character in front of any fence sends the text to the parser. Inside a fence, a shorter run is content and is skipped, and a bare run at least as wide closes the fence. A run at least as wide that names a language sends the text to the parser. That catches nesting whether the outer fence is bare or names a language (a bare fence wrapping a `bash` block is the commonest way a model nests). An outer fence already longer than every fence inside it passes without a parse. Passing the gate proves nothing either way: a python string holding a same-width `` ```json `` line reaches the parser too, and the early-close rules below decide. The container prefix spells its whitespace `[ \t]`, because `\s` would also consume a U+FEFF.
- **Cache.** A text that passes the gate is looked up in an eight-entry least-recently-used cache. The key is the mode (streaming or complete) plus the text, and the value is the result. A streaming bubble asks on every token, but the streaming pass only sees complete lines, so it hits while only the last line grows. The mode is part of the key because the streaming pass defers blocks the complete pass repairs. The size is eight because several bubbles can stream at once.
- **Blocks.** `parse` walks the tree in document order. For every `code` node whose source starts with three or more backticks it records the block and the children list it sits in. Indented code and tilde fences are skipped, since neither can be what a model meant as a backtick fence. A block counts as closed only when its span ends in a backtick run at least as long as the opener, and the span covers the value plus two lines (one line for an empty block whose closer follows the opener directly). An unclosed block that stops at a line break reports the next line as its end, so the line count alone would pass it for closed.
- **Inner opener (`innerOpeners`).** A value line with up to three spaces of indent, at least as many backticks as the block's own fence, and an info string. A zero-width character in front of the backticks keeps a line out, because that one was escaped.
- **Rounds (`repairParsed`).** Each round repairs zero-width escapes over the current parse, then applies at most one early-close repair and parses the result again. It stops when no candidate has evidence, or after 32 rounds (`MAX_ROUNDS`). The zero-width repair still runs on that last parse. The cost is one parse plus one per early-close repair; the zero-width repair adds none, because widening moves no block, so the parse still reads the text it rewrote. Rewrites only widen backtick runs, so a line index names the same line in every parse.
- **Zero-width escapes (`repairZeroWidthEscapes`).** Needs no further evidence, because the model marked the inner fences. It runs on every parse, because an early-close repair below can turn escaped fences it had left in prose into a block's content. A block it repaired no longer matches in the next round. Inside one block's value, zero-width fence lines are paired stack-wise: an opener carrying an info string with the next bare one. Paired lines lose the zero-width character. The outer opener and closer widen to one backtick more than the longest fence in the value, and never narrow. Unpaired zero-width lines, and zero-width fences outside any block, are left as written. U+FEFF counts as U+200B.
- **Early close, candidates (`closesEarly`).** A closed block that was not repaired for zero-width escapes qualifies when three things hold:
  - its value holds exactly one inner opener line;
  - that line is not the value's last;
  - the closer that ended the block is at least as long as that opener.

  Each refusal is a case with no single reading:
  - two inner openers;
  - a lone `` ```python `` line ending a block, which merely shows the line and cut nothing off;
  - a closer shorter than the inner opener, which cannot be that block's own.

- **Outer closer (`outerCloser`).** The first later sibling that is a backtick block and is either bare or unclosed. Prose, and closed blocks that name a language, are skipped, since an intact snippet holds those whole. When that block names a language there is no closer. Only siblings count, because a block in another container cannot have been opened by this block's closer. Bare blocks past the first are never read.
- **Evidence (`nextEarlyClose`).** Candidates are read from the last block to the first, so a later snippet's repair can take away the closer an earlier block would wrongly close over. The first candidate with evidence is repaired. Evidence is one of two things:
  - the closer is closed and holds an inner opener of its own;
  - the closer is unclosed and the pass is not streaming.

  A bare closer that closed with no inner opener is not evidence: it is as likely an inner block of the snippet, or an ordinary block after it. So a snippet whose second inner block is bare, or one followed later by an ordinary bare block, stays as parsed.
- **The rewrite (`closeAt`).** Widens the block's opener and the closer's opener to one backtick more than the longest fence line between them, so the block closes there.
- **Rewriting a line (`rewriteFence`).** Widens the first backtick run on the line and drops a zero-width character directly in front of it. A container prefix holds no backticks, so list indentation, blockquote markers and the info string stay as written.
- **Streaming.** With `streaming`, only the text up to the last `\n` is repaired. When that head changes, the partial last line is appended as it arrived; when it does not, the original string is returned. The streaming pass also refuses an unclosed closer, and accepts only a closer that swallowed an inner opener, which later lines cannot undo. So a line widened while streaming normally stays widened, and a snippet whose outer closer is the last bare fence so far is repaired at finalize.

  The known gap is a chain, where the closer is itself a broken snippet that a later fence repairs. Traced with a `markdown` snippet followed by a bare block holding a `python` opener and a bare block holding a `js` opener:
  - while streaming, the `markdown` opener and the first bare fence were widened;
  - once the `js` block's closing fence arrived, still mid-stream, the first and second bare fences were widened instead, which is also the complete result.

  `MessageStream` passes `isStreaming` only to the last live text block (`isStreaming && isLastBlock`), so earlier text blocks of a live turn, and every saved message, are repaired whole.

## Renderer Components

### Draft restoration and context-menu focus

- On a draft key change, `ChatInput` focuses the textarea, places both selection endpoints at its current value length and scrolls to the bottom. Its layout effect sizes to the restored text, capped at 180 px. Keystrokes do not rerun the caret effect. Transient mention/capability menus, note previews and expansion targets reset independently of saved fields.
- `DevelopmentComposer` retains `localDev.store.drafts[profileId]`. Its active/focus effect restores the end caret when the build composer returns; readiness and open dialogs still gate focus. Runtime choices remain installation settings, not draft fields.
- Copy receives initial menu focus. Pointer enter/move focuses the enabled item under the pointer; arrows wrap, Home/End select first/last. One focus background drives the highlight, with a 100 ms color transition disabled under reduced motion.
- Escape, Tab and PageUp/PageDown dismiss; outside pointerdown, wheel/touchmove, resize, blur and chat/profile change dismiss too. Programmatic scroll events are deliberately ignored so streaming bottom-follow does not close an action menu. Cleanup restores previous connected focus only if focus was still inside the dismissed menu.

### MessageBubble

- `src/renderer/src/components/chat/MessageBubble.tsx`

- **`MarkdownContent` (memoized)**: a `React.memo` subcomponent rendering `<Markdown remarkPlugins={breaks ? USER_REMARK_PLUGINS : REMARK_PLUGINS} rehypePlugins={highlight ? [rehypeHighlight] : []} components={chatMarkdownComponents}>`. `chatMarkdownComponents` (`src/renderer/src/components/chat/fileRefs.tsx`) is `markdownComponents` plus `pre`/`code` overrides that make resolved inline code a [file reference](../file_references/file_references.md); it is module-level so the memo never sees a new identity. `React.memo` skips re-parsing when the transcript re-renders but this bubble's `content` is unchanged; `highlight` is `!isStreaming` on the assistant path (and always true for user bubbles) so fenced code is highlighted once per turn rather than on every streamed token. `breaks` is passed only by the user path, which adds `remark-breaks` to `remark-gfm` so a single newline renders as `<br>`; the two plugin lists are module-level constants, so the memo sees a stable array. Pinned by `MessageBubble.lineBreaks.test.tsx`, which also checks an assistant's lone newline stays a soft wrap.
- **Meta popup**: optional `MetaPopup` shown on hover (info icon) for assistant messages with metadata.

### Code block styling

- `src/renderer/src/assets/main.css`, inside `@layer base`. `.markdown-body pre` sets the margin, 8 px radius, horizontal scroll and a `--color-bg` fill for every `pre` in a Markdown body.

Those sit inside `ToolNarrationBlock`'s `markdown-body` wrapper, in a summary box that already has a border.

Numbers and literals sit a step darker than built-ins and types, which share their hue. `rehype-highlight` runs only once a turn finalizes (`highlight={!isStreaming}`), so a streaming block is unhighlighted in either theme.

### Entry-animation triggering (in MessageStream)

- `prevRef` holds `{ chatId, messageIds }` from the previous render. A message is considered "new" only when `chatId` matches the previous render AND `messages.length === prev.messageIds.length + 1` AND the last message's id wasn't in the previous set. This skips initial loads, chat switches, and bulk re-fetches.
- For the messages list, `shouldAnimate` is computed as `msg.id === newMessageId && !suppressStreamReanimation`, where `suppressStreamReanimation = msg.role === 'assistant' && streamedIncrementallyChatId === chatId`. This means a saved assistant message for the chat that just streamed will NOT re-animate (chunks already animated individually), while a saved assistant message that did not come from incremental streaming — or a new user message — animates normally.
- For streaming plain-text blocks (`kind: 'text'` in `streamingBlocks`), MessageStream renders `<MessageBubble role="assistant" content={block.content} isStreaming={isStreaming && isLastBlock} />` — the same component as the persisted message, so Markdown formats live and there's no raw→formatted snap (or newline-handling shift) on the streaming→saved swap. `MessageBubble` defers `rehype-highlight` while `isStreaming`. There is no per-delta span animation.
- Streaming `thinking`, `tool`, and `tool_result` kinds still use `ThinkingBlock` / `ToolNarrationBlock` / `ToolResultBlock` with their joined `content` (block-level fade; `tool_result` uses a `<pre>` body instead of Markdown).

### Part-routing in MessageStream

For persisted assistant messages with `msg.parts`, `MessageStream` maps each `MessagePart` to a block via a switch on `part.kind` (`thinking` → ThinkingBlock, `tool` → ToolNarrationBlock, `tool_result` → ToolResultBlock, `text` → MessageBubble). Wrapped in a `space-y-2` container for visual separation. For streaming, the same routing happens against `streamingBlocks` entries — the shared merge rule (`continuingPartIndex` / `continuesPart`: the last block of the same lane, then text/thinking on kind, tool on kind+toolName unless the two name different toolIds, tool_result on kind+toolId+toolStream; a `newPart` delta always opens a block; a `user` block ends every lane) ensures consecutive deltas collapse into a single block where appropriate while different kinds — and stdout vs. stderr chunks — split into separate blocks. A `user` stream block (a message the running turn took in) renders as a plain user `MessageBubble` node, which also ends any run of dots around it.

### Subagent nesting

- **Where it runs.** `MessageStream` calls `nestSubagentParts` on three lists: a saved assistant row's `parts` (both the verbose and the compact render path), the live `streamingBlocks` (mapped to views; `user` and `tool_call` blocks pass through as placeholders), and the `parts` / live `subParts` of an orchestrated specialist's sub-thread. Every index the render uses afterwards — command pairing, Cinna CLI pairing, the ask-block decision lookup — is into `items`, the filtered list; `origin[i]` maps back to the input, and the live path renders `visibleBlocks = origin.map(...)`.
- **Grouping** (`nestSegment`). Every own `Agent`/`Task` call with a `toolId` (`SUBAGENT_TOOL_NAMES`, no `parentToolId`) is a group, with or without children. Each lane part goes to its root call, following nested `Agent` calls up through `parentToolId` (`rootOf`, cycle-guarded). A main-lane `tool_result` with the root's id is consumed: `stderr` → `status: 'error'` with the joined text as `errorText`, any other → `'done'`, none → `'pending'` if `live`, else `'done'`. A group with no lane parts takes its non-`stderr` results as its `parts`, so the report stays visible where nothing else repeats it. `agentName` is `toolInput.description`, else "Subagent"; `askMessage` is `toolInput.prompt`. The group is anchored at the call, or at the lane's first part when the call is not in the list.
- **Steers.** `nestSubagentParts` splits the input at `user` items and nests each segment on its own; only the last segment is `live`. This mirrors `saveTurnRows`, which splits a turn into rows at each steer.
- **Rendering.** `MessageStream.tsx:renderSubagentGroup(group, SubagentGroupRender)` <!-- nocheck --> draws an `AgentToolSubThread` with no `agentId` and no `onStop` (the subagent is the agent's to stop), `isStreaming = live && status === 'pending'`, and `holdOpen` when one of its permission or question parts is still open by `isOpenRequest` — the same predicate `renderRequestBlock` uses for liveness, extracted so the two cannot disagree. It is pushed as a `plain` node, never into a dots group. Inside a specialist's sub-thread, `AgentContribution.renderNested(index)` draws the group in place of the part at that index. A live group is keyed `stream-subagent-{parentToolId}-{origin}`, since a lane split by a steer is two groups.
- **Cursor.** `lastVisible` is the index in `visibleBlocks` of the stream's last block, or -1 when that block was nested, so no top-level block claims the cursor while a subagent's block is the newest.
- **`AgentToolSubThread` additions.** `holdOpen` forces `expanded` and makes the header click a no-op (`aria-disabled`, title "Answer the request first"). `status === 'error'` is part of the disclosure's initial and post-stream auto state, and adds an `X error` label to the compact header. `countSteps` counts `tool` (except the reserved permission/question names), `text` and `thinking` parts. The empty pending body is `AskLine` + "Working…".
- **`AskLine`.** A `line-clamp-2` span measured in a layout effect and on resize (`scrollHeight > clientHeight + 1`); the Show more/less toggle renders only while it overflows or is expanded. The expanded class is `block`, never combined with `line-clamp-2`: in the built CSS `block` wins over the clamp's `display: -webkit-box`, so nothing clamps — which jsdom, having no CSS, cannot show.
- **Tests.** `subagentParts.test.ts` (grouping, status, steer segments), `MessageStream.subagent.test.tsx` (live and saved nesting in both modes, the call's row from its first frame, a subagent ask holding the thread open, the failed call, the cursor, a steer, a specialist's subagent), `AgentToolSubThread.test.tsx`, `AgentContribution.askLine.test.tsx`, `chat.parts.test.ts` (lane-aware live merging, `newPart`, a user block ending every lane).

### Cinna CLI calls

`cinnaCliCommand` in `src/renderer/src/utils/cinnaCli.ts` recognizes `command` (falling back to `cmd`) only for Bash, shell, shell_command, exec_command or run_shell_command tool names, matched case-insensitively. The command itself must begin with the exact lower-case executable `cinna` after optional whitespace. `cinnamon`, prose mentioning cinna, shell prefixes such as `cd … && cinna …`, and non-string arguments do not match. This is a presentation guard, not a shell parser.

`pairCinnaCliTools` scans once, associates later result parts with the latest owning call by `toolId`, and collects every stdout/stderr result index. A reused ID is reassigned at its next tool call; unknown/missing IDs stay standalone. A slash invocation (`commandInvocation`) is excluded so existing command grouping wins. `MessageStream` uses the result for saved compact/verbose messages and live blocks; `AgentContribution` shares it for nested replies. `ToolCallBlock` handles the ordinary tool-call/result shape through the same component.

In compact mode, `groupWhenAlone` retains a one-command dots group. Any associated stderr makes the dot error/red; a live turn without output is pending; otherwise the dot is done/green, including persisted calls with no recorded result. This is UI state, not verification of remote success. `CinnaCliBlock` reports Waiting for output while live or No output recorded after completion when no result exists. Verbose mode shows each collapsed command header directly.

`CinnaCliBlock` composes `DisclosureBlock` with `defaultExpanded=false`, even while streaming. It omits narration only when empty, exactly the command, or its Bash/Shell echo; genuine explanatory text remains. Output lives in a keyboard-focusable region capped at `max-h-96`. stderr keeps danger text/tone. Both this component and generic `ToolResultBlock` preserve columns with `whitespace-pre`, `overflow-auto`, 12px monospace and `leading-[1.25]`; no font substitution or terminal-to-HTML-table conversion occurs.

`unwrapConsoleOutput` in `src/renderer/src/utils/consoleOutput.ts` peels at most eight whole-payload fences. Backticks or tildes must be at least three characters, with an empty, console, text, plaintext or output label (case-insensitive, optional whitespace). A closing fence must use the same character and at least the opener's length, and the first matching closer must be the final line. An unfinished opener is removed only during streaming. Multiple fenced blocks, prose around fences and other language tags remain untouched. Only the display string changes; stored message parts and output/error metadata are preserved. No Markdown/HTML is interpreted in these output blocks.

## Configuration

Draft retention and text actions have no setting or environment variable. Draft memory is per renderer lifetime, isolated by profile and surface; it is not localStorage or cloud state. Extra UI animation affects the curtain only through [Appearance configuration](../../ui/appearance/appearance_tech.md#configuration); it does not control draft retention or menu availability.

## Security

The context menu acts only on text captured inside its transcript and leaves editable controls to their native menu. Copy requires an explicit action; Save uses the existing main-owned profile boundary. The renderer profile guard prevents an old result from changing another profile's cache/view; it does not replace main authorization. Draft paths and IDs remain subject to the existing file path guards, note ownership and send-time destination validation. No transcript text is sent to an LLM merely to copy or name a note.
