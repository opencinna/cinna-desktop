## IPC Channels

- **The source of a command** (`UserCommandSource`, `src/shared/userCommands.ts`): `chatId` plus `messageId`, or — for a command built for a file in the preview, which has no message — `agentId`. `run`, `inspect` and `commandForFile` take it as their input; `chooseArgPath` takes `(chatId, messageId | null, agentId?)`. Main (`resolveAgent`) takes `agentId` only when `messageId` is absent and only when it is the chat's own `agentId`; a `messageId` wins when both are given, and a message not in the chat refuses. The IPC handler (`sourceOf`) passes only non-empty strings. Without that check any renderer-supplied agent id would pick whose folder a command runs in
- `userCommands:run({ chatId, messageId?, agentId?, command, reviewed, columns? })` (invoke; `columns` is passed on only when a number) returns `{ ok: true, itemId, folder } | { ok: false, code, reason, folder? }`, `code` one of `needs_review | not_local | folder_missing | chat_not_found | spawn_failed`
- `userCommands:output` (`ipcRenderer.postMessage` with `{ chatId, itemId }` and a MessagePort): frames `start` (command, folder, start time, backlog of the log's last 2 MB), `chunk`, `end`, or one `missing`. Closing the port never stops the run; the subscription also ends if the active profile changes
- `userCommands:outputText(chatId, itemId)` returns `{ ok, text, filename }` or a refusal. `userCommands:outputFile` returns the same text written to `<userData>/command-runs/<chatId>/<itemId>/<filename>` as `{ ok, path, filename }`, and records the path with `pathGuard` so the composer's ingest accepts it. The renderer uses `outputFile`
- `userCommands:commandForFile({ chatId, messageId?, agentId?, path })` returns `{ ok: true, command, folder } | { ok: false, code, reason }` (`UserCommandForFileResult`; `code` is the inspect codes or `not_runnable`). `path` is the absolute path the preview's reference holds; `folder` is the display folder. Builds the command and runs nothing; see below
- `userCommands:inspect({ chatId, messageId?, agentId?, command })` returns `{ ok: true, spec: ScriptSpec | null, folder } | { ok: false, code, reason }` (`UserCommandInspectResult`; `code` is `not_local | folder_missing | chat_not_found`). `spec` is null for everything main will not or cannot read; a refusal is the chat or agent being gone. `folder` is the display folder (`~/…`). Resolved like a run (chat, message, agent, workspace), but takes no `reviewed`: it reads and runs nothing
- `userCommands:chooseArgPath(chatId, messageId)` returns `{ ok: true, path } | { ok: true, canceled: true } | { ok: false, code, reason }` (`UserCommandChooseArgPathResult`). Core answers the agent's folder (`argPathFolder`), the desktop host asks, core turns the choice into the path (`relativeArgPath`: relative to the folder by real path when inside, `.` for the folder itself, else as chosen)
- `userCommands:home()` returns the home folder; the window shows the folder through `homeDisplayPath` (`src/shared/userCommands.ts`, `~/…`) because the sandboxed renderer cannot read it
- `userCommands:dismiss(chatId, itemId)` removes an ended run (a running one is refused with `running`)
- Stop is the existing `sessionActivity:stop`. Output refusals: `not_found | running | chat_not_found | unreadable`

All handlers require activation and a chat visible to the profile and not trashed.

## Services & Key Methods

- `run`: resolves the message (it must belong to the chat; an assistant message's `sourceAgentId`, else the chat's agent), then `deps.workspace(agent)`; `missing` becomes `folder_missing`; a null answer is `not_local`, except for an agent id with the folder-agent prefix (`FOLDER_AGENT_ID_PREFIX`), which is `folder_missing` too (a moved folder drops out of the rescanned list). With `reviewed: false` it calls `ownCommandRefusal({ folder, scriptRoots }, folder, command)`. It spawns `$SHELL -c` (the shell env's `SHELL` if absolute, else `/bin/zsh`) with `detached: true`, `stdio: ['ignore','pipe','pipe']`, env from `shellEnvForChild(getShellEnv())` plus the colour hints, `COLUMNS` = `commandColumns(input.columns)` and `PYTHONUNBUFFERED=1`, then reports an upsert (`kind: 'command'`, title the command, detail the display folder with `~`, `outputPath` the log, `canStop: true`)
- Output is decoded with a `StringDecoder` per stream before it is written, so the log holds the text the terminal was sent and a replay ends on a character boundary
- `LOG_CAP_BYTES` 20 MB, `BACKLOG_BYTES` 2 MB, `ATTACHMENT_BYTES` 200 KB, `STOP_GRACE_MS` 5 s, `SHUTDOWN_GRACE_MS` 2 s
- Starts in flight are counted per chat; a chat removed while a start is awaiting its spawn is detected afterwards and the process is killed before it is reported
- `shutdown` sets `closing` before it signals anything: a start still in flight (tracked in `inFlight`) kills what it spawned once it sees the flag and answers `spawn_failed` ("Cinna is quitting…"), and quitting waits for those starts within the same grace. A removed chat's still-running runs sit in `dying` so quit reaches them
- Windows kills with `taskkill /T /F`; elsewhere `process.kill(-pid)`
- An ended run whose row the hub no longer holds is forgotten (the service subscribes to hub changes at the first run)

### The command for a file (`commandForFile`)
1. Resolved as `inspect` is (`workspaceOf`). `path` must be absolute; `readableOwnScript` judges it against the folder alone (no pinned skill folders — a skill's script is not the folder's) and refuses protected files; the real path must be inside the folder's real path. Any miss is `not_runnable`
2. The file is opened as the judged one (`O_RDONLY | O_NONBLOCK | O_NOFOLLOW`, `dev`/`ino` checked, a regular file) and only its first 256 bytes are read (`SHEBANG_BYTES`) for the first line; a NUL means no first line. Executability is `accessSync(X_OK)` (never on Windows); `pyproject.toml` is looked for at the folder's root
3. `fileRunCommand({ rel, firstLine, executable, pyproject })` (pure, exported) chooses: `.py` → `uv run <path>` with a `pyproject.toml`, else `python3 <path>`; `.sh` → `bash <path>`; both regardless of the execute bit. Otherwise only a `#!` file **with an extension** (`/[^.]\.[^./]+$/`, matching the preview's rule): `./<path>` when executable, else the interpreter the shebang names by file name when that is `bash`, `sh`, `python` or `python3` and nothing follows it (`env bash` counts; `bash -e` and `env -S …` do not — an argument changes what running it by name would do). Python shebangs run through `uv run python` or `python3` by the same `pyproject.toml` rule. The path is `shellQuote`d; a name starting with `-` gets `./` first, since an interpreter reads a quoted `-x` as an option once the shell has stripped the quotes
4. When no command results but the file starts with `#!` and is not executable, the reason is `USER_COMMAND_NOT_EXECUTABLE_REASON` rather than `USER_COMMAND_NOT_RUNNABLE_REASON`: the missing execute bit is the only thing in the way. Never throws; an error is `not_runnable`

### Reading a script's parameters (`inspect`)
1. `commandScript(command)` (the script word past env assignments; null for several lines or an unparseable line) and `readableOwnScript` judge the file by name. Either null answers `spec: null`
2. `readSpec` opens the judged real path with `O_RDONLY | O_NONBLOCK | O_NOFOLLOW`, then `fstat`s the open descriptor and requires a regular file whose `dev` and `ino` are the judged ones and whose size is within 512 KB. The path was judged by name a moment before; a parent directory swapped for a symlink since would be followed by any new lookup, so only the identity of the judged file is trusted. `O_NONBLOCK` because a FIFO swapped in would otherwise hang main's thread. Text containing a NUL is not a script
3. Parsed specs are cached by `realpath\0scriptBaseName(script)` (the Usage line is matched against the name the command gives the script), valid while `mtimeMs` and `size` match, 64 entries, oldest evicted. The returned spec has `script` set to the word as written in this command
4. The whole method never throws; failure is `spec: null`, logged as a warning

### The parser (`scriptSpec.ts`)
- A small Python lexer (strings with prefixes and triple quotes, numbers, names, one-character operators; comments and breaks dropped). Any `Surprise` anywhere is caught in `parseScriptSpec` and answers null
- **click and typer**: read from the same token stream, with the same fail-closed `Surprise`. click: the decorators on the one `@click.command`'s `def` (`@click.option`, `@click.argument`; hidden options skipped), the command called and its name never rebound or reached into except by `.main`; a click decorator outside the stack, a group, `@x.command()` on anything else, or `from click import <builder>` / `import click as c` is a surprise. typer: `typer.run(F)` on an undecorated `def F`, or one `app = typer.Typer(…)` with exactly one `@app.command(…)` and `app(…)` called; parameters by annotation (`str`, `int`, `float`, `bool`, `Path`, `datetime`, `Optional`, `List`, `Annotated[X, typer.Option|Argument(…)]`, the older `= typer.Option(default, "--name")` style), `typer.Context` dropped; anything else is a surprise, and so are `*args`/`**kwargs`, a shared `typer.Option` and any use of `app` beyond the command and the call. A bool with no off flag but a true default (click `is_flag=True, default=True`, typer `--force` alone) is a surprise: the flag would turn it off, which no switch can show. **One framework speaks:** argparse, click and typer together are a surprise
- **`--x/--no-x`**: `optionDecls` splits the names; the second half become `offFlags`. typer's bool gets `--no-<name>` implied when it names none. `defaultOn` is a true default; `parseArgs` reads either flag as the same param and the last one given wins (`byFlag` holds both lists), and `paramArgs` writes nothing when the effective value equals `defaultOn`, else the preferred long flag or the preferred long off flag (`preferredOffFlag`)
- **Shell getopts**: `tokenizeShell` (words, operators and line breaks; quotes, escapes and substitutions kept inside their word; comments dropped; here-document bodies skipped; an unterminated quote, substitution or here-document is a surprise) feeds the getopts reader. A `getopts` inside a comment, string or here-document is not one. The loop must be `while getopts "<literal>" var` with a `case "$var" in … esac` as its only command; surprises are a second `getopts`, a non-literal optstring, a duplicate letter, a `case` on another variable, an arm pattern that is not a letter, `\?`, `:`, `*` or `?`, a letter arm the optstring lacks or placed after a catch-all, a letter in two arms, `;&`, and an optstring letter with no arm of its own (its handling would be the catch-all's, which cannot be told). **getopts decides the flag set; the Usage header names it**: a header option is kept with only its short flags, and one with no short flag getopts knows, a short flag it does not know, or a switch/value mismatch is a surprise. A letter the header omits is labelled by the variable its arm sets (when only it sets that), else by its flag. A switch whose arm runs `exit` is dropped. Positionals come from the header only
- **`ScriptSpec.optionsFirst`** is set for getopts: the script stops reading options at its first operand. `assignArgs` reads every word after the first loose word as an operand (and reports where it began, `operandAt`); `buildArgs` puts options before positionals; `editCommand` inserts a new option before the first operand (and before a `--`), keeping options and positionals inserted at one place apart (`beforeOptions`, `appendedOptions`). A getopts script that reads its arguments at the top level before its `while getopts` loop (`shift`, `set --`, `$1`–`$9`, `${1…}`, `$@`, `$*`), or whose Usage line puts a positional before an option, is a surprise too, for the same reason: the form's option-first order would not be the order the script reads. Function bodies (`f() { … }`, `function f { … }`) are skipped, so their own `$1` and `shift` do not count, and `$0`, `$#` and `OPTIND=1` still read; a function called before the loop is not followed (accepted residual).
- **Limits**: literal nesting 8 (each level rescans its range, so unbounded is quadratic on main's thread), 400 tokens per `add_argument(` call, 200 `add_argument` calls, a Usage block over 50 lines ignored
- **One parser**: exactly one `ArgumentParser(` assigned to a plain name; `parents=`, `add_subparsers`, a second parser, no `parse_args`/`parse_known_args` on it all surprise. A string that is an f-string or bytes literal is treated as an expression, not a value
- **Receivers are matched by name.** `add_argument` is accepted only on the parser or a group made from it (`add_argument_group`, `add_mutually_exclusive_group`, assigned to a name), and any other binding of one of those names (`parser = Fake()` before or after, a `for`/`as`/`def`/`class`/`import` target, `+=`, `:=`, tuple targets) is a surprise, since the calls could be on something else. `bindsName` errs towards yes
- **Factory aliases**: if the parser is built in a `def F(…)` whose body has `return <parser>`, then `X = F(…)` starting a logical line makes `X` a parser too, and `F(…).parse_args(…)` counts as the parse. The factory is found from indentation only
- Sources merge per parameter, a later one only fills gaps: argparse, then the Usage line (module docstring for Python, leading `# Usage:` block for shell, its only source), then the docstring's option lines for help text. The docstring is a gap filler when argparse spoke; alone, its surprise is the script's
- A default that is `Path("data")`, `int(3)` and the like (`SIMPLE_DEFAULT`) is shown as the literal inside; any other non-literal is `defaultComputed`. `writes` is set from `WRITE_NAMES` (apply, write, force, delete, commit, overwrite, push) or "writes/deletes/overwrites" in the help; display only

### Form and line (`scriptArgs.ts`)
- `readCommand(spec, line)` splits the line with `splitCommandSpans`, requires one line naming `spec.script` as its script word (env assignments allowed), and returns `{ prefix (the line through the script word, verbatim), values, other }`. Null means the form is hand-edited
- `parseArgs` reads `--x=v` and `--x v`, repeated short count flags (`-vvv`), and stops at `--`, keeping it and everything after as unknown. Unknown words come back shell-quoted as `other`
- `editCommand` rewrites word by word: replace the first word group a parameter owns (removing later ones), insert a new positional by its neighbours, append a new option before any `--`, keep gaps and quoting of untouched words. **It trusts its output only if `readCommand` reads it back to the values asked for** (and the same other words, in any order); otherwise it answers null
- `buildCommand(prefix, spec, values, other)` is the fallback: prefix verbatim, then `buildArgs` in spec order, then other. The modal then reads the result back, and if it does not parse (a free word taken as an optional positional) the form is marked hand-edited rather than shown wrong

### The window and the form
- **Store**: `RunScriptSource.viaChatAgent` marks a window opened from the file preview (no message; `agentId` is the chat's). `sourceInput(source, fallbackMessageId?)` turns a window into `{ chatId, messageId }` or `{ chatId, agentId }`, and `run`, `inspect`, `chooseArgPath` all take it from there; a run started from such a window remembers `viaChatAgent` in `runSources`. `askSpec` returns null (nothing asked) unless the source is known and `commandScript` finds a script. `specWithin` races the answer against `INSPECT_WAIT_MS`; the window is set once, with `spec` or null, and a late answer is dropped. A module-level `lastOpen` ticket is taken by every `openFromCode`, `openForRun` and `runFromMenu` and bumped by `close` and `dismiss`, so an open that was waiting opens nothing if a later open, a close or a profile change came meanwhile (alongside `seq`, which guards the answers after the window exists). `runFromMenu` asks for the spec in parallel with the run, so the wait is rarely felt; a Run in background asks nothing. `openForRun` uses the run's remembered source message, so a run reopened after a reload has no form
- **Modal**: `form` state is `{ read, handEdited }`. `onLineChange` re-reads the line (`handEdited` when it no longer parses, keeping the last `read`). `onFormChange` ignores edits while hand-edited, tries `editCommand`, falls back to `buildCommand`, and sets `tailPending` when the new line extends the old one so a layout effect scrolls the field to its end. `sizeRows` is `max(own rows, min(rows of formSizingLine, FORM_LINE_MAX_ROWS))`; `formSizingLine` appends, for every switch whose flags and off flags the command (read by `splitCommandLine`, whitespace if it refuses) does not already name, the flag a toggle would write — `preferredFlag`, or `preferredOffFlag` for a switch on by default (both from `scriptArgs.ts`)
- **Idle hint**: `specHint(spec)` is summary and description joined by a blank line. They are the script author's text written into a terminal, and a Python escape (`\x1b`, `\a`) is a real control character by then, so every C0 control except line break and tab, DEL and the whole C1 range (`\x9b` is a CSI to xterm) are stripped: it can only print. Null falls back to the Run hint
- **Form**: `RunScriptForm` is read-only when a run is going or starting, or hand-edited. Segmented choices need at most 4 choices and 24 characters of labels (`SEGMENT_MAX`, `SEGMENT_MAX_CHARS`); the date button drives an invisible `type="date"` input via `showPicker()` and writes `YYYY-MM-DD` into the field; Choose… calls `onChoosePath`, which the modal wires to `userCommands:chooseArgPath` with the window's source (`sourceInput`: the message, else the chat's agent for a window opened from a file, else the fallback recent reply) and shows a refusal in the action-error line
- **Escape and outside presses**: a portaled `SettingsInfoTip` popover carries `data-info-tip` (`INFO_TIP_ATTR`); the window's key handler ignores Escape while one exists and its mouse handler ignores presses on one

## Session activity changes

A `command` item is not the agent process's, so four places skip it by passing `kinds: AGENT_PROCESS_KINDS` (`subagent`, `background`):
1. `activityReapDeps` (`acpPool.ts`): `hasRunning` and `lastChangeAt`, so a long user run does not keep the agent's process alive (`lastChange` is tracked per agent per kind for this)
2. `wirePoolToActivity`: the process exiting does not end commands as `lost`
3. `releaseChatSessions` (`chatSessionRelease.ts`): switching a chat's agent does not either
4. Retention: `KEPT_ACROSS_ROUNDS` in `sessionActivityHub.ts` holds `command`; a new start does not drop its ended items. Only the `ENDED_PER_KIND` (5) cap and `hub.remove(chatId, itemId)` (ended items only) remove them

## Renderer Components

- **Click**: a command is detected once per text, in `fileRefs.tsx`, and only in a reply inside a `CommandMessageContext`; a click or Enter/Space calls `openFromCode`, with the click point or null for a key. A non-collapsed text selection and `event.detail > 1` open nothing. `command-ref` styling is in `main.css` (`code.command-ref`, `pre.command-ref`): the file reference's fill and hover transition with the edge from `--color-command-ref-edge` (`#3f6f52` dark, `#8cc09f` light); only colours differ, so nothing moves
- **Menu**: `menuCommandOf` finds `data-message-id` on the right-clicked code, reads the cached chat (`['chat', chatId]`) and agents (`['agents']`), requires an assistant message and `agentRunsCommands`, then `detectCommand` with the fence language. It is decided once at open. Run calls `runFromMenu` (the store starts it, so the answer lands after the menu has gone); `edit-run` calls `openFromCode`
- **Store and `seq`**: every open takes the next `seq` from a module counter that never repeats, even after a close, so the card (keyed by it) starts fresh and an open during the previous window's exit never reuses its card. Every asynchronous answer compares the `seq` it started under with the window now shown: `start` writes to the window only `still` if it is the same, and `runFromMenu` opens one only if none, or the one that was shown at the call, is still up (`mayOpen`). A late answer therefore never lands on a newer window; the run it started still reaches the badge. `openFromCode` and `openForRun` are ignored while a start is `pending`, as is `close` (the window cannot be dismissed while a start is in flight; `dismiss` can, for a profile change). The start lives in the store, not the window, so its answer lands if the window unmounted
- **Window**: `reason` is `commandReviewReason(command)` at `openFromCode`, main's reason at a `needs_review`, null for a run. The run shown is the last of `runs`; `start` appends. The `facts` per run (start time, end, missing) come from the output frames. The state text is `Running`, `Completed`, `Stopped`, `Exit N`, a signal name, `Failed`, or `Output no longer available`. The columns sent are the terminal's fitted count (`onColumns`), else 120
- **Exit**: `exit: 'collapse'` plays `playCardExit` into the badge's rect when `commandsBadgeOf` finds one on screen, else the plain reverse; `close` fades. The card unmounts after `CARD_MOTION.duration`, at once where nothing can animate
- **Terminal**: read-only xterm with `disableStdin`, theme read from the `--color-*` variables at mount and on theme change. Each run is its own `userCommands:output` subscription; a later run of the same window clears the terminal and begins with `runSeparator(n)`. The idle hint is dimmed and the first run clears it
- **Command line** (`RunScriptCommandLine.tsx`): a bordered `bg-secondary` textarea with an accent border on focus; the `read-only:` variants drop border and fill, and the 1 px border is taken out of the padding (`pt-[5px]`) so text stays level with the `$`. Rows from `commandLineRows`, decided at open from `measureCharsPerLine` in a layout effect before first paint. `caretVisualRow(line, cells, caret)` gives the caret's soft-wrapped row and the row count by the same breaks `wrappedRows` counts with, so ↑/↓ recall history only from the first/last row. `history` is the chat's `command` items' titles, newest first, deduplicated; `walk` keeps the typed draft so ↓ returns to it. Keys are in the business doc
- **Layout**: the transcript's scroll pills sit as for any chat; nothing is docked above the composer any more. Failed runs show the crossed circle (`CircleX`); the window header and the popover share `formatRunDuration`
- **Commands badge**: stays while the chat has any command item; the face is the icon and the running count, replaced by a check or crossed circle for the last result when nothing runs, in one fixed-size cell. A `lost` last result (the code handles it; nothing in the service ends a run as lost today, so it is defensive) shows the same glyph in the warning colour. Rows: Open output (always last; the `AppWindow` icon), Add output to message and Remove (ended). Open output calls `openForRun` with the click point (null for a keyboard activation) and then closes the popover through `onOpenOutput`; Remove calls `runRemoved`, which closes a window showing that run. The badge carries `data-chat-id`, which the collapse animation looks it up by

## Configuration

None. No setting, no environment variable. The constants above are the tuning.

## Security

- The guard is a filter, not a boundary (see the business doc). The IPC layer trusts nothing from the renderer: `reviewed: true` is the window's claim, and it only skips the rule, never the chat, message, agent and folder checks
- Chat ids are used as path segments, so `SAFE_SEGMENT` is checked before any path is built
- The environment carries the user's login shell variables and nothing from the agent runtime or the credential store
- Output paths the renderer sees are written by main and recorded with `pathGuard`
- **Reading a script is a file read the renderer can ask for**, so it has the run's gates (activation, visible chat, the message's agent and workspace) and its own: only the file `readableOwnScript` judged, opened without following a final symlink, the identity checked after open, never a credential or protected path, 512 KB, and never executed. The parser is bounded (nesting, tokens, calls) because it runs on main's thread over text the agent may have written
