# GitHub Repos

## Purpose

A folder agent can run `gh` and `git` against the user's GitHub repositories with no token in a file, no login in a terminal and no setup the user has to remember. The user signs in to GitHub once per Cinna profile, in the app; every kit agent's `gh` and `git` then authenticate through Cinna, and when something is missing the composer under that chat says what to click.

## Core Concepts

- **OpenCinna** — the one public GitHub App every profile signs in to (no client secret, no private key). Its access is the intersection of what the user can reach and what the app is **installed** on; installing is a separate step on github.com, per owner, on all repositories or on selected ones.
- **Sign-in** — GitHub's device flow, per Cinna profile (the guest profile included). The tokens belong to the profile and never leave main; the renderer sees a login, a state (`connected` or `expired`) and the coverage.
- **Coverage** — the installations of the app the signed-in user can see: owner, and either all repositories or a list. It decides whether a repository is reachable, and what **Allow access** opens.
- **Need** — what an agent could not do: **sign in**, **reconnect** (the sign-in died), or **install** for an owner (the app cannot reach a repository). Kept in memory per profile, deduplicated, remembering which agents hit it, and which of them hit it from a run no chat shows. Needs are what the composer rows show; a need a run with no chat hit is also an Inbox card and a row on the agent's page.
- **The `gh` wrapper** — a script Cinna puts first on the `PATH` of every child it launches. It, not the agent, decides which login a `gh` or `git` call uses.
- **Managed gh** — Cinna's own pinned GitHub CLI, downloaded only when the machine has no `gh`.

## User Stories / Flows

1. **First use.** An agent runs `gh repo clone owner/repo`. Nothing can authenticate, so the call exits with a sentence telling the agent to ask the user to click **Sign in to GitHub** under the message box, and the chat shows that row.
2. **Sign in.** **Sign in to GitHub** starts the device flow, copies the code to the clipboard and opens github.com/login/device. The row becomes "Enter code ABCD-1234 on GitHub. Only enter a code Cinna shows you." with a wait line and **Cancel**. Approving in the browser ends it. A declined or expired code is said in the row and offers **Get a new code** or the sign-in again.
3. **Allow access.** A signed-in user whose app installation does not cover the repository gets "Cinna's GitHub app can't reach owner/repo yet" and **Allow access**, which opens the installation's configure page (app installed on the owner, repository not selected) or the app's install page (not installed). When the window regains focus Cinna reads the installations again, so the row clears once the user is back.
4. **Continue.** When a need this chat showed clears (a sign-in from Settings or another chat, a coverage change), the row turns into "GitHub is connected." with **Continue**, which sends "GitHub is connected, go on" through the composer. The agent then reruns what failed.
5. **A run with no chat.** A kit command no chat shows (the agent's status refresh, a dashboard's refresh command or endpoint) or a scheduled command run hits the same refusal. With no composer to ask in, the need is also an Inbox card with a GitHub badge — "GitHub isn’t connected for Repo Agent", "The GitHub sign-in expired for Repo Agent", "Cinna’s GitHub app can’t reach your repos for Repo Agent" (the repositories on its one body line) — with **Sign in to GitHub** (the device flow told on the card), **Reconnect GitHub** or **Allow access**, and **Dismiss**; and the agent's page (its new-chat composer) shows the composer's own row, without Continue. Both go when the need clears; dismissing either dismisses the need.
6. **Settings → User Accounts → GitHub.** Signed out: the purpose and **Sign in to GitHub**. Connected: the login with **Sign out**, one line per installation ("acme: all repositories", "evgeny-l: shop, site") with **Manage repository access**, and where a full revoke is. Expired: **Reconnect GitHub**. **Sign out** asks first, and says that the app's access is fully revoked only at github.com/settings/applications.
7. **Reconnect.** A refresh token GitHub no longer accepts (rotated out, revoked, expired) marks the sign-in `expired`, drops its tokens and shows **Reconnect GitHub** in Settings. A chat gets the Reconnect row only when the agent's command then had nothing to fall back on (the user's own `gh` login, step 3 of the wrapper's order); a command the user's own login served shows no row.

## Business Rules

- **One sign-in per profile, used by every kit agent.** Folder agents are shared by all profiles, so an agent's request is served for the profile of what holds the agent right now: the profile a chat's turn (or its `/run:`) runs for, the profile that started a kit command no chat shows, the profile that owns a scheduled run. Switching profile mid-turn never hands the running turn the new profile's account. A hold that recorded no profile works for the profile active now (none before a profile is activated). Holds on one agent working for different profiles at once get nothing: they share one bearer, so a request cannot say which one it came from, and Cinna refuses rather than guess — the token route answers "Another Cinna profile is running this agent right now. Try again when its run has finished." (gh exits 1 with it; git's helper prints it and answers nothing) and no need is recorded. A need is recorded under the same profile the token was refused for. A profile that cannot serve (not activated, deleted, password-protected and not unlocked this session) gets no token, no status and no needs; an agent whose run works for a password-protected profile that is locked is told "This agent's Cinna profile is locked. Ask the user to unlock it, then run this command again." (gh exits 1, unless the user's own `gh` login serves it) and no row is shown; a deleted profile answers as if no one were signed in, and records nothing. A need shows on the agent's page and in the Inbox only when every run holding the agent is one no chat shows; while a chat's turn holds it too, the chat's row is enough.
- **Another host is not GitHub's.** A `gh` command whose `-R`/`--repo` names a host other than github.com (GitHub Enterprise, say) runs the user's own `gh` and config untouched.
- **Kit agents use Cinna's credential path for github.com.** In a kit agent's child, `git` asks Cinna for github.com credentials, not the user's macOS keychain (osxkeychain) or Git Credential Manager login: those are not used there. The user's own `gh` login is: when Cinna has no token to give, the wrapper falls back to it (for git too, through `gh auth git-credential`). A user who wants a kit agent to push with their own account therefore needs `gh auth login` (or the OpenCinna sign-in), not a keychain entry.
- **Public repositories need no installation for reading.** A repository the app's installations do not cover gets **Allow access**, except when a `gh` command only reads a public one: the token is handed out and the read works. A `gh` command known to write (creating or editing a pull request, issue, release, label, secret or variable; editing, deleting, archiving, renaming, forking or syncing a repository; `gh api` with a method other than GET or with fields) and git (which only asks for credentials to push or to fetch a repository that is not public) get Allow access whatever the visibility, since GitHub would refuse the app there. A repository GitHub hides (404) counts as private; when GitHub cannot say (a rate limit, an outage), a read gets the token and GitHub decides.
- **A token is never handed out with under ten minutes left.** Refresh tokens rotate: a refresh kills the previous access and refresh token at once. So a refresh runs once at a time per profile, and the new pair is persisted before anyone is answered. A refresh answered from two callers would have burned the first caller's pair and left the profile needing Reconnect.
- **A transient failure is not an expiry.** GitHub unreachable, slow, 5xx or unreadable answers "try again in a moment" and keeps the sign-in. Only `bad_refresh_token` and `incorrect_client_credentials` (or an expired refresh token) mean Reconnect.
- **The user's own `gh` login is the fallback, never the first choice for a kit agent.** Order of the wrapper, per call: the OpenCinna token; otherwise the real `gh` untouched when the user is logged in to it; otherwise the need is recorded and the call fails with a sentence and exit 4. A kit agent therefore acts as OpenCinna even when the user's `gh` is logged in as someone else, and a user who never signs in to OpenCinna keeps working on their own login.
- **Only a kit agent's child gets the OpenCinna route.** The loopback address and bearer, and the git credential-helper wiring, go to kit agents' engines, kit commands and scheduled runs. A bare agent, an MCP server, a Run Script window and a non-kit `/run:` keep the user's own keychain or credential-manager login for github.com; the wrapper is on their `PATH` too but falls straight through to the real `gh`. Pointing git's helper at a wrapper in a child that cannot reach the endpoint would have broken the user's own pushes.
- **Commits are the user's, whatever the clone method.** While the profile the agent works for is signed in, a kit agent's git commits in any repository with a github.com remote (https or ssh) as the profile's GitHub name and `<id>+<login>@users.noreply.github.com`, but only where git has no identity of its own: the user's own global config (`~/.gitconfig`, `~/.config/git/config`), the repository's config, `git -c` and `GIT_AUTHOR_*`/`GIT_COMMITTER_*` all win, key by key (a user global with only an email keeps that email and gets the GitHub name). Another host's repository gets git's normal behaviour; signed out, nothing is supplied. It follows the sign-in live: a turn refused before the sign-in and continued after it commits as the user. In addition, a repository a served `gh repo clone` creates keeps the identity in its own config (only when the user's config has none), so the user's later git in that clone outside Cinna commits as them too.
  - Limits: a git older than 2.36 gets nothing this way (Apple's git and the managed git are newer). A system-wide identity (`/etc/gitconfig`) ranks below it, as git ranks system below global. A `git config --global` an agent runs (a `safe.directory`, `gh auth setup-git`) is written to Cinna's file, not the user's `~/.gitconfig`, and kept there (it then wins over the user's own global values). A user global config with an email and no name gets the GitHub name with their email. A remote written through a `url.<base>.insteadOf` shorthand (`gh:owner/repo`) gets no identity, since the match is on the URL as configured. A `GIT_CONFIG_GLOBAL` the user set themselves turns this off. Claude Code in API Token mode (`CLAUDE_CODE_SUBPROCESS_ENV_SCRUB`) removes the variable from the agent's Bash, so there only the `gh repo clone` identity applies.
- **The token travels in the smallest place.** In the env of the one `gh` the wrapper runs (with an empty `GH_CONFIG_DIR`, so the user's gh config and login do not mix in) or on stdout to git. Never on a command line, in a file or in a log; the bearer reaches curl on stdin.
- **A sandbox that blocks loopback is told so.** If the endpoint cannot be connected to at all, the wrapper says the command needs network access and should be run again with escalated permissions, "not an internet outage" (exit 4). A connected-but-slow endpoint, or one whose answer broke off (a reset, an empty reply), says "try again in a moment" instead (exit 1). Without this split an agent reads the first as an outage and gives up, or asks for escalation it does not need.
- **Cinna answers in time.** The token answer stays within 35 s, below the wrapper's 40 s wait: reading the installations and a repository's visibility gets 12 s, and when it runs late the token is handed out (GitHub enforces the bounds) while the read finishes in the background for the next command.
- **One card per need, not per run.** The Inbox lists one card for the sign-in per profile and one per owner for an install, as the composer rows dedupe them; a card names the agents whose runs with no chat hit it. It is not counted in the Inbox badge (like the update and disconnected cards). A need only chats hit has no card and no agent-page row.
- **Dismissed is not resolved.** × on a row hides it and remembers its key, so another chat does not show "GitHub is connected" for a need the user merely closed. The same need arriving again un-dismisses it; sign-out clears the list.
- **Needs are stale as soon as they are false.** A sign-in need recorded while signed in, or an install need for a repository the cache covers, is dropped. A completed sign-in clears the account need; each coverage read clears the install needs it now covers.
- **A coverage read is rate-limited.** From the renderer a window focus reads at most once per 10 s; main applies the same 10 s per profile; a token request for an uncovered repository refreshes the cache at most once a minute. If the installations cannot be read at all, or not in time, the token is handed out anyway: GitHub enforces the bounds.
- **Sign-out forgets locally.** It does not revoke (that needs the app's secret); the dialog sends the user to github.com/settings/applications for that.
- **The managed gh is a last resort and never awaited.** Any `gh` the user installed wins. A completed sign-in with no `gh` on the user's `PATH`, or a wrapper call that finds none, starts one background download (once per app run). While it runs the wrapper says Cinna is still installing gh; if no install is running it says to install the GitHub CLI from cli.github.com. Behaviour of the download: [Developer Tools on a Bare Machine](../../development/shell_environment/developer_tools.md); the pin: [Runtime Pins](../../development/runtime_pins/runtime_pins_llm.md).
- **macOS and Linux only.** The wrapper is a POSIX script; on Windows nothing is installed and the agent's `gh` is whatever the machine has.

## What it does not do

- No MCP tools for GitHub: agents use `gh` and `git`.
- No organization-admin flow: the `admin` need kind exists in the shared type and is never produced or shown.
- It does not store a token in the agent folder, `credentials/` or any env value the user can see; it is separate from [Service Credentials](../service_credentials/README.md), whose loopback listener it only borrows.

## Architecture Overview

```
Agent turn -> engine child (PATH: gh-shim first; CINNA_GITHUB_URL/BEARER; GIT_CONFIG_* helper;
                            GIT_CONFIG_GLOBAL -> github-identity/<profile>.gitconfig)
  gh / git -> gh-shim/gh -> POST loopback /github/token -> githubAuthService (refresh, coverage)
        token  -> real or managed gh with GH_TOKEN / git on stdout
        needed -> user's own gh login, else POST /github/needed -> needs registry -> github:changed
Renderer composer rows / Settings -> window.api.github -> github:* IPC -> githubAuthService -> GitHub
```
