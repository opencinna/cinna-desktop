# Agent Vault — a local agent in an isolation nothing else on the Mac shares

## Purpose

Some local agents hold credentials that matter more than anything else on the laptop: a production database owner, a payment account, a signing key. Today any process running as the user can read what such an agent holds — its folder and `.env`, the delivered `credentials.json`, a running engine's environment, Cinna's own data — and any other agent can reach it through Cinna (a delegation, a handover, a conductor, a schedule). **Agent Vault** moves one existing folder agent into a Linux micro-VM that it shares with nothing: nothing gets in unless the user approves it through a prompt other software cannot forge, and nothing gets out unless the user approves it or the network allowlist names it.

It is for **local folder agents on Claude Code, Codex, OpenCode or Antigravity**, on **Apple silicon with macOS 15 or later**, and it needs nothing installed on the Mac (no Command Line Tools, Homebrew or uv).

## Core Concepts

- **Agent Vault** — the isolated environment of one agent: a micro-VM on Apple's Virtualization.framework, with a read-only system and one encrypted data disk of its own. One vault per agent. The agent keeps its id and stays in the sidebar, marked with a safe icon. A lock icon never means "this is a vault agent": it shows only whether the vault is locked or unlocked.
- **Vault Helper** — a separate signed program shipped inside Cinna (`VaultHelper.app`) that owns everything that must not depend on Cinna: the VM, the disk key, the user-presence prompts, the network proxy and the timers. Cinna asks it; it never takes Cinna's word for what the user approved.
- **cinna-vaultd** — the small daemon inside the guest that is the source of truth for everything in the vault: it starts the engine, writes files, keeps secrets and transcripts, and builds every command line itself.
- **Engine login** — the one API key an engine signs in with inside a vault: for Claude an Anthropic API key or a `claude setup-token` token (told apart by prefix: `sk-ant-oat…` is stored as `CLAUDE_CODE_OAUTH_TOKEN`, anything else as `ANTHROPIC_API_KEY`, and the vault keeps only one), OpenAI's for Codex, the model provider's for OpenCode, a Gemini API key for Antigravity. It is put into the vault and never kept by Cinna; a login on the Mac (a Claude subscription, a ChatGPT or Google sign-in) cannot be handed in.
- **Vault chat** — a chat with a vault agent. Its messages live only in the vault; Cinna's database keeps a stub row titled "<agent> · <date>".
- **Unlock window** — an unlock lasts the vault's **Lock after** time (30 seconds, **5 minutes** by default, or until Cinna quits) after the last turn, gated action or keystroke in a chat with its agent. A running turn keeps it open. When it ends the vault locks. The time is the vault's own, kept in the helper's signed `vault.json`, so Cinna cannot lengthen it without a prompt; the screen locking, sleep and logout lock the vault whatever it says.
- **Gated action** — an action that needs a fresh presence prompt (Touch ID or password, worded by the helper) *every time*, even while unlocked: moving in, installing or updating dependencies, exporting a file, opening a terminal, moving out, changing the network allowlist, changing the disk size, deleting the vault.
- **Approval token** — what the helper hands back after a gated prompt: a signed, expiring claim for exactly that action. The guest and the helper refuse a gated call that does not carry one, so a Cinna that asks without the user having approved gets nothing.
- **Host copy** — the original folder, left on the Mac after a move until the user deletes it.

## User Stories / Flows

1. **See what it is.** On the agent page, **Security → Agent Vault** is always there. On a Mac that cannot hold a vault it says why in words ("Needs macOS 15 or later on Apple silicon", "Not available inside a virtual machine", "The guest image isn’t installed") and offers no button. An agent that can move shows **Move to vault…** and an expandable "What a vault protects against".
2. **Move an agent in.** See [Moving an agent in and out](move.md): a pre-check, then create, unlock, copy, rebuild, credentials and a readiness check, with the original left untouched until the user deletes it.
3. **Talk to it.** Start a new chat with the agent. If the vault is locked the composer shows **Vault locked — Unlock**; the draft is kept. Unlock raises the helper's prompt, boots (or resumes) the VM (the first unlock after an app update first downloads the system image that version pins, and the button says "Unlocking… 40%"; nothing else changes on screen) and reopens the vault's chats. Pressing Enter on a locked vault's chat unlocks and then sends once, only if the vault really opened (another chat, an emptied draft, another refusal or a cancelled prompt drops the send). A locked vault's open chat shows a card, **This chat is in a locked vault**, with **Unlock**, instead of an empty-chat greeting. A turn runs inside; when it ends the window counts down, and typing in the composer restarts it (at most once per 5 s, nothing changes on screen) so a vault does not lock under someone writing a long message.
4. **Lock.** The window ending, **Lock now** (the Security tab, or the agent chip's menu, which a vault agent has instead of Open Agent Folder and Open Uploads: its folder is inside the VM), the screen locking, the Mac sleeping, a fast user switch and logout all lock every vault. A turn still running is suspended with the vault and continues after the next unlock.
5. **Change the vault.** The agent's Security tab carries: **Lock after** (30 seconds, 5 minutes, Until Cinna quits; a shorter choice applies at once, a longer one asks for a prompt, because a longer window leaves the vault open longer), **Disk size limit** (default 10 GB; raising it grows the image the next unlock; lowering below what is used is refused, naming the usage), **Network access** (the allowlist; the hosts always allowed are those of every engine set up in the vault), **Engine login** (the API key above), **Secrets** (names only are listed; values go in, never back), **Toolchain** with **Update dependencies**, **Terminal** with **Open terminal**, **Export…** of a file or folder through a save dialog, **Move out of vault…** and **Delete vault…**. Each of the gated ones prompts. The Security tab's second section, **Permissions**, is the agent's ordinary approvals, grants and delegation switches; a vault agent's live inside the vault.
6. **Change the engine.** A vault agent's settings page carries **Runs on**, the same select a local agent has, listing Claude Agent, Codex, OpenCode and Antigravity, in the place a local agent's runtime panel takes. The line under it says what it runs on inside ("Runs inside the vault on Codex 0.x · the CLI's default model.") and is always there, so nothing shifts. Each engine is **set up in the vault on its first choice**: a dialog lists what will happen (download the pinned runtime into the vault, allow the engine's hosts, store a key if one is pasted, switch) and then takes the fields it needs. It asks for Touch ID or the password once for the install and once more for the hosts, and only for what is missing, so an engine whose hosts are already allowed takes one. **Switching back to an engine already set up asks nothing** and happens as soon as it is picked. OpenCode always asks for a provider (OpenAI or Anthropic) and a model, even when set up, and the line carries **Change model…** to name another. The key is optional in the dialog; leaving it empty means adding it on the Security tab later. A vault that is locked shows "Unlock the vault to change the engine." with **Unlock** on that line and a disabled select: which engines are set up is known only to the vault. Chats the agent already has keep their history; the next message in one runs on a fresh session of the new engine, which does not know what the old engine's session knew.
7. **Open a terminal.** **Open terminal** (enabled only while unlocked) takes one prompt and opens a shell inside the vault as the agent, in its folder, in a dialog. The vault is held unlocked while the terminal is open, so the window does not close under someone typing; closing the dialog kills the shell. The dialog box can be resized and the shell follows (prompt, wrapping, `less`, `vim`); nothing typed or printed is logged. Resizing needs a guest image built with it: an older image keeps the size the shell opened at.
8. **Attach files in a vault chat.** Text files, PDFs and Office files go in as their extracted text and png, jpeg, gif and webp as inline images; anything else (an archive, a video, a binary) is refused at the composer with "This kind of file can't be sent into a vault yet; paste the text instead." The composer still stores a file under `userData` before the send, so Cinna deletes that copy (and a pasted image's temporary one) when the turn ends, whatever its outcome, and sweeps any left behind at start and on lock. The row keeps the name and size; the bytes live only in the vault. A file attached to a draft that is not sent before the vault locks is dropped with that sweep: the draft loses the chip, keeps its text, and the composer says "Vault locked: attach the file again". Only Cinna's staged copy went, so attach it again after unlocking.
9. **Open a file the agent names.** In a vault chat a file the agent mentions in inline code or a link (relative to its folder, or `/vault/agent/…`) links like any [file reference](../../chat/file_references/file_references.md). Click shows a **preview** read from inside the vault, with no prompt, into Cinna's memory only; images preview too. **Download** (the preview's ⋯ menu lists it first, the right-click menu has it too) saves a copy through the save dialog, behind the helper's export prompt; a referenced folder downloads whole. A vault file offers nothing else: no Open, Open folder, Copy full path, Pin, Publish, Run or Reference in a new chat, because the file is not on this Mac. On a locked vault the preview body says so and offers **Unlock**, and reads the file once it opens; links already shown stay.
10. **Leave.** **Move out** exports the whole folder back as a normal local agent and destroys the vault; **Delete vault…** destroys it and the agent with it.

## What it protects, and what it does not

The attacker is **any process running as the user's macOS account**: other agents in any permission mode, the user's own `claude` in Terminal, a malicious package an agent installed, anything that can write Cinna's database.

**Protected:** what the vault holds is confidential and unmodified (files, credentials, transcripts, engine login). Nothing enters without the user's approval. Nothing leaves without the user's approval, and the network goes only to the allowlist. The vault disk is sealed with a key in the Secure Enclave that needs the user's presence; a same-user process can read neither the key nor the disk.

**Not protected — said in the Security tab and here:**
- **Availability.** Any same-user process can delete the disk image or kill the helper, with no prompt and no administrator rights. It cannot read or change what is inside, but a deleted image is a lost agent.
- **Backups.** Cinna makes no backup of a vault. The disk key is wrapped by a Secure Enclave key that never leaves the Mac, so even a copy of the disk image cannot be opened on another Mac or after the keychain item is gone. Export… is the only way to keep a copy of what is inside.
- **Previews are not gated.** A preview of a file the agent named leaves the vault into Cinna's memory with no prompt, the same as the transcript does; vaultd answers it while the vault is unlocked (the unlock is the gate). It is capped at 10 MB, never written to disk, and a credential file (`.env*`, `*.pem`, `credentials/`…) is never previewed or offered a Download on its own. **Download is gated**, with the helper's export prompt, and a downloaded *folder* exports every file in it, credential files included, once approved.
- **The clipboard.** Copying a secret out of a vault chat exposes it.
- **Exposure from before the move.** Moving does not take back what other agents already read. The move ends with a **rotation checklist**: every attached service credential, every key in a `.env`, and the git history that moved in.
- **Screen capture, input monitoring and Accessibility** held by other apps (TCC grants).
- **Root on an unlocked vault.** A kernel compromise of the Mac does not read a locked vault (the key is wiped), but a running, unlocked one is not protected from it.
- **While unlocked, prompting rests on Cinna's code, not on its data.** Whoever holds Cinna's channel to the helper can prompt the agent and answer its permission asks. An unlocked vault is only as safe as Cinna's code integrity: the Electron fuses, asar integrity, and the helper's check that its parent really is Cinna. For that reason everything that changes how the agent behaves — approval mode, instructions, model, "Always allow" grants — is kept *inside* the vault and read from there at every launch; Cinna's database rows hold display copies only. A helper-side permission UI would remove the dependency; it does not exist.
- **A machine that holds the team's Developer ID key with codesign set to "Always allow".** The helper's keychain access group protects the Secure Enclave key only as well as that key does; on such a Mac (the maintainer's) an agent could sign a binary into the group. The release runbook and the developer Mac take that permission back.

## Business Rules

- **Four engines, each on its own key.** Claude, Codex, OpenCode and Antigravity run in a vault; any other engine is a pre-check blocker. OpenCode must name a model on an OpenAI or Anthropic credential (a vault reaches no other provider) and runs on that provider's key. Antigravity signs in with a **Gemini API key** only: its Google sign-in cannot be completed inside. The engine accepts any key at `session/new`, so Cinna asks Google about a pasted key once, with an 8 s limit, before it is stored (Security tab or move dialog; the move dialog stays on its form showing "Checking key…" until the move is accepted): a refusal blocks the save with the reason, and no answer (offline, timeout) lets it through unchecked. A `claude setup-token` token (`sk-ant-oat…`) is refused wherever it would be stored as `ANTHROPIC_API_KEY` (OpenCode on an Anthropic model, or a secret of that name): only Claude Code signs in with it, and Claude's own login files it as `CLAUDE_CODE_OAUTH_TOKEN`. Each engine's default allowlist is its own API and login hosts (`VAULT_ENGINE_HOSTS`); a vault's always-allowed hosts are the union over the engines set up in it, and setting an engine up adds its hosts.
- **A vault holds every engine the user has chosen, and one is active.** The agent's row names the engine it runs on; the others stay installed so switching back is free. There is a runtime per engine in one vault, so the vault's disk grows by what each takes. A switch changes the engine and its model only: the approval mode and sealed-or-native launch stay, and the model resets to the CLI's default (OpenCode names its own). A kit agent's prompt is the one assembled for the engine chosen, captured at move-in for every engine (see [moving in](move.md)); an agent moved in before that keeps the prompt it has when it switches. **Update dependencies** updates every engine set up, not only the active one, so an engine switched to later is not found a version behind.
- **Logins are never removed by a switch.** Engines share login names (OpenCode on Anthropic reads the same `ANTHROPIC_API_KEY` Claude uses), so a switch stores a pasted key under its own name and deletes no other. A `claude setup-token` token is refused while the vault holds an Anthropic API key, because Claude would sign in with the key and ignore the token; paste an API key or leave the field empty. A key that cannot sign in is refused in the dialog before any prompt.
- **A switch is refused, not queued,** while the vault is locked, while the agent is moving or updating, while a turn runs on it, or while background work (a subagent, a background task) still runs on it (a dashboard run is stopped instead). After a switch the old engine's process is retired, so nothing of it can start a follow-up turn in a chat. It holds the agent's turn lock and the vault open for its whole length so no message starts on the old engine halfway; both are released before it reports done, so a message sent at once is not refused as busy. A message that was waiting for the lock when the switch won it fails with "This agent's engine changed while the message was being sent. Send it again.", and starts nothing, instead of launching the old engine against a row that names the new one.
- **A failed switch leaves the agent on its old engine.** What was installed or allowed before the failing step stays (a runtime set up, hosts allowed); the next try skips them. A prompt that is declined fails at its step as "Cancelled at the prompt." There is no way yet to remove an engine from a vault, to approve everything in one prompt, or to remember a model per engine.
- **The runtime must match its pin, twice.** Every engine and adapter is a pinned artifact: vaultd compares what it received with the pin before it commits it to the vault, and the launcher compares the installed one again before it runs it. An engine the pin does not name, or one edited inside the disk, does not start.
- **An engine receives only allowlisted environment.** Of the vault's secrets the engine process gets only the names on an allowlist (its own key), plus the fixed variables vaultd sets and the few model/effort names Cinna may pass (`VAULT_ENGINE_EXTRA_ENV`); no secret, however named, overrides a fixed variable or steers the engine's own configuration (`CODEX_*`, `OPENCODE_*`, `XDG_*`). A denylist of steering names had been the first form of this rule, and a name nobody listed got through.
- **Service credentials are delivered into the vault, from what was attached at move time.** The attachments the agent had when it moved are captured into the vault's own store; Cinna renders `credentials.json` (and a service account's side files) in memory and hands them over with `secrets.putFile` at the move and before a turn when the bytes changed. The vault keeps a root-only copy and gives the agent a read-only one; the agent's scripts reach it through `CINNA_CREDENTIALS_PATH`. Nothing is written on the Mac. Attaching or detaching afterwards does not change what a vault agent has (it has no folder here to hold the attachment), and a Google token is never refreshed from inside: there is no token server a vault can reach, so a renewed token travels in with the next delivery. The checklist still asks for their rotation, because they were on the Mac before.
- **The disk image lives in the reserved `SecureAgents/` folder** of the default agents folder. The name is reserved: no agent can be scaffolded with it, no scan or watcher enters it, and a folder of that name Cinna did not make (it writes a marker file) is refused with the reason. It carries a `.gitignore` of `*`, so a workshop that is a git repo never commits a disk image.
- **A test-flavor helper is never accepted by a packaged app**, and the packaging step refuses to ship one; a dev or fake backend shows a "Test helper" badge.

## Architecture Overview

```
Renderer (Security tab, vault chat)
   │ window.api.vault.*  /  vault:state push
Main (Hub core — untrusted for secrets)
   ├─ vaultService   state, unlock/lock/hold, gated changes, agent rows
   ├─ moveService    Move to vault… / Move out / host copy / export / update
   ├─ transcriptStore  vault chat rows in memory, journaled into the vault
   ├─ VaultFileAccess  file references: stat, capped read, gated export (vaultd files.*)
   ├─ VaultBackend (seam) ── appleVz │ fake │ unavailable
   │        │ helper stdio frames (no socket, no port)
   │        ▼
   │   Vault Helper  (VM, Secure Enclave key, prompts, proxy, timers)
   │        │ vsock                         guest (Linux, read-only system + LUKS disk)
   │        └──────────────────────────────▶ cinna-vaultd ── engine (Claude + ACP adapter)
   └─ VaultAcpConnection  ACP over an attached vaultd stream
```
