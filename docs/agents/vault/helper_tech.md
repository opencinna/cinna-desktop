The part of Agent Vault that does not trust Cinna. Everything above it is in [Vault — technical reference](vault_tech.md); the build and release steps are in [the runbook](vault_llm.md).

## Helper

**Why a separate program.** Cinna's main process and renderer are not in the trust base: same-user processes can tamper with their data. The helper is signed with the team's Developer ID, hardened, shipped inside the notarized app, and holds what must not depend on Cinna. It ships at `Contents/Library/Helpers/VaultHelper.app`, and electron-builder is told not to re-sign it (`signIgnore`), because a re-sign would drop the keychain entitlement and the Secure Enclave key's access group with it.

**Channel.** Main talks to the helper over the helper's **stdio**, not a socket or XPC: nothing listens anywhere a same-user process could connect. Frames are length-prefixed with a type (control JSON, data, eof, reset) and a channel number; channel 0 is control, any other channel is a bridged vsock connection to a guest port. Maximum payload 256 KiB. Control methods: `hello`, `availability`, `vault.list/create/unlock/lock/hold/release/status/approve/setEgress/setLockTimeout/touch/resize/destroy`, `channel.open`; events `vault.state`, `egress`, `log`.

**Flavors** (fixed at compile time, reported in `hello`, written into `Info.plist` as `CinnaVaultFlavor`):
- **release** — parent check, LocalAuthentication, Secure Enclave key in the keychain group. The only flavor a packaged app accepts.
- **dev** — keeps the parent check but accepts an Apple Development or Developer ID signed parent of the team; its own keychain group and key tag (`…vault-helper.dev`) so a dev build never touches the release key. Built only on a machine with the team identity.
- **test** (`-D VAULT_TEST_GATE`) — approvals and unlock granted without a prompt, the disk key in a plain file beside the disk, no keychain, ad-hoc signed. Compiled out of release; the test binary carries a marker string that `verifyVaultHelper` looks for in the bytes, whatever its plist says. Test-only environment knobs (`CINNA_VAULT_TEST_WINDOW_MS`, `…_HOLD_MAX_MS`, `…_PAUSED_STOP_MS`, `…_UNLOCK_DELAY_MS`, `…_SCREEN_LOCKED=0|1`, `…_ENFORCE_PARENT=1`, parent identifier and team overrides) exist only here, as does `SIGUSR1` standing in for a screen lock.

**Who may drive it.** At start the helper audits its parent and refuses to run unless the parent is Cinna: the check is by **audit token** read from the helper's stdin socket (not by pid, which an attacker could exec into), verified against a code requirement (identifier `io.opencinna.desktop`, team `G5E484HA2U`, Developer ID in release), hardened runtime, and **no `ELECTRON_RUN_AS_NODE`** in the parent's launch environment — the run-as-node fuse is still on, so without this check any process could run its own JS under Cinna's signature and drive the helper. The verified process identity is then **pinned and re-read after every frame**, so a process that exec'd into Cinna after the check, or a forked accomplice holding the pipe, ends the helper. Stdin that is not a socket is untrusted.

**Key custody.** One Secure Enclave P-256 key per install, permanent, in the data-protection keychain under an access group only the helper claims, protected by user presence and "when unlocked, this device only". It never exists as a file. Each vault's 32-byte disk key is wrapped with it (ECIES-style); unwrapping prompts. `vault.json` — the vault id, agent id and name, engine, size, allowlist, image pin and lock timeout (`lockAfterMs`; absent, or a value this build does not offer, reads as the 5-minute default rather than as tampering); no secrets — is one atomically written file, signed with a per-install key, and the helper also keeps rollback digests in the keychain group, so a host edit or an old validly-signed copy reads as `tampered`.

**Prompts.** `vault.unlock` and `vault.approve` raise LocalAuthentication with text the helper builds from the action, the detail and the agent name in the signed `vault.json`. Cinna cannot change it. `egress`, `resize`, `destroy` and `lock-timeout` tokens are verified by the helper itself; the others by the guest.

**Lock.** The helper owns the idle timer: the vault's `lockAfterMs` (30 s, 5 min, or 0 = none) from the last hold release, gated action or `vault.touch`. `vault.setLockTimeout` takes a strictly shorter value (0 is the longest) with no token, anything else only with a `lock-timeout` token for that exact value, and restarts a running vault's window at once; on a vault that is not unlocked it changes the file and sends no `vault.state`. `vault.touch` restarts the window of an unlocked, unheld vault with a timer and is otherwise a no-op. The test flavor's `CINNA_VAULT_TEST_WINDOW_MS` overrides every vault's value. The helper also caps a hold at 4 hours, and watches `com.apple.screenIsLocked`, will-sleep, session-resign and power-off — Cinna is not asked, so a compromised Cinna cannot keep a vault open across a screen lock. A lock tells the guest to `cryptsetup luksSuspend` the data disk (freezing I/O and wiping the dm-crypt key from guest kernel memory), pauses the VM, then zeroes the helper's own copy of the key. An unlock of a paused VM prompts, unwraps again, resumes and gives the guest the key to `luksResume`. A paused VM is stopped cold after 30 minutes; stdin EOF stops all VMs and exits. A bumped lock generation makes a lock that lands mid-unlock win; unlock is refused while the screen is locked; one `flock` on `data.img` per VM.

**Network.** No NAT and no virtio-fs or clipboard device. The guest's only route is a CONNECT proxy in the helper on vsock port 1080: CONNECT only, port 443 only, the target a DNS name (never an IP literal) on the vault's allowlist (`*.example.com` matches subdomains only), resolved by the helper, which never connects to loopback, link-local, multicast or unspecified addresses, so an allowlisted name that resolves to `127.0.0.1` cannot reach services on the Mac. Install hosts are allowed only for a CONNECT carrying `Proxy-Authorization: Basic base64("cinna:<cred>")` of a live **per-install proxy credential**, minted with a `move-in` or `install` approval, given by vaultd only to that exec, and revoked when the exec ends, at token expiry, or on lock (tunnels it opened are cut).

**First boot and recovery.** `boot.js` runs `cryptsetup isLuks` before it formats anything. A disk that already holds LUKS is opened, never formatted again, and makes a filesystem only if none is found (`blkid`), so a first boot cut off between `luksFormat` and `mkfs` recovers on the next one. The helper fails the unlock if it cannot persist that the disk is formatted. Measured on a real guest: a cold boot with `init_on_free` about 2.7 s, a resume about 80 ms.

**VM.** 4 vCPU (at most host cores − 1), 4 GB, kernel command line `console=hvc0 quiet loglevel=0 init_on_free=1 init_on_alloc=1` plus the time, the verity root hash and offset, `root=/dev/vda`. Devices: the read-only rootfs and the data disk.

## Guest

- **Image.** Debian trixie arm64 (glibc), read-only **erofs with dm-verity**; the root hash is compiled into the helper, so a rootfs the helper did not expect fails to boot. The kernel (`Image`, Alpine `linux-virt`) and `initrd.img` ship **inside** `VaultHelper.app`. Contents: `ca-certificates curl git socat cryptsetup-bin e2fsprogs ripgrep procps less openssh-client` (ssh for git over https only, no sshd), Node 22, uv, the vaultd bundle. No DNS (`/etc/resolv.conf` points at loopback); proxy env set for every tool, and tools must be proxy-aware. Every input to the build is pinned by sha256 in `native/vault/guest/build/inputs.lock`.
- **Data disk.** One sparse **LUKS2 ext4** image per vault, mounted at `/vault`: `agent/` (the agent folder, cwd), `home/`, `runtime/<engine>/<version>/`, `adapter/…`, `secrets/` (root only), `transcripts/<chatId>.jsonl`, `state/kv.json`, caches and `python/`. `boot.js` runs `cryptsetup isLuks` before formatting, so an encrypted disk is never reformatted; the helper fails the unlock if it cannot persist that the disk is formatted.
- **Boot.** `initrd/init` opens the verity root and switches to it; `vault-init` reads one boot message on vsock 1090 (disk key, approval key, whether to format, size to grow to), opens or formats the disk, mounts it and starts vaultd. The disk key goes to cryptsetup on stdin only and is handled as bytes, never a JS string, and zeroed.
- **Unprivileged work.** vaultd is root; engines and the shell run as uid 1000 `agent`, install and check presets as uid 1001 `build`, each through `setpriv` with no extra groups, empty capability sets and `no_new_privs`. The `build` user is the one that sees install hosts, and only `rebuild` and `uv-python-install` get a proxy credential; `uv-sync` runs with none and so syncs only what the uv cache holds. No setuid file on the rootfs; `/vault`, `/tmp` and `/run` are `nosuid`. The console prints only fixed status words, never a path or a name.
- **Engines are not in the image.** Main streams each engine's pinned runtime and adapter in (Claude Code with the patched adapter's closure; Codex's executable and host as one tar with the `codex-acp` package; OpenCode's package; Antigravity's server as a tar); the guest hashes what it received and refuses a result that is not the pin before it commits the runtime, and the launcher checks the installed hashes again before it runs one. The agent's command line is built by vaultd from an engine id and a few allowlisted options; there is no arbitrary argv except a gated terminal.

## vaultd protocol (port 5000)

Each connection starts with one JSON line: `control` (JSON-RPC 2.0, ndjson) or `attach` to a stream id (raw bytes; closing is EOF). Port 5001 is the helper's own control channel, never reachable from main.
- Read-only and layout: `hello`, `layout.ensure`, `disk.usage`, `runtime.status`, `files.list`, `auth.status`, `kv.get/put`, `transcript.read/list/append/delete`, `secrets.put/putFile/list/delete`. `putFile` keeps a root-only copy under `secrets/files/` and refreshes the agent's read-only copy in `run-secrets/` (see [vault_tech](vault_tech.md#security)).
- Engine: `engine.spawn` → a stream carrying ACP ndjson (+ `engine.exit`, `engine.stderr`), `engine.kill`, `auth.login`. `options.extraEnv` is limited to an allowlist in `protocol.ts`; of `/vault/secrets` vaultd adds only allowlisted names (the engine's key), under the fixed variables it sets itself; `options.mode` becomes the vault's own `permissions.defaultMode`.
- Gated: `runtime.install`, `files.import`, `files.export`, `exec` presets (`uv-python-install`, `uv-sync`, `rebuild`, `check`, `shell`). `exec.resize` (the shell's window size) is ungated: the terminal token already opened the shell. The sync is `uv sync --locked --no-build --no-install-project --no-install-workspace`; `rebuild` first runs `uv lock --no-build` when there is no `uv.lock`, while `uv-sync` (no install credential) refuses without one. Wheels only; the agent's own project is never built while the install hosts are open. Session tokens (`move-in`, `install`) authorize import, runtime install and the install presets until they expire; single-use tokens (`export`, `terminal`, `move-out`) bind a nonce and a hash of the exact detail.
- **Approval token** = base64url(claims) + "." + base64url(HMAC-SHA256(approval key, first part)); claims name vault, action, detail hash, nonce, expiry. Only the helper (and the fake backend, standing in for it) signs. The guest holds the key only in tmpfs and refuses a gated call with a missing, forged, expired, replayed or mismatched token.
- Fake mode (`--fake`): the same protocol over a unix socket under a temp root, no LUKS, `node` as the host's; used by `fakeBackend.ts`, the contract test and E2E. It protects nothing and says so (`flavor: 'fake'`).

## Security notes

- The release helper is only as strong as the team's Developer ID key: where it sits in a login keychain with codesign "Always allow", an agent can sign a binary into the access group. See the threat model in [Agent Vault](vault.md).
- The helper cannot be hardened against a host kernel compromise; an unlocked vault is not protected from root.
