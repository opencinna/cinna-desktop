# Agent Vault — technical reference

## File Locations

**Shared (no imports from main; also bundled into the guest)**
- `src/shared/vault/protocol.ts` — the two wire protocols as types and literals: helper frames and control methods, vaultd requests, gated actions and token lifetimes, the allowlists, `VAULT_LOCK_TIMEOUTS` / `VAULT_DEFAULT_LOCK_AFTER_MS` / `vaultLockTimeoutShorter()` (the unlock window is per vault; there is no global constant), `VAULT_PAUSED_STOP_MS`, `VAULT_DEFAULT_SIZE_BYTES`, `approvalDetail()`, `vaultKvInstructionsFor(engine)` (`cinna.instructions.<engine>`), `VAULT_ENGINE_NAMES_MODEL` (OpenCode only) and `VAULT_OPENCODE_DEFAULT_MODEL`.
- `src/shared/vault/types.ts` — renderer DTOs, `VaultResult`, error codes, move steps, `VAULT_SWITCH_STEPS` (`runtime`, `egress`, `credentials`, `engine`; `VaultMoveStep` is the union of move-in, rebuild and switch steps), `VaultEngineChoiceDto`, `VaultSwitchEngineOptions`, `SECURE_AGENTS_DIR`, `isSecureAgentsName`, `vaultOtherChatReason`.
- `src/shared/runtimePins.ts` — `RUNTIME_PINS.vaultGuest`, each engine's `vaultAdapterTarSha256` (Claude, Codex) and `vaultRuntimeTarSha256` (Codex, Antigravity).

**Main — hub core (no Electron)** `src/main/vault/`
- `backend.ts` — the `VaultBackend` seam: `kind`, `capabilities()` (besides the hardware flags: `lockTimeouts`, the timeouts it can keep, empty when none, and `idleTouch`), `hello()`, `availability()`, `list/create/status`, `unlock/lock`, `hold/release`, `approve`, `setEgress/setLockTimeout/touch/resize/destroy`, `open()` (a byte stream to vaultd), `onEvent`; `installVaultBackend`, `unavailableBackend(reason)`.
- `vaultService.ts` — `vaultService`: availability, `SecureAgents/` creation, state cache and `vault:state` publishing, unlock/lock/hold, gated changes (`setEgress`, `setSize`, `destroy`), `setLockTimeout` (validated against the backend's `lockTimeouts`; shorter than the current one goes without a token, otherwise a `lock-timeout` approval first) and `touch` (fire-and-forget, only for a vault known to be unlocked and a backend with `idleTouch`), `bindChat`, the shared vaultd connection, secrets/runtimes/files reads, the transcript journal queue, quit drain. `guestRootfs()` (in `guestImage.ts`) says whether an image can be had.
- `guestImage.ts` — which `rootfs.img` a vault boots: the dev image unpackaged (no image in `build/vault-guest/` is an error that names the folder and says `make vault-image` or `make vault-dev-restart`), else the pinned one; `ensureGuestImage` downloads it into `SecureAgents/.images/rootfs-<version>.img` (the shared managed-asset code checks the sha256 and publishes by rename, leftovers swept, concurrent callers joined); `guestHashMismatch` compares the helper's compiled-in root hash with the image's before anything is created. `pruneGuestImages` (packaged, published pin only) deletes every other `rootfs-*.img` and the `.staging-*` leftovers directly inside `.images/`, and nothing else; `vaultService.pruneGuestImages` runs it once at start (`hub/core.ts`) for a `SecureAgents/` Cinna made, never creating one. It is safe because no unlock boots anything but the pinned image.
- **Unlock boots the pinned image.** `vaultService.unlock` first calls `unlockRootfs`: for a real backend it runs `ensureGuestImage` (instant when the file is there; after an update it downloads, publishing `vault:unlock-progress` `{ agentId, vaultId, percent }`, `percent: null` when done or failed; a download failure is the unlock's error) and passes the path as `backend.unlock(vaultId, purpose, rootfsPath)`; the fake passes none. A vault records the image it was created with, which an update replaces and the helper could no longer verify, so the record is never what boots. The lock generation is read *before* the download and compared after it: a lock during a download of minutes voids the unlock before the helper prompts, not after.
- `moveService.ts` — pre-check, `moveIn`, host copy, `moveOut`, `exportFile` and `exportVaultPath` (save dialog, then the helper's prompt for a single-use `export` token naming the path, then `files.export` unpacked where the dialog said; shared by the Security tab's Export… and a file reference's Download), `updateDependencies`, `switchEngine` and `vaultEngineChoices`, rotation list.
- `vaultCredentials.ts` — service credentials into the vault: renders `credentials.json` and side files in memory (`serviceCredentialService.vaultFiles`) and sends them with `secrets.putFile`; the attachments are the ones captured at move time (`cinna.serviceCredentials` in the vault's store); re-delivered before a turn only when the rendered bytes changed.
- `vaultChatFiles.ts` — attachments in a vault chat: `vaultChatAccepts`, `discardVaultChatFiles` (the `userData` copies deleted when the turn ends).
- `vaultTerminal.ts` — Open terminal: hold, `terminal` token, `exec` preset `shell` (opened at the window's size), bytes both ways, `resize` forwarded to vaultd `exec.resize`, one `exit` or `error`. `engineLoginCheck.ts` — checks a pasted engine login before it is stored: `sk-ant-oat…` under `ANTHROPIC_API_KEY` is refused; a Gemini key is asked of Google once (8 s; 400/401/403 block, no answer passes). Called through `refuseBadLogin` by `vaultService.setSecret` and `moveService.moveIn`, before moveIn's busy check since it can wait seconds; failures are `VaultError('invalid')`. vaultd `pty.ts` — `ShellPty`: script(1) runs the shell with a pipe on stdin so it never sizes the pty; vaultd (root) finds the shell's pts through script's child fd 0 and runs `stty -F` **as the agent user**. Fake mode and non-Linux apply nothing.
- `adapterTar.ts` — the deterministic adapter tars written by the app build (`out/vault/claude-adapter.tar`, `codex-adapter.tar`).
- `fileAccess.ts` — `VaultFileAccess` (`resolve`, `read`, `exportFile`), the seam file references use to reach a vault's files; `createGuestFileAccess` is the default over vaultd (`files.stat` in batches of 200, `files.read` capped at 10 MB, export via `moveService.exportVaultPath`). `vaultService.files()` returns `VaultBackend.files?.()` when a backend runs no vaultd, else the guest one. Nothing in the agent-file service touches a vault except through it.
- `isVaultAgent.ts` — the one predicate, `refuseVaultAgent`, `VaultAgentRefused` (code `vault_agent`), `vaultChatReadiness`.
- `transcriptStore.ts` — `vaultTranscripts`: in-memory vault chats, the journal sink, detached transcripts.
- `vaultAgentState.ts` — the vault's own key-value state: sessions, always-allow grants, captured instructions, launch settings.
- `vaultdClient.ts` — JSON-RPC client over a channel; `frames.ts` — helper frame codec and `HelperClient`; `approvalTokens.ts` — HMAC tokens (signed only by the fake backend); `runtimeInstall.ts` — streaming each pinned engine and adapter in; `fakeBackend.ts` — vaultd as a plain Node process; `secureAgentsDir.ts`, `hostCopy.ts`, `vaultHost.ts` (save dialog and Time Machine probe, injected).
- `testSupport/` — fixtures shared by the vault tests.

**Main — drivers** `src/main/agents/drivers/acp/`
- `vaultAcpConnection.ts` — the third ACP transport, beside stdio and WebSocket.
- `vaultLauncher.ts` — Claude's launcher and the readiness shared by every engine inside a vault; `vaultEngineLaunchers.ts` — the Codex, OpenCode and Antigravity launchers (no MCP servers, no host plugins or config; the vault's key is the login); `vaultRuntime.ts` — wires the launcher, readiness and the turn's hold into the ACP driver.

**Main — desktop host** `src/main/host/desktop/vault/`
- `installVaultBackend.ts` — picks the backend and finds the helper; `appleVzBackend.ts` — spawns the helper, speaks frames, implements `VaultBackend`.

**IPC** `src/main/ipc/vault.ipc.ts`; **database** `src/main/db/migrations/chat-vault.ts`, `src/main/db/chats.ts`, `messages.ts`, `inflightTurns.ts`, `agents.ts`.

**Renderer** `src/renderer/src/components/agents/local/security/` (`SecurityTab`, `AgentVaultSection`, `VaultOnPanel`, `MoveToVaultDialog`, `VaultDialog`, `VaultTerminalDialog` (xterm), `vaultText.ts`), `src/renderer/src/hooks/useVault.ts`, `src/renderer/src/components/chat/VaultOtherChatNotice.tsx`, the `vault_locked` row in `ComposerReadiness.tsx`.

**Native** — see [Vault Helper and Guest](helper_tech.md).

## Database Schema

- `chats.vault_id` — nullable, added by `migrateChatVault` (`src/main/db/migrations/chat-vault.ts`, called from `runAllMigrations` right after the chat migrations; no DML). Set once by `chatRepo.bindVault`, never changed. A chat with it keeps a stub row only.
- `agents.source = 'vault'` marks a vault agent; the id is unchanged (`folder:<manifest id>`). `driverConfig.vault` holds `vaultId`, `engine`, display copies of `kind`/`model`/`approval`, and `hostCopyPath`/`hostRootId` while the original folder remains. `localPath` is null. `agentRepo.markVault`, `unmarkVault`, `patchVaultConfig`, `listVault`, `listVaultAgentIds`, `findVault`; folder-index replace and prune skip rows of this source.
- `messages` and `inflight_turns` rows are **never** written for a vault chat. `messageRepo`, `inflightTurnRepo` and `chatRepo`'s message reads route through `vaultReadRoute` / `vaultWriteRoute` in `chats.ts`, so the FTS triggers never fire. A write to a vault chat whose vault is locked throws `VaultTranscriptLocked` (`vault_locked`) rather than fall through to SQLite.

## IPC Channels

All answer `VaultResult<T>` (a thrown code does not cross IPC, so failure is data) and are reached as `window.api.vault.*`.
- `vault:availability` — `VaultAvailabilityDto`: availability or reason, backend kind, helper flavor, capabilities.
- `vault:unlock-progress` (push, `window.api.vault.onUnlockProgress`) — the image download of an unlock; `useVaultUnlockProgress` / `useVaultUnlockPercent` in `useVault.ts` feed the pending labels ("Unlocking… 40%"; the composer's detail line says `vaultImageDownloadText`, "Downloading vault image… N%"). `VaultUnlockLabel.tsx` is the Unlock button's label on the locked chat card and the file preview; `StableLabel`'s `reserve` slot sizes the button for "Unlocking… 100%" from the start so it never widens.
- `vault:list`, `vault:status`, `vault:unlock`, `vault:lock` — states; `vault:set-size`, `vault:set-egress`, `vault:set-lock-timeout`, `vault:destroy` — gated or settings; `vault:touch` — fire-and-forget (nothing returns; an unactivated session does nothing).
- `vault:precheck`, `vault:move-in`, `vault:cancel-move`, `vault:host-copy`, `vault:delete-host-copy`, `vault:move-out`, `vault:update-dependencies`.
- `vault:engines` (`agentId`) — `VaultEngineChoiceDto[]`: each vault engine, `setUp` and the installed version; needs the vault unlocked. `vault:switch-engine` (`agentId`, `VaultSwitchEngineOptions`) — `{ moveId }`; the options are validated again in main (`parseSwitchOptions`: OpenCode needs a provider and a model, any other engine takes neither). Progress is `vault:move-progress` with the switch steps; the final event is `engine` done, or the failed step.
- `vault:agent-details` (`agentId`) — `VaultAgentDetailsDto`: manifest, description, `STATUS.md` summary, the three kit prompts, credential slot states from the `.env` names, and `launch` (kind, model, approval); needs the vault unlocked, read-only. `vault:grants` (`agentId`) — the vault's *Always allow* grants as `StoredPermissionGrant[]`, newest first. `vault:forget-grant` (`agentId`, key or `null` for all) — what is left; a key that is neither a string nor null is `invalid`.
- `vault:secrets`, `vault:set-secret`, `vault:delete-secret` — names only come back; `vault:engine-auth`, `vault:runtimes`, `vault:list-files`, `vault:export-file`.
- Pushes: `vault:state` (`VaultStateEvent`, to every window) and `vault:move-progress` (`VaultMoveProgressEvent`, also used by Update dependencies and a switch of engine; the Move dialog ignores steps that are not its own).
- Chat detail (`chat:get`) carries `vaultId` and `vaultReadiness` (`vault_other_chat`).

- `vault:open-terminal` is not request/response: the window sends the agent id with `ipcRenderer.postMessage` and a `MessagePort` (id as the second argument, port on `event.ports`, see CLAUDE.md). The window posts `VaultTerminalCommand`s (`input`, `resize` with cols/rows, `close`); main posts `VaultTerminalEvent`s (`open`, `data`, then exactly one `exit` or `error`) and closes the port. The port closing ends the session. It needs user activation like every vault channel Sizes are integers clamped to `VAULT_TERMINAL_COLS`/`ROWS` (2–500 × 2–200); the latest size is kept and sent once `exec` returns, and the shell starts at it (`exec` takes optional `cols`/`rows`). `exec.resize` takes no token (the terminal approval opened the shell; a size grants nothing) and answers `not_found` for any stream that is not a shell. It needs a rebuilt guest image to take effect.

## Services & Key Methods

- **Backend choice** — `installVaultBackend.ts:installDesktopVaultBackend()`: `CINNA_VAULT_FAKE=1` in an unpackaged build → the fake (checked first, so an E2E run never boots a real VM); not macOS → `unsupported-os`; not arm64 → `unsupported-hardware`; the helper present (assumed when packaged) → Apple VZ; else `helper-missing`. `vaultService.availability()` adds `image-missing` when `guestRootfs()` finds no image (a packaged build while `RUNTIME_PINS.vaultGuest.published` is false; a dev build with no `rootfs.img`); a published image that is not downloaded yet is not `image-missing`, the move's `create` step fetches it, and turns a helper that will not say hello into `helper-missing`. A packaged app refuses any helper flavor but release (`appleVzBackend.ts`).
- **State** — the helper pushes `vault.state`; `vaultService.ts:onBackendEvent` updates the cache, drops transcripts and the vaultd connection on any state but `unlocked`, publishes `vault:state` and re-asks the agent's readiness so the composer follows. A per-vault lock generation makes a lock that lands during an unlock win. Only a **change** to a non-unlocked state leaves unlocked: a repeat of the state the last event (or the cache) already held does not bump the generation, which would void an unlock in flight and sweep staged files. The helper, for its part, sends no `vault.state` when a setting changes on a vault that is not unlocked, since main reads a non-unlocked event as "left unlocked"; `vault.state` carries `lockAfterMs`.
- **Turns** — the ACP driver holds the vault (`vault.hold`) for the whole turn and releases it in a finally; a locked vault fails the turn with "Unlock it to send a message". Readiness order: engine a vault cannot run → `vault_locked` → `not_installed` (runtime missing; fix with Update dependencies) → `not_logged_in` (add the engine's API key) → `ok`, the same for all four engines; `vault_other_chat` (a chat that began before the move) is answered by `vaultChatReadiness` before any of it.
- **Behaviour comes from inside** — `vaultLauncher.ts` reads `cinna.launch` and `cinna.instructions` from the vault's key-value store at every launch; `vaultAgentState.ts` keeps `cinna.sessions` and `cinna.permissionGrants` there instead of a host `desktop.json`. Grants are cached in memory while unlocked (the ask path is synchronous) and a failed write is asked again next time.
- **Changing the engine** — `moveService.ts:switchEngine()` validates and refuses at once (locked, `movingAgents`, the turn lock held by anything but a dashboard run, the same engine again unless it is OpenCode, a key that cannot sign in, a Claude token while `secrets.list` holds `ANTHROPIC_API_KEY`), takes `turnLock.acquire(agentId, 'vault-engine')` and adds the agent to `movingAgents`, then `runSwitch` holds the vault (`backend.hold`) and runs the steps in order, each `skipped` when there is nothing to do: `runtime` (`runtime.status`; when `installedRuntime` says missing, an `install` approval and `ensureRuntimes`), `egress` (when `VAULT_ENGINE_HOSTS` has a host the allowlist lacks, `vaultService.applyEgress` raises an `egress` approval for the union), `credentials` (`secrets.put` of the key under its own name only), `engine` (`switchLaunch`: copy `cinna.instructions.<engine>` into `cinna.instructions` when one was captured, write `cinna.launch` keeping kind and approval with the new model and provider; then `agentRepo.patchVaultConfig` on the row, `refreshVaultAgents`, `agentChanged`, `vaultService.readinessChanged`). The lock and the `movingAgents` entry are released **before** the final event is sent, so a send right after done is not refused as busy. **vaultd, the guest image and the helper are untouched**: everything it writes is existing `kv.put`, `secrets.put`, `runtime.install` and the helper's existing approvals, so no rebuild of either is needed.
- **The row is the source of truth for the engine.** `driverConfig.vault.engine` decides which launcher a turn plans; `vaultService.toStatus` reports it (not the helper's `vault.json` copy, which is the engine the vault was created with). `model` and `provider` on the row are display copies (`localAgentService.vaultDisplayLaunch` onto `LocalAgentDto.vault`); `cinna.launch` decides. **Set-up engines are never stored**: `vaultService.engines` derives them from `runtime.status` on every call (`moveService.vaultEngineChoices`: set up when `installedRuntime` finds the runtime and adapter this app pins, at any version; an outdated one is still set up and Update dependencies moves it).
- **Instructions per engine** — move-in writes `cinna.instructions.<engine>` for all four engines (`vaultKvInstructionsFor`) besides the active `cinna.instructions`, because the host folder, which assembles the prompt, is gone after the move. Nothing reads the per-engine keys but a switch. A vault moved in before this has none: a switch then keeps the active prompt as it is.
- **The turn lock and the stale plan** — a turn plans its engine, then waits for the lock; a switch holds it exclusively and changes the row meanwhile. The driver therefore reads the engine again under the lock (`AcpDriverDeps.currentVaultEngine`, wired in `drivers/index.ts` through `vaultLaunchInfo`) and fails with `ACP_VAULT_ENGINE_CHANGED` and no process started when it differs from `plan.spec.vault.engine`; the same pattern as `ACP_FOLDER_MOVED`.
- **Logins during a switch** — `putEngineLogin` in `vaultService.ts` (Security tab key: store under the name, delete the engine's other names) is unchanged for that path. A switch does not use it: it stores under its own name and **never deletes another name**, since names are shared between engines (OpenCode on Anthropic and Claude both read `ANTHROPIC_API_KEY`); deleting Claude's token because OpenCode was given a key would break an engine the user did not touch. A Claude setup-token is refused while `ANTHROPIC_API_KEY` is held (`CLAUDE_TOKEN_UNDER_KEY`), since an API key wins over a token.
- **Failure** — the `engine` step restores `cinna.launch` and `cinna.instructions` to what `readLaunch` read (`restoreLaunch`) when `switchLaunch` or the row update fails; if even that fails the message adds that the vault's launch settings could not be put back, because the vault may then disagree with the row. A failure before the `engine` step changes neither. **What stays after a failure:** a runtime already installed, hosts already allowed and a key already stored. A declined prompt is `Cancelled at the prompt.` at its step.
- **Update dependencies** — `updateDependencies` reads `runtime.status` and runs `ensureRuntimes` for every engine set up, plus the active one even when its runtime went missing, under one `install` token, then the rebuild.
- **Credentials and attachments** — `vaultCredentials` runs at the move's `credentials` step and again before a turn. Attachments: `attachmentUploadsDir` is null for a vault agent, so files travel inline in the prompt (text, PDF and Office as extracted text; png/jpeg/gif/webp as image blocks); `fileService.ingest` refuses anything else for a vault chat before a byte is stored, and `discardVaultChatFiles` deletes the stored copies when the turn ends. Any copy a turn left behind is swept at start and when a vault locks, so a turn the app died under does not leave a file in `userData`.
- **Swept drafts** — a lock that deleted staged attachment copies publishes `vault:chat-files-swept` (`VaultChatFilesSweptEvent`: vault id and, by chat, attachment ids; never for the sweep at start). `useVault.ts:applyVaultChatFilesSwept` removes those chips from every `chat:<id>` draft in `composerDraft.store` (so an unmounted composer shows it on return) and sets the file error `vaultChatFilesSweptText`.
- **Transcripts** — every row op is a `TranscriptOp` journaled through the sink (`transcript.append`), queued in order while the vault is locked and delivered after the next unlock; the vault's chats are rebuilt from `transcript.read` on unlock. A chat whose turn is running when the vault locks becomes a **detached** transcript until the turn finishes writing; a detached one reads as locked, so a half-written transcript is never shown as the chat's whole history. A quit is held up to 3 s (`index.ts` `will-quit`, `vaultService.pendingQuitDrain`) to deliver queued rows, then the helper stops every VM.
- **File references** — `agentFiles/vaultFileSource.ts` is the vault's `AgentFileSource` (see [File References](../../chat/file_references/file_references_tech.md#file-sources)), wired in `host/desktop/agentFiles.ts` with `vaultService.refFor` and `vaultService.agentCwd`. It resolves only paths inside the agent folder (`~/` and other absolute paths name nothing), stats and reads through `VaultFileAccess`, re-checks that the path vaultd opened is the one it stat-ed, applies the credential rule again in main, and answers `locked` for a locked vault. Download of the folder itself is refused (use Export… on the Security tab). A vault state push, or the agent list showing an agent moved in or out, drops that agent's resolved refs in the renderer (`useVault.ts`) because the old source offered other actions, and re-checks an open preview.
- **Exclusions** — callers of `isVaultAgent` / `refuseVaultAgent`: `delegationService` (target list, `requireTarget`, create), `taskService` and `taskExecutionService` (assignee), `handoverService` (agents and intake), `chatService` (add on-demand agent, bind), `conductorBridge` and `a2aAsMcpProvider` (no `cinna` MCP, no loopback URL, no attachment), `agentService`, `localScheduleService` (save, enable, scheduled runs), `commandService` (Run commands), `openInService` and `agentFileService`, `serviceCredentials/service.ts` (credential files), `inboxService`, `chatTitleService` (`vault_chat`), `jobExecution/desktop.ts`, `sync/scriptAgents.ts`, and `localAgentService`, whose `locate` throws `vault_agent` for any host-path consumer. `vaultChatReadiness` is applied in `runExecutionService` before a vault agent answers in a chat of another vault or none.
- **Reserved folder** — `SECURE_AGENTS_DIR` is skipped by `scannerService`, `externalScan`, `watcherService` (both event paths), `kit/validator.ts` (`UNWALKED_DIRS`); `scaffoldService` and `localAgentService` refuse the name; `vaultService.ensureSecureAgentsDir` writes the `.gitignore` (`*`) and the `.cinna-vaults` marker and refuses a folder without it (`secureAgentsDir.ts`).
- **Errors** — `VaultError` codes (`unavailable`, `not_found`, `not_vault_agent`, `locked`, `denied`, `busy`, `invalid`, `tampered`, `internal`); a cancelled prompt is `denied` and the UI says "Cancelled at the prompt — nothing changed."

## Vault agent page reads

A vault agent's DTO carries no manifest, status or prompts (there is no folder to scan), so the page asks the vault.
- `vault/vaultAgentDetails.ts` reads `cinna-agent.json`, `app-data/storage/STATUS.md`, the three prompt paths and `credentials/.env` through `VaultFileAccess` (512 KB each) and calls `vaultAgentState.launch`. A file the vault does not have (`not_found`, `invalid`) is absent; a read that answers with a different path than asked (a link elsewhere in the folder) counts as absent, so no other file's bytes show under this one's name. Parsing is `services/localAgents/agentFolderText.ts` (`parseEnvKeysText`, `parseStatusText`, `credentialStates`), the same functions the folder scanner uses, so a vault and a folder agent cannot disagree about a file. `.env` values never leave that module.
- `vaultAgentState`: `listGrants` waits for queued writes, then reads `cinna.permissionGrants`. `forgetGrants` removes the key from the in-memory copy at once, then queues the vault write behind earlier ones and re-applies the removal to the copy afterwards. `load` (before a turn) is queued in the same chain. The failure this prevents: a `load` read concurrently with a revoke put the revoked grant back into the copy a turn reads, and the turn's next `rememberGrant` wrote it back into the vault. A failed revoke write leaves the copy without the key (this session asks again) and reports the error to the page.
- Renderer: `useVaultAgentDetails` (enabled only while open), `useVaultGrants`, `useVaultForgetGrants`, `useVaultOpen`, and `useAgentGrants` (picks the vault or the folder source; `locked` for a shut vault). A lock disables the queries; their cached rows are not shown while locked. `VaultOverview.tsx`, `VaultCredentialsTab` (in `ServiceCredentialsTab.tsx`), `PermissionsCard`'s `VaultApproval`, and `security/VaultLockedCard.tsx` (`VaultDetailsGate`: locked card with Unlock, one reading line, then the cards read-only). `PromptDocCard`'s `KIT_PROMPT_CARDS` is shared with the folder Overview. `LocalAgentPage.tsx` drops `addons` and `tasks` from a vault agent's tabs.
- `VaultEnginePanel`'s Unlock is a fixed-width secondary button on the right of the card (`VaultUnlockLabel`); its slot is kept, only hidden, once unlocked, so the select never changes width.

## Renderer Components

- `SecurityTab.tsx` — **Agent Vault** section first, **Permissions** second, owning the Move dialog so the move outlives the section's state. The tab id was `permissions`; `ui.store.ts` maps a persisted or requested `permissions` to `security`.
- `AgentVaultSection.tsx` — never disappears: off, unavailable-with-reason (`vaultText.ts` wording per reason), or on. The "What a vault protects against" panel states both halves of the threat model. A non-release helper shows a "Test helper" badge.
- `VaultOnPanel.tsx` — status and the countdown ("Unlocked · locks in 4:32", "Running" while a turn holds it, plain "Unlocked" with no timer), Unlock / Lock now, the **Lock after** select (`LockAfterRow`; choices from `capabilities.lockTimeouts`, none ⇒ no row; shows the value being asked for while the prompt is up), the host-copy row, Disk size limit, Network access, Engine login (per engine key; an engine whose login has several names — Claude's API key or `claude setup-token` token — is described by `VAULT_ENGINE_LOGIN` in `shared/vault/protocol.ts`, and `vaultService.setSecret` files the value by prefix and deletes the other name), Secrets, Toolchain, Terminal (Open terminal, enabled only while unlocked), the folder browser with **Export…**, Move out, Delete vault. Rows reserve their height so an unlock does not shift the controls.
- `MoveToVaultDialog.tsx` — pre-check, progress by step, rotation checklist; built on `VaultDialog.tsx`. Exports `StepIcon` and `StepStatus` for the engine dialog.
- `VaultEnginePanel.tsx` — rendered by `LocalAgentPage.tsx` in settings mode for a vault agent, where `RuntimePanel` is for any other: the **Runs on** select (`VAULT_ENGINE_CHOICE_NAME` in `vaultText.ts`, "needs setup" on engines not set up, disabled while locked or switching) and its one reserved-height line (Unlock, switching, error, Refresh, Change model…). ## Configuration

- `CINNA_VAULT_FAKE=1` — fake backend (unpackaged only); `CINNA_VAULT_FAKE_WINDOW_MS` overrides every vault's lock timeout (unset: each vault's own).
- `CINNA_VAULT_GUEST_DIR` — directory holding `rootfs.img` (unpackaged only; default `build/vault-guest/`).
- Release scripts (`scripts/vault/`): `guest-pin.cjs` (reads the pin, `check-release <dir>` compares a guest dir with it), `pin-guest.cjs` (`npm run vault:pin-guest`: stages the four assets and prints the pin block), `release-helper.cjs` (`make vault-release`); `make vault-clean` removes the local build leftovers. Order and rules in [the runbook](vault_llm.md#release).
- Pins: `RUNTIME_PINS.vaultGuest` (`published`, `version`, `rootHash`, `hashOffset`, and `kernel`, `initrd`, `rootfs` — each a `VaultGuestAsset` `{ file, url, sha256, size }`; the first two go into the release helper's bundle, only `rootfs` is downloaded by main; the block is one `const VAULT_GUEST` of plain literals because `scripts/vault/guest-pin.cjs` reads it by text), and per engine `vaultAdapterTarSha256` / `vaultRuntimeTarSha256`. The guest checks each against the pin before `runtime.install` commits it, and the launcher checks the installed one again before it runs it.
- `CINNA_VAULT_TEST_SCREEN_LOCKED=0|1` — test-flavor helper only (see [the helper](helper_tech.md)).
- Constants: default lock timeout 5 min (offered: 30 s, 5 min, 0 = until Cinna quits), paused-VM stop 30 min, default disk 10 GB (allowed 1 GB–2 TB), approval token lifetimes in `APPROVAL_TTL_MS` (move-in, install and move-out 30 min; the rest 10 min).
- Default allowlist per engine: `VAULT_ENGINE_HOSTS`; install hosts: `VAULT_INSTALL_HOSTS`.

## Security

- **Cinna is a requester, never the approver.** `approve` returns a token the helper signed after its own prompt; main cannot mint one, and the helper builds the prompt text from the action, the detail and the agent name from the signed `vault.json`.
- **Secrets are write-only.** `secrets.put` / `secrets.putFile` / `secrets.list` / `secrets.delete`; there is no `secrets.get`. Values reach the engine only through vaultd, as env (an allowlist of names) or files it writes inside. A `putFile` secret has two copies on the encrypted disk: a root-only stored one and a read-only (0400) copy owned by `agent` in `run-secrets/`, refreshed at every `engine.spawn`; its path is `CINNA_CREDENTIALS_PATH`.
- **vaultd is ungated by design once unlocked** (`transcript.read`, `kv.get`, …): the unlock is the gate. `vaultService.client()` refuses to hand out a connection unless the vault is known to be unlocked.
- **A stalled stream is not an exit.** A vault that locks mid-turn pauses; `VaultAcpConnection` treats the engine as gone only on the attached stream closing or vaultd's `engine.exit`.
- **No logging of vault content.** Tool-call inputs are left out of the log for a vault session (`acpDriver.ts`).
- **Known limit:** see [Agent Vault](vault.md#what-it-protects-and-what-it-does-not) for D34 (prompting rests on Cinna's code integrity) and the developer-Mac signing caveat.
