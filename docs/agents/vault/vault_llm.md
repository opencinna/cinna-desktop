# Agent Vault — developer runbook (LLM reference)

Concepts: [Agent Vault](vault.md). Files and IPC: [vault_tech.md](vault_tech.md). Helper and guest internals: [helper_tech.md](helper_tech.md).

## Lanes

| Lane | Command | Needs | Billed |
|---|---|---|---|
| Unit + guest contract (vaultd in fake mode, frames, tokens, transcript routing, exclusions, move service, renderer) | `npm test` | nothing | no |
| Guest image | `make vault-image [RELEASE=1] [VERSION=<x.y.z-n>]` | Apple silicon, `swiftc`, node, network; `RELEASE=1` refuses a placeholder vaultd, so run `npx electron-vite build` first (it bundles `out/main/vaultd.js`) | no |
| Helper | `make vault-helper [FLAVOR=test\|dev\|release]` (default `test`) | Xcode; `dev` and `release` need the team's Developer ID identity in the login keychain and talk to Apple | no |
| Helper against the real guest | `make vault-helper-smoke [NO_NET=1]` | builds the test flavor, then needs `build/vault-guest/` | no |
| Move against a real VM | `make vault-move-smoke` | test helper + image; runs `moveService.moveIn` with the pinned runtime and adapter, **sends no prompt**; `SMOKE_ENGINE=codex\|opencode\|antigravity` moves an agent on that engine instead of Claude; `SMOKE_PYPROJECT=1` adds a rebuild through the proxy (locks inside the vault when there is no `uv.lock`), `SMOKE_KEEP=1` keeps the workshop | no |
| Live | `make vault-live` | test helper + image; **one Haiku turn** on the repo `.env` `ANTHROPIC_API_KEY`; sandboxed `HOME` and `userData` | **yes** |
| Guest boot by hand | `node scripts/vault/guest-smoke.mjs` | `build/vault-guest/` with the real vaultd | no |
| E2E | `make e2e-one SPEC=e2e/specs/agent-vault.spec.ts` (the spec sets `CINNA_VAULT_FAKE=1` itself; `npx electron-vite build` first) | an unpackaged build; vaultd runs as a plain Node process, no VM, no prompt | no |

- `agent-vault.spec.ts` (V1–V5) proves the app's side on the fake backend: the Security tab, a move through every step and its rollback leaving the folder byte-identical, Delete original, the lock on the agent, the composer's locked row, a chat that never reaches SQLite, and a pre-move chat refused. It proves nothing about isolation, prompts or the allowlist. Its engine is the scripted Claude CLI. There is no `make vault-contract`.
- **Measured on the real guest (test helper):** a cold boot with `init_on_free` about 2.7 s, a resume about 80 ms, a move about 7 s, a live turn about $0.0024.
- `make vault-helper-smoke` covers: hello and flavor, parent-check probes, create/unlock/cold boot, approvals accepted and forged, egress allowed and denied, hold/release and the window running out, resume, the screen-lock stand-in, install hosts only with a live proxy credential, lock beating a pending unlock, tamper detection, destroy, stdin close. `FLAVOR=dev … helper-smoke.mjs --keychain` exercises the real keychain on a machine with the team identity.
- **A test-flavor helper never prompts and keeps the disk key in a file.** Use it only in sandboxes. A packaged Cinna refuses it; the Security tab shows a red "Test helper" badge for any non-release flavor.
- **`CINNA_VAULT_TEST_SCREEN_LOCKED=0`** (test flavor only) makes the helper treat the screen as unlocked, so the unattended lanes (`vault-helper-smoke`, `vault-move-smoke`, `vault-live`) run on a Mac whose screen is locked, where unlock would otherwise be refused; `=1` forces locked. It is compiled out of the release helper. Other test-only knobs are listed in [helper_tech.md](helper_tech.md#helper).
- `CINNA_VAULT_GUEST_DIR` points an unpackaged build at a directory holding `rootfs.img`; `VAULT_GUEST_DIR` does the same for `build-helper.sh`. Defaults are `build/vault-guest/`.

## Rules that bite

- **Rebuild the helper whenever the guest root hash changes.** The helper embeds the kernel, the initrd and the verity root hash (`GuestPins.swift`, generated by `build-helper.sh` from `build/vault-guest/guest.lock.json`). A new `rootfs.img` with an old helper fails verity at boot; a helper built without a guest reports `image-missing`. So the order is always `make vault-image`, then `make vault-helper`.
- **Pin the adapter when it changes.** The vault receives each patched adapter's dependency closure as one deterministic tar and compares its hash with `RUNTIME_PINS.<engine>.vaultAdapterTarSha256` (Claude and Codex). The tars are written once per app build into `out/vault/claude-adapter.tar` and `codex-adapter.tar` by `electron.vite.config.ts` and ship inside `app.asar`, under asar integrity; `afterPack` fails a package whose tar hashes to anything but the pin. After changing an adapter, its dependencies or its patch, run `npm run vault:pin-adapter`, copy the printed values into `src/shared/runtimePins.ts`; `runtimeInstall.test.ts` fails until you do. A move refuses any other closure.
- **Codex and Antigravity runtimes are repacked, and the repack is pinned.** The Codex executable and its `codex-code-mode-host` go in as one tar (`codex.vaultRuntimeTarSha256`), Antigravity's server as another (`antigravity.vaultRuntimeTarSha256`); a runtime bump recomputes both (`runtimeInstall.ts`), or the guest refuses the install. The guest enforces the pin before it commits a runtime and the launcher before it runs one.
- **Engine versions** move only in `src/shared/runtimePins.ts`, by [Runtime Pins](../../development/runtime_pins/runtime_pins_llm.md); a vault picks them up with **Update dependencies**, not a new image. A bump of Codex or Antigravity also needs the repack pin above.
- **vaultd is shared code.** `native/vault/guest/vaultd` is bundled to `out/main/vaultd.js` by an esbuild pass in `electron.vite.config.ts` and imports nothing but Node builtins and `src/shared/vault/protocol.ts`, which must stay import-free.
- **Never hand-edit** `GuestPins.swift` or `build/vault-guest/`; both are generated and gitignored, as is `resources/vault/`.
- **Don't run the real-keychain lanes on a Mac that holds the team Developer ID key with codesign "Always allow"** without knowing the consequence (the threat model's signing caveat). The maintainer's Mac should have that permission removed.
- **Tests that must keep failing if the rule is broken:** `vault/channels.test.ts` (every Cinna channel refuses a vault agent id even when called directly), `vault/transcriptRouting.test.ts` (no vault text reaches SQLite or FTS), `vault/approvalTokens.test.ts` and `vaultd/test/vaultd.test.ts` (a gated call without a valid token is refused), `vaultd/test/privileges.test.ts`, `shared/packagingSecurity.test.ts` and `scripts/packaged-dependencies.test.cjs` (the helper check at packaging).

## Release

The vault is in a release only when all of this is true; until the first image is published a packaged app reports `image-missing` and offers no vault.

1. `npx electron-vite build` (it also writes the adapter tars into `out/vault/`), then `make vault-image RELEASE=1 VERSION=<x.y.z-n>` — writes `build/vault-guest/{Image,initrd.img,rootfs.img,guest.lock.json}`.
2. Upload `rootfs.img` as a **release asset**.
3. Fill `RUNTIME_PINS.vaultGuest` in `src/shared/runtimePins.ts` from `guest.lock.json`: `published: true`, `version`, `rootHash`, `hashOffset`, and `rootfs` (`file`, `url` of the asset, `sha256` and `size` from `files["rootfs.img"]`). It is `published: false` today.
4. `make vault-helper FLAVOR=release` **after** step 1, on the release machine (Developer ID identity, Xcode, network for the provisioning profile). It embeds `Image`, `initrd.img` and the root hash and signs the helper with its own profile; the export step must keep `keychain-access-groups` (the script fails if it does not).
5. `npm run release:mac`. `afterPack` verifies the two adapter tars against their pins and (`verifyVaultHelper` in `scripts/packaged-dependencies.cjs`) fails an arm64 package unless the helper is the **release** flavor, has no test-gate marker in its bytes, carries the provisioning profile and the keychain group, passes `codesign --verify --strict --deep`, and has `Image` and `initrd.img` inside; it removes the helper from the x64 package. `electron-builder.yml` ships it at `Contents/Library/Helpers/VaultHelper.app` and keeps it out of electron-builder's re-signing.

Publishing the pin is enough for a packaged app: the first move downloads `rootfs.img` into `<SecureAgents>/.images/` (`guestImage.ts:ensureGuestImage`), checks its sha256 against the pin, and keeps it for the next vault. The helper must be built from the **same** image: its compiled-in root hash is compared with the pin's before anything is created, and a mismatch stops the move naming both.

**Still to do for the first release with vaults:** upload the rootfs as a release asset and fill `RUNTIME_PINS.vaultGuest` (it is `published: false` today, so a packaged app reports `image-missing` and offers no vault).
