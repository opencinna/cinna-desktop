# Agent Vault — developer runbook (LLM reference)

Concepts: [Agent Vault](vault.md). Files and IPC: [vault_tech.md](vault_tech.md). Helper and guest internals: [helper_tech.md](helper_tech.md).

## Lanes

| Lane | Command | Needs | Billed |
|---|---|---|---|
| Unit + guest contract (vaultd in fake mode, frames, tokens, transcript routing, exclusions, move service, renderer) | `npm test` | nothing | no |
| Guest image | `make vault-image [RELEASE=1] [VERSION=<x.y.z-n>]` | Apple silicon, `swiftc`, node, network; `RELEASE=1` refuses a placeholder vaultd, so run `npx electron-vite build` first (it bundles `out/main/vaultd.js`) | no |
| Helper | `make vault-helper [FLAVOR=test\|dev\|release]` (default `test`) | Xcode; `dev` and `release` need the team's Developer ID identity in the login keychain and talk to Apple | no |
| Release helper | `make vault-release [DRY_RUN=1]` | Developer ID, Xcode, network; built only from the pinned guest (see Release below) | no |
| Pin a new guest | `npm run vault:pin-guest -- --app-version <x.y.z>` | `build/vault-guest/` from `make vault-image RELEASE=1` | no |
| Clean up | `make vault-clean` | nothing | no |
| Helper against the real guest | `make vault-helper-smoke [NO_NET=1]` | builds the test flavor, then needs `build/vault-guest/` | no |
| Move against a real VM | `make vault-move-smoke` | test helper + image; runs `moveService.moveIn` with the pinned runtime and adapter, **sends no prompt**; `SMOKE_ENGINE=codex\|opencode\|antigravity` moves an agent on that engine instead of Claude; `SMOKE_PYPROJECT=1` adds a rebuild through the proxy (locks inside the vault when there is no `uv.lock`), `SMOKE_KEEP=1` keeps the workshop | no |
| Live | `make vault-live` | test helper + image; **one Haiku turn** on the repo `.env` `ANTHROPIC_API_KEY`; sandboxed `HOME` and `userData` | **yes** |
| Engine switch live | `make vault-switch-live` | test helper + image; moves an agent in on Claude with no key, then `switchEngine` to OpenCode (`openai`, `gpt-5.6-luna` or `CINNA_E2E_LIVE_MODEL`, repo `.env` `OPENAI_API_KEY`), to Antigravity (`GEMINI_API_KEY`; the lane pins `gemini-3.8-flash-low` in `cinna.launch`, since the switch leaves the CLI default and the app offers no Antigravity model in a vault) and back to OpenCode with no key; **one short turn per engine**, counts the helper's approvals (set-up: `install` + `egress`; back: none), checks all three engines' hosts and no SQLite transcript. `VAULT_SWITCH_SKIP_ANTIGRAVITY_TURN=1` checks readiness instead of the Antigravity turn: the Gemini free tier allows 20 Flash requests a day, and on a 429 the server retries silently, so the turn only hits the lane's 3-minute turn timeout | **yes** (OpenAI, Gemini) |
| Guest boot by hand | `node scripts/vault/guest-smoke.mjs` | `build/vault-guest/` with the real vaultd | no |
| E2E | `make e2e-one SPEC=e2e/specs/agent-vault.spec.ts` (the spec sets `CINNA_VAULT_FAKE=1` itself; `npx electron-vite build` first) | an unpackaged build; vaultd runs as a plain Node process, no VM, no prompt | no |

- `agent-vault.spec.ts` (V1–V7) proves the app's side on the fake backend: the Security tab, a move through every step and its rollback leaving the folder byte-identical, Delete original, the safe icon and lock state on the agent, the composer's locked row, a chat that never reaches SQLite, a pre-move chat refused, and (V7) a file the agent names linking, previewing from inside the vault and downloading through the export. It proves nothing about isolation, prompts or the allowlist. Its engine is the scripted Claude CLI. There is no `make vault-contract`.
- **Measured on the real guest (test helper):** a cold boot with `init_on_free` about 2.7 s, a resume about 80 ms, a move about 7 s, a live turn about $0.0024.
- `make vault-helper-smoke` covers: hello and flavor, parent-check probes, create/unlock/cold boot, approvals accepted and forged, egress allowed and denied, hold/release and the window running out, resume, the screen-lock stand-in, install hosts only with a live proxy credential, lock beating a pending unlock, tamper detection, destroy, stdin close. `FLAVOR=dev … helper-smoke.mjs --keychain` exercises the real keychain on a machine with the team identity.
- Real keychain and Touch ID (person at the Mac, screen unlocked): `FLAVOR=dev make vault-helper && node scripts/vault/helper-smoke.mjs --keychain [--presence]`. A dev/release helper enforces its parent, so the smoke re-runs itself under a throwaway copy of `node` signed as `io.opencinna.desktop` with the team's Apple Development (or Developer ID) identity. `--keychain` checks the Secure Enclave key, the wrapped disk key and `vault.json` signing with no prompt; `--presence` adds four real prompts (unlock, resume after a lock, an export approval, destroy). Rebuild `FLAVOR=test` afterwards for the unattended lanes.
- The app with a dev helper (real Touch ID through the UI): `FLAVOR=dev make vault-helper && make vault-dev`. Plain `npm run dev` runs the stock ad-hoc Electron, which the dev helper refuses (`helper-untrusted`, vault shown as unavailable); `scripts/vault/dev-electron.sh` signs a copy of Electron.app as `io.opencinna.desktop` with the hardened runtime and `disable-library-validation` (dev native modules in node_modules are not team-signed) into `build/vault-dev-electron/` (re-made when Electron changes) and runs `electron-vite dev` on it via `ELECTRON_EXEC_PATH`. It uses the real profile. After a change to vaultd, the guest or the helper, `make vault-dev-restart` does the whole chain in one go: `npx electron-vite build` (bundles vaultd) → `make vault-image` → dev helper (embeds the new image's root hash) → `make vault-dev`; `NO_IMAGE=1` skips the image build when only app code changed.
- **A test-flavor helper never prompts and keeps the disk key in a file.** Use it only in sandboxes. A packaged Cinna refuses it; the Security tab shows a red "Test helper" badge for any non-release flavor.
- **`CINNA_VAULT_TEST_SCREEN_LOCKED=0`** (test flavor only) makes the helper treat the screen as unlocked, so the unattended lanes (`vault-helper-smoke`, `vault-move-smoke`, `vault-live`, `vault-switch-live`) run on a Mac whose screen is locked, where unlock would otherwise be refused; `=1` forces locked. It is compiled out of the release helper. Other test-only knobs are listed in [helper_tech.md](helper_tech.md#helper).
- `CINNA_VAULT_GUEST_DIR` points an unpackaged build at a directory holding `rootfs.img`; `VAULT_GUEST_DIR` does the same for `build-helper.sh`. Defaults are `build/vault-guest/`.

## Rules that bite

- **A vaultd method change needs a new guest image.** `files.stat` and `files.read` exist only in an image built after they landed (`make vault-image`, then `make vault-helper` for the new root hash); `make vault-dev-restart` does both. Unit tests and the fake backend run the new vaultd directly and will not show a stale image.
- **Rebuild the helper whenever the guest root hash changes.** The helper embeds the kernel, the initrd and the verity root hash (`GuestPins.swift`, generated by `build-helper.sh` from `build/vault-guest/guest.lock.json`). A new `rootfs.img` with an old helper fails verity at boot; a helper built without a guest reports `image-missing`. So the order is always `make vault-image`, then `make vault-helper`.
- **A switch of engine needs no new image or helper.** It writes only existing vaultd methods; only a change to a vaultd method needs a rebuild. `moveService.switchEngine` is covered by `vault/switchEngine.test.ts` (prompts, restore, login names, lock hold) and `VaultEnginePanel.test.tsx`.
- **The fake backend sets up Claude and Codex only** (`hostRuntimeSource`: this computer's own `claude` and `codex`, sha256 unchecked, plus the shipped adapter tars), so under `CINNA_VAULT_FAKE` a switch to Codex works end to end on the scripted CLI, while OpenCode and Antigravity always show "needs setup" and a switch to them fails at the `runtime` step ("…on Claude or Codex only"). The real set-up of those needs a real guest (`make vault-move-smoke` with `SMOKE_ENGINE`, which moves in rather than switches).
- **Pin the adapter when it changes.** The vault receives each patched adapter's dependency closure as one deterministic tar and compares its hash with `RUNTIME_PINS.<engine>.vaultAdapterTarSha256` (Claude and Codex). The tars are written once per app build into `out/vault/claude-adapter.tar` and `codex-adapter.tar` by `electron.vite.config.ts` and ship inside `app.asar`, under asar integrity; `afterPack` fails a package whose tar hashes to anything but the pin. After changing an adapter, its dependencies or its patch, run `npm run vault:pin-adapter`, copy the printed values into `src/shared/runtimePins.ts`; `runtimeInstall.test.ts` fails until you do. A move refuses any other closure.
- **Codex and Antigravity runtimes are repacked, and the repack is pinned.** The Codex executable and its `codex-code-mode-host` go in as one tar (`codex.vaultRuntimeTarSha256`), Antigravity's server as another (`antigravity.vaultRuntimeTarSha256`); a runtime bump recomputes both (`runtimeInstall.ts`), or the guest refuses the install. The guest enforces the pin before it commits a runtime and the launcher before it runs one.
- **Engine versions** move only in `src/shared/runtimePins.ts`, by [Runtime Pins](../../development/runtime_pins/runtime_pins_llm.md); a vault picks them up with **Update dependencies**, not a new image. A bump of Codex or Antigravity also needs the repack pin above.
- **vaultd is shared code.** `native/vault/guest/vaultd` is bundled to `out/main/vaultd.js` by an esbuild pass in `electron.vite.config.ts` and imports nothing but Node builtins and `src/shared/vault/protocol.ts`, which must stay import-free.
- **Never hand-edit** `GuestPins.swift` or `build/vault-guest/`; both are generated and gitignored, as is `resources/vault/`.
- **Don't run the real-keychain lanes on a Mac that holds the team Developer ID key with codesign "Always allow"** without knowing the consequence (the threat model's signing caveat). The maintainer's Mac should have that permission removed.
- **Tests that must keep failing if the rule is broken:** `vault/channels.test.ts` (every Cinna channel refuses a vault agent id even when called directly), `vault/transcriptRouting.test.ts` (no vault text reaches SQLite or FTS), `vault/approvalTokens.test.ts` and `vaultd/test/vaultd.test.ts` (a gated call without a valid token is refused), `vaultd/test/privileges.test.ts`, `shared/packagingSecurity.test.ts` and `scripts/packaged-dependencies.test.cjs` (the helper check at packaging).

## Release

A release carries vaults only when `RUNTIME_PINS.vaultGuest` is published and the release helper is built from exactly that guest. Until the first image is published a packaged app reports `image-missing` and offers no vault. The full order, with the app's own steps around it, is in [Release & Distribution](../../development/distribution/release.md#agent-vault-in-a-release); this is the vault part.

**A new guest image** — only when vaultd (`native/vault/guest/vaultd/`), the guest (`native/vault/guest/`) or `scripts/vault/build-guest.*` changed since the published one (`git log <last release tag>.. -- native/vault/guest scripts/vault/build-guest.*`):

1. `npx electron-vite build`, then `make vault-image RELEASE=1 VERSION=<x.y.z-n>` → `build/vault-guest/`.
2. `npm run vault:pin-guest -- --app-version <next app version>`: refuses a placeholder vaultd, stages the four assets as `vault-guest-<version>-{Image,initrd.img,rootfs.img}` and `vault-guest-<version>.lock.json` in `build/vault-guest-release/<version>/`, and prints the `const VAULT_GUEST` block (URLs under `releases/download/v<next app version>/`) and the `gh release upload` line. Paste the block into `src/shared/runtimePins.ts` and commit it **before** `npm version`.
3. After `npm run release:mac` has created the draft, run the printed `gh release upload` line, so the guest assets sit on the same draft and go public with it.

**Every release** (new guest or not):

4. `make vault-release` (Developer ID identity, Xcode, network). With an unpublished pin it removes `resources/vault/VaultHelper.app` instead (the release ships no helper; the app reports Agent Vault unavailable). With a published one it uses `build/vault-guest/` if its lock is exactly the pin, otherwise downloads the pinned Image, initrd and rootfs into `build/vault-release-guest/<version>/` and checks their sha256 and size; then builds the **release** helper into `resources/vault/`. `DRY_RUN=1` only picks and checks the guest. `build-helper.sh` refuses a release flavor whose guest lock or Image/initrd hashes differ from the pin, so a dev image left in `build/vault-guest/` can no longer slip into a release helper.
5. `npm run release:mac`. `afterPack` (`verifyVaultHelper`) fails an arm64 package unless the helper is the release flavor, has no test-gate marker, carries its provisioning profile and keychain group, passes `codesign --verify --strict --deep`, holds `Image`, `initrd.img` and `guest.lock.json`, and — with a published pin — that lock's version, root hash and hash offset equal the pin. x64 packages drop the helper.

**After the release:** `make vault-clean` (removes `build/vault-guest*`, `build/vault-release-guest`, `build/vault-dev-electron` and `resources/vault/VaultHelper.app`), then `make vault-helper` for the test lanes, or `make vault-dev-restart` to keep developing with Touch ID.

**On users' Macs** nothing is left behind: every unlock boots the guest the app pins now (downloaded first if it is missing, "Unlocking… N%"), whatever image a vault was created with, and at start a packaged app deletes the other `rootfs-*.img` files and partial downloads in `<SecureAgents>/.images/`.

**Never delete a GitHub release that hosts the guest assets** the current pin names (its URLs say which), nor one an app version still in use pins: that app could no longer create a vault.

Release-machine details live in [Release & Distribution](../../development/distribution/release.md#agent-vault-helper-and-guest-image).
