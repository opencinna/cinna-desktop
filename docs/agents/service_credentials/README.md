# Service credentials

Credentials supplies explicitly attached service accounts, tokens, and logins to real local folder agents. It is independent of AI Credentials and requires no skill installation.

## Using credentials

1. In Default Settings → Credentials, select **Add Credential** (the dashed button closing the list), search the type cards, then fill in the type-specific form for an API token, IMAP/SMTP login, Odoo login, or Google service account. Every form exposes **Service URI**, with a hint explaining how it matches a credential type to an agent requirement. Each record is a collapsible [row](#credential-rows): its header opens the edit form inside the row, and its trash icon opens a delete confirm there instead. While an edit or add form is open, the other rows, every trash icon and **Add Credential** are disabled; the open row's header closes it. A form holds unsaved input, and a click elsewhere that replaced it would discard that input silently. The delete confirm holds nothing, so it does not lock: its row's header or **Add Credential** closes it. Values are write-only; editing metadata preserves the encrypted value unless you select **Replace stored values**.
2. With a Cinna profile active, Profile Settings → Credentials lists owned and shared cloud records under the profile's [account reference](#credential-rows). Remote rows do not expand and have no delete; each has an icon-only **Manage** that opens that record in Cinna web, and **Manage on Remote** beside **Sync Now** opens the whole list there, to manage values and sharing. A shared record requires its owner's **Allow local use** consent. The list is not the server's full set, and the **(?)** beside **Remote credentials** ("About remote credentials") says so: Core lists only credentials a local agent can use. Those are the caller's `mine` records (owned, or shared directly) of the types IMAP, SMTP, Odoo, API token and Google service account, plus [issued Agent API keys](#agent-api-keys). OAuth, SSH, MCP, automatic and bundle credentials, and Agent API *connections* (an agent's own agent-to-agent credential), never reach the desktop, and materialize refuses them if asked. The one unusable record Core does list is a share whose owner has not allowed local use; it arrives flagged so Desktop can explain it. Desktop keeps no category or type rule of its own. It treats Core's list as the complete locally usable set and prunes a cached record, attached or not, once Core stops listing it. A second rule on this side would drift from Core's, and would either show records that materialize then refuses or hide ones Core has started allowing.
3. Open an agent's Settings → Credentials and select **Attach**. The picker lists **This computer** first, then each [eligible account](#eligible-accounts) by profile name, with its server host and, when its last sync failed, the reason. Search filters every group by name, type, Service URI and owner email, hiding groups with no match. Each card has its own **Attach** button, and shows the status icon only when the record is not ok: a check on every healthy card would be noise. Attaching keeps the picker open and turns that card into a disabled **Attached** in place, so the grid never reflows under the pointer while several are picked. A failed attach shows its reason on the card. Cloud records whose owner has not allowed local use are left out of the picker; one already attached stays in the agent's list as *local use not allowed*.
4. The tab shows a kit agent's `.env` card first, then **Attached Credentials**, with **Attach** as its action and the explanation of the generated file behind its **(?)**. Attachments are listed as rows under the same groups; an account group is headed by its account reference rather than the profile name. A cloud row has **Manage**; every row has an icon-only **Detach**. **Detach** removes generated files after a running turn releases the folder; it leaves the record and other agents' attachments intact. Missing references remain visible and recover when access returns.

   There is no reordering. Order within a group still matters: the file lists groups in their fixed order and each group's references in attachment order, and the helper returns the first filled entry that matches a slot, so of two attachments for one service in one group, the earlier wins. **Attach** appends, so the only way to put a record first is to detach the others and attach them again.
5. For older kit folders, use **Update credential helper**, offered when the folder's `HELPER_VERSION` is older than the bundled reader's (or absent). This checks the file stamp before replacing `scripts/cinna_credentials.py`.

Attached values override `.env` for a whole matching slot. The page reports overlapping variable names. Readiness and the Python helper require both the credential type and the declared service: an explicit `service_uri`, or the slot name matched against credential name/service URI. A token for another service does not satisfy the slot. Readiness checks metadata and names, never values. A missing credential warns; an unsafe generated-file destination refuses execution.

## Eligible accounts

Agents receive their local attachments plus the attachments of **every eligible account**, whichever profile is current. A profile switch is a change of view, not of intent: an agent attached to a work account keeps that credential while the user works in another profile. Switching profiles rewrites no generated files unless the eligible set itself changes.

An account is eligible when its Cinna profile has a server URL and stored tokens from which the account identity can be read, and either has no password or was unlocked in this app session. The current profile always counts as unlocked. A locked password profile contributes nothing until it is unlocked, because its password is what stands between its account and anyone at the keyboard. A profile that was logged out of stays ineligible for the rest of the app session, even though its tokens may remain, until that profile is activated again. Logout also clears every profile's unlock memory, so other password profiles drop out with it; passwordless ones stay.

Accounts are keyed by `sha256(serverOrigin + "\n" + jwt.sub)[:16]`. When two profiles derive the same key (a recreated profile), the current one owns it. Group order is local first, then accounts by profile name.

The set is recomputed on profile activation, unlock and lock changes, logout, profile deletion (sign-out removal included), setting a password, and token renewal of **any** profile, current or not. Recomputing retires accounts that left the set and starts accounts that joined it. Only agents with attachments stored under a changed key are queued for regeneration.

Each account owns its own sync flight, scheduler (five-minute, or one-minute while it watches an issued key), epoch and abort controller, sync error, last-sync time and `current_user` identity entry. Retiring an account aborts its requests, bumps its epoch, stops its scheduler and drops that entry. The global epoch covers only suspend and shutdown. A turn's preparation guards only the accounts its agent has attachments under, so an unrelated account leaving the set does not fail it.

References stored under a key that is not currently eligible are kept, never delivered, and reported as `account_unavailable` under the label "Signed-out account". Their credential metadata is hidden even when a locked profile's cache still holds it, so a locked profile's credential names do not surface while another profile is in use. Such a list can only shrink: **Detach** works, because removing a reference needs no rows, tokens or network, while adding is refused ("Sign in to that account to change its credentials."). A deleted profile's key may never be eligible again, and a list that could not shrink would strand its references. Emptying a group removes its key from Desktop State. These rows offer **Detach** only; they have no **Manage**, since the DTO carries no server or account for an unavailable group.

Settings pages are unchanged by this: Profile Settings → Credentials, its status, and **Sync Now** show only the current profile's cache. A current Cinna profile whose identity cannot be derived has no account and reports `reauth_required`.

## Agent API keys

A producer's owner can issue an **Agent API key** to a person; that person's key is an `agent_api` credential Core lists to Desktop so a local agent can call the producer agent's REST API. Only keys issued *to the signed-in user* are delivered. Connections between cloud agents (also `agent_api`) stay on the server, and Desktop ignores and prunes any `agent_api` item that is not `owned` or carries no valid `key_status`, so a Core bug cannot put a foreign key into a file.

**Opt-in.** Desktop sends `?include=agent_api_keys` on **both** the list and the materialize call. Without it Core refuses the type as `unsupported_type`; a Core that predates keys ignores the flag. A key's list item carries `key_status`, an `agent_api` object (producer name, issuer email, `base_url`, `spec_url`, `expires_at`, every field optional) and an expiry that is epoch seconds *or* an ISO-8601 string. Keys are the only type whose expiry may be ISO; any other type still needs a number.

**Fail closed.** Only `active` delivers a token. Every other status, including one this build has never heard of, is unavailable: the cached token is dropped at the next list pass, nothing is fetched while the status stays, and an attached key is written as a **token-less entry** carrying `unavailable_reason` (`key_revoked`, `key_expired`, `key_paused`), the `key_status`, and a stub of its non-secret fields (`base_url`, `spec_url`, `label`, `producer_agent_id`) so the agent can say why it cannot call the producer instead of silently failing. `api_disabled` and `external_access_paused` are *paused* and recover by themselves; revoked, expired, producer-removed and issuer-removed do not. A token-less entry never counts as a filled slot, so a working credential for the same service wins over it, and an unavailable key does not make its account a contributor to the `current_user` entry. If Core's list still says `active` but materialize refuses the key, the refusal's status is recorded as a backstop. It holds only until the next list pass, which takes the status from Core again: a pause and resume can leave Core's revision where it was, so a status remembered across passes could outlive the fault.

**Address guard.** A key's `base_url` must be `https`, or `http` to this computer (`localhost`, `127.0.0.1`, `[::1]`), or `http` to the very origin the account already signs in to (a local or LAN Core the user set up). Any other address is **blocked**: the delivery is not stored, the row carries `keyBlocked = insecure_base_url` until Core's revision changes (the address is part of it, so a fix arrives as a new revision and the refusal is logged once per revision), and the agent's file gets a token-less entry whose `unavailable_reason` is `insecure_base_url`. That reason exists only on Desktop; Core never sends it. The reasoning: a bearer token must not go anywhere the user's own account bearer would not already go. An `https` address on another origin than the account is allowed and logged.

**Staying current.** An issued key can be rotated, and the old token dies five minutes later, so the usual cadence is too slow:
- While any attached key is active or paused, the account polls every **60 s** instead of 300 s, and the timer is re-armed at once when polling speeds up so the first fast tick is not five minutes away. Detaching the last key returns it to 300 s.
- A turn that starts while an attached live key's account has not *attempted* a sync in the last two minutes syncs it first, bounded to **5 s**, and falls back to the cache when Core is slow or offline. The gate is the last attempt, not the last success: otherwise an offline Core would cost every turn its five seconds.
- A **running** turn holds the agent's folder shared, and ordinary credential changes wait for it. A key's rotation or loss cannot wait that long, so those two, and only those, are written in place while the turn runs, atomically per file. The write is allowed only when the new generation differs from the one on disk in nothing but issued keys: an active key's token changed, or a key entry lost its token. It is all-or-nothing per generation. If the same pass also carries any other change (another credential rotated, one detached), nothing is written and the key change waits with it for the exclusive hold. The failure this accepts: such a turn can keep using a rotated-out token for as long as the turn runs.

**What the user sees.** The type is named **Agent API key** (icon and badge); its tooltip reads "Agent API key for *producer*" when Core named one. The ownership glyph reads "Issued to you by *issuer*" rather than "Owned by you", since the issuer is the one fact the row would otherwise lose, and the picker shows it on key cards too. The status label names the issuer or producer when Core sent them ("Revoked by *issuer* — ask them for a new key", "*Producer*'s API is turned off — works again when its owner turns it back on", "Expired — ask *issuer* for a new key"), and falls back to generic wording when not. A blocked key reads "Blocked — this key's API address isn't secure (https); ask your Cinna server's admin to fix it". A paused key is a warning, the rest errors. The picker hides keys that are revoked, expired or removed unless the agent already has them attached (then the row stays, with **Detach**); paused keys stay. **Manage** opens the record in Cinna web, where a key is dealt with. The remote list's **(?)** says keys others issued to you are included. The prompt lists an unavailable key as "unavailable — *reason*".

**Agents call the producer** with `cinna_credentials.agent_api_session("<slot>")` (contract 1.7.0): a stdlib client that joins relative paths onto `base_url`, rereads the token on every request, and sends `Authorization` only to `base_url`'s exact origin on every redirect hop. The slot is the key's `service_uri`, `<producer-slug>-api` by default. It raises when the slot is missing, of another type or unavailable. **Update credential helper** compares the folder's reader with the bundled one, so a folder at an older version is offered 1.7.0.

Desktop does not notify the user when a key dies and does not renew or request keys; issuing and revoking stay in Cinna web.

## Finish setup

Credentials never travel with a [shared agent](../local_agents/team_sharing.md): what arrives from the Team library carries its manifest's slots and none of the values or attachments behind them. Finish setup is how such an agent gets its credentials on this computer, first without asking where the answer is unambiguous, then in one dialog for the rest.

### Attaching without asking

After a team-library **Get**, an **Update** that brought changes, or **Use the team's version**, main attaches the active profile's cloud records that fit a still-missing slot beyond doubt:

- **Which records fit** is the scanner's own matching, so nothing is attached that readiness would not then count: same type, local use allowed, not a dead issued key; then the slot's `service_uri` when it declares one, otherwise records named like the slot, then records whose Service URI is the slot's name. Within that, records the user owns come before records shared with them. The first non-empty group is the match, and it is attached only when it holds **exactly one** record. Two owned records for one slot are a choice for the user, never a guess
- **Only the active profile's account**, only into that account's group, and **only appends**: nothing already attached is removed or reordered, a record already attached is not offered again, and one record is never attached to two slots in one pass
- **Only when something is missing.** An agent whose slots are all satisfied gets no sync and no write. Otherwise the account is synced first, bounded to five seconds like a turn's sync, so a record created on the server a moment ago can still be found
- **It never waits behind a turn.** A running turn refuses the write at once and nothing is attached; the dialog then offers the same records. A short exclusive write by something else (a regeneration, a sharing verb) is retried for up to five seconds, never queued
- **It never fails the verb.** Any error is logged and the verb answers as if nothing matched. A Get that landed is not reported as failed because a credential could not be attached

The verb's result says what was attached (`autoAttached`, slot and record names) and whether the dialog should open (`setupNeeded`): after a Get, when any required slot is still missing; after an Update or Use the team's version, only when a required slot is missing that was not missing before the verb, so **Finish later** is not undone by every Update. When it is set, the agent page opens **Finish setting up *Name*** as soon as it shows that agent, even after a Get whose page was not mounted yet. It stays requested until the dialog is closed, so leaving the page and coming back still shows it.

### The dialog

Opened that way, or from **Finish setup** on the agent page's readiness strip whenever the agent reads `credentials_needed`. One row per slot, each in the scanner's own verdict, so the dialog can never call ready what readiness calls missing:

- **Connected automatically** / **Connected** — a matching attachment is ready; *automatically* when main attached it without asking during this app session
- **Set on this computer** — no attachment, and `credentials/.env` fills the slot
- **Missing**, or **Optional** for an optional slot — with the attachment that stopped counting, when there is one, shown so the user sees why
- Under a slot that is not connected: the active account's records that fit it, best first, each with **Use this**, which appends it to that account's group and waits for a running turn like any attach. Then *or enter it on this computer* and one password field per declared `.env` name, with **Save** for the slot (Enter saves too). A name already set reads **Set** with **Replace**; Replace shows the field again with **Cancel**, which keeps the saved value
- A slot without `fields` has no names to ask for (the kit reads any `<prefix>…`), so it offers its records and **Open credentials/.env**
- A slot nothing in the account fits, with no names to fill: *Nothing in your account fits it. Attach one on the Credentials tab.* Local records are attached there, not here
- Below the agent's slots, a **Skills** group for the slots its skills declare, which never decide whether the dialog opens ([Skill credential slots](#in-finish-setup))

**Finish later** (focused on open) and **Done** close it. Done saves whatever was typed and not yet saved first, and stays open on a refusal. Nothing here blocks the agent: a missing credential stays the page's warning, as before. The dialog is owned by the agent page, so switching between chat and settings neither closes it nor drops a write's result.

The layout is built so nothing moves under the user ([UX Rules](../../development/ui_guidelines/ux_rules.md), rule 1): the dialog's top is pinned, so a row that grows moves only what is below it; the slot list scrolls inside a dialog no taller than the window; every `.env` name keeps its row whether it is a field or **Set**; the footer reserves two lines for a refusal or a note beside its buttons; **Save** comes and goes with Replace, Cancel and a save, never with typing. **While anything typed is unsaved, the backdrop and Escape close nothing**: a click outside would otherwise throw away a secret the user just pasted, with no way to tell it had.

### Writing `credentials/.env`

Values typed into the dialog go to `credentials/.env` through main, never anywhere else:

- **Only names the manifest declares** (and only plain variable names); a value must be non-empty and one line. Anything else is refused whole
- **Refused while a turn runs**, with nothing changed and "save again when it finishes", rather than waiting: a write queued behind a long turn would leave the dialog spinning with no end the user can see
- **Refused when no `.gitignore` rule covers `credentials/.env`**, after installing the contract's own `credentials/.gitignore` where the folder has none. A secrets file the next share could commit is worse than no file
- **Merged in place.** Every other line and comment stays; a name's first assignment, or its commented seed (`# KEY=`) when nothing assigns it, is replaced where it stands, and any later assignment of it is dropped, because the reader takes the last one. Written `0600` through a temporary file and a rename
- **Quoted so both readers read it back unchanged.** The kit's reader knows no escapes and python-dotenv, which an agent's own script may use, does, so each value takes the first form both agree on: bare, then `"…"`, then `'…'`. A value that needs quoting and holds a backslash, or both `"` and `'`, falls back to `"…"`, which the kit reader reads exactly and python-dotenv may not. No form stops python-dotenv expanding `${NAME}` unless the script loads with `interpolate=False`
- The answer is the slots' new states, names only; no value is logged or returned

## Skill credential slots

A kit agent's [skills](../local_agents/skills.md) — its own and the catalog skills it pins, once cached — may declare credentials in their `SKILL.md` under `credentials:`. Each declaration is a **slot**, which is a Service URI, and a type. A skill script finds its credential by that slot, exactly as it does in a cinna-core environment: `from core.cinna_api import credentials` and `credentials.require_slot("<service uri>")`. So skill slots are kept apart from the manifest's own slots and follow core's rules, not the agent's:

- **Strict match.** A slot is filled only by an attached record of the slot's type whose Service URI **is** the slot, exactly. There is no name fallback, unlike an agent slot without `service_uri`: the script asks by Service URI and would not find a record matched any other way
- **Never blocking.** A missing skill slot changes no readiness, never sets `setupNeeded`, and never opens Finish setup by itself. The script fails at call time with core's sentence naming the slot, which the agent relays. Core treats skill slots the same way
- **Only deliverable skills count.** One entry per `(slot, type)` across the agent's deliverable skills, listing the skills that declare it. A skill no engine is given needs no credential
- **The scan judges them.** Each declared slot on the agent's skill rows carries whether a strictly matching attachment is ready, and which attachment it was judged by. The Skills row on the Addons tab does not draw that yet; Finish setup does

### Filling them without asking

After **Add to agent** or **Update** of a catalog skill, after a sharing verb's background fetch of the agent's pinned skills, and whenever **Finish setting up** opens, main fills skill slots where the answer is unambiguous:

1. **Only slots nobody chose for.** Any attachment with the slot's Service URI, of any type or state, is the user's choice: the slot is left alone, never given a second record and never replaced
2. **`provision-local` first.** For each pinned catalog revision that declares an open slot, main asks core (`POST /api/v1/skills/packages/{uuid}/revisions/{n}/provision-local`, idempotent, no values) to share the publisher's credentials for a local install with this account. Best effort, 30-second timeout each. Its per-slot outcome (`shared`, `already_shared`, `user_provides`, `not_shareable`, `not_allowed_locally`) is remembered for this app session and only ever shown
3. **Then a sync** of the active account, bounded to five seconds like a turn's; when core just shared something, a sync already in flight is followed by a fresh one rather than joined, because the list must be read after the share
4. **Exactly one fits, or nothing.** A cloud record of the active account is attached only when it is the one record, owned before shared, that fits `(type, service_uri = slot)` — the same `autoMatch` the agent's slots use, at its strict tier. Appends only; one record is never attached twice in a pass; and **a Service URI two skills declare with different types gets one record, not one per type**. Decided again under the agent's lock on the fresh state, so a slot the user filled meanwhile keeps their choice
5. **Never waits behind a turn, never fails anything.** A running turn refuses the write at once and nothing is attached; a short exclusive write is retried for a few seconds. Errors are logged and answer "nothing attached"

Add and Update answer at once and do this in the background, because `provision-local` may take its full timeout per revision. What was attached reaches the renderer on `service-credentials:changed` as `autoAttached {agentId, items}` (each item `skill: true`), which the app remembers for the session, so Finish setup can still say **Connected automatically** however long it took. Finish setup's own call answers the same list directly.

### In Finish setup

Below the agent's own slots, a **Skills** group: "Skills find these by Service URI. A missing one does not stop the agent; the skill fails when it needs it." One row per skill slot, drawn by the same row as an agent slot, with **Needed by skill(s) *names* · *type*** under the name. It offers the account's strictly fitting records with **Use this**, never `.env` names (a skill reads only the credentials file). A missing row with nothing to offer says why, in this order: an attached record has the Service URI but another type ("*name* has this Service URI but is a *type* credential, not *type*."); the publisher provides it but not for this computer; the publisher provides it but cannot share it with you; or "Nothing in your account fits it: it needs a credential of type *type* whose Service URI is *slot*." A skill slot is remembered under `skill:<slot>`, so it never reads as an agent slot of the same name.

Not built: an entry into Finish setup from the readiness strip when the only gaps are skill slots (the strip opens it only for `credentials_needed`), and detaching what was attached for a skill when that skill is removed — nothing records why an attachment was made.

## Credential rows

Local settings, remote settings and an agent's attached list render one `CredentialRow`: type icon, name, type badge, status icon, ownership icon (owned, shared by *email*, or stored on this computer), the Service URI as code, then the row's actions. Every element is one line and fixed-size, so a status change does not move its neighbours. The icons carry their sentence as a tooltip and an accessible name. `credentialPresentation.ts` holds what the rows say, as pure functions, so the three lists cannot drift into different words for one state.

Status comes from `credentialHealth`. In an agent's list, main's attachment state is authoritative, because it already knows the shared-record expiry the record DTO does not. In settings, the status is derived from the record, most blocking first: local use not allowed, then incomplete or placeholder, then expired. A remote record without downloaded values is ok ("Available — values download when an agent uses it"), because values are fetched only for attached records and their absence is not a fault.

An account is shown as **Name \<email\> host**: the Cinna full name, else the profile's display name; the profile's username as the email, dropped when it would repeat the name; the server host as a link that opens the server. It heads the remote settings list and each account group of an agent's attached list. For the latter, the attachment DTO carries `serverUrl` and `account {name, email}`, both null for local references and unavailable accounts, which keep their plain label. The picker's groups keep the profile name and host. A display-name change in profile settings refreshes the accounts so their labels follow the rename.

**Manage** opens `<server>/credential/<cloudId>` and **Manage on Remote** opens `<server>/credentials`, both joined onto the stored server URL as a suffix. Resolving `/credentials` against the URL would drop a path prefix, and a Core served under one would open the wrong page. **Manage** is absent for local records, for unavailable accounts and when the server URL does not parse. A refused browser open is reported as an error under the list.

## Runtime contract

Kit agents receive a cloud-compatible array at `credentials/credentials.json`. Bare agents receive it under the Hub's userData `agent-credentials/<realpath hash>/` directory, outside their folder. Only `CINNA_CREDENTIALS_PATH` is injected into script children; values never enter process environment variables or the prompt. The prompt lists names, types, slots, and availability.

A kit agent's engine (Claude, Codex or OpenCode alike), kit commands and scheduled runs also get the **skill runtime** first on `PYTHONPATH`: `core.cinna_api`, a stand-in for cinna-core's env-side package vendored from core (`resources/skill-runtime/core/cinna_api/`), so a skill written for a cloud agent runs unchanged. It reads the file `CINNA_CREDENTIALS_PATH` names afresh on every call and supports `credentials` (`all`, `get`, `by_type`, `all_by_type`, `by_slot`, `require_slot`, `agent_api_session`, and `access_token` without a platform refresh), `CredentialMissing` and `CredentialRefreshError`; core's agent REST API SDK is not provided. With the variable unset every slot is `not_linked`. The shipped folder is copied once to `<userData>/skill-runtime/<content hash>/` and that copy is what goes on the path, because Python writes bytecode beside what it imports and the shipped folder is inside the signed app bundle. A bare folder gets none of this. Both the env and the copy are built by `skillRuntime.ts` `engineCredentialEnv`, the one hook the ACP driver and `commandService` share.

The shared Python reader (`HELPER_VERSION` 1.7.0) uses the injected path, the nested array/envelope, the legacy root object, then environment and `.env`. `get_credential`/`has_credential`, `require_credential`/`list_credential_slots`, and strict `by_slot`/`require_slot` are supported. Files are reread on every call. Placeholders cannot silently borrow environment fields. Service-account keys live in separately inventoried JSON files. There is no SSH, OAuth, MCP or Agent API *connection* delivery path: Core never sends those types, and a delivery item carrying a non-null `ssh_key` is rejected as incomplete rather than written. Core's `owner_identity` response field is always null and is ignored.

Runtime preparation (`prepare(agentId)`, which takes no profile) occurs inside the per-agent turn lock (a turn's shared hold), after launch planning and before process/session acquisition. Turns of one agent run side by side and each prepares, so materialization is chained per agent folder (`materialize` in `service.ts`): writing the files reads the old ones, awaits the cloud fetch and path checks, and only then writes or unlinks, and two interleaved would act on a stale read. The chain covers every caller — turns, commands, attachment edits and regeneration. Session identity includes a fingerprint of the effective credential material, the `current_user` entry when one is written, and the keys of the **contributing accounts** (those with at least one ready cloud credential attached), independent of any epoch. No account fingerprints as null, one account as its bare key, several as the ordered key list. A single account therefore keeps the fingerprint it had before several accounts could contribute, so an upgrade does not restart its sessions.

`current_user` is the only identity entry, and Core gives every one the same fixed id. It is written only when exactly one account contributes; with several contributing, none is written, because one entry would have to name an arbitrary one of them and two would collide on the id. When contributions drop back to one account, its entry returns. A Core record attached under two accounts (one profile owns it, another receives it as a share) is written once, and the first group in order wins: two entries with one id would also collide on the service-account side file.

Empty attachments have a stable fingerprint across resume and re-authentication. Commands use the same preparation hook. Synthetic chat/conductor/build runtimes, remote A2A, and custom ACP transports do not receive attachments. Each delegated local executor resolves its own attachments through its ordinary folder driver; delegation permissions remain unchanged.

## Storage and lifecycle

`service_credentials` stores metadata and keystore-encrypted bundles. Local records use `__default__`; cloud cache rows are scoped to the local profile, server origin, and cloud UUID. The metadata DTO includes `hasValues`, never payloads. Service credentials reject Linux `basic_text` storage without changing app-wide provider/OAuth encryption behavior. An unavailable secure keystore forbids secret writes and preparation removes generated secrets before refusing execution.

Desktop State stores UUID-only attachment lists: machine-wide local references and cloud references keyed by account key. This recovers intent after signing into a recreated local profile while keeping an ineligible account's list inert. Eligibility derives this identity from the stored token without refreshing it or waiting for network access.

Cloud metadata sync runs per account every five minutes (every minute while an attached [issued key](#agent-api-keys) is active or paused), immediately when an account joins the set or its tokens are renewed, and on demand. Manual sync is pinned to the displayed current profile and syncs only its account. Retiring an account aborts its credential requests; an account never joins another account’s pending sync. Credential HTTP requests bypass the browser cache and have a 30-second timeout. Secret delivery is lazy for attached records. Desktop never receives OAuth or refresh tokens. Failed/malformed lists do not prune cache rows. Owner opt-out or a materialize refusal clears the payload; a record Core stops listing loses its cache row. Either queues regeneration. Same-account offline use is allowed until a record's stated expiry, when Core gives one; shared cached values also expire seven days after delivery. Owned cache has no other TTL.

Epoch checks after awaited work prevent responses for a retired account, and suspended responses, from updating cache or files. Background writes coalesce until the agent has no turn or command running, and then take the lock exclusively; the one exception is an issued key's rotation or loss, which is written while a turn runs (see [Agent API keys](#agent-api-keys)). A change to the eligible set regenerates affected agents' files before their next turn; cleanup failure blocks only that agent's turn, while activation and other agents continue. The first activation after launch brings every agent's files current. Attachment changes wait for every running turn of the agent to release the folder — with turns that keep overlapping, indefinitely — and reject if that group's account leaves the set while waiting; a profile switch alone does not reject them. Logout removes that profile's cloud cache rows but retains UUID attachment intent. An account's timer stops when it leaves the set, on reauth failure, on suspend and at shutdown; resume regenerates every agent. HTTP 403 reports a permission refusal and retains scheduled retries; HTTP 401 requires reauthentication. A full activation scan removes inventoried bare secrets for folders that no longer exist, preserving unrecorded files.

## File and output boundaries

Generated directories are mode `0700`, files `0600`. Writes use exclusive temporary files, fsync, and rename, and unchanged bytes retain their modification time. UserData inventories permit deletion only of names written by this feature. Authored files and `credentials/README.md` are preserved. Kit writes require static kit ignore coverage plus actual untracked/ignored Git status; missing Git or a broken repository fails closed. The full `credentials/` directory is excluded from export and content hashes in Desktop, Core, and CLI.

Known sensitive strings of at least eight characters are redacted before transcript/task/request/delegation persistence, task and handover files, logs, renderer events (including split chunks and nested agent events), and outbound Cinna task/delegation writes. Retired secrets stay in memory until shutdown to cover finishing old turns. Raw values and their JSON-escaped file representation (including `api_key` fields) are covered. This is substring redaction: other encoded/transformed values and strings shorter than eight characters are outside its guarantee. Generated files are plaintext for execution; local processes running as the same OS user can read them. Revocation cannot recall copies made outside the managed cache. Long turns do not refresh files mid-turn, except for an issued key's rotation or loss.

## Implementation and verification

Hub owns `src/main/services/serviceCredentials/`, the repository/migration, and redaction. IPC and renderer consume metadata-only typed outcomes. `service-credentials:attach-options` (agent ID) returns the picker groups with each item's `attached` flag. `service-credentials:set-attachments` (agent ID, group, refs) replaces one group's list, where group is `'local'` or an account key. `service-credentials:attach` (agent ID, group, ref) appends one record to a group, computed under the agent's lock so it never drops a reference written in between (Finish setup's **Use this**). `service-credentials:setup-state` (agent ID) answers `CredentialSetupDto`: each slot's state, the attachment it was judged by, and the active account's records that fit it, plus `skillSlots` (`CredentialSetupSkillSlot`: slot, type, declaring skills, state, the strict attachment, a `typeMismatch` record, strict options and the last `provision` outcome). `service-credentials:setup-skills` (agent ID) runs `autoAttachSkills` and answers what it attached; Finish setup calls it once per opening. Skill slots are judged in `skillSlots.ts` (`collectSkillSlots`, `skillSlotSpec`, `judgeSkillSlot`, `slotClaimed`, `judgeSkillRows`, pure); `provision-local` is `cloud.ts` `provisionLocal`; `prepare(agentId)` answers `skillRuntime` beside the file path. All three writes go through `writeAttachments` in `service.ts`. `autoAttach(agentId)` is called by the sharing verbs, never over IPC; the fit rules are `slotMatch.ts` (`autoMatch`, `slotCandidates`, `isDeadKey`), pure and mirrored from the scanner's `credentialStates`. The `.env` writer is `localAgentService.setEnvValues` over `localAgents/envFile.ts` (`mergeEnv`, `envLine`, `envValueProblem`), reached through `local-agent:set-env-values`. The dialog is `FinishSetupDialog.tsx` (`useFinishSetup`, owned by `LocalAgentPage`); the sharing mutations hand it the verbs' results through `stores/finishSetup.store.ts`, at hook level so the request survives the caller unmounting. `hub/core.ts` installs the session unlock check (`installUnlockCheck`, backed by `userActivation.isUnlocked`); `activation.ts` recomputes the set on unlock changes and reports renewal of any profile through `renewed`; `authService` reports logout (`signOut`), deletion and password changes. `renewed` starts an account's scheduler only when the account already existed: one that just became eligible was started by the recompute, and starting it again synced it twice.

`ServiceCredentialsTab` owns attaching, not `CredentialAttachModal`, so an attach survives the picker closing. Every list write (attach, detach) runs on one promise chain and applies its change to a freshly read copy of that group's list. Without that, a detach made while an attach was in flight would write back a list without the new reference. Skills use this same attachment and materialization path — skill slots are filled by attaching records and read from the same credentials file — and must never grow a second delivery path.

See [verification.md](verification.md) for exercised flows and commands. Core API documentation lives in `workflow-runner-core/docs/application/desktop_credentials/README.md`.

Desktop reads and validates the contract 1.4 sibling `publications.json` ledger. Legacy `manifest.publications` remains readable when no sibling exists; reads never migrate or mutate either file. The one write is sharing a skill, which upserts that skill's entry in `publications.json` → `skills[]` ([Agent Skills](../local_agents/skills.md#sharing)).
