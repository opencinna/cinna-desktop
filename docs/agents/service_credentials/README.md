# Service credentials

Credentials supplies explicitly attached service accounts, tokens, and logins to real local folder agents. It is independent of AI Credentials and requires no skill installation.

## Using credentials

1. In Default Settings → Credentials, select **Add Credential**, search the type cards, then fill in the type-specific form for an API token, IMAP/SMTP login, Odoo login, or Google service account. Every form exposes **Service URI**, with a hint explaining how it matches a credential type to an agent requirement. Values are write-only; editing metadata preserves the encrypted value unless you select **Replace stored values**.
2. With a Cinna profile active, Profile Settings → Credentials lists owned and shared cloud records. Use **Manage on Remote** beside **Sync Now** to manage values and sharing in Cinna web. A shared record requires its owner's **Allow local use** consent. The list is not the server's full set, and the **(?)** beside **Remote credentials** ("About remote credentials") says so: Core lists only credentials a local agent can use. Those are the caller's `mine` records (owned, or shared directly) of the types IMAP, SMTP, Odoo, API token and Google service account. OAuth, SSH, Agent API, MCP, automatic and bundle credentials never reach the desktop, and materialize refuses them if asked. The one unusable record Core does list is a share whose owner has not allowed local use; it arrives flagged so Desktop can explain it. Desktop keeps no category or type rule of its own. It treats Core's list as the complete locally usable set and prunes a cached record, attached or not, once Core stops listing it. A second rule on this side would drift from Core's, and would either show records that materialize then refuses or hide ones Core has started allowing.
3. Open an agent's Settings → Credentials and select **Attach**. The picker lists **This computer** first, then each [eligible account](#eligible-accounts) by profile name, with its server host and, when its last sync failed, the reason. Search filters every group by name, type, Service URI and owner email, hiding groups with no match. Each card has its own **Attach** button. Attaching keeps the picker open and turns that card into a disabled **Attached** in place, so the grid never reflows under the pointer while several are picked. A failed attach shows its reason on the card. Cloud records whose owner has not allowed local use are left out of the picker; one already attached stays in the agent's list as *local use not allowed*.
4. The tab lists attachments under the same group headings. **Move up** reorders within a group. **Detach** removes generated files after a running turn releases the folder; it leaves the record and other agents' attachments intact. Missing references remain visible and recover when access returns.
5. For older kit folders, use **Update credential helper**. This checks the file stamp before replacing `scripts/cinna_credentials.py`.

Attached values override `.env` for a whole matching slot. The page reports overlapping variable names. Readiness and the Python helper require both the credential type and the declared service: an explicit `service_uri`, or the slot name matched against credential name/service URI. A token for another service does not satisfy the slot. Readiness checks metadata and names, never values. A missing credential warns; an unsafe generated-file destination refuses execution.

## Eligible accounts

Agents receive their local attachments plus the attachments of **every eligible account**, whichever profile is current. A profile switch is a change of view, not of intent: an agent attached to a work account keeps that credential while the user works in another profile. Switching profiles rewrites no generated files unless the eligible set itself changes.

An account is eligible when its Cinna profile has a server URL and stored tokens from which the account identity can be read, and either has no password or was unlocked in this app session. The current profile always counts as unlocked. A locked password profile contributes nothing until it is unlocked, because its password is what stands between its account and anyone at the keyboard. A profile that was logged out of stays ineligible for the rest of the app session, even though its tokens may remain, until that profile is activated again. Logout also clears every profile's unlock memory, so other password profiles drop out with it; passwordless ones stay.

Accounts are keyed by `sha256(serverOrigin + "\n" + jwt.sub)[:16]`. When two profiles derive the same key (a recreated profile), the current one owns it. Group order is local first, then accounts by profile name.

The set is recomputed on profile activation, unlock and lock changes, logout, profile deletion (sign-out removal included), setting a password, and token renewal of **any** profile, current or not. Recomputing retires accounts that left the set and starts accounts that joined it. Only agents with attachments stored under a changed key are queued for regeneration.

Each account owns its own sync flight, five-minute scheduler, epoch and abort controller, sync error, last-sync time and `current_user` identity entry. Retiring an account aborts its requests, bumps its epoch, stops its scheduler and drops that entry. The global epoch covers only suspend and shutdown. A turn's preparation guards only the accounts its agent has attachments under, so an unrelated account leaving the set does not fail it.

References stored under a key that is not currently eligible are kept, never delivered, and reported as `account_unavailable` under the label "Signed-out account". Their credential metadata is hidden even when a locked profile's cache still holds it, so a locked profile's credential names do not surface while another profile is in use. Such a list can only shrink: **Detach** works, because removing a reference needs no rows, tokens or network, while adding is refused ("Sign in to that account to change its credentials."). A deleted profile's key may never be eligible again, and a list that could not shrink would strand its references. Emptying a group removes its key from Desktop State. These rows offer **Detach** only, not **Move up**.

Settings pages are unchanged by this: Profile Settings → Credentials, its status, and **Sync Now** show only the current profile's cache. A current Cinna profile whose identity cannot be derived has no account and reports `reauth_required`.

## Runtime contract

Kit agents receive a cloud-compatible array at `credentials/credentials.json`. Bare agents receive it under the Hub's userData `agent-credentials/<realpath hash>/` directory, outside their folder. Only `CINNA_CREDENTIALS_PATH` is injected into script children; values never enter process environment variables or the prompt. The prompt lists names, types, slots, and availability.

The shared 1.4.0 Python reader uses the injected path, the nested array/envelope, the legacy root object, then environment and `.env`. `get_credential`/`has_credential`, `require_credential`/`list_credential_slots`, and strict `by_slot`/`require_slot` are supported. Files are reread on every call. Placeholders cannot silently borrow environment fields. Service-account keys live in separately inventoried JSON files. There is no SSH, OAuth, Agent API or MCP delivery path: Core never sends those types, and a delivery item carrying a non-null `ssh_key` is rejected as incomplete rather than written. Core's `owner_identity` response field is always null and is ignored.

Runtime preparation (`prepare(agentId)`, which takes no profile) occurs inside the per-agent turn lock, after launch planning and before process/session acquisition. Session identity includes a fingerprint of the effective credential material, the `current_user` entry when one is written, and the keys of the **contributing accounts** (those with at least one ready cloud credential attached), independent of any epoch. No account fingerprints as null, one account as its bare key, several as the ordered key list. A single account therefore keeps the fingerprint it had before several accounts could contribute, so an upgrade does not restart its sessions.

`current_user` is the only identity entry, and Core gives every one the same fixed id. It is written only when exactly one account contributes; with several contributing, none is written, because one entry would have to name an arbitrary one of them and two would collide on the id. When contributions drop back to one account, its entry returns. A Core record attached under two accounts (one profile owns it, another receives it as a share) is written once, and the first group in order wins: two entries with one id would also collide on the service-account side file.

Empty attachments have a stable fingerprint across resume and re-authentication. Commands use the same preparation hook. Synthetic chat/conductor/build runtimes, remote A2A, and custom ACP transports do not receive attachments. Each delegated local executor resolves its own attachments through its ordinary folder driver; delegation permissions remain unchanged.

## Storage and lifecycle

`service_credentials` stores metadata and keystore-encrypted bundles. Local records use `__default__`; cloud cache rows are scoped to the local profile, server origin, and cloud UUID. The metadata DTO includes `hasValues`, never payloads. Service credentials reject Linux `basic_text` storage without changing app-wide provider/OAuth encryption behavior. An unavailable secure keystore forbids secret writes and preparation removes generated secrets before refusing execution.

Desktop State stores UUID-only attachment lists: machine-wide local references and cloud references keyed by account key. This recovers intent after signing into a recreated local profile while keeping an ineligible account's list inert. Eligibility derives this identity from the stored token without refreshing it or waiting for network access.

Cloud metadata sync runs per account every five minutes, immediately when an account joins the set or its tokens are renewed, and on demand. Manual sync is pinned to the displayed current profile and syncs only its account. Retiring an account aborts its credential requests; an account never joins another account’s pending sync. Credential HTTP requests bypass the browser cache and have a 30-second timeout. Secret delivery is lazy for attached records. Desktop never receives OAuth or refresh tokens. Failed/malformed lists do not prune cache rows. Owner opt-out or a materialize refusal clears the payload; a record Core stops listing loses its cache row. Either queues regeneration. Same-account offline use is allowed until a record's stated expiry, when Core gives one; shared cached values also expire seven days after delivery. Owned cache has no other TTL.

Epoch checks after awaited work prevent responses for a retired account, and suspended responses, from updating cache or files. Background writes coalesce until the agent is free. A change to the eligible set regenerates affected agents' files before their next turn; cleanup failure blocks only that agent's turn, while activation and other agents continue. The first activation after launch brings every agent's files current. Attachment changes wait for the running turn to release the folder and reject if that group's account leaves the set while waiting; a profile switch alone does not reject them. Logout removes that profile's cloud cache rows but retains UUID attachment intent. An account's timer stops when it leaves the set, on reauth failure, on suspend and at shutdown; resume regenerates every agent. HTTP 403 reports a permission refusal and retains scheduled retries; HTTP 401 requires reauthentication. A full activation scan removes inventoried bare secrets for folders that no longer exist, preserving unrecorded files.

## File and output boundaries

Generated directories are mode `0700`, files `0600`. Writes use exclusive temporary files, fsync, and rename, and unchanged bytes retain their modification time. UserData inventories permit deletion only of names written by this feature. Authored files and `credentials/README.md` are preserved. Kit writes require static kit ignore coverage plus actual untracked/ignored Git status; missing Git or a broken repository fails closed. The full `credentials/` directory is excluded from export and content hashes in Desktop, Core, and CLI.

Known sensitive strings of at least eight characters are redacted before transcript/task/request/delegation persistence, task and handover files, logs, renderer events (including split chunks and nested agent events), and outbound Cinna task/delegation writes. Retired secrets stay in memory until shutdown to cover finishing old turns. Raw values and their JSON-escaped file representation (including `api_key` fields) are covered. This is substring redaction: other encoded/transformed values and strings shorter than eight characters are outside its guarantee. Generated files are plaintext for execution; local processes running as the same OS user can read them. Revocation cannot recall copies made outside the managed cache. Long turns do not refresh files mid-turn.

## Implementation and verification

Hub owns `src/main/services/serviceCredentials/`, the repository/migration, and redaction. IPC and renderer consume metadata-only typed outcomes. `service-credentials:attach-options` (agent ID) returns the picker groups with each item's `attached` flag. `service-credentials:set-attachments` (agent ID, group, refs) replaces one group's list, where group is `'local'` or an account key. `hub/core.ts` installs the session unlock check (`installUnlockCheck`, backed by `userActivation.isUnlocked`); `activation.ts` recomputes the set on unlock changes and reports renewal of any profile through `renewed`; `authService` reports logout (`signOut`), deletion and password changes. `renewed` starts an account's scheduler only when the account already existed: one that just became eligible was started by the recompute, and starting it again synced it twice.

`ServiceCredentialsTab` owns attaching, not `CredentialAttachModal`, so an attach survives the picker closing. Every list write (attach, detach, reorder) runs on one promise chain and applies its change to a freshly read copy of that group's list. Without that, a detach made while an attach was in flight would write back a list without the new reference. The follow-on skills feature should call this attachment/materialization service, never implement a second delivery path.

See [verification.md](verification.md) for exercised flows and commands. Core API documentation lives in `workflow-runner-core/docs/application/desktop_credentials/README.md`.

Desktop reads and validates the contract 1.4 sibling `publications.json` ledger. Legacy `manifest.publications` remains readable when no sibling exists; reads never migrate or mutate either file.
