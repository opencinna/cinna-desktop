# Agent Skills (A Kit Agent's Own, Catalog and Marketplace Skills)

## Purpose

A kit agent has skills from three places: folders under `skills/` in the agent folder, each with a `SKILL.md`, skills from the platform's catalog that its manifest pins in `catalog_skills[]`, and skills from the skills marketplaces connected to cinna-core that it pins in `marketplace_skills[]`. The desktop reads and checks all three, lists them on the agent page's **Addons** tab, beside its connectors, downloads each pinned catalog revision or marketplace snapshot once into a shared read-only cache, and hands every deliverable skill to whichever engine the agent runs on, by that engine's own mechanism. Without this, an author's skills sat in the folder and no session ever saw them, and a pinned catalog skill was a row with nothing behind it. From the same section an own skill can be shared to the catalog, and a catalog skill updated or removed; adding one starts in the catalog dialog.

## Core Concepts

- **Authored skill** — a folder `skills/<name>/` directly inside a kit agent's folder, holding a `SKILL.md` whose frontmatter names the skill and says what it is for. Marked **Authored** on its row
- **Catalog skill (pin)** — an entry of the manifest's `catalog_skills[]` (contract 1.10.0): a skill from the platform's catalog, referenced by `package_id`, `package_uuid`, `name`, `revision_number`, an optional `version` label and `archive_sha256`. Marked **From the catalog**. Its files never live under `skills/`: the contract forbids copying them there. Both sources share one row shape, told apart by `source` (`authored` / `catalog`)
- **Catalog skill cache** — `<userData>/catalog-skills/<instance>/<package_uuid>/<revision>/<name>/`: one unpacked copy per pinned revision, shared by every agent that pins it, read-only on disk, keyed per Cinna server (`<instance>`). A revision is either there whole, with a marker naming the package, revision and archive digest, or not there at all
- **Marketplace skill (pin)** — an entry of the manifest's `marketplace_skills[]` (contract 1.15.0): a skill from one of the skills-format marketplaces an admin connected to cinna-core, referenced by `entry_uuid`, `marketplace_uuid`, `marketplace_name`, `name` and `archive_sha256`, with an optional `commit_hash` and `version` kept for display. **Content-addressed**: the pin names the snapshot's digest, so a marketplace that moves on is an offer to update, never a silent change under the agent. Core snapshots the marketplace and serves the archive; the desktop never touches git. Marked **From *marketplace name***; row `source` is `marketplace`
- **Marketplace skill cache** — `<userData>/marketplace-skills/<instance>/<entry_uuid>/<archive_sha256>/<name>/`: the catalog cache's twin, built from the same machinery (shared, read-only, complete-or-absent, per server, a marker whose digest must equal the pin's). The digest is the folder, so a re-pin to the entry's next snapshot is a new folder beside the old
- **Skill rules** — the checks a skill must pass. They are cinna-core's (`skill_manifest.py`), ported line for line: the codes, the sentences, the limits and the restricted frontmatter reader are core's. **Core is the source of truth**: a rule changes there first and is ported here after, and nothing is checked here that core would not say about the same folder. A cached catalog skill is checked by the same rules as an own one
- **Issue** — one finding on a skill, with core's code and sentence. An **error** keeps the skill from every engine; a **warning** is worth knowing and changes nothing
- **Deliverable** — a skill with no error. Only deliverable skills reach an engine, in any form. A pinned skill (catalog or marketplace) is deliverable only once its copy is cached and passes the rules
- **Skills plugin** — a desktop-owned local Claude plugin per kit agent, under `<userData>/cinna-plugins/agents/<key>/`, whose `skills/` holds one symlink per deliverable skill: to the agent's real `skills/<name>/` for an own skill, to the cached folder for a catalog one. Claude loads it as a plugin; OpenCode is pointed at its `skills/` folder (the **links folder**)
- **Changeable agent** — one whose pins this person may change: any folder that is not a Cinna team agent, or a team agent where the catalog listing gives them `edit` or `maintain`. A team agent they may only **use** (or whose access the listing does not say) is not: its skills arrive with the team's next version
- **Skill credential slot** — a credential a deliverable skill's `SKILL.md` declares under `credentials:`, named by its **slot**, which is a Service URI. Filled only by an attachment of that type whose Service URI is exactly the slot ([Service Credentials](../service_credentials/README.md#skill-credential-slots))
- **Shared skill** — an own skill shared to the active account's catalog, recorded in the agent's `publications.json` → `skills[]`. Its row shows the version it was shared as and a **Shared** badge

## User Stories / Flows

### Seeing an agent's skills

1. Agent page → **Settings** → **Addons**. A kit agent's skills are rows in the tab's one list, beside the connectors; a bare agent has none, because it made no promise about a `skills/` folder
2. Each skill is a card in the shell every addon row shares: a name, a source badge, a status glyph and the row's actions on the title line, then the description clamped to two lines, a **Needs** line naming the credential slots its `SKILL.md` declares (two shown, the rest folded into `+N`; each chip marked ✓ when a ready attachment fills it and with a warning triangle when none does), and the issues, each only when there are any
3. The glyph is the shared status glyph: the first error's sentence when there is one, else the warnings, else "Every engine of this agent gets this skill"
4. An own skill has a reveal button, which opens its `SKILL.md` in the file manager, or its folder when it has no `SKILL.md`. A failed reveal is shown inside that skill's card, never as a page-level error
5. A catalog skill is named by its title in the catalog listing (the folder name stays in the tooltip, and is what every engine calls it), with its pinned **Version N (label)** muted beside it and **From the catalog**, titled with the `package_id`. It has no reveal: none of its files are in the agent's folder. Its description and **Needs** line come from the cached `SKILL.md` once the revision is on this computer, and are absent until then
6. A catalog row that is not on this computer says so: "Not on this computer yet." when nothing has tried, or the last download's own sentence when one failed. The latter is remembered only until the app restarts
7. A catalog row whose package is no longer in the person's catalog listing — the publisher took their access away, made it private or deleted it — is <a id="disconnected"></a>**Disconnected**: it warns "Disconnected — this skill is no longer in the catalog for you. The copy on this computer is now a local version: it keeps working but no longer syncs or gets updates." A warning, not an error: the cached copy is still given to every engine, and it is no validation finding. Only on an agent no team tracks (one not got from or shared to the catalog, whose pins come with the team's version instead), only once the active Cinna account's listing has loaded (no account, not loaded yet, or an instance without the catalog: nothing), and only while the copy on this computer was downloaded from that account's server — a row that is not keeps its own state above, and a copy fetched under another profile's server says nothing about this listing. It is read from the cached listing on every list, so it appears and clears when the listing moves; the Inbox shows **Disconnected: _skill_ in _agent_** for it, with **Remove** (where the person may change the agent, after the same confirm, worded for a skill that may not come back) and **Dismiss**, which hides that card until the pin is connected again — a later disconnect shows a new one ([Inbox](../../jobs/tasks/inbox.md)). On a team-tracked agent the Inbox card appears only when the team agent itself can no longer reach the skill: the last download of the pinned revision was refused as not available and the folder is not behind the team's version.
   A pin with **no copy on this computer** is Disconnected too once its download was refused as not available (404) — on an agent no team tracks, while a loaded listing does not list the package again; on a team-tracked agent, when the team agent is in the listing and the last **Update available** read found the folder not behind it. The row then says what the Inbox card says: "Disconnected — this skill is no longer in the catalog for you, so this agent can’t download it. Ask a maintainer for access, or remove it." It offers no **Try again** while that refusal is known (it is remembered until the app restarts); instead **Check again** (_Check skill again_) runs the same download once more — access may have come back without a new team version. If it lands, the refusal is forgotten and the row and the Inbox card go; refused again, the row just stays Disconnected, with no error line. **Remove** stays. A Disconnected row whose copy is on this computer has no Check again: that copy keeps working. Where the card does not apply the row keeps the download's own sentence and Try again — a team-tracked agent behind its team version reads "This version is not available to you. If the agent is shared, update it to the team’s latest version first."
8. With a `skills/` folder but no skill in it and no pin, the section says "No skills yet."
9. A deliverable skill with a slot nothing fills ends its **Needs** line with a **Finish setup** link, which opens **Finish setting up** on the agent page — the dialog whose **Skills** group lists exactly those slots
10. The **Addons** tab's badge counts skills beside connectors. When any connector is not connected, any skill has an issue other than "Not on this computer yet.", or a deliverable skill has a slot nothing fills, the badge shows how many need attention, warning-toned, titled "*k* of *n* skills need attention" (or connectors, or addons when both kinds are present); otherwise the neutral total. "Not on this computer yet." is left out because it is transient and its **Try again** sits on the row; a failed download is counted
11. Adding, removing or editing an own skill refreshes the tab without a manual rescan, on every platform; a catalog verb or a finished download rescans too. A new version in the catalog listing shows **Update** on an open row without a rescan: the agent list and every open agent page are re-read whenever main's cached listing moves, because a row's **Update** and shared version come from that listing, not from the folder, so no folder change ever announces them

### Adding a skill from the catalog

1. Two doors lead to the same add. From the skill's side, the **Catalog** dialog's skill tiles and details carry **Add to agent…**, a menu of this computer's kit agents ([Bundles Catalog](../bundles_catalog/bundles_catalog.md#browsing-the-catalog)). An agent that already pins the package reads **Added**, one shared with the user to use only reads **Can use only**, and while sharing status is still being read each reads **Checking access…**; those rows are disabled
2. From the agent's side, the Addons tab's one **Add** opens the **Addons for *agent*** picker ([Agent Addons](addons.md#adding-to-the-agent)), a search over every source the account may use, skills and connectors together. A catalog skill is a tile of kind **Skill** from **Cinna** (its source reads **Catalog**), with its detail over the grid and **Add to *agent*** beside it; Back finds the search, the filters and the scroll where they were. Signed out, the Cinna source has no skills and says nothing is wrong. **Add** is refused, with the reason on the tile and in the detail, on a team agent shared to use only ("Its skills come with the team’s version") and while sharing status is still being read ("Checking access…") — the same rule that hides Update and Remove, because a pin added there would be overwritten by the team's next version. A skill on a bare agent (no `cinna-agent.json`) is blocked with the reason; connectors work there
3. A pick reads **Adding…**. Main pins the package's **latest** version: it downloads and checks the revision first, then writes the pin to `cinna-agent.json`. The menu closes on success; a refusal stays under that agent's row in main's sentence. In the picker the dialog stays open and the detail turns to **Ready in the next chat** and **Done**, so several skills can be added in one visit; a refusal stays beside the button. The tile reads **Added** only while the pin exists: a skill removed since can be added again. It once stayed Added for as long as the app ran. Both doors share the add's state, keyed by package, so closing either surface mid-add loses neither the progress nor the refusal
4. The tile then says **In N agents**. The new row in the agent's Addons list is already on this computer, so — unless the cached copy breaks a skill rule — the agent's next session has it
5. In the background main reports the install to core (with the agent's manifest id) and fills the skill's credential slots where exactly one of the account's credentials fits

### Adding a skill from a link

1. A catalog skill is shared as a link: `https://<core>/get/skill/<package_id>` (what **Copy install link** writes, and what the public skill page shows) or `cinna://skill/<package_id>?server=<origin>` (the page's **Open in Cinna Desktop** button; `server` is optional). A Cinna server has a web origin and a backend origin, a profile stores either, and the two forms usually carry different ones: the https form the web app's, the deep link the backend's. Matching a link to a profile therefore does not compare strings (see the rule on matching below). `<package_id>` is core's reverse-DNS id (`[A-Za-z0-9._-]`, at most 255). The link carries no version: it always means the latest, and the offer names the version the person would get
2. Four things raise the offer on a composer: pasting a link as the **whole** paste into it, clicking a link in a transcript, the OS delivering the `cinna://` form, and **New agent with this skill** coming back after a cancel (below). The offer is a row at the top of the composer's notice panel, in the accent tone; an agent warning row stays below it. It reads *skill title · Version N (label) · by publisher on host*, with the host as a link to the server and a **Details** toggle for the description and the credentials the person would have to provide. **Dismiss skill link** (×) puts it away. At most one offer exists; a newer link replaces it
3. The row is the confirm step: nothing is installed until a button is pressed. **Add to *agent*** adds it to the agent the composer is addressed to; **New agent with this skill** opens the Add an agent dialog at its name step, headed *New agent with the skill*, with the skill's title as the suggested name, and adds the skill once the agent is created. On a successful Add or Update the row turns to *Added <title>. Checking its credentials…* until main's fill of the skill's credential slots settles, then goes; when the skill still lacks a credential, the composer's skill-credential row with **Finish setup** takes its place at the same height, so the panel does not move ([Service Credentials](../service_credentials/README.md#in-the-composer))
4. What the row says is decided in main from a **fresh** catalog listing, never the cached one, and arrives as data:
   - **Add to *agent*** (primary), when the agent can take it. Refused, it stays visible but inactive, with the reason on the button and on the row's line after the skill's title, in place of the version and publisher (which stay in the tooltip): no single agent is picked ("Pick one agent to add it to, or make a new one." — the button then reads **Add to agent**; a link opened from the OS lands here), the agent is not a kit agent, it is shared to use only, its access cannot be told, or it already has a skill of that folder name
   - ***Skill* is already on *agent* (Version N)**, when the agent pins the package. **Update to Version N** is offered only where Update would run, which is where Add would not be refused
   - **Switch to *account***, when the link's server is another profile of this app: the offer moves to the start screen while the login runs and stays put if the login fails
   - **This skill is on *host*. Connect to it first.** with **Connect…**, which opens the ordinary connect confirm step for that server; with no server at all, "Sign in to a Cinna account first."
   - **You don't have access to this skill on *host*.** Core answers the same for a private package and one that does not exist, so the row does not tell them apart
   - **Couldn't reach *host*…** with **Try again**, and **Sign in to *host* again…** with **Try again** when the session is gone (main has raised the sign-in prompt as well)
5. While the lookup runs the row reads *Looking up package on host… Nothing is added until you choose.* Changing the composer's agent re-asks and keeps the last answer on screen with its buttons inert, so a button never acts on an answer about another agent
6. **Copy install link** writes the https form to the clipboard and says **Copied** in place for a moment. It sits on the catalog skill's detail (both the Catalog dialog and the Settings catalog), on a catalog skill's row in the Addons tab, and on an own skill's row once it is shared to the catalog. The link names the server's **web app**, not the origin the profile happens to store: a profile signed in through a `cinna://connect` link stores the backend origin, and a link on it opens nothing in a browser. The web origin comes from the server's discovery document; an older core that does not publish one, or a server that cannot be asked, falls back to the stored origin, and the button is never withheld or late for it. It is absent without a Cinna account, on a marketplace skill (marketplace skills have no catalog link) and on an own skill that was never shared. A clipboard refusal shows as the surface's own error line

### Adding a skill from a marketplace

1. The picker lists, beside the catalog's skills, every skill the skills marketplaces visible to the active Cinna account offer. Each is a **Skill** tile whose source reads the marketplace's name; the **Source** select filters to **Cinna**, and the search matches name, summary, marketplace and owner. A detail names the marketplace, owner, version, whether it **runs code on this computer** (ships scripts), and links to the source
2. An entry core could not snapshot is listed but cannot be added, with a sentence for its reason (no valid `SKILL.md`, a path outside its repository, over 16 MB); one core is still preparing reads as being prepared. A skill the agent already pins reads **Added**
3. **Add** pins the entry's **current** snapshot: main downloads and checks it, then writes the pin. The picker stays open so several can be added in one visit, as for the catalog; a refusal stays beside the button
4. There is no Catalog / Marketplaces switch: the two used to be separate panes, with the last choice remembered for the session so that someone adding several marketplace skills did not pick Marketplaces every time. One list makes the choice unnecessary
5. In the Addons list a marketplace row wears **From *marketplace*** and **Version** when the pin has one, with a **source link** (opens the entry's repository page in the browser) while the entry is still visible. **Update** appears when the entry moved to another snapshot; **Download again** when the pinned snapshot is not on this computer; **Remove** opens the same in-card confirm, worded "It stays in its marketplace; you can add it again"
6. A pin whose entry the person can no longer see — removed from its marketplace, or the marketplace is no longer theirs — warns **No longer available to you**. A warning, not an error: the cached copy keeps being delivered.
7. Update, Remove and the credential follow-up are the catalog's: Add and Update fill the new skill's credential slots where exactly one credential fits, and Remove and Update detach what was attached without asking for slots no remaining skill declares

### Updating, re-fetching and removing a catalog skill

1. **Update** (an arrow icon, titled "Update *title* to Version N (label)") appears when the catalog listing has a newer revision than the pin and the agent is changeable. It downloads the latest revision, then moves the pin to it, keeping the pin's name and any keys it does not know. In the background, credentials that were attached without asking for a slot the new version no longer declares are detached, then the new version's slots are filled. The same update is offered in the Inbox as **Update available for *skill* in *agent*** ([The Inbox](../../jobs/tasks/inbox.md))
2. **Try again** (a circular arrow, "Download *title* again") appears whenever the pinned revision is not on this computer. It fetches every missing pin of the agent; the row shows its own failure, if any
3. **Remove** (trash) opens a confirm inside the card: "Remove *title* from this agent? It stays in the catalog; you can add it again. *title* stops being available to this agent in new chats." On a shared agent the person may change, it adds "Share changes to pass this on to the team." **Remove skill** drops the pin and reports the removal to core, and in the background detaches what was attached without asking for slots no remaining skill declares ([Service Credentials](../service_credentials/README.md#detaching-what-it-attached)). The cached revision stays: a turn may still be reading it, and the next app start removes it if no agent pins it
4. On an agent shared with the user to use only, Update, Make editable and Remove are not shown; Try again is. While the agent's sharing status is still being read, Update and Remove are hidden too
5. A verb in flight spins its icon and disables the other rows' actions; a refusal is the card's last line, and is not repeated when it is the very sentence the row's issue already says

### A team agent's pinned skills

1. After a team-library **Get**, an **Update** that brought changes, or **Use the team's version**, main fetches every pinned revision the agent lacks, in the background. The verb never waits for it and never fails because of it
2. A revision that cannot be fetched is an issue on its row — a teammate whose copy is behind gets "This version is not available to you. If the agent is shared, update it to the team's latest version first." — never a failed Get or Update. On an agent no team tracks the same refusal (core's 404) means the person's own access went, and reads "This skill is no longer available to you — its publisher took away your access or removed it from the catalog." An agent is team-tracked when its `shared_remote` link names a Cinna team agent, or, without one, its git `origin` is a Cinna team agent's. One download serves every agent pinning the revision, so each agent's answer and row are worded by that agent: two agents pinning the same withdrawn revision can read the two different sentences. The row reads the link only, so an agent cloned by hand from a Cinna team origin, with no link, has its row read the access-withdrawn sentence while Try again answers the behind one
3. Then the skill credential slots are filled where exactly one credential fits, as after Add to agent

### Sharing an own skill

1. An own skill that is deliverable, on an agent this person may change, with a Cinna account active, has **Share** on its row (a share icon, "Share *name*…"). Once shared, it reads "Share a new version of *name*…", offered only while the catalog listing gives the person `edit` or `maintain` on that package
2. **Share *name*** opens on everything at once, words filled in when the catalog's preview answers: the **Version** it will become, its **Catalog id**, **What people need** for each declared credential slot (**Each person connects their own**, or one of the sharer's own credentials offered for everyone), an optional **Note**, and on a first share **Who can use it**: **Everyone on this server can use it** and named people at Can use / Can edit / Maintainer
3. On a later version each slot starts at what the last version provided, and a line says when that could not be carried over. Someone who did not first share the skill is offered no credential of theirs, because core refuses one. Access stays as it was: "People who can use it keep access."
4. **Share** packs and uploads the folder. Before any byte is sent it refuses links, anything that is not a file or folder, files that look like secrets, more than 16 MB and more than 2000 files and folders, each with a sentence that says nothing was sent
5. On success the dialog closes; the catalog's version label is written into the skill's `SKILL.md` (that one line) and the share is recorded in `publications.json`. The row then shows **Version N** and **Shared**. In a team agent both are ordinary file changes to share with the team
6. A refusal stays in the dialog, under the fields
7. The preview carries the version the folder holds (`base_revision_number`) and so does the share. If the package has a newer version, the dialog says so before any byte is sent: "*Person* shared Version N since your copy. Get it first, then share your changes." as an alert last before the buttons, with **Share** disabled and **Get Version N**, which brings it in without closing the dialog and previews again. When the folder also has unshared changes the button is not offered (it would need a backup); a second sentence points at **Replace** on the skill's row. A share that core refuses as stale after all (someone shared in between) shows the same line
8. On a **first** share, when packages of this skill's name that someone else shares and the person may edit exist, the dialog starts with **Share as**: **New version of *publisher*'s *name*** (the default) or **A separate skill**. The first sends the folder as that package's next version, based on the latest version the dialog showed; Who can use it and provided credentials are then left as that package has them, and a line says so in place of those controls. If such a package appeared between the preview and the share (`editable_package_exists`), the dialog previews again so the choice shows. The choice never moves the radios or the note: what depends on it sits below the note
9. Everything arrives with the preview, above the note, so the note is disabled (like every control) until the preview answers and takes focus then: a section arriving never pushes a field the person is typing in

### Making a catalog skill editable

1. A catalog pin whose package the cached listing gives the person `edit` or `maintain` on has **Make *title* editable…** (a pencil) on its row, on an agent they may change. The row carries the listing's `access`; a pin the listing does not have, or a marketplace pin, never offers it. A maintainer's pin row also has **Who can use *title*…** (below), whatever the agent's state, because that is about the package and not the agent
2. It opens a confirm inside the card: the skill's files move into `skills/<name>/` at the package's **latest** version (not the pin's, even when the pin is behind: the copy is what the next share builds on), linked to the catalog skill; Share sends the changes as its next version; catalog updates stop, newer versions show on the row to get when the person chooses. **Make editable** or **Cancel**; one confirm is open in a card at a time
3. On success the pin is gone and the row is an **Authored** one, linked to the package at that version. A refusal is the card's last line. Refused, with nothing written: `not_editor` (core's listing, read afresh for this check, gives less than `edit`: a grant lowered since the row last refreshed still refuses), `folder_exists` (something, a dangling link included, is already at `skills/<name>/`: "Rename or remove the skill's folder under skills/ first."), `download_mismatch` (the copied files do not hash to the version's published `content_hash`), and the pin verbs' own refusals, the read-only-agent ones included
4. The credentials attached for the skill's slots stay: the copy declares the same slots as an own skill. Core is told the pin was removed, as for Remove

### Keeping a linked skill in step

1. An own skill linked to a catalog package (it has a `publications.json` record for the active server: shared, made editable, or brought in by Get) shows where its folder stands against the package, from the cached listing and a hash of the folder: in step, **changed** (edits not shared yet), **behind** (a newer version exists, the folder is untouched), **diverged** (both), or unknown (the listing does not have the package, or a file could not be read, or the folder holds a link). Only behind and diverged show on the row: a muted line says which version and who shared it
2. On **behind**, **Get Version N of *name*** (an arrow icon, titled with who shared it) brings the version in, on an agent the person may change. On **diverged**, **Replace *name* with Version N…** opens a confirm inside the card: the unshared changes are moved to a backup folder outside the agent (`<userData>/skill-backups/<agent>/`), and the skill's files become Version N. The backup is never deleted by the app. Neither verb is offered when the folder is in step or only changed: `up_to_date`
3. Get reads the listing fresh (core may know a newer version the cached listing does not yet) and hashes the folder on its bytes before and again right before the swap: an edit made while the download ran is not replaced without a backup (`has_changes`). Refused with nothing changed: `not_linked`, `package_not_found`, `up_to_date`, `has_changes`, `download_failed`, `download_mismatch`, `write_failed`, `unreadable`
4. A crash in the middle of a swap does not lose the skill (below)
5. Finder's `.DS_Store` is neither packed nor hashed: Reveal opens Finder in the folder, and a file the person never wrote would otherwise travel with a share and make an untouched linked copy read as changed

### Changing who can use a shared skill

1. An own skill shared to the active account's catalog, or a catalog pin, whose package the catalog listing says this person maintains, has **Who can use *name*…** on its row (a people icon), after Share and Make editable and before Reveal and Remove. The catalog's skill detail — the catalog dialog and Settings → Catalog — offers the same to a maintainer, as an icon titled **Who can use *name*…** beside **Add to agent…**
2. It opens **Who can use *name***: the same **People** list a shared desktop agent has on its Sharing tab — a row per person or role with its access (Can use / Can edit / Maintainer), a remove behind the row's own confirm, an **Everyone on this server** row while the skill is public, and **Share with a person…** and **Share with everyone** (while it is not public) beside the title. Above the list a **Maintainers** line names every maintainer from the catalog listing, as the Sharing tab's Where section does — a co-maintainer has access without a row in the list. The maintainer's own row is left out, as on the agent's tab; with no row left the list reads **No one else has access yet.**, or **No one but the maintainers has access yet.** when someone else maintains it too
3. **Share with a person…** replaces the list with the search and the access select inside the same dialog; the search's answers are a dropdown fixed to the field (below); **Add** goes back to the list once the server took them, **Cancel** or Escape go back without a change
4. Each change is saved at once. A refusal stays in the dialog beside the control that made it (Share with everyone's under the header); nothing closes on one. **Close** or Escape closes the dialog; opened from the catalog, Escape closes only this dialog, not the detail under it
5. Someone who may not see the list (not a maintainer) sees the maintainers and "Only a maintainer can change who has access."

### A session using a skill

1. The agent's session starts. On Claude and OpenCode the engine already lists the agent's skills by name; the assembled prompt says only that its own skills — and, when it pins any that are cached, the catalog skills it pins — are available through the skill tool. On Codex the prompt lists each skill with its description and the path of its `SKILL.md` (agent-relative for an own skill, absolute in the cache for a catalog one), and tells the agent to read it before using the skill. Antigravity gets the same listing with paths
2. The agent opens a skill when the task matches its description. On OpenCode this does not stop the turn for a click; on Claude it follows the session's ordinary approvals
3. A skill script that needs a credential does `from core.cinna_api import credentials` and `credentials.require_slot("<service uri>")`, exactly as in a cloud agent. The desktop puts that module first on the engine's `PYTHONPATH` for a kit agent, and for its kit commands and scheduled runs. A slot nothing fills fails at call time with a sentence naming the slot

## Business Rules

### Which skills exist and which are delivered

- **Kit agents only.** Only a kit agent's record carries skills; on a bare agent the field is absent, and every surface (the tab, the badge, the engine config, the Claude plugin, the skill runtime) asks whether the field is there rather than what kind of agent it is. A bare folder that runs natively on Claude loads whatever skills its own settings name, which is the engine's doing, not this feature's ([Bare Agents](bare_agents.md))
- **Only the agent's own sessions get its skills.** A chat conductor, an AI function, a synthetic chat runtime and Cinna's build session each run as an isolated folder too, and each is given no skills plugin
- **A skill is deliverable only when its frontmatter `name` equals its folder name and it has a description.** Claude names a plugin skill by its **folder** and OpenCode by its frontmatter **name**, so only a skill whose two agree is the same skill on both engines. A skill without a description gives the model nothing to decide when to open it. Both are core errors too (`name_mismatch`, `missing_description`); here they also decide what the engines can be handed. For a catalog skill the folder name is the pin's `name`
- **The other errors are core's, verbatim**: not a directory (including a **symlinked** skill folder, which is refused), no `SKILL.md`, unreadable (not UTF-8; a leading byte-order mark is tolerated), no valid frontmatter, no name, an invalid name (lowercase words joined by single hyphens, at most 64 characters), a name reserved by a platform command, a description over 1024 characters, an invalid `credentials:` block (the sentence names the first problem), and over budget
- **`cinna-tasks` is reserved.** An own skill or a pin by that name is an error and is never linked, so it can never shadow the platform's [`cinna-tasks`](../../jobs/tasks/task_protocol.md) skill on any engine
- **Warnings never withhold a skill.** `secrets` — files in the skill that look like they hold a credential (`.env` and its variants except examples, `credentials.json`, SSH private keys, `.pem` / `.p12` / `.pfx` / `.key`), each named on the card — `links` — symlinks inside the skill folder, each named on the card (desktop only: core's scanner skips links without a word, but Share refuses them; a link inside `.pytest_cache`, which Share never packs, is not one) — and `oversized`, a `SKILL.md` body above 64 KB. (Sharing refuses a skill with `secrets` or `links`; delivery does not.)
- **The budget is per agent, in name order**: at most 50 deliverable own skills and 16 MB of skill files. Past either cap a skill that would have been delivered gets the `budget` error instead; a skill already in error costs nothing. Catalog skills are not counted against it
- **What `skills/` holds besides skills is skipped silently**: plain files and dot-folders at its root are not skills (the kit ships `skills/README.md` as scaffolding). No `skills/`, or a `skills/` that is a file, is an agent with no own skills
- **Skills do not decide readiness.** A broken skill is a row with its issue; the agent still runs, without that skill. The folder validator reports the same problems `kit.py validate` does — every skill error, the budget, a malformed pin, a pin clash — as **errors** in the agent's findings, because the platform leaves such a skill out and refuses to publish it; but the scanner ignores those findings when it decides whether the agent is `invalid`. An error there removes the whole agent from the engine, and one broken skill is no reason to stop an agent that runs fine without it ([Agents Home, Scanner & Folder Index](folder_index.md#readiness-in-the-order-the-user-cares-about)). A missing download is not a validator finding at all
- **The validator, the Addons tab and the engines use one scanner.** The findings, the tab's rows and the engines' lists come from the same code, so the three cannot disagree about which skills are broken. Two validator findings have no row issue: a `version` the platform would not keep as written (not one line of text, or over 64 characters) is a warning, as in `kit.py`; and the row's `secrets`, `links` and `shadowed` warnings are not findings, because `kit.py` does not report them

### Pins

- **A pin is checked field by field, as `kit.py` checks it.** `package_id` the catalog's id shape, `name` a skill name of at most 64 characters, `package_uuid` a UUID (compared canonically, so the same package pinned twice in two spellings is still a duplicate), `revision_number` a whole number of 1 or more, `version` absent, null or text of at most 64 characters, `archive_sha256` 64 lowercase hex characters. Each malformed field is its own error. A `package_id` that reads as a different skill name than the pin's `name` is only a warning: the `name` is what counts
- **A pin's name must be free.** It may not be a folder under `skills/` (broken ones included — "Remove the pin or rename the folder"), a skill the platform provides (`cinna-tasks`), or another pin's name. Each is an error on the pin's row and in the findings, and a clashing pin is never delivered or downloaded, cached or not. Where an own skill and a pin share a name, both rows are listed, the own skill first. Add and Update refuse a name that would clash, decided again on a fresh read after the download
- **One pin per package.** Adding a package the agent already pins is refused ("This agent already has this skill.")
- **Add always pins the latest version** the catalog listing names. A package with no version, or one missing from the listing even after one refresh, is "not in the catalog any more"
- **Pins change only on a changeable agent (U9).** Add, Update and Remove refuse a team agent the person may only use ("Its skills change when the team shares a new version") and one whose access the listing does not say, rather than guess. Main decides from the folder's git `origin`, matched to the listing by repository id, with the `shared_remote` link as a second key; when git cannot answer, the link alone decides. Any other git remote is the developer's own business. The surfaces make a cheaper call and the verbs decide again: a row's `updatable` and `shareable` come from the `shared_remote` link and the cached listing alone, and the row's Update / Remove icons and the catalog menu's **Can use only** from the agent's sharing status (a Cinna team agent without `edit` or `maintain`, unknown access included). The failure this prevents: a local pin change in an agent they may only use would be a change they can never share, silently diverging from the team
- **Downloading needs only the agent (U7).** Anyone who may use an agent may fetch what its pins name, so Try again and the background fetch after a sharing verb have no changeability check
- **A pin change goes through the manifest guard.** The manifest is re-read and written only if it did not change underneath; one that changed while the skill was downloading answers "cinna-agent.json changed while the skill was downloading. Try again." and nothing is written. The rest of the manifest, unknown keys included, survives
- **Update keeps the pin's name.** The name is what the engines call the skill; the package's latest `package_id`, revision, version label and digest replace the old ones, and an old version label never survives into the new pin

### Downloads and the cache

- **Two digests, both checked, before anything is written.** The downloaded bytes must equal the server's `X-Content-SHA256` header (a missing header is a mismatch) **and** the pin's `archive_sha256`. Either mismatch is "The download did not match the published skill, so nothing was kept."
- **A safe reader, no tar tool.** The archive is unpacked by the desktop's own reader: regular files and folders only (any link, device or other type refuses the whole archive), no absolute path, no `..`, no backslash or NUL, no path twice (case-insensitively, as macOS sees them), every entry under exactly one root — core's `skills/<name>/`, or `<name>/` — named like the pin, a `SKILL.md` at its top, at most 10,000 entries, 16 MB downloaded and 64 MB unpacked, so a small download cannot expand into a disk-filling bomb
- **Complete or absent.** A revision is unpacked into a staging folder beside its place, marked, and renamed in in one step; a folder without a marker matching the pin (uuid, name, revision, digest) is not a cached skill. A revision another install landed first stands
- **Read-only.** Files 0444 (0555 when the archive marked them executable), folders 0555, so an engine or an assistant reading a skill cannot edit the copy every other agent uses
- **Never through a link.** The cache refuses a linked instance, package or revision folder both on read and on write, so a link planted in the cache cannot make it read, or write, somewhere else
- **Per server, found on any.** A download lands under the active profile's server; a lookup prefers that server's folder and then tries the others, because a pin names a package and a digest, not a server, and an agent folder is not tied to one profile. Only a marker whose digest equals the pin's counts
- **One download per pin at a time**, keyed by server, package, revision and digest, so two pins of one revision with different digests are two checks and one never answers for the other
- **A failure is a row issue, not a thrown error.** The sentence says what to do where there is something: sign in again, update the team agent first, that access to the skill was withdrawn, or simply that it could not be downloaded. Failures are kept in memory per pin and forgotten at restart; the row then reads "Not on this computer yet." again
- **A missing pin is fetched in the background, with a limit.** A pin that arrives without a click — a hand edit, a `git pull` outside the app, a restored folder — is fetched without anyone pressing Try again, for catalog and marketplace pins alike. Two triggers: **a turn** (when the agent's skills are built for a session, on every engine) fetches each missing pin **at most once per pin per app session**, so a pin that keeps failing is not retried on every turn, and **a profile becoming ready** (sign-in, profile switch, renewed credentials) forgets what was tried and sweeps every agent again, **including the pins whose last download failed** — a lapsed session (`reauth_required`) is exactly what renewed credentials fix. That session goes without the skill and the next one has it; the fetch is never awaited and never fails a turn. Nothing is tried, and nothing is marked tried, without a Cinna account, so a later sign-in still fetches. The row's Try again always runs, whatever was tried. Add, Update, Try again and the sharing verbs fetch as before
- **Marketplace pins follow the catalog's rules, with their own identity.** Name space, changeability, manifest guard, two-digest check (the server's `X-Archive-Sha256` and the pin's `archive_sha256`), safe reader and size limits are the catalog's. Specific to marketplaces: the pin carries no revision number — the digest is the version; Add pins the entry's current snapshot; a person may download a snapshot exactly when discovery shows them its entry; and the sharing verbs and Get fetch marketplace pins beside catalog ones. A marketplace pin may not share a name with an own skill, a platform skill, a catalog pin or another marketplace pin; `cinna-agent.json` with such a pin is flagged by the validator as `kit.py` would
- **The unused-snapshot clean-up is per cache.** At app start the catalog and marketplace caches each remove the folders no registered kit agent pins, under the same keep-everything-when-in-doubt rule
- **A revision no agent pins is removed at the next start, never sooner.** Once per app start, before any profile is active and so before any turn or schedule can hold a path into the cache, every cached revision no registered kit agent pins is deleted, on every server's folder (a lookup falls back across them, so a pin keeps its revision on all), with the package and server folders it leaves empty. Remove and Update never delete: a turn running at that moment may still read the old revision. Pins are read from every registered root as the agents list scans it, so a kit folder the index has not seen yet still keeps its pins; a bare folder pins nothing
- **When in doubt, nothing is removed.** If any agent's pins cannot be read — a manifest gone or unparsable, an indexed agent whose root the scan does not reach (a drive not mounted) — the whole clean-up is skipped and logged: deleting a revision someone still pins is worse than keeping a stale one. A start with nothing cached reads no agent's pins at all. A staging folder is removed only once it is stale (ten minutes), dot-names are left alone, and a link anywhere in the cache is removed as a link, never followed. A pin whose revision was cleaned away — one that arrived while its agent was unreadable, say — reads "Not on this computer yet." and **Try again** fetches it
- **Local installs are reported, best effort.** After Add, Update and each fetch, main tells core that this device holds the revision in the agent with that manifest id (`host_manifest_id`); after Remove, that it no longer does. Never awaited, never failing the verb, and skipped for a manifest without an `id`

### Plugin skills

- **A pinned plugin's skills join the agent's delivery, and nothing else about them is a skill pin.** The skills in a plugin's cached `skills/<name>/` ([Marketplace Plugins](plugins.md)) are given to every engine through the same plugin of links, `skills.paths` and prompt listing as the agent's own, catalog and marketplace skills, as rows of source `plugin`. They are not rows of the Skills section: the plugin's own row on the Addons tab lists them, each with its switch
- **The agent's own skill wins a name clash.** A plugin skill whose name is an own, catalog or marketplace skill's, a platform skill's (`cinna-tasks` and the other reserved names) or an earlier plugin's is not delivered, and the plugin's row says why ("This agent already has a skill with this name, which wins." / "Another plugin of this agent has a skill with this name." / "This name is reserved for a skill Cinna provides."). Letting the plugin win would have meant installing a plugin silently replaced a skill the user wrote
- **The same deliverable rule applies.** A plugin skill is handed over only with no error: its frontmatter `name` equals its folder and it has a description. A skill the user turned off on the pin (`disabled.skills`) is not delivered. A plugin whose cached copy no longer matches what was unpacked delivers nothing at all
- **Only a plugin on this computer is delivered.** One that is not cached is fetched in the background and the next session gets it

### Delivery

- **Each engine gets the skills by its own mechanism:**
  - **Claude** — the agent's skills plugin, passed beside the `cinna-tasks` plugin in the same session options, on the isolated branch only (a native folder loads its own skills from its settings). A plugin passed that way is not a user or project setting, so the isolated branch's `settingSources: []` does not hide it. Claude offers each skill as `<plugin>:<folder>`, the plugin named after the agent's slug when that is a clean kebab name, else `agent-skills`
  - **OpenCode** — the links folder is added to `skills.paths` after the platform skills' own folders (`cinna-tasks`, `cinna-artifacts` while the instance keeps artifacts, and `cinna-dashboards`), each deliverable skill is allowed by name in `permission.skill` beside `cinna-tasks`, and reads under the links folder are allowed in `external_directory`, because OpenCode reports a linked skill's location there, outside the project. When the agent links a catalog skill, reads under the catalog-skill cache are allowed too, but the cache is never a skills path: OpenCode checks the literal path a tool names, and a model quoting the real cache path would otherwise stop the turn for a click. Without the allows, every opening would stop the turn under the agent's ask-by-default profile ([Permissions](permissions.md))
  - **Codex** — no skill loader, so the prompt lists each skill and the path of its `SKILL.md`: inside the agent folder for an own skill, the absolute cache path for a catalog one
  - **Antigravity** — the same listing with paths. Its loader reads only skill folders inside its own home, and the agent's skills are not copied there. The platform's `cinna-tasks` is: an isolated folder's home (`<folder>/.cinna/antigravity`) gets a copy under `config/skills/cinna-tasks/`, so the prompt names it as a skill. The copy is refreshed only when the source's contents change (a digest stamp beside it) and is swapped in by rename. A native folder runs on the user's own `~/.gemini`, which is never written to, so its prompt names `SKILL.md` by path as on Codex ([The Antigravity Engine](antigravity_engine.md#instructions))
- **OpenCode is never pointed at the agent's real `skills/`.** It registers every `SKILL.md` under a path by its frontmatter name and a later path wins, so it would register broken and reserved skills too, and an authored `cinna-tasks` there replaced the platform's skill. The links folder holds only deliverable skills, which is why the same folder serves both engines
- **Links, not copies.** An edit to an own `SKILL.md` reaches the engine through the link with nothing rebuilt, and the links folder is rebuilt only when the *set* of deliverable skills, a link's target (a re-pinned revision), or the plugin's name changes. On OpenCode the set is part of the generated config, so adding or removing a skill replaces the warm process and an unchanged set never does
- **The prompt never promises what the engine was not given.** "Available through the skill tool" is said only when the links folder was written; when it could not be, the prompt falls back to the Codex-style listing with paths, which is true on every engine. The `cinna-tasks` stub has no such fallback, which is the gap [The Cinna Task Protocol](../../jobs/tasks/task_protocol.md) names
- **A failure to deliver skills never fails a turn.** A plugin that cannot be written is a session without the agent's skills, logged

### Credentials a skill declares

- **Shown on the row, judged in the scan, never blocking.** The scanner judges each declared slot against the agent's attachments — filled only by a ready attachment of the slot's type whose Service URI is exactly the slot, no name fallback — and records it on the row's credential (`filled`). Each **Needs** chip wears the shared status glyph for that judgement: ✓ where it is filled, as a credential row says *connected*, and a warning triangle where it is not (its tooltip says whether nothing is attached or the attachment is not ready). A slot the scan did not judge has no glyph. Never an error tone: an unfilled skill slot is a warning. The gaps are listed in **Finish setting up**'s **Skills** group ([Service Credentials](../service_credentials/README.md#skill-credential-slots)). A missing slot never changes readiness and never opens that dialog by itself, as in core: the script fails at call time instead
- **Announced by the badge and the row, never by a banner.** A deliverable skill's unfilled slot counts toward the Addons badge and puts **Finish setup** at the end of that row's **Needs** line. Neither the agent page's strip nor the composer's notice panel raises a line for it: the agent is ready, and a banner is for something that needs attention before it runs ([UX rules](../../development/ui_guidelines/ux_rules.md), rule 2)
- **Only deliverable skills' slots count.** A skill no engine is given needs no credential
- **The skill runtime is a copy.** The `core.cinna_api` shim ships inside the app and is copied once to `<userData>/skill-runtime/<content hash>/`, rebuilt only when the shipped tree changes; that copy goes first on `PYTHONPATH`. Python writes `__pycache__` beside a module it imports, and the shipped folder sits inside the signed app bundle, which must never change. An agent's own `PYTHONPATH` entries are kept after it, so a `core` package of its own is shadowed by the shim. A copy that cannot be made is logged and the engine runs without it rather than with the bundle on its path

### Sharing

- **Share is offered, not enforced, by changeability.** The row offers it only on a deliverable own skill, with a Cinna account active, on an agent this person may change (a share writes `SKILL.md` and `publications.json`, which they could not send back in a team agent they may only use), and for a later version only with `edit` or `maintain` on the package. The publish verb re-checks it too, before anything is read or sent: an agent linked to a Cinna team agent the cached listing gives only `use` is refused `read_only`, and one the listing does not have `access_unknown`, each saying nothing was sent. It decides from the `shared_remote` link and the cached listing — the rule the row's `shareable` is drawn by — not the git `origin` the pin verbs also read. The row is the renderer's; without the check a stale row, or any caller of the IPC, could write `SKILL.md` and `publications.json` into a team agent the person can never share back. The preview has no such check
- **The archive is deterministic.** One top-level `<name>/`, members in byte order, mtime 0, owner 0, modes collapsed to 0755 / 0644, gzip mtime 0 — the same folder packs to the same bytes on any computer. Junk folders core drops (`.git`, `.venv`, `node_modules`, `__pycache__`, tool caches) and `.pyc` / `.pyo` are left out
- **Who can use is the agent's People list, over the package.** The same grants and visibility routes as a desktop agent (`…/catalog/items/{uuid}/grants`, `PATCH` visibility), addressed by the package uuid from `publications.json`; the visibility and maintainers come from the cached catalog listing. Everyone is public visibility, any list without it `users` (an unlisted public skill is left public, as for an agent). The grants go first, so a refused list changes nothing; after a write the listing is read again, so the row's access and the catalog's detail follow. Offered only to `maintain`: core lets only a maintainer change access, and an icon that always fails would be one more control that does not earn its place
- **A first share chooses who can use it; a later one never touches access.** **Everyone** is sent as public visibility, and people at Can use are then not sent (everyone can already use it; the dialog strikes them through in place and says so); named people alone make it visible to those users. A later version carries the recorded package and no visibility or grants
- **A skill shared before is found again.** A first share that core answers with "package exists" (the person's own package of that name, shared from another folder or with a lost record) is retried once into that package as its next version, without visibility or grants, because core would apply them to the existing package and could narrow a public one
- **Credentials provided for everyone are kept only when named.** Core keeps only the slots a publish names, so the dialog preselects each slot the latest version had provided and says when one could not be carried over; an unnamed slot becomes each person's own
- **Afterwards, two file writes.** The returned version label replaces the `version:` line of `SKILL.md` and nothing else, and `publications.json` → `skills[]` gets the entry for this server and name (replaced in place, unknown keys kept; the file created with `publications: []` when absent). If either cannot be written, the share still happened, and a later share finds the package itself

- **The record is the revision the folder holds, with core's hash of it.** Share, Make editable and Get each write the `publications.json` entry (`revision_number`, `content_hash`); the sync state is that hash against a hash of the folder. A hash the catalog does not send (an older core) is replaced by the copy's own, which hashes as core's does. A copy that does not match a hash the catalog did send is thrown away: the person's files must be the published ones, or the next "changed" would be a lie
- **A swap is staged, and a crash leaves it recoverable.** Make editable and Get write the new files under a dot-name beside `skills/<name>/` (`.<name>.cinna-staging-…`, which the scan and the watcher skip), then move the old folder aside (`.<name>.cinna-previous-…`, or the backup folder for Replace), rename the new one in and update `publications.json`; any failure after the move puts the folder and the record back. A crash can still leave the folder set aside under a dot-name with no `skills/<name>/`, which the scan skips, so the skill would just be gone. At the start of every Get and Make editable, and once per app start over every folder agent, the leftover sweep puts the newest set-aside folder back where `skills/<name>/` is missing and removes staged copies older than ten minutes (a younger one may belong to a verb still running). A set-aside folder it does not put back (beside a folder that exists, or an older one) is moved to the backup folder as `…-set-aside`, never deleted: it may hold the only copy of edits, and left in place it would come back as the skill the day the person removed the real one
- **Make editable never touches the person's files.** It refuses when anything is at `skills/<name>/`, and a failure after the copy removes the copy and restores the ledger byte for byte
- **The dropdown of a people search is not inside the dialog.** In every sharing dialog the search's answers are portaled to the page and fixed to the field, flipping above it when there is more room, and re-measured on resize, scroll and when the list or dialog changes size. Inside the dialog's scrolling body an absolute list was cut off at the dialog's edge. Because it lives outside the dialog, it is marked (`data-dialog-popover`) so a press on it does not count as a press outside and dismiss the dialog

### Skill links

- **A link is taken only when it is the whole thing.** The grammar is strict: after trimming whitespace and one pair of `<>` (how mail clients wrap a link) the text must be exactly one link, with `https` (or `http` on loopback for development), no credentials, exactly `/get/skill/<id>` and no query or fragment. A link inside a sentence stays text, and so does anything that is not exactly a link. Without this, pasting a message that mentions a skill would be swallowed by the composer. **Cmd/Ctrl+Shift+V** pastes a link as text. A paste carrying files is never read as a link
- **The offer is never an installer.** Add is the unchanged `catalog-skills:add`, and its own refusals are the final word: the verdict on the row may be stale by the click. The lookup decides nothing Add does not decide again
- **The answer is data, never a thrown error**, because a thrown code does not survive IPC. Every outcome, an unexpected failure included, is a state the row can show
- **The server in a link is matched to a profile, never trusted.** The link's origin is reduced like the connect link's (`url.origin`, the parse and not a substring), then matched to a Cinna profile this app has. A profile stored on exactly that origin matches without the network; otherwise each profile's **own** `/.well-known/cinna-desktop` says which origins its server answers on (the stored one, its token and userinfo endpoints', and `web_origin`), so a web-origin link finds a profile stored on the backend and the reverse. The link's origin is **never** the thing asked: a pasted or clicked link must not make the app contact a server it names. All profiles are asked at once within one bounded wait, and the request is aborted at its end. Two other profiles claiming one origin match **none** — a guess would offer to switch to the wrong account. A server that could not be asked answers **offline** (Try again), not not-connected: the person may well be on it, and "Connect…" would send them to sign in to what they already use; the active profile's silence also stops another profile taking the link. Only the active profile's catalog is read; another profile's cached listing may supply a title for the Switch sentence and never answers access
- **The deep link has its own buffer.** `cinna://skill/…` is routed by its action to its own one-intent slot, separate from the connect link's. A shared slot would let a skill link evict a connect intent the person is reading in its confirm step, and that step's later consume would drop the wrong one. See [The `cinna://connect` Link](../../auth/onboarding/connect_link.md#one-funnel-two-slots)
- **A link opened from the OS goes where the person is.** It raises the offer on the composer on screen (a chat, a folder or remote agent's new-chat page, a dashboard's open chat panel) or, when the view has none, on a new chat. It is held through sign-in, onboarding and an OAuth flow in flight, then raised once
- **The offer stays only on the composer it was raised on.** Opening another chat, New chat, the first send on the start screen, another agent's page or a view with no composer puts it away (one App-level rule, because the start screen's composer and a chat's are separate). The exceptions are an offer mid-move for Switch, and the offer coming back after New agent with this skill is cancelled
- **A cancelled New agent with this skill loses nothing.** The queued skill is taken off at **Create**, so closing the dialog after a create raises nothing; closing it any other way raises the offer again on the composer it came from and restores the sidebar tab the dialog switched. A failed create puts the queue back. The add after the create runs outside the dialog, which is gone as the agent lands; the agent is kept whatever happens, and a refused add raises the offer again on the new agent's new-chat composer with Add's own sentence
- **A raised offer leaves [Minimal View](../../chat/minimal_view/minimal_view.md)**, whose cloud has no notice panel: nobody would see it
- **Row height never changes.** The row is one truncated line held one button tall (the whole sentence is its tooltip), with its buttons and × at the end of the line, whichever answer arrives; an Add or Switch failure takes the line's place in the danger colour rather than adding one; pending labels (*Adding…*, *Switching…*, *Trying…*) share a cell with the label they replace. Without it the composer jumped as the lookup answered ([ux rules](../../development/ui_guidelines/ux_rules.md), rule 1)

### What is not built

- **A readiness line for skill slots.** An agent whose only gap is a skill slot shows nothing on the agent page's strip or in the composer's notice panel (above); the way into its Skills group is the row's **Finish setup**
- **A fetch of missing pins on opening the page.** Only a turn and a ready profile trigger one
- **Pinning an older marketplace snapshot**; Add and Update always take the entry's current one
- **Pinning a specific older version** or choosing a version on Add; **deleting a shared skill** from the catalog. Access after the first share is changed through **Who can use** (above), not in the Share dialog
