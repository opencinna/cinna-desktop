# Team Sharing of Folder Agents

## Purpose

Let a team work on the same folder agent from several machines. A `Local/<slug>/` kit agent can be put in the active Cinna account's catalog, where it is listed as an agent that **Runs on your computer**; a teammate **Gets** it, both of them change it, and the app moves those changes between the machines with three verbs — **Update**, **Share changes** and, when both of them changed it, **Bring together**, which has the agent itself read the two sides in a chat before anything is shared — and, when the two sides do not fit together at all, a two-button choice. Underneath it is git, and the user never has to know that.

## Core Concepts

- **Shared agent** — A kit agent directly under a root's `Local/` whose folder is **its own** git working tree with an `origin`. That is the whole definition: an agent a developer cloned by hand is recognised exactly like one the app fetched. A folder inside an enclosing repository (the workshop's), a bare agent, and an agent outside `Local/` are never shared
- **Team version** — What the team has: `origin`'s `main`. For a Cinna remote, the catalog listing's `desktop.head_sha` says where it is without a fetch
- **Team library** — The desktop agents in the active Cinna account's catalog: the items of `GET /api/v1/catalog/items` with `kind: agent` and `runs_on: desktop`, each with the caller's access (`use`, `edit`, `maintain`), its visibility, whether the catalog lists it, its maintainers and its latest version. The name is this doc's and the code's (`libraryService`, `useTeamLibrary`, `TeamLibraryGet`) for that slice of the listing; **the user never reads it**. They see one [Catalog](../bundles_catalog/bundles_catalog.md) dialog, where these agents sit beside agents that run in Cinna and skills under a **Runs on your computer** badge, and every sentence says *the catalog*.: one catalog, so there is no source name to learn and no second place to look for an agent
- **Version** — What the catalog numbers each accepted send of a team agent: **Version N**, with who shared it, when, and the notes it was shared with. An entry has none until its first send
- **Catalog id** — The entry's `bundle_id` on the server (`<reversed host>.<8 hex of the manifest id>`, core mints it). Recorded per machine in the agent's `app-data/desktop.json` and shown read-only in the Sharing tab; the user never types it
- **Local install** — The catalog's record that this computer holds a team agent at a given version, keyed by a per-installation device id. Core counts them, and refuses to delete an entry while other people hold it
- **Remote kind** — `cinna` when `origin` is `…/git/<repo_id>.git` on a git origin that the instance of a Cinna profile on this machine uses: either its own origin or one it named itself (see [An instance's git may live on another origin](#an-instances-git-may-live-on-another-origin)). `external` covers anything else (the user's own GitHub, GitLab or SSH remote, authenticated by their own git setup)
- **Get** — Fetch a desktop agent from the catalog into the agents home's `Local/<slug>/`
- **Update** — Bring the team's changes in, when they apply cleanly
- **Share changes** — Record everything this machine changed under one note (pre-filled by an AI summary) and send it to the team. When the team changed the agent too, its first step is Bring together
- **Share with the team** — Put a not-yet-shared agent in the catalog, in place, for the people chosen (and everyone on the server, when ticked) and nobody else
- **Use the team's version** — The answer to a collision: this folder becomes the team's version, and what was here is kept beside it as `<slug>-mine`, named "*Name* (my copy)"
- **Bring together** — The answer when the team changed the agent and this machine has changes it has not shared, on different lines: the app records this machine's loose edits as a version, combines the two sides, and opens a chat in which the agent reads both and makes the instructions consistent again. Offered by a banner when the agent's chat opens, and as the first step of Share changes
- **Session** — The time between Bring together and **Finish** or **Discard** (an *adoption session* in the code), recorded in the folder's `app-data/desktop.json`. While it lasts the agent reads **Bringing team changes together**, and nothing else moves its history
- **The brief** — The session's first chat message, written by the app in the user's voice: the team's versions since the two sides last matched and this machine's, each with its note, author, date and files, the changes to the files that carry instructions, and what the agent is asked to do, ending with a section headed *Summary of what I did*
- **Finish** — Checks the folder, lifts the agent's own summary from the session's chat, ends the session and opens Share changes with that summary in the field. It records nothing and sends nothing: the session's edits stay loose until Share changes records them under the note the user read
- **Discard** — Puts the folder back exactly where the session began, after a confirmation. This machine's own changes, recorded when the session began, stay
- **Not now** — Declines the banner's offer for the team version it stands at; the banner returns once the team moves again. Share changes still offers Bring together
- **Share badge** — A shared agent's state with the team, as the first badge in the agent page's chat-mode row of runtime badges, with **Update** and **Share changes…** beside it when the state allows, or **Finish…** and **Discard** during a session. A click opens the Sharing tab
- **Sharing tab** — The agent page's Settings tab for a shared agent, and only for one: **Where it's shared**, **People**, **History** and **Remove sharing**
- **People** — Who may get the agent from the catalog, and with what access: **Can use** (`use`), **Can edit** (`edit`), **Maintainer** (`maintain`). The catalog item's grants, read and written whole, plus **Everyone on this server**, which is not a grant on the server but the item's `public` visibility
- **Remove sharing** — Disconnect this folder from the team. It stays on this computer as an ordinary agent, history and all; a maintainer may also delete the entry from the catalog
- **Remove from this computer** — Deleting a shared agent: the folder goes to the Trash, the team's version is untouched

## User Stories / Flows

### Getting an agent from the team

1. On a Cinna account, **Agents → + → Install from catalog** opens the **Catalog**. Shared agents are tiles in the one grid, among agents that run in Cinna and skills, each with the **Runs on your computer** badge; **Agents** narrows the grid to agents of both kinds
2. A shared agent's tile has its name, **Version N**, **by** its maintainers, its description and the credentials it needs, with **Get** — or, when this machine already has it, **Open**, and **Update** beside it while the team has moved past this computer's copy. Its detail adds every version with who shared it, when, and its notes
3. **Get** fetches the agent into `Local/<slug>/`, the dialog closes, and the user lands on the new agent's page. A refusal stays on the tile it came from and closes nothing
4. If the agent needs a credential this computer does not have, the page opens **Finish setting up *Name*** (below)
5. Opening the dialog re-reads the catalog, so what the user browses is the team's list as it is now

### Seeing where an agent stands

1. In chat mode, a shared agent's page shows a share badge first in the row of runtime badges under the path. It says one of: **Up to date with the team**, **N changes not shared**, **The team changed this agent**, **You and the team both changed it**, **Bringing team changes together**, **No longer shared**, **Shared on another account**, or, when the read itself failed, **Couldn't check with the team**. Both changed, no longer shared and a failed read are in the warning colour; a session in progress is not, since the user chose it. The full sentence is its tooltip
2. Beside it sit the buttons that state allows, at the badges' height: **Update** when the team moved and nothing here is in the way of a clean combine, **Share changes…** when there is something of this machine's to send and the account may change the team's version, and during a session **Finish…** and **Discard** in place of both
3. Clicking the badge opens **Settings → Sharing** and moves focus to that tab. There the same state is the full sentence (**N changes you haven't shared**, **Bring together to combine yours with the team's — you both changed this agent**, …), with the same buttons beside it
4. The sidebar row carries nothing. Sharing is a fact about the agent, read on its page, not something to scan a list for
5. An edit to the agent's folder, by the agent, an editor or the page itself, re-reads the badge at once: **N changes not shared** and **Share changes…** appear without leaving the page. That re-read never reaches the network

### The Sharing tab

1. **Where it's shared** — the state and its buttons (during a session **Finish…** and **Discard**, the label reading just **Bringing team changes together**; below the divider a **Session** row with **Open the session** as an accent link, only while the session's chat still exists), then: the server (a Cinna instance's host, which opens it in the browser, or **Your own server** and the remote's address for an `external` remote); for a library agent, **Name in the catalog**, its folder name, **Your access**, its maintainers, then the latest version as three facts — **Version** *N*, **Shared by** *who*, **Shared on** *when* — each only when the catalog says (an entry not sent to yet shows none), and last the **Catalog id**, read-only and truncated with the whole id in its tooltip. When the catalog itself narrows who can get the agent, one more fact, **Who can get it**, says so: *Only people who can edit it — it isn't listed in the catalog*, or *— it's private in the catalog*. Opening the tab re-reads the library, so these are the library's facts as they are now
2. **People** — only for a Cinna team version on the active account that the library still lists. A maintainer sees everyone with access, each with an access select; a grant can also be **Everyone with the *X* role**, listed and removed like a person. **Everyone on this server** is a row too while the entry is public and listed: always **Can use**, with no select (that is what sharing with everyone means), and a remove like any other row. Nobody changes their own access here. A maintainer is already named under **Maintainers** above, so their own row is left out of People; anyone else's own row reads **You** with their access shown read-only and no remove. Every change still saves the whole list, own grant included, unchanged. With no one else on it the list reads **No one else has access yet.** — or **No one but the maintainers has access yet.** when another maintainer is named above Removing anyone else asks in the row (**Remove *X*'s access?** with **Cancel** and **Remove**), not in a dialog. **Share with a person…** opens a search by name or email: two characters at least, asked once typing settles, people who already have access left out. The person picked joins as **Can use** unless the select says otherwise. Beside it, while the agent is not public (no Everyone row, and the catalog entry not `public`), **Share with everyone** adds the Everyone row in one click, saved like any other change: the People controls hold while it saves, the button shows the spinner, a refusal is the server's sentence under the list (where the list's own refusals go, so nothing above moves), and closes nothing, and on success the row appears and the button goes. Anyone who is not a maintainer sees only the maintainers and **Only a maintainer can change who has access.**
3. **History** — this folder's versions, newest first, at most thirty: each version's note, who recorded it and when. A version recorded here and not on the team version yet carries **Not shared yet**. It is a list to read; nothing in it is clickable
4. **Remove sharing** — last, and asking before it does anything (below)

### Updating

1. **Update** — from the share badge, the Sharing tab, the catalog tile, or the Inbox card — brings the team's changes in, and the agent's page, sidebar and catalog reflect them at once
2. Edits here that are not shared yet are in the way: Update refuses — whenever this folder has versions the team does not have and the team has moved, not only for loose edits — and says to bring the team's changes together first (*Share changes will offer it*), which is also what the Inbox card shows. The agent page and the Sharing tab do not offer Update at all while both sides have moved; the catalog tile and the Inbox card still do, and get that refusal
3. When the team changed this agent too and the two do not combine, the Inbox card and the catalog tile take the user to the agent page, where the choice lives
4. An Update that brought changes attaches matching credentials like a Get, and opens **Finish setting up *Name*** only if a required slot is now missing that was not missing before the Update (below)
5. After a **Get**, an **Update** or **Use the team's version**, the catalog skills the agent pins are fetched in the background — the agent's access is what allows the download. A skill that cannot be fetched shows on the agent's Skills section; the verb itself never fails because of it ([Agent Skills](skills.md))

### Finishing setup

1. After a **Get**, an **Update** that brought changes, or **Use the team's version**, main attaches the active account's cloud credentials that fit a missing slot beyond doubt — exactly one candidate — without asking
2. The agent's page then opens **Finish setting up *Name***: each slot's state, the account's credentials that fit it with **Use this**, and fields for the `.env` names it declares. After a **Get** it opens whenever a required slot is still missing. After an **Update** or **Use the team's version** it opens only when a required slot that was not missing before is missing now, so a slot the user already chose to leave for later does not bring it back on every Update. **Finish later** closes it and the agent stays usable, with the composer's missing-credentials row
3. The same dialog opens any time from **Finish setup** on that row of the composer's notice panel, for as long as a credential is missing

### Sharing changes

1. **Share changes…** opens one field, **What changed**, editable from the first frame with "Writing a summary…" as its placeholder. An AI summary of the changes fills it, unless the user has already typed. After Finish the field opens with the session's own summary instead, and no AI summary is asked for
2. When the team changed this agent too, the dialog opens on a step before the field: the banner's sentence and **Bring together** in place of Share ([below](#bringing-the-teams-changes-together)). Nothing is sent from that step
3. **Share** records everything not ignored, and sends it. If a teammate shared first, the app brings their version in and tries once more — but only when their versions touch none of the files this machine's unsent versions touch. When a file is in both, the send stops with **The team changed this agent again while you were sharing. Bring the changes together, then share.** and the dialog shows the Bring together step
4. If the two sets of changes do not fit together, the share dialog gives way to **The team changed this agent too**: **Use the team's version (keep mine as a copy)** or **Keep working on mine (share later)**. The recoverable one has focus
5. **Use the team's version** replaces this folder with the team's, keeps the old folder as "*Name* (my copy)" in `<slug>-mine`, and says so in the page's note — naming any per-machine file (a credential, say) that could not be copied over

### Bringing the team's changes together

1. The user opens a shared agent's chat while the team has changed it and this machine has changes it has not shared. A banner sits above the messages from the first frame: **The team changed this agent and you have changes you haven't shared. Bring them together before working?**, with **Not now** and **Bring together**. It is decided when the page opens, from the list of statuses the sidebar already holds; a state that becomes *both changed* while the page is open waits for the next open, or for Share changes, whose first step is the same offer
2. **Bring together** records this machine's loose edits as a version of their own (**Changes made before bringing the team's version in**), writes the session's record, and combines the team's versions with this machine's. Like an Update, it then attaches matching credentials, opens **Finish setting up *Name*** only for a required slot it made missing, and fetches the catalog skills the team's version pins. When the two sides do not combine, nothing is combined: the record goes, the recorded version stays, and **The team changed this agent too** opens with its two buttons
3. A new chat with the agent opens, titled **Bringing team changes together**, whose first message is the brief. It is the agent's ordinary chat, on the engine it already runs with: the agent edits its own files and may ask the user a question. The badge reads **Bringing team changes together**, with **Finish…** and **Discard** beside it, and the Sharing tab adds a **Session** row with **Open the session**, present only while that chat exists (deleting it, or having it out of the active profile's sight, removes the link; the session stays). If the chat could not be started, the page says so and the folder is still brought together: Finish or Discard from the badge
4. **Finish…** checks the folder and, when it is whole, lifts the agent's *Summary of what I did*, ends the session and opens **Share changes** with that summary in **What changed**. The user reads it, may rewrite it, and presses **Share**, which records the session's edits under that note and sends. Finish itself records and sends nothing, so in between the agent reads *N changes you haven't shared*. A folder that cannot finish says why in the page's line (or the Sharing tab's, while it is open), and the session stays
5. **Discard** opens **Discard the session's changes**: what is kept first — the team's version and this machine's own recorded changes — then what is dropped, the edits made since the session began. **Cancel** has focus. **Discard changes** puts the folder back where the session began and ends the session
6. **Not now** takes the banner away and remembers the team version it was declined for. The banner returns once the team shares again; until then Share changes is where Bring together is offered

### Sharing an agent with the team for the first time

1. **⋯ → Share with the team…** on a kit agent that is not shared yet, on a Cinna account whose catalog listing answered
2. The dialog asks a **Name**, pre-filled from the manifest, then who gets it: **Everyone on this server can use it**, an unticked checkbox above the people search (the same words and place as the skill Share dialog), and **People**, found by name or email and each added as **Can use** unless changed. The list starts as **Only you, for now.**, or **No one named — add people who may change it.** while Everyone is ticked. Unlike a skill, a person at **Can use** is still sent beside Everyone and is not struck through: core keeps an agent's grants under `public`, so removing Everyone later in People leaves them their access. There is no description field: the manifest's description is sent as it is. **Share** creates the agent in the catalog for the sharer (as maintainer) and the people chosen — one request, so it exists for nobody else at any moment — and only then sends this folder as its first version. The folder stays where it is. An agent whose `cinna-agent.json` has no `id` is refused before anything reaches the server, since the catalog binds the entry to that id for good
3. An agent whose team version was **deleted from the library** is offered Share with the team again. Its badge reads "No longer shared". Main first re-reads the library rather than trusting the cache. The restart goes ahead only when all three hold:
   - that read was a real listing, not a `404`/`403` standing in as empty
   - it does not list the entry
   - the old link is a Cinna remote of the active profile's instance

   The old link (`origin`, and the `shared_remote` link in `desktop.json`) is dropped **only once the new library entry exists**. A refused preflight or a failed create therefore leaves the folder linked to its old team version, exactly as it was. The folder's history stays: each version keeps its note, author and date, and only what never travels (`credentials/`, `app-data/`, `.claude/settings.local.json`) is taken out of it (see [never travel](#the-credentials-and-app-data-folders-never-travel-to-a-team-library-whole))
4. A folder that cannot be sent — busy with a turn, or already tracking a file that can hold a secret — is refused **before** the library entry is created, so a refusal leaves nothing on the server

### Removing a shared agent

1. **⋯ → Remove from this computer…** opens a dialog of that title: the folder goes to the Trash, the team's version stays in the catalog, untouched, and the user can Get it again any time
2. While this machine has changes the team does not have, main refuses and names up to three of the files: removing would lose them

### Removing sharing

1. **Settings → Sharing → Remove sharing…** opens a confirmation in the danger tone, focused on **Cancel**. It says what stays first: the folder, its files and its history stay on this computer, the agent becomes an ordinary one that can be shared again later, and teammates keep their own copies
2. A maintainer of an entry the library still lists also sees an unchecked **Also delete it from the catalog — teammates can no longer get it**
3. **Remove sharing** disconnects the folder; the badge and the Sharing tab go, and the page's note says *X* **is no longer shared with the team.** A refusal stays in the dialog and closes nothing
4. The server refuses the delete while other people have the agent on their computers, in its own words (**1 person uses this. It can be removed once nobody does.**). The dialog then adds **Untick the box above to remove sharing from this computer only.**: the way out needs nobody's say. Ticking or unticking the box clears the refusal, since it answered the other choice
5. Unshared changes do not stop it, unlike Remove from this computer: nothing on this machine is lost

### A teammate changed something

1. The Inbox lists **Update available for *X*** with the **Runs on your computer** badge, **Version N**, who shared it and the date, when the catalog says, and **Update**. The agent's name opens its page. It is the same card an agent that runs in Cinna gets when its install is behind ([Bundles Catalog](../bundles_catalog/bundles_catalog.md#update-available)): one kind of notice for one kind of event, whichever computer the agent runs on
2. After Update the card says **Updated. This agent now has the latest version.** and stays until the user leaves the Inbox

### A blocked job needs an agent the team has

1. A job bound to a folder agent this machine lacks is blocked ([Local Agents Are Not Synced](local_only.md)). When the Team library lists an agent with that dependency's manifest id, and this machine has no copy, its row offers **Get *X* from the catalog**
2. After the Get the dependency resolves against the new folder and the job unblocks

## Business Rules

### Whether an agent is shared is never stored

Every time, the app reads back from `origin` whether an agent is shared, where its team version lives and which repository it is. The caller's access and the team's latest version come from the cached library listing, and that listing is never persisted. There is no table and no column. A stored "is shared" would disagree with the folder the first time a developer ran `git remote remove` in a terminal, and the folder is what the agent runs from.

Four things are written down, and none of them is the answer to "is this shared":

- **`cinna.server` in the folder's `.git/config`**: the instance a folder was shared through or came from. It is a hint for choosing a profile and never makes a remote trusted (see [below](#an-instances-git-may-live-on-another-origin))
- **The trust file in main**: which git origins each instance has named
- **`shared_remote: {kind, repo_id, clone_url, bundle_id}` in the agent's `app-data/desktop.json`**: the per-machine link that contract 1.8.0 names in `shared_remote.local_state`, with the catalog id contract 1.10.0 adds. It is written on Get and Share with the team, and cleared on a kept copy, on Remove sharing and when Share with the team starts over. It is there for other hosts that read the folder. The desktop reads back only its catalog id, and only to show it; it decides nothing from the link, because a developer's own clone has `origin` and no such link
- **The device id in main**: one random id per installation, which names this computer in the catalog's local installs (below)

### The library is polled, not pushed

There is one listing, `GET /api/v1/catalog/items`, read once and kept whole: every kind the caller may see (cloud agents, desktop agents, skills), with the team library derived from the desktop agents in it. A desktop agent that lacks what a Get needs (`desktop.repo_id`, `clone_url`, `slug`) is left out of the team library. Core emits two realtime events for the catalog, `catalog.updated` after an accepted send and `catalog.granted` to people who just gained access, each to the reader's own room. **The desktop does not consume them**: it polls. Main lists the catalog when a Cinna profile becomes active (and on wake), every five minutes while it stays active, and on demand: when the catalog opens, and after Update, Share changes, Share with the team and Use the team's version. The renderer is told (`sharing:changed`) only when the set of desktop agents, their heads, latest version numbers, visibility, listing or the caller's access moved, not on every poll. A move in any other item of the listing (a cloud agent's install, a skill's version) is the lighter `catalog:items-changed`, which re-reads the Catalog dialog and the Inbox and none of the sharing reads: every shared agent's status re-reads on `sharing:changed`, and costs git to answer. Reads can overlap (the poll, the catalog opening, an action's own re-read) and answer out of order; an answer older than one already taken is dropped, and its caller gets the newer listing. The Sharing tab's People and History are re-read on that same signal, and after any action that changed them; they have no poll of their own. Polling stops on profile switch, sign-out, sleep and an expired session; re-activation starts it again.

A listing is what lets a shared agent say **The team changed this agent** without a network fetch per folder per screen. For an `external` remote there is no listing, so its page fetches on open — at most once a minute per agent, whatever triggered the read.

Core's listing shows a new head a few seconds after a send lands, not at once. A teammate whose app re-reads the library straight after a send still gets the old head, and its badge still reads **Up to date with the team** until a later read. Nothing on the desktop can shorten that delay. The live specs wait for core's listing to show the sender's head before they check a teammate.

### An instance without the catalog listing is an empty library

A `404` or a `403` from `GET /api/v1/catalog/items` is an **empty listing** — no shared agents, and **This server has no catalog yet.** in the Catalog dialog — logged once per host, not an error. The first is a Cinna server that does not have the routes yet; the second one that gates them by role. Treating either as a failure would show a broken catalog to every user of a server that simply does not offer the feature, and treating a `403` as a dead session would raise the re-auth prompt on every poll for a session that is fine.

### Words the user never reads

The sharing surfaces never say branch, commit, push, pull, merge, rebase, remote, repository, conflict or SHA. Every sentence lives in one map, and a test reads all of it against that list. The people this is for share an agent the way they share a document; a dialog that says "rebase failed — resolve conflicts" asks them to learn a tool before they can use the feature. The AI share summary is held to the same words (and "diff") by its system prompt.

### One state, decided in main

The badge and the Sharing tab show one state, with this precedence: **bringing together**, **other account**, **no longer shared**, **both changed**, **team changed**, **changes to share**, **up to date**. Main decides it; the renderer only chooses the sentence.

- **Bringing team changes together** — the folder's `app-data/desktop.json` holds a session record. It outranks everything, whatever happened to the team version meanwhile, because the only two ways out of a session are Finish and Discard: a folder reading "no longer shared" mid-session would offer Share with the team over a half-reconciled tree. It is the one state not in the warning colour — the user chose it
- **Shared on another account** — a Cinna remote on a server the *active* profile is not signed in to. Counts come from disk; no listing is read, no token is minted, nothing reaches the network. A token is only ever sent to the server that issued it, or to a git origin that server named
- **No longer shared** — a real listing for that server loaded and no longer has the repository. A `404`/`403` listing stands in as empty and says nothing about any entry, so it never makes an agent "no longer shared"
- **N changes you haven't shared** — files that differ from what the team has: recorded-but-unsent versions and working-tree edits measured from the **merge base**, so a file only the team changed is never counted as the user's, plus new files the ignore rules do not exclude. A new file is a change to share; `credentials/.env` is not
- **The team changed this agent** — when the listing's head is not in this folder's history. Without a fetch the app may know only that the team moved, not by how much; the sentence is the same either way

The badge can take a while to settle, and it is not wrong while it does. Against a real core, two cases have been seen; their cause is not established:

- **After a library refresh, up to about 15 s to read *The team changed this agent*.** This happened when this machine's copy of a tracked local-only file (`.claude/settings.local.json`) was edited, and the badge read **Up to date with the team** until then. In the collaboration spec, once in about fifteen runs, the badge did not change within Playwright's default wait, and that was not reproduced
- **Right after an Update over a team version that tracks `.claude/settings.local.json`, briefly *1 change not shared*,** before it settles to **Up to date with the team**. The file is never counted as a change to share once the state is re-read (below)

### The badge is there from the first paint, or not at all

Whether the badge and the Sharing tab exist is decided from the list of shared agents the sidebar already holds, not from this agent's own status, which arrives later. The badge is there from the first frame for a shared agent and absent for any other, and the agent's own read only changes its words. A badge that appeared once the status landed would push the runtime badges sideways under a user already reading them ([UX Rules](../../development/ui_guidelines/ux_rules.md), rule 1).

It sits **first** in the row, so the runtime label settling and the model and setup badges arriving late never move it. Badge and buttons are one unit that never wraps; the badge's words truncate instead, so a state change on a poll never adds or removes a line.

### The share actions belong to the page, not to the badge

Update and Share changes, and the dialogs they open, are owned by the agent page and shared by the badge and the Sharing tab. Clicking the badge switches to Settings, which unmounts the badge; an Update started from it can still come back a collision afterwards, and the two-button dialog must still open. A dialog owned by the badge would have nowhere to open. A refusal goes to the Sharing tab's own line while the tab is open, otherwise to the page's one-line slot.

### Update never resolves a collision, and never tries

Update is a fast-forward, or nothing. When this machine has versions recorded but not yet sent and the team has moved too, Update refuses as **dirty** without touching anything: combining two sides is a decision, and only Bring together and the send's own gated retry make it. A rebase that stops is aborted and the folder is exactly as it was. Tracked edits refuse it as **dirty**, and so does an untracked file sitting where an incoming one would land; the `dirty` sentence points at Bring together, which Share changes offers.

The reason is the one [Agents Folder Updates](folder_updates.md) gives for a root: deciding whose work survives, in files an agent will next run from, is not something to do on the user's behalf. What changes here is the answer to "and then what". When the two sides touch different lines, the answer is **Bring together** (below): the app combines them and the agent reads the result before anyone runs on it. When they touch the same lines, the user is offered **two buttons and never a diff**, and either choice keeps both versions.

### Bring together: the app combines, the agent reads, a person decides

Git combines two sets of changes to different lines without seeing what they mean. An agent then runs on instructions that are textually whole and semantically broken: one file says a client's rate is 10 % and another 20 %, a rule is added in the old place after the team moved rules elsewhere, the same rule is written twice. Update and Share changes accepted such a combine silently, and that is the defect Bring together removes: it puts the agent itself, in an ordinary chat, between the combine and the next run. No AI Function is involved — the agent knows its own job, has the files, runs on the engine it already runs with, and can ask the user a question, which a one-shot summariser cannot.

The condition is the **both changed** state: the team's version is not in this folder's history, and this machine has recorded-but-unsent versions or loose edits. Nothing moves until the user says **Bring together**; the banner and the dialog step only read the status already known.

- **The app owns the mechanics; the agent only edits files.** Bring together takes the agent's turn lock, fetches, records this machine's loose edits as a version of their own (a `dirty` refusal has no place in this flow: the inputs to the combine are made clean first), reads the three points it is anchored on — where the two sides last matched, this folder's tip, the team's — and **writes the session's record before anything moves**. Then it combines exactly as Update does: the unsent versions cleaned of what never travels and rebased onto the team's, with this machine's local-only files kept around it. The record goes first so that Discard is possible whatever happens next. If begin fails unexpectedly after the record was written, the record is cleared only when history has not moved; once it has, the record stays so that Discard can put the folder back. A collision aborts the rebase, drops the record and answers with the two-button dialog; the recorded version stays, since it is the user's work, now recorded instead of loose. A team version this folder already has is refused with "Nothing to bring together". The agent is told not to run version-control commands, not to change the manifest id and not to touch `credentials/` or `app-data/`; the app records and shares
- **The brief is a visible first message, in the user's voice, the same for every engine.** It says the two sets of changes were combined line by line, without anyone reading what they mean; lists the team's versions since the two sides last matched and this machine's, each with its note, author, date and the files it touched; shows the change to every file that carries instructions (markdown, `cinna-agent.json`, anything under `skills/`, `knowledge/` or `config/`) as a diff, naming the other changed files without showing them; and asks, in order, to find where the two sides disagree (the same fact stated two ways), overlap (the same rule twice, in different words or places) or where this machine's changes landed in a structure the team changed; **to ask about a business fact the two sides state differently, never to guess it**, with the team's notes as the context for the question; to make the edits so one consistent set of instructions remains; and to end with a section headed exactly *Summary of what I did*. One file's diff is cut at 6 000 characters and the whole brief at 40 000, leaving files out rather than the asks. What never travels and every secret-shaped file are left out — even one a version deleted, whose diff would otherwise show its old contents — and the rest is scrubbed of credentials, as the AI share summary's input is. It is a message rather than a system prompt because the user can read what was asked and the agent's answer refers back to it. This machine's side is read from the tip **before** the combine, so what the brief calls "mine" is what the user actually had
- **Finish checks and hands over; it records nothing and never sends.** Finish refuses — the reason in the page's line, the session kept — when an earlier combine is still half-done in the folder, when the folder is off its line of history, when any text file holds both versions marked with `<<<<<<<` and `>>>>>>>` lines (naming up to three), or when the team's version the session brought in is no longer in the folder's history — each answered `adoption_blocked` with the sentence, which the page shows whole. Otherwise it lifts the agent's text after its *Summary of what I did* heading from the last answer in the session's chat (a heading, bold or a bare line, at most 1 500 characters), ends the session and opens Share changes with the summary in **What changed**, so that a person reads the note before the team does. The session's edits are left loose and the next Share changes records them under whatever that field then holds: recording at Finish would have written a note nobody had read, and left the field nothing to be the note of. No fixed note is written anywhere. The chat is looked up in the active profile's scope, as the chat itself is (a chat the profile does not see, or one in the trash, yields no summary). A session that changed nothing finishes all the same. A team that shared again during the session is not brought in by Finish; the next Share changes meets it like any other, with the step offered again when the files overlap
- **Discard puts the folder back where the session began.** A folder that cannot be put back is `adoption_blocked` too, with a fixed sentence: git's own output is never shown. Any half-done combine is aborted, the tree reset to the recorded tip and files made since removed — never the ignored ones, never what never travels — with this machine's local-only files kept around it as on every history move here. The version recorded at the start stays. It asks first, naming the agent and saying what is kept before what is dropped, with Cancel focused
- **A session survives restarts and the chat being deleted.** The record lives in the folder's `app-data/desktop.json`, which git ignores and which never travels, so a reset or a clean in the folder cannot remove it. The chat id in it serves only **Open the session**, and is trusted only in the active profile's scope: it is refused (*That chat could not be found.*) when recorded for a chat that profile does not see or has trashed, and a chat that disappears later reads as none, so the link goes while the record keeps the id. A record this build cannot act on — malformed, or a kind of session a newer build wrote — reads as no session, since Finish and Discard would otherwise be offered on points that cannot be restored
- **While a session lasts, nothing else moves the folder's history.** Update, Share changes, Use the team's version, Remove sharing and Remove from this computer are refused with "Finish or discard the session that is bringing the team's changes together first." Trashing the folder would lose the session and what it reconciled; the other four would move history under it
- **Not now is remembered per team version.** Declining the banner records the team version it was declined for; the banner stays away while the team's version is still that one and returns when the team moves. A banner that came back on every open would be dismissed by reflex. Share changes still offers the step, because a send over a both-changed folder is where the silent combine used to live
- **The banner is decided when the page opens, from the list the sidebar already holds**, so it is there from the first frame or not at all and nothing moves while the user types ([UX Rules](../../development/ui_guidelines/ux_rules.md), rules 1 and 2). It is a labelled region, as wide as the composer below it. It leaves on Not now — which holds even if the page is reopened at once, before the statuses list refetches — and the moment the state stops being *both changed* — Bring together, or an Update or a share from elsewhere
- **The brief's fixed words are held to the same list as every sharing sentence** (no branch, commit, push, pull, merge, rebase, remote, repository, conflict or SHA), because the agent echoes the words it was given and the user reads the answer. The diffs' own content is not held to it: that is the user's and the team's text

### Share changes sends, and retries once

It records with `add -A` (honouring the ignore rules) under the user's note — or "Changes shared from Cinna Desktop" when the field is empty — then sends to `main`. A team that moved before the send, and a rejection because a teammate shared first, are each answered with one clean Update and one more send — **only when the team's versions touch none of the files this machine's unsent versions touch**, measured from where the two sides last matched. When a file is in both, the answer is `team_changed_again` ("The team changed this agent again while you were sharing. Bring the changes together, then share.") and the dialog shows the Bring together step: a file both sides changed is exactly what a person and the agent should read, and the one-Update retry used to combine it blindly. Disjoint files are combined as before. A second rejection reads "The team version changed again while sending." **Never a force**: a force would overwrite what the teammate just shared.

The gate fetches first, so a team that shared a moment ago is seen, and measures from the merge base, not from the last fetch. It guards every path that combines before a send: the retry above, the one Update a combined send ([below](#a-version-the-library-refused-is-sent-again-as-one)) makes before its resend, and the clean-up of unsent versions that precedes a send. No send path combines the team's versions with this folder's when a file is in both; each of them answers `team_changed_again`.

A refusal from the server carries the server's own sentence; a `403` reads as "ask a maintainer for edit access". An account with `use` access is not offered Share changes at all.

### A version the library refused is sent again as one

A Cinna team library checks **every** new version in a send, not only the latest, and refuses one that holds a symbolic link, an oversized file or an invalid manifest. That version stays here as not shared yet, so once the user fixed the file, every later send was refused with the same sentence, for good.

So when a Cinna library refuses a send for what it holds — its push policy declining the content, not a teammate sharing first, a `403`, the network, a sign-in, a server that could not take the lock, or the policy saying it *can't check this change right now* — the app sends once more, automatically, with every version the team does not have **combined into one**. Its content is what the folder holds now, already cleaned of what never travels ([below](#the-credentials-and-app-data-folders-never-travel-to-a-team-library-whole)), on top of the team's version, so it adds what the team lacks and nothing else. Its note joins the unsent versions' notes, newest first, without repeats; it is from whoever shares, as any version is. With a single unsent version there is nothing to combine, and the refusal stands.

One content refusal is never answered with a combined send: **This agent's identity changed; share it as a new agent instead.** The catalog binds each entry to the manifest `id` it was created with and refuses any send whose `id` differs, in any case. That is a verdict on what the folder is now, which a combined send carries just the same, so resending would only double the refusal. It is said once, in the server's words.

- **History changes only once the library accepted it.** The combined version is built aside; this folder's history moves to it only after the send succeeded, and only if nothing was recorded here meanwhile. The files on disk are not touched: they are already exactly what was sent
- **A version recorded meanwhile** (outside the app, from a terminal, say) is replayed onto the combined version, so the work just sent is not shown as unshared and the next Update does not collide with it. If that replay stops, it is undone and history stays as it was, logged
- **Refused again** — the file is still bad — history stays exactly as it was and the answer is the server's sentence, as before
- **The team moved meanwhile**: one Update, one more combined send, never a third and **never a force**
- **A send the library accepts is never combined**: each version keeps its note, author and date. Only `external` remotes never combine

### A file that can hold a secret is never sent

Before anything is recorded, two things are made true:

- **The kit's agent ignore rules are in the folder's own `.git/info/exclude`**, in one marked block, rewritten only when the kit's rules change. What `add -A` records must not depend on a `.gitignore` a teammate (or a developer's own repository) left in the folder. The same block is written into every clone before it becomes visible
- **No file that can hold a credential is already tracked.** That covers anything the contract's `secret_files` rules call secret, and the desktop-owned `app-data/desktop.json`, which holds a bearer token. For a Cinna team library, a tracked secret under `credentials/` or `app-data/` is not a refusal, because the app takes those folders out itself ([below](#the-credentials-and-app-data-folders-never-travel-to-a-team-library-whole)). An ignore rule cannot untrack a file, so the folder is refused (`secrets_tracked`) when a secret is tracked anywhere else (a `.env` at the agent's root, say), or anywhere at all for an `external` remote. Nothing is recorded or sent, and up to three of the files are named. The sentence ("…is recorded in this agent's history") asks whoever maintains the agent to remove them, because a non-developer cannot take a recorded file out of the agent's history, and it may already be in the team's version. The secret shapes are matched **in any case** (`PROD.ENV`, `Server.KEY`) since the adoption session landed, the same way the never-travel paths already were; an agent shared earlier with an upper-case secret tracked outside those folders is refused on its next Share changes until the maintainer removes it

Sharing for the first time also writes the kit's agent ignore files the folder lacks, so an agent made before it was a repository does not send its secrets with the first share. A folder that is already its own repository is checked for tracked secrets **before** the library entry is created: a refusal after the entry existed would leave an empty agent in the team's library.

The AI share summary is held to the same line. Its text is built from the folder's differences with every tracked secret file left out, because the summary goes to whatever backend AI Functions resolves to — and the dialog drafts it *before* Share has had the chance to refuse the folder.

### The credentials and app-data folders never travel to a team library, whole

This applies to **Cinna team libraries only**. An `external` remote, such as a developer's own GitHub, gets the kit's ordinary ignore rules and nothing more: what goes into their repository is theirs to decide.

The contract's `shared_remote.never_travels` (1.8.0) names folders that never go to a shared remote **in full**, not just their secret files, and since 1.9.0 one single file, `.claude/settings.local.json` (below). An entry ending in `/` is a folder and covers everything under it; any other entry is one file, matched exactly, so `.claude/settings.local.json.bak` still travels. Both are matched **in any case**, as the server matches them: a case-insensitive disk (macOS, Windows) lands `Credentials/` or `.Claude/Settings.local.json` on the same place, so those count too. That includes the template's own `credentials/README.md` and `.env.example`. When a workshop's own `.cinna-kit/` predates 1.8.0, the app uses the same two folders, `credentials/` and `app-data/`, because the server enforces them whatever the folder's contract says. The team library's server refuses any send that carries a file under them in **any** new version, not only the latest. A first share once failed on exactly this: the template's `credentials/README.md` went with the first version and the server refused all of it.

- They are in the exclude block, written so they match in any case whatever the clone's own case setting. Before every recording, anything already recorded under them is dropped from what is recorded, and the files stay on disk. Share with the team's preflight only checks and changes nothing, because a preflight that then refuses must leave the folder as it found it
- **Before a send, the versions not yet sent are cleaned, not squashed.** A version may have recorded one of these folders: a first send the server refused, say, or a developer's own history. First the app fetches, so "not yet sent" is measured against the team's version as it is now. Every unsent version then has those paths taken out and keeps its note, author, dates and place. Then, if the team has moved on, the cleaned versions are rebased onto it. Clean first and rebase second, because replaying a version that untracked a file would delete that file from disk. Nothing the team already has is rewritten. The working tree and the index are untouched, and the branch moves only if nothing else moved it meanwhile. A folder on a detached HEAD is refused with a sentence saying to switch to its branch. A fetch that fails refuses the send (`fetch_failed`)
- **Update** cleans the same way before it rebases this machine's unsent versions, for the same reason: otherwise the rebase could delete a credential from disk. A send that is rejected because a teammate shared first is cleaned again after its one Update. Bring together combines as Update does, and cleans the same way
- **Get** gives the fetched agent the template's `credentials/` and `app-data/` folders and `.claude/settings.local.json` locally, only what is missing, since the team's version never has them. A `.claude/settings.local.json` the team's version does carry is replaced by the template's (below)

**`.claude/settings.local.json` never travels either.** It holds Claude's permission allow rules, the commands that run without asking, and the kit template ships one. A teammate with edit access could otherwise widen what runs without asking on everyone's machine. It is cleaned exactly like the two folders: in the exclude block, left out of what is recorded and of unsent versions, and a tracked copy is no reason for Share with the team to refuse. Contract 1.9.0 lists it, and the kit's agent `.gitignore` ignores it; the app keeps it in the list itself as well, for a workshop whose own `.cinna-kit/` predates 1.9.0. The server refuses a send whose latest version still contains it (since core d5bb0a16), and accepts one that removes it. A team version recorded by an older client or plain git may still track it, and this machine's copy then differs from it for good; that difference is never counted as a change to share (it would be taken out, not sent), so the badge does not read "1 change not shared" over it. **Such an agent heals on the next share from someone who can edit**: that share takes the file out of the team's latest version, which is what the server requires — a send that kept it would be refused, which is why the app untracks it before recording and never sends it. Plain git that pushes a version still holding it is refused.

**This machine's copy always wins.** An agent shared before this rule, or by an older client or plain git, may have the file in the team's version; arriving, it would replace this machine's rules with a teammate's (possibly wider) ones, or the version that stops tracking it would delete them. So:

- **Update** keeps the file before and writes it back over whatever git left, whether the update landed or was refused. With no copy here, a team version that carries one gets the template's file instead. The copy is also kept under `.git/cinna-local-only/` for the length of the update; one left there by an interrupted update is put back, over what is on disk, before the next sharing action or status read on that agent, then removed
- A folder that still **tracks** the file (shared before the rule) is not refused as having unshared edits because approving a permission rewrote it: only other tracked edits refuse an Update
- **Get** replaces a carried file with the template's, never the team's
- **Use the team's version** gives the team's version this machine's copy from the kept folder, else the template's, over whatever the team's version carried

### Who a version is from

A repository or global git config that names someone keeps it — a developer's versions stay theirs. Otherwise the active Cinna profile's name and email; a profile without an email gets a no-reply address on the server's own host, built from the profile's local id; anything else an anonymous `.invalid` address. **Never this machine's login or host name**, which git would otherwise fill in and every teammate would then receive. Signing is switched off for versions the app records: a global `commit.gpgsign` would wait on a pinentry the app has no terminal for.

### The Cinna token reaches git only through the environment

A Cinna remote is authenticated with the active profile's access token as an `Authorization: Bearer` header, **minted immediately before each git child** and passed as `GIT_CONFIG_*` environment variables scoped to the remote's origin — never in argv, where any process listing shows it, and never in `.git/config`, where it outlives the operation. **Redirects are switched off** for those children: git's default follows a first-request redirect and then sends the rest of the operation, header included, to the new location. A Cinna git endpoint has no reason to redirect, so one that does fails as unreachable rather than handing over the token. Anything git prints is scrubbed of bearer headers, JWTs and URL passwords before it is logged or shown.

### An instance's git may live on another origin

cinna-core builds `clone_url` from its **backend** address, while a profile is often signed in through the web app's origin that proxies the API — `localhost:5173` against `localhost:8000` in development, an `app.` against an `api.` host in a deployment. So the git origin is **whatever the instance itself says**, and nothing else:

- A `clone_url` from a library listing or from the answer to creating an entry, fetched over that profile's session, teaches this machine that the instance's git lives at that origin. The list is kept **in main**, in `<userData>/team-library-trust.json`, so it holds from the first launch before any listing has loaded — not in the settings store, which the renderer can write, and never read from the folder
- A remote is the instance's (`cinna`), and takes its profile's token, only when its git origin is the instance's own or one that instance named. The header is scoped to that origin
- The folder records its instance in `.git/config` as `cinna.server`, which only **chooses between** instances that already trust the origin. `.git/config` is writable by anything running in the folder — an agent's own turn included — so a remote URL on its word alone would send the token wherever it pointed; such a remote is `external` and gets no token
- **Plain http** carries a token only when the instance itself is on http or the address is this machine (loopback). Anything but http(s) is refused

### A retry finishes the entry this folder left empty

The catalog entry is created before the folder is first sent, bound to the folder's manifest id. If the send fails, a retry's create is refused with a `409` — core's own sentence, for the slug taken or the manifest id already in the catalog. The retry then looks for **this folder's own** entry in a fresh listing: the same manifest id (in any case, since core stores it lowercased), no version yet, and maintained by this account. Only that one is adopted and sent to. Core never lets a teammate's entry carry this folder's manifest id, so nothing else matches; an entry under the same name that is not this folder's, or one that already has a version, stays a refusal with the server's sentence. Nothing is recorded on this machine for it: the manifest id is the record, so an entry an attempt left empty is found from any build and any computer that holds the folder.

### A new agent reaches only the people chosen, never everyone by default

Share with the team never gives the agent to everyone unless **Everyone on this server can use it** is ticked. With nobody picked, only the sharer can get it. The create (`POST /api/v1/catalog/desktop-agents`) carries the slug, display name, the manifest's description, the manifest id, visibility `users` (`public` with Everyone ticked) and the chosen people as grants, and core applies them in one transaction with the sharer added as maintainer. So the entry is never visible to anyone the sharer did not pick, not even for a moment. Visibility is `users`, not core's default `private`, because a person's **Can use** grant counts only under `users`: with nobody picked it reaches the maintainers alone, exactly as `private` would, and a person added later in People can get it at once.

An **adopted** entry — the one a failed earlier attempt left empty — still has whatever that attempt chose. Before anything is sent to it, its whole grant list is replaced with its maintainers as **Maintainer** plus this attempt's people, and its visibility is set to this attempt's choice (`public` or `users`) when it differs. If the server names no maintainer, or refuses either write, the folder is not sent and the dialog says why; a retry adopts it again.

### People is the server's list, written whole

The People list is the catalog item's grants as the server answers them, plus **Everyone on this server** when the item is `public`. A change is the **whole desired list**. The grants are written in one `PUT`; only when Everyone was added or removed does a second write follow, a `PATCH` of the item's visibility: `public` with Everyone, `users` without. After it, the list shown is what the server answered, or a fresh read, and never the list that was sent, which lacks the names. The next edit therefore builds on the server's list. A rule the server enforces, such as keeping at least one maintainer, comes back as the server's own sentence under the list.

- **Grants first.** They are what the server checks (a maintainer left, a known role, an active person), so a refusal there changes nothing at all; and when Everyone goes, the people named already have their own access before the item stops being public. Core sets no order between the two. A visibility refused after the grants went in comes back as the server's sentence with the list as it now stands
- **Everyone is visibility, never a grant**, because that is how core stores it. Shown as a row, it keeps the list one shape for the user
- **An unlisted entry shows no Everyone row**, even when it is `public`: unlisted, core counts neither `public` nor a **Can use** grant, so it reaches no one but those who can edit. Saving a list without the row therefore leaves such an entry public rather than reading the missing row as a request to narrow it. The Sharing tab's **Who can get it** says the entry is unlisted (or private) instead

A `403` on reading the list means the caller is not a maintainer. The tab then shows only the listing's maintainers and **Only a maintainer can change who has access.**, and never the sign-in prompt, because the session is fine and the list is just not theirs to see. A `403` on a write reads **Only a maintainer can change who has access to this agent.** "You" is the row whose account id matches the subject of the profile's stored token. When that cannot be read, no row is marked or left out: a wrong guess would hide someone else's row, or their remove button.

Search goes to the active profile's server and asks for ten people at most. Fewer than two characters asks nothing. A `403` or `404` from the search finds no one, so a server without the route offers an empty search rather than an error.

### History lists versions, it never restores one

History is this folder's own versions, read locally with no network, newest first and at most thirty. A version is **Not shared yet** when it is recorded here and not on the team version (`origin/main..HEAD`). With no team version to measure against, as on a folder never fetched, none is marked. No version identifier reaches the renderer: there is nothing to restore to, and nothing to compare.

### Remove sharing disconnects; deleting from the library comes first

Remove sharing removes `origin`, clears the `shared_remote` link in `desktop.json` (catalog id included) and unsets `cinna.server`. The folder, its files and its own `.git` history stay, and the agent becomes an ordinary local one that Share with the team offers again. It takes the turn lock like every verb that writes `.git`, and refuses while a turn runs. Unshared changes do not block it, since nothing is lost. It works for any shared agent, including one shared on another account or with an `external` remote.

**Also delete it from the catalog** is offered only to a maintainer of an entry the library still lists. The delete (`DELETE /api/v1/catalog/items/{uuid}`) is done **first**: if the server refuses it (a `403` reads **Only a maintainer can delete it from the catalog.**, anything else carries the server's sentence — most often **N people use this. It can be removed once nobody does.**), nothing on this machine changes. An entry already gone (`404`, or a real listing that no longer has it) counts as deleted; a listing the instance refused (`404`/`403` standing in as empty) says nothing about the entry and is refused as unreachable ("Check your connection and try again…"), never read as a delete.

Without the delete, the entry stays, and the catalog is told in the background that this computer no longer holds it. Otherwise this machine's install would keep counting against a maintainer's delete for a copy that is no longer a team copy at all. If the delete succeeded and the local disconnect then failed, the folder reads "No longer shared", and Remove sharing again finishes the disconnect (the delete is no longer offered, and would count as done). Teammates' copies are untouched either way. After a delete, their folders read "No longer shared" at their next poll.

### This computer tells the catalog what it holds

Core keeps a local install per person, device and entry, which it uses for install counts, for "who is behind" for maintainers, and for the delete refusal above. So after a **Get**, an **Update** that brought changes, **Use the team's version** and a **Share changes** that sent, main reports the version this folder is now at (`POST …/local-installs {device_id, revision_number}`); after **Remove from this computer** of a shared agent, and **Remove sharing** without the delete, it reports the removal (`DELETE …/local-installs/{device_id}`).

- **Best effort, always.** The report runs in the background after the verb has finished: it never blocks, delays or fails it, and a failure is only logged. This computer's folders stay the truth about what it holds; the catalog's count is a convenience for others
- **Only a version the catalog knows.** The folder's head is the latest version's when it matches the listing's head; otherwise the entry's versions are looked up by commit. A folder at no shared version — changes of its own on top — is not reported, rather than claimed to be at a version it is not
- **Its own device id.** A random id minted once per installation and kept in main, naming this installation and nothing about the machine or the person. The data-sync device id would not do: it exists only once sync is set up, per profile, and it decides write authority over task runs. A lost file mints a new id, which core reads as one more device — a count off by one, never a failed verb
- Share with the team reports nothing: the sharer's first send makes them a maintainer, not an installer

### Get refuses anything already here

Get refuses when `Local/<slug>/` exists, or when an agent with the same manifest id (in any case) is already on this machine — checked against the listing first, then against what actually arrived (the listing's id can be missing or stale), and the clone is removed. It clones into a hidden staging folder and renames it into place, so the scanner and the watcher never see half an agent and a failure leaves nothing. What arrives must have a `cinna-agent.json` at its root.

### Credentials are set up after, never carried

A team version never holds `credentials/` (see [never travel](#the-credentials-and-app-data-folders-never-travel-to-a-team-library-whole)), so every Get lands an agent without its credentials, and an Update can add a slot nobody here has filled. Rather than leave the user to discover that from a failed run, the three verbs that bring the team's files in end by attaching what fits beyond doubt and asking in **Finish setting up *Name*** when that leaves a required slot missing: any, after a Get; one the verb made missing, after an Update or Use the team's version. Asking again about a slot the user already left for later would make **Finish later** mean nothing; the composer's missing-credentials row and its **Finish setup** are there for it. The rules — what counts as a fit, why it never waits behind a turn, never removes an attachment and never fails the verb — are [Service Credentials' Finish setup](../service_credentials/README.md#finish-setup). Share changes, Share with the team and Remove sharing bring nothing in, and do none of it.

### Use the team's version keeps everything, and leaves one id per folder

- The old folder is renamed to `<slug>-mine` (or `-mine-2`, …, a long slug shortened so the name stays within a slug's 63 characters), the team's version is cloned at the original path, and the kept copy gets a **fresh manifest id**, its folder's name as its **slug** (the validator requires the two to match, and two agents never share a slug), "(my copy)" after its name, and no `origin` — it is nobody's team agent. The original id stays with the team's version, so the chats bound to the agent follow the team
- **Per-machine files are carried over**: everything git ignores in the old folder — `credentials/.env`, `credentials.json`, `app-data/` — which no clone brings. Copied, not moved, so the kept copy still runs; only where the team's version has nothing at that path, so nothing that arrived is overwritten. Rebuildable folders (`.venv`, `node_modules`, `__pycache__`) are not carried. What could not be copied is named in the page's note ("Some of this computer's files didn't come across: …"), because the team's version may not run until the user puts, say, a credential back
- **Anything that fails part way puts the folder back** as it was before the click — id, `origin` and all. A clone that already landed is first renamed to a hidden dot-folder and only then deleted, so a delete that fails half way (a file held open) never leaves a partial clone carrying the original id at the agent's path. Two folders with one id is the state never allowed: the scanner would refuse one of them, and which one is a coin toss
- The agent's warm engine process is retired, because its working directory is now the kept copy

### Busy agents are not changed underneath

Update, Share changes, Share with the team, Use the team's version, Remove sharing, Bring together, Finish and Discard take the agent's turn lock exclusively and refuse while a turn runs ("nothing was changed"). The session's chat is an ordinary turn, so Finish and Discard are refused while the agent is still answering, and nothing is changed under it. Share with the team takes it too: the first share is an `add -A` of whatever is there. Get writes a folder no agent runs from yet. Update is not followed by a process restart: like a root update it changes files in place, and every turn reads them afresh.

### A shared agent's folder stays out of the workshop's repository

When a `Local/<slug>/` becomes its own repository inside a workshop that is itself one, its path is added to the workshop repository's `.git/info/exclude` — per clone, never committed — so it does not appear there as an untracked directory or, after someone's `git add -A`, a stray nested entry.

### What it deliberately does not do

- **No diff view, no merge tool, no restore.** History is a read-only list of versions: no version opens, compares or comes back. A user who wants those has their own tools, and the folder is an ordinary repository they can open with them
- **No sidebar marker.** A shared agent's row looks like any other; its state is on its page
- **No combine of the same lines.** Bring together handles the two sides touching different lines; the same lines still get the two buttons, and no file is ever left holding both versions for the agent to sort out
- **No hidden prompt.** The brief is an ordinary first message in an ordinary chat; the agent's system prompt and the kit's are untouched, and no AI Function reads the two sides
- **No automatic Bring together.** The banner and the dialog step offer it; nothing records, combines or opens a chat until the user says so
- **No realtime.** Core's `catalog.updated` and `catalog.granted` events are not listened to; a teammate's share reaches this machine at the next five-minute poll, or when the catalog opens
- **No renaming, unlisting or catalog editing.** The display name and description are set once, at Share with the team; listing and every visibility other than Everyone's `public` / `users` switch belong to the server's own catalog pages. The desktop shows an unlisted or private entry's effect and does not change it
- **No catalog id input.** It is core's, minted at create, and the desktop only shows it
- **No sharing of bare agents** or of agents outside `Local/`: they are not the kit shape the library and Get produce
- **Root-level updates are unchanged.** A whole agents folder that is a git repository still gets only [Agents Folder Updates](folder_updates.md)' fast-forward

## Architecture Overview

```
Catalog (Runs on your computer tiles) / share badge / Bring together banner / Sharing tab / ⋯ menu / Inbox card / blocked-job row
  → useSharing hooks → window.api.sharing.* → sharing:* IPC (activation gate, settings scope)
      → sharingService (core: resolves every folder from an agent id)
          → gitService share verbs (execFile git, token env per child)
          → app-data/desktop.json (the session record, written before history moves; Not now's team version)
          → adoptionBrief (the session's first message) → the renderer's new-chat flow → the agent's ordinary turn
          → libraryService cache  ← GET /api/v1/catalog/items, every 5 min while active
          → POST /api/v1/catalog/desktop-agents (Share with the team; on an adopted entry PUT …/grants, and PATCH visibility when it differs, first)
          → GET / PUT /api/v1/catalog/items/{uuid}/grants, PATCH …/items/{uuid} visibility (People)
          → GET /api/v1/users/search (the people picker)
          → DELETE /api/v1/catalog/items/{uuid} (Remove sharing, when asked)
          → serviceCredentialService.autoAttach (after Get, Update, Use the team's version)
      → catalogLocalInstalls (background, best effort) → POST / DELETE …/items/{uuid}/local-installs
      → rescan + sharing:changed → renderer invalidates sharing, agents, Inbox
```

## Verification

### Observed against a real cinna-core

Four live specs, `e2e/specs/live-team-sharing*.spec.ts` ([how to run them](../../development/e2e/e2e.md#team-sharing-against-a-real-cinna-core)), drive one app per core user side by side: A shares, B and C are teammates. Each app is signed in with desktop tokens minted through core's real OAuth flow, against a local cinna-core. The runs described here were made on 2026-10-10 against core `570c6d51`, where shared agents are desktop agents in core's catalog (`/api/v1/catalog/*`, local installs reported). All 28 tests passed in their final runs: the main spec 1, credentials 8, collab 13 and lifecycle 6. Earlier runs used the team library routes core has since removed, at `511ea03a` and `d5bb0a16`. The test agent's `/run:check-creds` prints a hash of each credential value its script reads, so "the agent runs with the right credential" is observed, not inferred. Seen end to end:

- **Share with the team** — core lists the agent as `kind=agent`, `runs_on=desktop`, with the sharer's manifest id, the folder's `HEAD` and Version 1 published by the sharer. The sharer's `app-data/desktop.json` records the catalog `bundle_id` in `shared_remote`, and the Sharing tab shows **Version** 1, **Shared by** the sharer and the **Catalog id**, read-only. The catalog grants are exactly the sharer as `maintain` and the people picked as `use`, found through core's user search in the dialog. A clone of the entry's full history on core holds nothing under `credentials/` or `app-data/`, no `.env`, no `.claude/settings.local.json` and neither of the sharer's secret values, and every version names the sharer's account. A person who was not picked neither sees the entry in the listing nor can clone it (`403`)
- **Get** — the agent lands with the sharer's slug, manifest id and tracked files, plus the template's `.claude/settings.local.json`. A credential the server's admin shared with both people is attached without asking (**Connected automatically**). The teammate's `desktop.json` records the same `bundle_id`, and core lists the Get as that person's local install at Version 1 (`my_installs`), with the sharer's `install_count` at 1. Finish setting up asks for the `.env` key, and the script then reads both values. A teammate the credential is not shared with gets no cloud option and nothing of the sharer's on disk. With two matching records nothing is attached, both are offered, and the one picked is the one the script reads. Get is refused by folder name (from the tile) and by manifest id (over IPC, caught by the listing's id), and `Local/` is left as it was
- **Update and Share changes, both ways** — each accepted send is a new catalog version (2 by A, then 3 by B), with the send's note in its release notes, and the Sharing tab's **Version** and **Shared by** follow it. Each side's note and author show in the other's History, and both folders end on the same version. When a teammate shared first, the share runs one Update and one more send. When both changed the same lines, the collision dialog opens with **Keep working on mine** focused, and that button leaves both changed. **Use the team's version** keeps the old folder as `<slug>-mine`, named "(my copy)", with a fresh id, no `origin`, and ready to run. With edits here and a team that moved, the tile's Update is refused as `dirty`; Share changes then brought the team's version in and sent — the silent combine that Bring together has since replaced, and whose step, session and send gate are not yet among the live runs (below). An open page shows **1 change not shared** after a file edit with nothing but the folder watcher
- **Access** — a **Can use** account is offered no Share changes, and core refuses a raw `git push` with its token (`403`). Demoted to Can use while the Share changes dialog is open, the send reads the ask-a-maintainer sentence. Removing a person in People leaves **No one else has access yet.**, and that person's copy reads **No longer shared**
- **Core's push refusals** — a symlink, an 11 MB file, an invalid manifest and a changed manifest id ("This agent's identity changed; share it as a new agent instead.") each come back as core's own sentence after "Fix what the team library refused, then share again." Core's head does not move and the version stays **Not shared yet**. Once the symlink or the big file is fixed, the next Share changes lands as **one** version carrying both notes, and core's history has no symlink and no blob over 10 MB
- **Remove sharing with the delete** — while a teammate holds a copy, core refuses it and the dialog shows core's sentence alone: "1 person uses this. It can be removed once nobody does." Nothing changes on either side. After the teammate's **Remove from this computer**, core drops their local install (`install_count` 0), the delete goes through and the entry is gone from core. Sharing the same folder again makes a new catalog entry at Version 1. A teammate's copy reading **No longer shared** is seen after their access is removed (above)
- **The Inbox card** updates the agent and says **Updated.** **A blocked job's Get *X* from the team library** unblocks the job, with the same agent id
- **Credentials over time** — when the admin revokes B's share, the slot reads missing and Finish setup is offered. Re-sharing makes the same attachment ready again, and after a rotation the script reads the new value. An empty `KEY=` in `credentials/.env` leaves the slot missing. A slot a teammate added arrives with Update and reopens Finish setting up. After Finish later, an Update that leaves nothing newly missing does not reopen it. **Use the team's version** keeps this machine's `credentials/.env` and attachment
- **A secret refused before core** — a folder tracking a `.env` at its root is refused in the Share with the team dialog, and afterwards there is no catalog entry and no `origin`
- **`.claude/settings.local.json`** — core refuses a plain-git version carrying the file, as `.claude/settings.local.json` or `.Claude/Settings.local.json`, with its own sentence, and its team version does not move. When A edits their own copy and shares a change in the app, B's Update keeps B's copy, git does not track it, and B reads **Up to date with the team**, both as Can use and after being promoted to Can edit. A later Get has the template's file. An entry that already tracked the file from before core `d5bb0a16` can no longer be set up against core; that migration (B's copy surviving Update, never counted as a change, and the next in-app share taking it out) is covered by the `gitService` unit tests
- **Timing seen against core** — core records a version a moment after the send lands: right after Share with the team closes, the catalog can still answer `latest: null`, and a teammate (who sees a desktop agent only once it has a version) may not find it yet; the specs wait for Version 1 before reading it. After a manifest id is changed by hand, the agent is new to the app: the open page reads "This agent is not indexed", and after a rescan main reports one unshared change while the badge kept reading **Up to date with the team** for over 30 s, until the app was relaunched

`live-sharing-agents.spec.ts` (fixture `live-catalog.py`, people A–D; [how to write and run it](../../development/e2e/e2e_llm.md)) adds People against the same kind of core:

- **Named people, then everyone** — Share with the team with B and C picked leaves core with A as `maintain`, B and C as `use` and visibility `users`; B and C list the agent and C's Get is recorded as a local install, while D, named nowhere, does not list it. People shows B and C at **Can use** and no Everyone row. **Share with everyone** turns the entry `public`, shows Everyone at Can use and drops the button, and D can then Get it. Removing Everyone (asked in the row) puts core back to `users` with the grants unchanged, after which D no longer lists the entry although D holds a copy. Access changes from the select are followed by core each time
- **A second maintainer** — a teammate at Can use sees only the maintainers and who can change it. Once A makes B a **Maintainer**, B's own People is editable and B adds C through **Share with a person…**, which core records. A list that would leave no maintainer is refused with core's sentence ("This item needs at least one maintainer.") and nothing changes
