## Database Schema

`agent_mcp_providers` (`src/main/db/migrations/agent-mcp-providers.ts`):

| Column | Notes |
|---|---|
| `agent_id` | FK `agents.id`, `ON DELETE CASCADE` |
| `mcp_provider_id` | FK `mcp_providers.id`, `ON DELETE CASCADE` |
| `created_at` | Attach time. Lists are ordered by it, then by `rowid` |

The primary key is (`agent_id`, `mcp_provider_id`), with an index on `mcp_provider_id` for the "used by" and fan-out lookups. Keyed by `agents.id` rather than the manifest id, so a stamp re-key has to move the rows (it does). A folder pruned by the scanner takes them with it, while a rescan of an unchanged folder keeps the row and so keeps them.

`mcp_providers.registry_ref` (JSON text, nullable, `{source, id}`): the directory entry a connector was created from. Null for a connector set up by hand and for every row that existed before the column. Written on insert only, so an edit never moves it.

## IPC Channels

Every handler is activation-gated and scoped with `getSettingsScopeUserId()`.

| Channel | Signature | Notes |
|---|---|---|
| `local-agent:mcp-list` | `(agentId) → string[]` | Attached connector ids, oldest first. `[]` for an id that is not a folder agent in this scope |
| `local-agent:mcp-attach` | `({agentId, mcpProviderId}) → {success: true}` | Throws `LocalAgentError('not_found')` for a non-folder agent and `McpError('not_found')` for a connector outside the scope. Attaching an already-attached connector is a no-op |
| `local-agent:mcp-detach` | `({agentId, mcpProviderId}) → {success: true}` | Agent checked as above; detaching what is not attached is a no-op. Async: on a kit agent the answer comes after the connector's `mcp_servers[]` requirement was dropped (a failed write is logged, never a failed detach) |
| `mcp:agents-using` | `(mcpProviderId) → {id, name}[]` | The folder agents a connector is attached to, oldest attachment first. Read by the delete confirm |

The directory's own channels (`addons.ipc.ts`; activation-gated, scoped with `getSettingsScopeUserId()`; ids, refs and the query are validated, the query capped at 200 characters):

| Channel | Signature | Notes |
|---|---|---|
| `addons:directory` | `({agentId, refresh?}) → AddonDirectoryResult` | `{ok, entries, sources, policy}`. `refresh` re-reads the providers' caches |
| `addons:search` | `({agentId, query}) → AddonSearchResult` | Only the search-only providers (the public MCP registry), gated by policy. A hit that is already a local connector comes back as that connector |
| `addons:add` | `({agentId, ref}) → AddonActionResult` | `{ok: true, next, mcpProviderId?, message?}`; `next` is the step a connector still needs |
| `addons:remove` | `({agentId, ref}) → AddonActionResult` | Unpins or detaches; what the agent does not have is a no-op; a connector is detached, never deleted. On a kit agent the requirement written for it is dropped first |
| `addons:mcp-requirements` | `({agentId}) → AddonMcpRequirementsResult` | `{ok, items}`: each `mcp_servers[]` element with `state` (`ready`, `needs_setup`, `unavailable`), `reason`, the local `mcpProviderId` and the `entryRef` the picker opens for it. `[]` for a bare agent |
| `addons:policy` | `() → AddonPolicy` | The active account's stored policy (the default without one); `useAddonPolicy` reads it so Settings → MCP shows "Turned off by your admin" where an Add button was (`MCPSettingsSection.tsx`) |
| `addons:remove-requirement` | `({agentId, name}) → AddonActionResult` | Removes one requirement by name (one no source lists, or a custom one); refused as data on a team agent shared to use, a non-kit agent, a missing name (`invalid_name`) or a failed write (`write_failed`); a name not in the list is a no-op |
| `addons:plugin-status`, `:set-plugin-disabled`, `:update-plugin`, `:reveal-plugin`, `:recheck-runtimes` | | The plugin row's channels: [Marketplace Plugins — Technical Details](plugins_tech.md#ipc-channels) |

Their refusals are **data** (`{ok: false, code, message}`; codes such as `not_found`, `invalid_ref`, `blocked`, `preparing`, `unsupported`, plus the pin paths' own), including a `DomainError` thrown by the attach (caught in the directory and returned), because a thrown error's code does not survive IPC. The `marketplace-skills:discover` and `:add` channels were removed with the old skill modal; `local-agent:mcp-attach` remains the connector attach the directory calls.

The four connector channels above throw rather than return outcomes: their failures are only ever shown as a sentence (`unwrapIpcError`), so no code has to cross the boundary.

## Services & Key Methods

### `src/main/db/agentMcp.ts` — `agentMcpRepo`
- `listProviderIds(ownerId, agentId)`: an inner join on `mcp_providers` filtered by `mcp_providers.user_id = ownerId`, so a link to another scope's connector is never returned
- `attach(agentId, id)`: `onConflictDoNothing`, which keeps the first attach time. Returns whether a row was inserted
- `detach(agentId, id)`: returns whether a row was removed
- `agentsUsing(ownerId, id)`: joins `agents`, filtered by the agent's owner
- `agentIdsFor(id)`: every agent, any owner. It exists for tool-change fan-out, but the bridge currently re-reads per entry with `addonIds` and never calls it

### `src/main/services/agentMcpService.ts` — `agentMcpService`
- `list` / `attach` / `detach` / `agentsUsing`: the IPC surface. A folder agent is one that `agentRepo.listFolder(ownerId)` returns (`takesAddons`). `attach` and `detach` call `refreshAgent(agentId)` only when the row actually changed. That is a dynamic `import('./conductorBridge')`, because the bridge imports this service
- `providerIds(ownerId, agentId)`: the bridge's read. It does not check the agent's ownership, because the run already resolved the agent
- `ensureConnected(ownerId, agentId, {signal, waitMs})`: never throws. For each attached id:
  - already `connected`: forget its retry state, skip
  - a connect *this service* started is in flight (`connecting` map): wait for it only if it is a first try
  - a connect someone else started is in flight (`mcpManager.connecting(id)`, e.g. Settings): wait for it if this version has no history yet; never call `connect`, which would cancel it
  - `connectsUnattended(row)` false (disabled, `connected`, `awaiting-auth`, OAuth with no tokens, bearer with no token), or `needsUser` recorded, or `Date.now() < retryAt`: skip
  - otherwise call `mcpManager.connect(mcpRowToConfig(row), { interactive: false })`. On success, delete the record. A result of `disconnected` while `mcpManager.connecting(id)` holds another attempt means the user's own connect replaced this one. That is not a failure either: the record is deleted and the next turn treats it as a first try. Any other result records `{version, failures, retryAt, needsUser: mcpManager.needsUser(id)}`, where `retryAt = now + min(BASE · 2^(failures-1), MAX)`. `version` is re-read from the row *after* the attempt, so a refresh that saved new tokens and then failed does not count as a new version and earn a fresh first try
  - a first try is marked in `tried` *before* it settles, so a turn that starts meanwhile shares it rather than starting a retry
  - waits on `Promise.race(allSettled(first tries), timer(waitMs), abort(signal))`
- `versionOf(row)`: `configRevision` + the sha256 of the encrypted OAuth or bearer blob. Both maps (`connecting`, `tried`) are module state, so a restart starts over
- `resetForTests()`

### `src/main/services/addonDirectory/`
- `createAddonDirectory(deps)` is pure over its deps (providers, agent facts, the pin and attach calls for skills, plugins and connectors, `pluginBlock` / `mcpBlock`, `policies`, `noteMcpRequirement` / `dropMcpRequirement`, `mcpSetup`, `findMcpByRef`, `createMcpFromDirectory`, `deleteMcp`), so the merge, the states and the dispatch are tested with fakes; `index.ts` wires `localAgentService`, `catalogSkillService`, `marketplaceSkillService`, `marketplacePluginService`, `stdioRuntimes`, `agentMcpService` and `mcpService`. Source ids: `core-catalog`, `core-marketplace`, `core-marketplace-plugin`, `core-mcp-directory`, `this-computer`, `mcp-registry:<id>`
- `list`: every ungated provider is read first (core's policy comes with them, stored through `policies.set(settingsUserId, policy, account)` with the account fixed *before* the read), then those the policy allows (given `coreMcpDirectory` in the context when core's index answered); the answers are ordered by provider order (Cinna, this computer, MCP registries); a throwing provider becomes that source's `error` and the rest answer. Then `mergeLocalProviders`, then `withPluginBlocks` (`pluginBlock` for a plugin, `mcpBlock` for a local MCP entry — once per entry per read, `blockReason`), then each entry gets its state. The skill-access check (`changeability`, one git read of the folder's remote) runs once per read and only for a kit agent, and **fails open**: a failed check never fails the read, and Add checks again
- `mergeLocalProviders`: a `this-computer` entry whose `registryRef` matches another source's entry takes that entry's place, carrying its metadata but keeping the local ref, `mcpProviderId` and local setup facts; failing that, one whose `serverKey` (`serverIdentity.ts`: `serverKeyOfConnector` — a normalised URL, or the registry and name of what its `npx` / `uvx` / `docker run` command runs, no version) equals the `serverKeyOfInstall` of a `core-mcp-directory` entry takes that entry's place, once per entry (what a local ref took first is not doubled). `add` of a core MCP entry attaches such a connector (`deps.findMcpByServer`) rather than creating one. This is the only merge of two entries; the Cinna Official index is separately left unlisted when core's directory answered (`mcpRegistries.list`)
- `stateOf` order: already added (`mcpProviderId` attached, or a skill pin with that package/entry uuid, or a plugin pin with that entry uuid) → `added` (with "Added — *what it needs*" when the connector has a pending step); `pending` → `preparing`; `unsupported` → `blocked`; skill or plugin on a non-kit agent → `blocked`; skill or plugin with a read-only agent → `blocked` with `changeabilitySentence`; `blockReason` → `blocked`; plugin whose `compatibilityOf(components, null, agent.engine)` is not compatible → `partly_compatible` / `incompatible` with its sentence; a `setupReason` → `addable_with_setup`; else `addable`
- `search`: asks the providers that have `search` and pass the policy, remembers the hits (`searched`, an LRU of 500, so a detail or an Add can name an entry no list holds), folds hits that are already local connectors into those, and states each for the agent
- `add`: catalog → `catalogSkillService.addToAgent`; marketplace → `marketplaceSkillService.addToAgent`; `core-marketplace-plugin` → `addPlugin` (`marketplacePluginService.addToAgent`, its `next` passed on); `this-computer` → attach, then the connector's `mcpSetup`. Any other ref: an unowned ref is `not_found`, a gated provider is `blocked`; an existing connector with that `registry_ref` is attached; else the entry is found (memory, the provider's `find`, or its list) and refused if it is a plugin, pending, or not an MCP entry with an install; then `blockOf` (a local server's runtime or the policy → `blocked`); otherwise `mcpService.createFromDirectory`, then attach, and **on an attach failure the connector just created is deleted** before the refusal is returned. After a connector add on a kit agent, `noted` writes its requirement (never failing the add)
- `remove`: finds the pin by package/entry uuid (catalog, marketplace, plugin) and calls the existing remove; a connector is detached by local id or by `registry_ref`, and on a kit agent its requirement is dropped first (`dropMcpRequirement` — a local ref is resolved to the connector's directory ref)
- `mcpRequirements(userId, agentId)`: for each `mcp_servers[]` element of a kit agent, in order: no ref → `needs_setup` "Set it up as a custom connector"; a local connector with that `registry_ref` that is not attached → `needs_setup`, attached with a pending `mcpSetup` step → `needs_setup` with the step's sentence, attached and fine → `ready`; none, and the owner provider unknown or gated → `unavailable`; else the entry is looked for in the listing (read once, lazily) or the provider's `find`, → `needs_setup` with `entryRef` the ref; its source errored → `needs_setup` "Could not check…"; nothing → `unavailable`. `MCP_REQUIREMENT_TEXT` holds the sentences
- Providers: `cinnaCore` — see below. `thisComputer` lists `mcp_providers` as `mcp` entries, **leaving out every managed row** (a plugin's servers show inside the plugin's row), and computes the step with `setupOf(row, status, needsUser)`: `enable` (switched off), `env` (`missingEnvOf(row)` — a plugin's or directory connector's empty setting), `bearer` (no token), `oauth` (no tokens and the server asked for the user or is `awaiting-auth`), `connect` (status `error`), else none. `mcpRegistries` lists the `cinna-official` registry whole (limit 100) **unless `ctx.coreMcpDirectory`** (set only when core's index returned MCP entries) (core's MCP directory is seeded from it; `find` still resolves its refs) and searches the `official` one (limit 50, an empty query returns nothing); it is gated by `externalDirectories`, uses an entry's first remote, and marks an entry that `requiresAuth` as needing a sign-in or token after adding
- `cinnaCore` (`createCinnaCoreProvider(reads)`): `list` returns nothing, without an error, when signed out or local-only, and `invalidate()` on `refresh`. **Unified read** (`unified`): `GET /api/v1/addons/directory?runs_on=desktop` through `cinnaSend`, mapped by `fromCoreEntry` (per-source kinds in `KINDS_OF_SOURCE`; a marketplace *plugin* gets the `core-marketplace-plugin` ref; an MCP row's `install.mcp` goes through `fromCoreMcpConnect`, which accepts an http/sse URL or an npm/pypi/oci stdio package and drops anything else, leaving the row `unsupported`/`unknown_source`) and `fromCorePolicy` (snake_case flags; a missing or non-boolean one keeps the default). The answer is cached with its `etag` for `CORE_DIRECTORY_TTL_MS` (60 s); after that, and on a refresh, it is asked with `If-None-Match` and a 304 keeps the held entries. A 404 puts the account in `legacy` (the three older reads: `libraryService` catalog listing, `marketplaceSkillService.discover`, `marketplacePluginService.discover`; no policy) until the next refresh; 401/403 and a reauth error are `errorCode: 'reauth'`; any other failure serves the cached index (`staleListing`) with `CORE_SOURCE_TEXT.directoryFailed`. The listing carries `mcpDirectory: true` only when the index holds at least one `core-mcp-directory` entry (`withMcpFlag`), which is what `ctx.coreMcpDirectory` and the registries provider's silence follow
- `mcpService.createFromDirectory(userId, input)`: `input` is a remote server (`{transportType: 'sse'|'streamable-http', url, authType}`) or a local one (`{transportType: 'stdio', command, args, env}` — the setting names, each stored empty and the values encrypted) plus `{name, registryRef, connect}`. It inserts the provider enabled with its `registryRef` and, unless `connect` is false (a bearer server with no token yet, a local one with settings to fill in), connects with `{interactive: false}`. It returns `{id, status, needsUser, error?}`. In `index.ts` the local branch first installs the managed uv for a PyPI package (a failure is the refusal `runtime_failed`), builds the command with `directoryStdioLaunch` (a package that fails the grammar is `unsupported`, `DIRECTORY_PACKAGE_REFUSED`), and derives the setup step: `env` when the server declares any, else `connect` (with the error) for a failed connect, none when connected. A remote one's step is `bearer` for a bearer server, `oauth` when `needsUser`, `connect` for any other failure, none when connected
- `mcpProviderRepo.upsert` writes `registryRef` on insert only

### Policy
- `src/main/services/addonDirectory/policy.ts`, `addonPolicies`: `get(settingsUserId)` returns the active account's policy — the in-memory one, else the stored one (`addonPolicyRepo`), else `DEFAULT_ADDON_POLICY`; the argument names the scope the caller is in and does **not** pick the policy. `set(settingsUserId, policy, forAccount?)` writes through (only when the policy changed) for the account the read began with, and is ignored with no account. `accountKey()`, `store()` (what the directory is given) and the test hooks `_configure` / `_reset`. The account is `<profile>@<server origin>` of the active profile when it is a `cinna_user` with a server URL, else null. A store that cannot be read (no database, in a test) falls back to memory, then the default; `storedPolicy` accepts only an object with all four booleans
- Readers: the directory (`allowed(provider, policy)`, the result's `policy` that the picker honours), `mcpService.upsert` (`customMcp`), `managed.ts` `managedLaunchBlock` / `directoryLaunch` and `stdioRuntimes.blockOf` / `marketplacePluginService.serverBlock` (`stdioMcp`), `drivers/index.ts` `kitAgentAddonPlugins` and `marketplacePluginService.status` (`pluginHooks`)

### `src/main/services/conductorBridge.ts`
- `prepare()` no longer returns early for `input.nested`. It still requires `runScope`, `canConduct(agent)` (ACP, not WebSocket) and a non-remote plan. Then:
  - `addons = addonIds(agent, runScope)`. A nested run with none returns `undefined`, so there is no lease, as before
  - with any addons, it `await`s `agentMcpService.ensureConnected(settingsUserId, agent.id, { signal: input.signal })`
  - nested: the entry key is `['nested', chatId, agentId]` (direct: `[chatId, agentId]`), `wake` is replaced with `() => false` (a nested session cannot open a turn of its own), the delegation/handover providers are not built, `applyConductorToolPolicy` and the conductor context are skipped, and `messageRepo.saveToolCall` is skipped (results still `publish`). `Entry.nested = true`
  - session digest: direct turns read and save `conductor_sessions` as before. Nested turns never touch it. `freshSession` is `plan.sessionToolsFixed && nestedDigests.get(key) !== hash`, and with `sessionToolsFixed` the lease carries `session: {read, save}` over `nestedSessions`. `sessionReady` / `sessionLost` write `nestedDigests` / `forgetNested(key)`
- `providers(entry)`: a deleted or invisible chat gives `[]`; a chat conductor with `toolPolicy === 'none'` gives `[]`; `entry.nested`, or a chat that is neither the agent's own nor `router === 'human'`, gives `connectedMcp(addons)`. Otherwise it gives controls, then handovers, then `connectedMcp(chat ∪ on-demand ∪ addons)`, then (with no controls, in a coordinator chat) agent tools. The middle-branch rule used to return `[]` for a chat bound to another agent
- `refreshAgent(agentId)`: `refreshTools()` on every live entry (retiring included) whose agent matches, in any chat
- `onMcpToolsChanged`: an entry re-lists when the changed provider is in its chat's baseline, its on-demand set **or its agent's addons**
- `installChatSessionForgetter`: also `forgetNested(key)`

### `src/main/agents/drivers/acp/acpDriver.ts`
- `runTurn`: `if (conductor?.session) ctx.sessionSlot = conductor.session`. `remembered` reads that slot when set, else `runtime.readSession(chatId)`
- `rememberSession`: saves to `ctx.sessionSlot` when set, else `runtime.saveSession`
- Test: `acpDriver.test.ts` › "keeps a nested session in the lease's own slot, leaving the agent's session in the chat alone"

## Configuration

None user-facing. The wait and backoff are the constants above, and the admin's policy (`AddonPolicy`: `externalDirectories`, `customMcp`, `pluginHooks`, `stdioMcp`) arrives from core, not from a setting.

## Security

- Tokens never leave main. The agent's runtime reaches a connector only through the Cinna MCP endpoint (loopback, per-session bearer), and the bridge proxies calls through `mcpManager`. See [Orchestrated Agents — Technical Details](../../chat/orchestrated_agents/orchestrated_agents_tech.md)
- An unattended connect is `interactive: false` all the way down to `ElectronOAuthProvider.redirectToAuthorization`, which throws `McpReauthorizationRequiredError` instead of opening a browser. Nothing a turn does can put an authorization page in front of the user
- The values of a local directory connector, like a plugin's, are encrypted (`env_secret_enc`, safeStorage) and decrypted in `directoryLaunch` only; the DTO carries names and `hasValue`. A requirement written to the manifest carries env *names* only and the portable command, never a value, a token or the managed binary's path
- A directory row is checked against its registry's package grammar before it becomes a command (`isRunnablePackage`): no flag, URL, `git+`/`github:`/`file:` source or path can reach `npx`, `uvx` or `docker`
- Attach checks both the agent (folder agent in the settings scope) and the connector (owned by the settings scope). Reads join on the connector's owner
