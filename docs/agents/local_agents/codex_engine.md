# The Codex Engine

## Purpose

Run kit and bare folder agents inside Cinna's chat UI on a Codex CLI that Cinna installs for itself: one pinned version, downloaded on first use and verified before it is ever run. Codex owns the login and coding tools; Cinna supplies the folder instructions, controls the run, and presents streaming output, approvals and questions through the shared ACP driver.

## Core Concepts

- **Codex engine** — `runtime.engine = codex`, an ACP launcher rather than a new driver or a Managed agent. It can be an agent's own choice or this machine's Default runtime.
- **Managed CLI** — the pinned Codex build Cinna downloads into `<userData>/runtimes/` and checks against a recorded SHA-256 and the version it reports. Every session Cinna spawns runs on it: folder agents, plain Codex chats and AI Functions. The version is the one the [interface contract](contracts/codex_interface.md) was run against, which is the point — the CLI that was tested is the CLI that runs.
- **Codex Path** — an explicit executable in **Settings → Local Development → Developer Tools**. It replaces the managed copy and is run as-is, so every surface labels it **unverified**. It exists for a platform Cinna has no pinned build for, and for trying a newer Codex before it becomes the pin.
- **The `codex` on the user's PATH** — not what a session runs on, with one exception: a copy that reports **exactly the pinned version** is used instead of downloading the same release again (`path-pinned`, shown as *your install*). It is version-gated, not checksummed, run from its real path, and re-identified before each turn, so a copy that updates itself is resolved again. At any other version it is still detected, because **Open in Codex** launches it and because a fresh installation reads it as a hint that this user wants Codex as the default runtime.
- **CLI login** — the authentication saved by Codex, including a ChatGPT login or a saved API-key login. Cinna holds no Codex credential and does not infer a subscription from a successful login check.
- **CLI profile** — Codex's normal user/project configuration and saved state, selected by `CODEX_HOME` when set. User/project instructions, skills and MCP configuration remain Codex's responsibility.
- **Work complexity** — Simple, Medium or Complex selects low, medium or high reasoning effort. No choice means medium effort. The model stays Codex's configured default unless the agent explicitly names one.
- **Approvals** — a separate per-agent Codex setting: Ask for approval by default, or Automatic. Both retain Codex's workspace-write sandbox; the setting chooses who reviews escalation requests.

## User Stories / Flows

### Select Codex and start a chat

1. Run `codex login` in a terminal; Cinna does not perform the login. Nothing needs installing first: the login is kept under the home directory, not beside a binary, so a login made with any Codex is the one the managed CLI reports.
2. Select **Codex** as the machine default, or choose it in the agent's **Settings → Runs on** selector. Codex is always offered, because there is nothing for the user to have installed; only a failed install withdraws it, and an agent that already names Codex keeps the option even then.
3. Optionally press **Install now** on the Runtime status line. The download is about 90 MB, and the alternative is paying for it at the top of the first Codex message, which waits for it.
4. Pick **Work complexity**. Changing to Codex clears the previous desktop credential/model and preserves the complexity, so a model from another runtime is not silently sent to Codex.
5. Send a message. Cinna checks the folder, installs the CLI if this machine has none, checks the login, assembles the instructions, opens or resumes the chat's Codex session and applies the approval mode before prompting.
6. Read text, tool results and plans in the normal chat. Answer any approval or question inline or through the shared Inbox request surface. A question's Other answer returns to the original Codex question, without a second companion-field widget.
7. Use **Stop** to cancel. Cinna settles pending asks and bounds the cancellation wait; a process that will not stop is retired by the shared driver.
8. A command Codex leaves running after its reply appears as a **Background** badge under the composer, with a Stop control. A subagent Codex starts appears as a **Subagents** badge. See [Session Activity](../session_activity/session_activity.md).

### Recover installation or login readiness

1. "Not installed" is only ever an install that **failed**: no pinned build for this platform, a download that did not finish, a checksum or version that did not match, or a Codex Path that is not a runnable file. The sentence names the remedy, and **Try again** sits on the Runtime status line beside it. A CLI that simply has not been fetched yet is not a problem and refuses nothing — a readiness that refused while the CLI was merely on its way would block the one action that fetches it.
2. A definite logged-out verdict asks for `codex login`. The check is asked of the binary the sessions run on, never of the PATH copy.
3. **Check again** on a failed install starts another attempt and answers at once rather than waiting for it; progress arrives on the Runtime row. After logging in, **Check again** refreshes the login verdict, as does Runtime tool refresh. A changed shell `CODEX_HOME` requires an app restart because shell environment resolution is cached for the process lifetime.
4. Saving or clearing the Codex Path takes effect when it is saved: the binary is resolved again and the remembered login verdict is dropped, so the Runtime row, the picker and the login state stop describing the previous binary. Before this, a row left red by a failed install stayed red above a path that would have fixed it, until a turn happened to run.
5. An inconclusive login probe permits a turn. The actual startup can then return its error; an unfamiliar CLI status message must not permanently strand a working installation.

### Continue after a restart or a settings change

1. Each chat remembers its engine session through the existing desktop and SQLite stores. A resumed session suppresses replay so prior output does not become a second copy of the next answer.
2. The next turn re-reads the folder and prepares current instructions and runtime settings. A changed launch specification replaces that agent's pooled process, then loads the remembered session with current configuration.
3. If the local engine cannot load its remembered session, the shared driver creates a new session. Existing Cinna transcript messages remain visible; they are not automatically replayed as replacement model history.

## Business Rules

- **Every spawned session runs the pinned version, and a PATH copy at any other version is never one of them.** Precedence is the Codex Path when one is set, else the PATH copy when it reports exactly the pin and Cinna has no managed copy yet, else the managed copy. A configured path that is not a runnable file is an error, never a silent fall back to the managed copy: the user named something specific, and quietly running a different Codex than the one they named is worse than saying the path is wrong. OpenCode accepts a PATH copy at any version; Codex accepts one only at the pin, because the version under test has to be the version that runs — the exact-version copy passes that same gate and saves only the download. [Claude Code](claude_engine.md#which-claude-runs) resolves the same way.
- **Nothing unverified is ever published.** The archive is compared with its recorded SHA-256 before it is unpacked, and the unpacked binary must then report exactly the pinned version before its directory is renamed into place. The digest proves these are the pinned bytes; the version proves the pinned bytes are what the manifest says they are. Either failure leaves nothing on disk a later run could mistake for an install. A successful install also removes this tool's superseded version directories and abandoned staging directories, which nothing did before.
- **Windows has no managed build.** Its release archive is several executables rather than one, so "publish the one file that was verified" does not describe it. A Windows user sets a Codex Path, which is the answer any unlisted platform gets; the restricted profile below is POSIX-only regardless.
- **Plain chats and AI Functions use a separate restricted profile.** Codex is selectable in chat modes, but starting a synthetic session requires the exact pinned CLI version on POSIX — read from the same manifest the installer reads, so the version installed and the version accepted cannot drift apart. A Codex Path running any other version therefore runs folder agents and is refused here by design: that override is unverified, and a restricted chat is exactly where unverified is not good enough. It also requires the reviewed adapter patch and a model from the bundled CLI catalog. It disables native actions and inherited MCPs while allowing only the chat's attached Cinna capabilities when its tool policy permits them. Unsupported configurations refuse with a remedy; saving a mode is not a compatibility check. Ordinary folder agents retain the native permissions described below. See [restricted policy](codex_engine_tech.md#restricted-chat-and-ai-function-policy).

- **The declared engine wins.** With no recognized engine, a declared credential or model retains the OpenCode path; otherwise the agent follows the machine default. On the first successful default-settling pass, an existing selection is preserved; an installation already holding folder agents keeps OpenCode; a fresh installation prefers an installed Claude, then Codex, then OpenCode. This is the one decision the PATH copy of Codex still informs: finding it says the user wants Codex, not that a session will run on it. Detection chooses installation, not login readiness. The result is saved once, so installing another CLI later cannot silently change billing or permissions.
- **No desktop credential on the Codex path.** Reading a manifest with both Codex and a credential ignores the credential and warns; Cinna refuses to write that combination. CLI readiness does not depend on the desktop provider catalogue or its credential enablement.
- **An explicit model is respected.** Folder Codex settings have no desktop provider-model catalogue or Advanced picker. A model can be declared in the runtime data; otherwise the CLI selects its default. Unsupported model/effort combinations are errors from Codex, not an invitation for Cinna to substitute a different model. The shared writer refuses model plus complexity together; tolerant reads still pass a declared model and derive effort from any recognized complexity. Chat-mode selectors separately use the runtime's cached session catalog or an explicit model ID.
- **The folder prompt supplements Codex, and how much of it depends on the folder's runtime mode.** A **kit** folder is a harness the desktop scaffolded, so its whole assembled prompt becomes `developer_instructions`. A **bare** folder is somebody's own repository and runs natively: Codex reads that folder's `AGENTS.md`, the user's `~/.codex/config.toml` and this project's trust decision by itself, exactly as it does for a terminal session there, so `developer_instructions` carries only the desktop's own context — what this turn is, where human input comes from, the machine's locale, where long output belongs. A folder adopted through `AGENT.md` or `CLAUDE.md` still has its instructions pasted in, because that is not the file Codex reads. Codex retains its own core instructions and normal configuration. Cinna does not apply Claude's settings isolation to Codex, and an empty injected MCP list does not promise that Codex has no configured MCP servers.
  - **Codex reading `AGENTS.md` natively is decided, not watched.** The interface contract does not cover it either. No Codex install was available for the 2026-09-17 engine probe, so unlike Claude's half of this rule ([the ACP contract](acp_contract.md#a-bare-folders-session-is-the-folders-own-and-that-was-watched)) it rests on the CLI's documented behaviour. If it turns out to be false, the symptom is a bare Codex agent that does not know its own instructions, and the fix is one entry in the per-engine map that decides what gets pasted in.
- **Ask for approval means escalation approval.** Workspace writes can proceed without a request; network access and filesystem operations outside the sandbox's allowed roots require escalation. Codex's normal temporary-directory allowances remain. Cinna does not promise a request before every edit or every external-file read.
- **Automatic uses Codex's reviewer in the same sandbox.** It is independent of Claude's setting and default. Cinna never selects full access, and a mode-setting failure refuses the turn before prompting. Grants can only answer requests the CLI actually forwards to Cinna.
- **Remembered grants belong to the agent and engine.** `codex:` action names prevent grants from another engine authorizing a Codex request. Command identity includes the complete request scope, including SOCKS host/protocol information that the adapter carries outside its raw input. Every patch path must be covered. Cinna sends only a one-time allow even when applying a saved grant, so it does not write the CLI's own persistent approval rules.
- **The CLI makes provider requests of its own.** Watched against the pinned version: once per session, beside the first turn, it asks a second model (`gpt-5.6-luna`, whatever model the session uses) for a thread title, and that request carries the user's first message verbatim — AI Function inputs included — though not Cinna's session instructions. After a model change it sends one compaction request on the model being left, carrying the conversation so far. Neither is offered a tool a restricted session is not allowed. Cinna asked for neither, cannot switch either off, and both are spent on the user's login; they are pinned by the contract (`codex.provider.auxiliary-request`) so a release that adds a third, or gives one of them native tools, fails a test rather than passing unnoticed. Because Codex titles every thread anyway, a chat whose root runs on Codex is named with that title and Cinna makes no title call of its own for it, so the first message is not sent to a model twice ([Auto titles](../../chat/auto_titles/auto_titles.md#codex-chats-are-named-by-codex)).
- **The CLI also contacts `chatgpt.com`, `github.com` and `api.github.com` on its own. Why is not known and has not been investigated.** Seen on 0.155.0 (2026-09-18) with the model provider on loopback: the E2E whole-flow run refuses each of these connections before TLS and pins the list, so a new host fails the run. Nothing here says what those requests are for, or what they would carry if they got through; Codex has no contract entry for it yet.
- **A rate limit is not recognised as one. Known gap.** A provider 429 ends a Codex turn normally, with the retry error as assistant text. The shared driver pauses a rate-limited chat on the Claude adapter's error shape, which Codex never sends, so on Codex a rate limit reads as an ordinary finished turn whose answer is the error. The contract pins what Codex does send, for whoever closes the gap.
- **The tool list is fixed when the session is created.** Codex ignores `tools/list_changed` mid-session, so a specialist attached mid-chat is given a new session rather than announced to the old one. The contract pins the ignoring: if it ever flips, that workaround is dead weight, and while it holds, removing it makes the specialist never callable.
- **Every Cinna tool call raises a permission ask, and a conducting session answers it itself.** Each call to an attached agent or MCP server arrives as a `codex:execute` request. The request carries no title or input, so it is recognised as Cinna's by the `tool_call` update with the same id, whose `rawInput.server` is `cinna` — never by the title, which for a shell call is the command. On a session conducting a chat (chat-owned or a folder agent) such an ask is allowed with no block and nothing recorded, provided `rawInput.tool` is a tool Cinna's MCP server listed to that session; the user attached those tools, and an Allow button per specialist call decided nothing. Anywhere else — no conductor lease, or a tool the server did not list — a standing grant answers it, otherwise the user is asked. In a chat-owned runtime an ask about anything that is *not* a Cinna tool is rejected outright. See [permissions](permissions.md#a-session-conducting-a-chat-is-not-asked-about-cinnas-own-tools). If the id stops matching, every Cinna call surfaces an opaque ask again; if the ask disappears, recorded `codex:` grants stop matching anything.
- **Authentication stays with the CLI.** The narrowed child environment preserves the selected profile and tool PATH but excludes shell billing keys and adapter overrides. This is environment narrowing, not isolation from Codex's own readable configuration or saved login.
- **A mid-turn message can start a turn nobody reads, so that turn is cancelled.** The adapter advertises the steering extension, so a message sent to a running Codex agent is offered to its turn. When that turn has already ended underneath, the adapter ignores the request to start nothing and starts a turn of its own. The desktop cancels it, retires the process unless another turn already holds it, and queues the message for the next turn. A steer sent before Codex has registered the turn it was just prompted with gets the same answer, only after that whole turn is over, so the desktop offers a message only once the turn has streamed its first content. Like every engine that steers, Codex is offered a message only while no tool call is running; a message sent during a command is queued and handed in when the command ends. The rule came from Claude, whose CLI aborts a running command for a steer; whether Codex would is not known, and waiting costs it only the wait. See [Pending Messages](../../chat/pending_messages/pending_messages.md) and [the ACP contract](acp_contract.md#the-steering-extension).

- **Background terminals are reported; subagents are read from the root session.** Codex is sent the AIR `asyncTasks` capability only. Sent `nativeSubagentSessions`, the adapter would drop the spawn call from the parent, and nothing on the wire would link the subagent to the chat. So Codex subagents are read from the "Start subagent" / "Complete subagent" tool calls on the root session (`_meta.codex.subagent`). A second collaboration shape (`spawnAgent` receivers, `agentsStates`) is also read. It was derived from the adapter's code and has not been watched ([the contract](acp_contract.md#subagents-nativesubagentsessions)).
- **Codex was not seen to start a turn of its own.** After its prompt returns it sends late updates for that turn's commands and the task's final state. Those update the activity badges, and they never open a turn, since saved rows are not rewritten. Should Codex ever start a turn of its own, it would be saved as a [follow-up turn](agent_turn.md#a-turn-the-agent-starts-on-its-own-is-a-follow-up-turn). Codex sends no end marker, so that turn would end after ten seconds with no traffic, no command running and no ask waiting.
- **A background terminal exists only when the model leaves a command running.** A prompt to "run it in the background" was watched turning into `nohup … &`: an ordinary command that ends at once, with nothing to show or stop.

## Architecture Overview

Agent settings / chat → typed preload and IPC → runtime resolution / shared ACP driver → Codex launcher → Codex binary service (Codex Path, else the managed pinned CLI, installed on first use) → Electron Node running the pinned ACP adapter → that CLI's app server → CLI-owned model and tools.

Approval / question → ACP request → shared pending request and Inbox → user answer → ACP response → the same running Codex turn.
