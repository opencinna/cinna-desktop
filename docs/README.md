# Cinna Desktop

Desktop client for remote agents (MCP, A2A, OpenCinna).

## Glossary

| Term | Definition |
|------|-----------|
| **Chat** | A conversation with an LLM, persisted in SQLite with messages and model/provider binding |
| **Chat Mode** | A named preset bundling an LLM provider/model, MCP servers, and a color — used to quickly start configured chats |
| **Provider** (a.k.a. **LLM Provider**) | An LLM service (Anthropic, OpenAI, Gemini, OpenAI-compatible, Ollama) configured with an encrypted API key — or, for a **keyless** type, with a host and no key at all. **UI naming:** surfaced to users as **"AI Credentials"** (the sidebar section, page title, "Add AI Credentials" button, and the chat-mode field). "LLM Provider" remains the canonical/technical name in code and these docs; "AI Credentials" is purely the friendlier user-facing label, matching CinnaCore. The two terms refer to the same thing |
| **Managed Provider / Chat Mode** | An LLM provider / default chat mode auto-materialized from a Cinna admin-provisioned credential (`managed = true`). Profile-scoped, sync-owned, read-only (local enable/disable only). See [Account Provisioning](llm/account_provisioning/account_provisioning.md) |
| **Adapter** | Implementation of the `LLMAdapter` interface that translates between our chat system and a provider's SDK |
| **Keyless Credential** | An AI credential that authenticates with nothing — Ollama today (`KEYLESS_PROVIDER_TYPES` in `src/shared/credentials.ts`). It carries a **host** in the existing `base_url` column instead of a key, so it needed no migration. `isCredentialUsable` is the single predicate every layer must call in place of `hasApiKey && !unsupported`: main and renderer both import it, because the rule about which credentials can run must not be able to differ between the screen that offers one and the service that spends it. It says nothing about `enabled` — that is `isCredentialActive`, the `enabled && usable` conjunction under a name, for the callers that mean both — and nothing about **reachability** — whether the server is answering has a different answer every minute and belongs to the detection probe. Two write-path rules guard it: a renderer-supplied `baseUrl` is honoured **only** for keyless types (a keyed row pointed at an arbitrary URL is key exfiltration with extra steps), and a credential's `type` is immutable, since the repo preserves a stored key on update and re-typing a row would spend that key under another transport. See [Local Models & Keyless Credentials](llm/local_models/local_models.md) |
| **Ollama Detection** | The `provider:detect-ollama` probe: `GET /api/version` then `/api/tags` against `OLLAMA_HOST` and `127.0.0.1:11434`, or against one host the renderer names. It **reaches any http(s) host it is given, and that is inherent** — a user's Ollama may legitimately be a box on the LAN, so there is no host list to check against. What bounds it is the shape of the answer and the cost of asking: `{running, host, version, models, alreadyConfigured}` and nothing else, 5 s and 1.5 s ceilings, no retry, no port scan, no LAN sweep, and **no probe the user did not cause** by opening the AI Credentials screen or pressing Test. `http`/`https` only, userinfo dropped, so a pasted link cannot smuggle a credential into a stored host |
| **MCP Server** | A Model Context Protocol server (local stdio or remote HTTP) that exposes tools to the LLM |
| **MCP Connection** | A live client session to an MCP server, managed by MCPManager |
| **On-Demand MCP** | An MCP server the user `@-mentions` into a chat so its tools are available only for that chat — tracked separately from the chat mode's baseline MCP set |
| **Baseline MCP** | The chat-mode-owned MCP set of a chat (`chat_mcp_providers`). Exactly the mode's list — empty means none. Unioned with the on-demand set at stream time; rendered as locked chips (no `×`) in the composer, since it's managed on the mode |
| **Tool Call** | LLM requests a tool -> main process calls MCP server -> result fed back to LLM |
| **MessagePort** | Electron's streaming channel used to send LLM response chunks from main to renderer |
| **Turn Outcome** | Internal result of one main-owned execution, distinct from whole-task completion: completed, needs_input, failed, canceled or budget, with saved final/partial text. Explicit runner ownership defers task finalization; uncertain request cleanup forbids automatic progression. See [Turn Outcomes](chat/messaging/turn_completion.md) |
| **Run Event** | One frame from a main-owned turn, optionally forwarded over a MessagePort — `RunEvent` (`src/shared/runEvents.ts`), the single vocabulary for agent and LLM chats. A nested agent's work arrives as `child`; a run waiting on a human posts `needs_input` — answerable by id now (`reply`) or by the next message (`next_message`) — and, for a `reply` ask settled while the turn is open, `input_resolved`. Events are live; transcript parts remain separate, while the Inbox persists driver reply addresses, durable next-message continuations and runner-owned gates. See [Stream Event Typing](development/stream_event_typing/stream_event_typing_llm.md) |
| **safeStorage** | Electron's OS-keychain encryption used for API keys and OAuth tokens at rest |
| **Agent** | An external AI service (e.g. A2A agent) registered by the user, communicating via a standardized protocol |
| **A2A** | Agent-to-Agent Protocol v1.0 — open standard for AI agent interoperability (discovery, messaging, streaming) |
| **Agent Card** | A2A discovery metadata (JSON) fetched from a well-known URL, describing agent capabilities and endpoint |
| **Message Part** | A typed segment of an assistant message (`kind: 'text' \| 'thinking' \| 'tool' \| 'tool_result' \| 'command_result'`) — A2A messages may persist a structured `parts[]` list driven by the Cinna `cinna.content_kind` metadata convention. The sibling `'notice'` kind bypasses `parts[]` and lands on its own `agent_transition` row (agent-side system notice). The `'command_result'` kind carries the synchronous output of a platform slash-command and IS the assistant turn for that user message |
| **Pinned** (transcript) | Whether the chat transcript is following the bottom of a streaming reply. Only the user changes it: scrolling up unpins, scrolling back into the bottom 64 px or clicking **Jump to latest** re-pins, and an arriving chunk never re-pins on its own. Unpinning requires the view to have actually moved *up* — not merely to be far from the bottom, since content growing opens up that distance with no gesture behind it. Following is instant and never animated; a smooth scroll restarted per chunk is what made a streaming table read as the window shaking. See [Transcript Scrolling](chat/conversation_ui/scroll_following.md) |
| **@-mention** | Typing `@` in the new-chat input to open a popup for selecting references (agents, and extensible for future types) |
| **Composer Menu** | The single left-side `[+]` button on the chat composer (`ComposerPlusMenu`) that consolidates attach-files, chat-mode, and add-agents/MCP into one menu — the mouse-driven sibling of the `@` / `~` triggers |
| **Capability** | A polymorphic chat tool source — an agent or an MCP server — surfaced uniformly as a selectable card in the `[+]` Add-agents/MCP picker |
| **Capability Picker** | The search-and-cards modal opened by the `[+]` menu's "Add agents / MCP" (`AgentPickerModal`, `activeFirst` multi-select): selected cards float to the top and hold position while toggling |
| **Router** | `chats.router` — who answers the next message: **`direct`** (the chat's bound agent, or the local model when there is none), **`human`** (several agents, and the *user* addresses one per message — **no model is involved at all**, so it works with no AI credentials configured), or **`coordinator`** (the local model conducts, calling agents and MCP servers as tools). One value read by the composer, the send path, the attachment scope and the job runner from one helper (`src/shared/chatRouting.ts`); it replaced a boolean that could not say "several agents, and the user routes". Surfaced as the badge left of Send. See [Chat Routing](chat/chat_routing/chat_routing.md). Only router persists after legacy orchestrated backfill and mirror removal. |
| **Address** | Which agent a message in a `human` chat is for. A **gesture, not a mention parsed from the text** — picking an agent from `@` or clicking its chip sets it; nothing scans the message body, so nothing moves while the user types. Defaults stickily to whoever the last user message addressed, then to the first attached agent |
| **Catch-up packet** | The compact transcript of what an agent missed while somebody else was answering, put in front of the user's text on the wire. Built from a per-`(chat, agent)` cursor (`chat_agent_cursors`) that advances **only on a completed turn**, so a failed or stopped turn leaves the same gap for the retry. Ordinary packets name tools and attachments without payloads; autonomous specialist packets include bounded tool-result text; capped at 4000 chars dropping the oldest. The same packet for every driver — a resumable session holds that agent's *own* turns, not the other agents' |
| **Orchestrated Mode** | The `coordinator` router: an LLM-root chat where the local model is the conductor and each attached agent is exposed to it as an emulated MCP tool, unioned with the real MCP tools |
| **On-Demand Agent** | An agent `@-mentioned` into a chat. In a coordinated chat the conductor calls it as a tool; in a `human` chat it is one of the counterparties the user addresses. Mirrors On-Demand MCP exactly (`chat_on_demand_agents`, sticky chips, one-shot announce) |
| **Tool Provider** | Polymorphic tool source the orchestrator unions — an MCP provider (`McpToolProvider`), an agent provider (`A2AAsMcpProvider`), or internal runner-only controls (`CoordinatorToolProvider`). Tool calls route by provider type |
| **Agent Sub-thread** | An agent-backed tool call rendered as an expandable nested thread showing the agent's own parts (thinking/tool/tool_result/text) rather than an opaque result string |
| **cinna.mcp Descriptor** | Optional backend-supplied shape (tool name, description, input schema) describing how an agent appears as an emulated MCP tool. Synthesized from agent fields when absent |
| **Note Attachment** | A profile note attached to a user message via the composer's `?` mention popup. Materialized at send time into a synthetic `.md` riding the standard file-attachment pipeline |
| **Attachment** | A file attached to a single user turn. Three sources: `cinna` (bytes on the Cinna backend, A2A-referenced), `local` (bytes in `userData/files/<userId>/<chatId>/`, used for raw-LLM chats), or `pending` (composer-only, paths held on disk for the new-chat flow until scope is known) |
| **Media Part** (file) | Resolver output handed to an LLM adapter: `image`, `document` (native non-image bytes like PDF), or `text` (UTF-8 from extraction). Adapters translate to provider-native content blocks |
| **Path Guard** | TTL-based allowlist of OS paths the renderer is permitted to reference. Populated by file dialogs and `webUtils.getPathForFile` so a compromised renderer can't synthesize arbitrary absolute paths |
| **User Account** | A local profile (username + optional password) that scopes all data — chats, providers, agents, settings |
| **Default User** | Built-in guest account (`__default__`) with no password, always present |
| **Cinna Account** | A user account linked to a remote Cinna server (cloud or self-hosted) via OAuth 2.0 + PKCE |
| **Cinna Server** | Remote service (cloud at `opencinna.io` or self-hosted) providing agent orchestration and future features |
| **Default Scope** | Shared storage under `__default__` user id — LLM providers, MCP servers, chat modes, and local agents live here and are visible from every profile |
| **Profile Scope** | Per-account storage under the active user id — chats, remote agents, agent overrides, and Cinna tokens live here and swap on user switch |
| **Agent Override** | Per-profile boolean (`agent_overrides` table) that overlays a synced agent's `enabled` flag so user toggles survive resync |
| **Job** | Reusable profile-scoped definition. Its stored local/remote schema selects an owning Job executor; ordinary desktop work prepares one renderer turn, while autonomous and remote admission belongs to main. See [Jobs](jobs/jobs/jobs.md) |
| **Local Schedule** | Reviewed kit static-prompt declaration enabled for one profile on this device; matching observed minutes create script Job attempts while Cinna is open. Consent and occurrence receipts never sync. See [Local Schedules](jobs/tasks/local_schedules.md) |
| **Job Executor** | Main-owned definition admission, preparation and dispatch, with explicit `renderer_turn` or `accepted` result disposition. Separate from the Task’s current executor and the agent transport. See [contract](jobs/jobs/execution_tech.md) |
| **Job Folder** | User-defined sidebar grouping for jobs (profile-scoped, name + collapsed-state + sort position). Thin collapsible separator — owns ordering, not execution config. A job lives in exactly one folder or at the root |
| **Job Run** | One execution of a Job. New runs link a durable task; local attempts retain their chat and remote attempts retain their binding. The shared executor reports ordinary turn results once after closure: failure/refusal and the model-round budget become failed, Stop becomes cancelled, and open continuations defer completion. Explicit runner-owned turns leave the whole-task decision to their runner. Remote refresh projects into only the matching active attempt; historical attempts retain their outcomes. See [Jobs](jobs/jobs/jobs.md), [Tasks](jobs/tasks/tasks.md) and [Turn Outcomes](chat/messaging/turn_completion.md) |
| **Cinna Task Job** | Stored remote Job definition: creates a local task and hands it to an available adapter. Original run provenance remains; refresh follows its current task ownership |
| **Script Definition** | Version-1 portable agent aliases and dependency steps stored on a Job/Task; validated at authoring and execution. [Definition](jobs/tasks/script_definitions.md) and [runtime](jobs/tasks/script_execution.md) |
| **Autonomous Task** | Main-owned coordinator or script execution with durable questions, bounded queues and explicit checkpoint recovery; storage alone does not start work |
| **Task** | Durable, profile-scoped work with an immutable goal, current status, assignee and handoff note; a job is its reusable spec and a run is one attempt. See [Tasks](jobs/tasks/tasks.md) |
| **Inbox** | One list of live driver replies, durable runner/next-message questions and remote asks on known blocked tasks, rendered through the transcript's shared controls. Failed reads disclose an unknown count; failed delivery preserves the question draft. See [the Inbox](jobs/tasks/inbox.md) |
| **Executor** | Where a task runs now (`desktop` or `remote`), distinct from its immutable local/remote origin. A desktop executor also has a device claim; takeover changes ownership without starting work. See [Tasks](jobs/tasks/tasks.md) |
| **Task Comment** | Authored content on a cinna task (`comment_type = message \| result`); see also Activity for system-generated entries |
| **Task Attachment** | A file attached to a cinna task or one of its comments. Distinct from `FileUpload` (chat attachments) — uses a task-scoped download URL (`/api/v1/tasks/{taskId}/attachments/{id}/download`) |
| **Task Activity** | UI grouping for system-generated comment types (`status_change`, `assignment`, `system`) — shown as a compact collapsible log separate from authored comments |
| **Handoff Note** | The markdown one worker on a task leaves for the next (`tasks.handoff_note`). Also **exported** as `<userData>/tasks/<task-id>.md` — frontmatter naming the task, the note as the body — so something outside the app can read it. The database is the note and the file is a view of it: nothing is ever read back in, so the export hangs off **every** `taskService` write rather than the note write alone, because five of the frontmatter fields change from elsewhere and a file claiming `in_progress` under a task that finished an hour ago would never be corrected by anything. It never throws — the row is already committed, and a visible wrong status is worse than an invisible missing file. Not in an agent folder: exactly one file in one of those is the desktop's, and most assignees have no folder at all. The same rule reaches the sync apply path — a task arriving from another device is written through `taskService`, never `taskRepo`, so the file follows a row this machine did not author. See [The Handoff Note, Exported](jobs/tasks/handoff_note_export.md) |
| **Manifest Handback** | A declared kit agent’s bounded final-answer note, authorized only for the existing task coordinator’s handed-off specialist. Normal unmarked return remains unchanged. See [Manifest Handback](jobs/tasks/manifest_handback.md) |
| **Handoff Receipt** | Local durable record of a remote handoff attempt, including accepted or uncertain execution and explicit recovery. Survives task deletion, never syncs, and is removed with its owning account. See [Remote handoff](jobs/tasks/remote_handoff.md) |
| **Remote Task Adapter** | `RemoteTaskAdapter` — everything system-specific about a task that also lives somewhere else (cinna-core, Linear, GitHub Issues, a managed-agent service), behind one interface, the way `AgentDriver` does for agents. **Callers ask `capabilities()`, never the id**, so a poorer remote is expressible rather than broken; **only `create` invents a binding**, and every other call returns the one it was given; and **ordinary sync follows a committed local write**. Explicit handoff records uncertain create/execute outcomes before permitting another start; it does not retry them as ordinary field writes. `adapterFor(id)` is total — an id this build does not implement resolves to a **null adapter** that keeps the id, refuses everything and says which service it stands for, because a task bound by a newer build must still open. No adapter id may be compared to a literal outside `src/main/tasks/adapters/`, which the kind-branch ratchet holds at zero. Liveness is the separate tri-state `liveSession` method, never a snapshot field; an unknown answer requires an explicit take-over confirmation. One implementation ships — cinna-core — and it is a subject of the same contract suite as the six fakes, over a fake *server* rather than a fake adapter. See [Remote Task Adapters](jobs/tasks/remote_adapters.md) and [the cinna adapter](jobs/tasks/cinna_adapter.md) |
| **Remote Dirty Marker** | One entry in `tasks.remote_dirty` — `title`, `description`, `priority`, `assignee`, `status` or `handoffNote` — meaning **this device knows something the bound service does not**. Written by `taskService` on any mutation of a bound task, never by anything that talks to a network, which is what lets a laptop that was asleep, offline or unlinked push the change later. Cleared by the push, and **only when the value it stands for has not moved since the attempt**: clearing by name alone erased the marker for a field the user changed *after* the old value went up, leaving it no longer dirty so the next pull overwrote the newer value with the older one the service was given. A pull never overwrites an owed field for the same reason. `goal` is deliberately absent (immutable once created) and so is `router` — no remote has a field for who answers in this app's chat. It is also one of the two columns that **never travel to the user's other devices** (with `remote_synced_at`): a peer that has never spoken to that service must not inherit a list of fields this machine owes it. See [Keeping a Bound Task in Step](jobs/tasks/remote_sync.md) |
| **Executor Claim** | `tasks.executor_device` — the sync device id of the one device allowed to speak for a task's **run**. `status`, `assignee` and `handoffNote` are writable only there; `title`, `description`, `priority` and `router` are writable anywhere, because fixing a title on the machine in front of you is not a claim on the run. **A claim, not a lock**: nothing on the server arbitrates, so what it guarantees is only that two devices cannot both *believe* they own a run without one of them having written that it did. Enforced twice — `requireRunsHere` on the local write path and its twin on the **apply** path, since app-sync is whole-record last-writer-wins and an ungated edit on a second device otherwise pushed that device's stale copy of the three guarded fields back over the holder's fresh handoff note, finish time and error. The guard is narrow on purpose: it holds only while this device is the named holder *and* the arriving record still agrees, so a record naming a different holder is a take-over and yields entirely, and a `null` claim confers nothing. A null used to mean both "nobody in particular" and "this device", which read as *mine* on every machine once a profile gained peers — enrolment adopts what nobody holds. Surfaced as `TaskDto.runsHere`, derived in main because the renderer cannot ask which device it is. See [A Task on the User's Other Devices](jobs/tasks/cross_device.md) |
| **Status Path** | The *sequence* of status writes that moves a remote copy to where the local task is, not the destination on its own (`taskStatusPath`). A remote validates transitions, so a desktop job that ran and finished between two polls pushes `new → completed` — which is refused, on the same HTTP status that also means "not your task", which is why the most predictable defect in this area would have read as a permanent deletion. Breadth-first, because a **longer route records a false history rather than a richer one**: routing a task cancelled before it ever ran through `in_progress` makes the service stamp an execution time for work nobody did, and replaying a `blocked` that is already over lights the user's own inbox for a resolved block. Every step is itself a push, so the walk is confined to `REMOTE_WRITABLE_STATUSES` — which is what keeps `archived`, reachable from everywhere and reaching nothing, out of the middle of a path. `null` is a real answer: there is no way to tell a completed remote the task is in progress again, and the marker is dropped rather than retried for ever |
| **Note** | A profile-scoped markdown document (title + body) the user inline-edits in the Notes tab. Autosaves on debounce; rendered with the same `react-markdown` stack used for chat bubbles |
| **Note Folder** | User-defined sidebar grouping for notes (profile-scoped, name + collapsed-state + sort position). Mirrors Job Folder semantics — a thin collapsible separator that owns ordering, not content |
| **Hint** | One line of shortcut-teaching copy shown in the new-chat screen's bottom bar. Either **ambient** (enters a shuffled rotation) or **contextual** (preempts the rotation when a matching user action fires). Gated on being actionable, and retired once the user has used what it teaches. See [Hints](ui/hints/hints.md) |
| **Login-Shell Environment** | The environment a user's shell produces after sourcing its profile. A Dock-launched macOS app inherits `launchd`'s bare environment instead, so the app resolves the login shell's once per lifetime and takes `PATH` from it. See [Shell Environment Resolution](development/shell_environment/shell_environment.md) |
| **Child Inherit Set** | The narrow, fixed allowlist a spawned third-party process (today: a stdio MCP server) receives — the MCP SDK's list valued from the login shell, plus session and proxy/CA variables — with the caller's own `env` map merged on top and always winning |
| **Detected Tool** | A developer tool the desktop probes for on the login-shell `PATH` (`claude`, `codex`, `opencode`, `code`, `cursor`, `uv`, `git`, `make`, `python3`), offered as a `cli-assistant`, an `editor`, or a feature-gating `runtime` |
| **Default Tool** | The one `cli-assistant` or `editor` a local agent folder opens in with a single click — the agent page's **Open in <tool>** button and the New-agent flow's "Build it with…" step. Stored as a `LocalToolId` in the `localAgentsDefaultTool` setting, **rewritten by the last pick** from either surface, set or cleared explicitly in Settings → Local Agents, and resolved against the detected list on every read so an uninstalled tool degrades to "ask". `localAgentsAutoOpen` lets a new agent open there without the step. See [Open in Tools](agents/local_agents/open_in_tools.md) |
| **Init Prompt** | The paste-anywhere briefing for one local agent folder — its path, the agent's name, and the first entry document the folder actually has (`AGENTS.md` → `CLAUDE.md` → `README.md`, else the manifest plus `Local/<slug>/docs/WORKFLOW_PROMPT.md`; a **bare** folder uses `README.md` → `AGENT.md`, the builder's document first). Built in main from the **index row**, copied to the clipboard by the Open-in menu's "Copy prompt for another tool". It is how an assistant the desktop cannot *launch* — one already running elsewhere, one in a browser, one with no launcher — is pointed at the same folder. See [Open in Tools](agents/local_agents/open_in_tools.md) |
| **Agents Root** | A registered folder local agent folders live under. Two kinds (`agent_roots.kind`): **workshop** — the kit shape, which may carry its own `.cinna-kit/` copy of the contract and is where new agents are scaffolded — and **external**, a folder the user pointed at that is only ever read. Every "Open in…" target must `realpath` to a directory at or under one, which is why overlap between roots is refused — see [Open in Tools](agents/local_agents/open_in_tools.md) |
| **External Root** | An `agent_roots` row with `kind = 'external'`: a folder adopted for the agents already in it. **Cinna installs nothing into it** — no templates, no `.cinna-kit/`, no `Local/`, no `app-data/`; the only file ever written there is an agent's own `AGENT.md`, and only when the user edits it on the agent page — and it is walked two levels deep for folders holding an `AGENT.md`. Registered by a two-call adopt (`local-agent:folder-pick`, then `:folder-add`, which refuses any path but the one just picked). See [Bare Agents & External Roots](agents/local_agents/bare_agents.md) |
| **Bare Agent** | A folder that is an agent because it holds an `AGENT.md` — singular, and deliberately not `AGENTS.md` — and for no other reason (`LocalAgentDto.kind = 'bare'`). No manifest, so no commands, credential slots, example prompts or publications; its system prompt is `AGENT.md` alone, and its identity is **positional** (`folder:external:<rootId>:<relPath>`) because there is no file to state a durable one. It **does** choose its own runtime, from the same "Runs with" panel a kit agent gets — but the answer is kept in that agent's Desktop State rather than in the folder, since the desktop writes nothing there; with no choice made it runs on the Default runtime. Adopted by path, never scaffolded. See [Bare Agents & External Roots](agents/local_agents/bare_agents.md) |
| **Agents Folder Update** | The git check on a registered root that is a working tree: is it behind, what are the missing commits, and one action — `merge --ff-only`. **It never resolves a conflict and never tries**; every state it cannot handle (`dirty`, `diverged`, `no_upstream`, `fetch_failed`, `not_fast_forward`, `git_missing`, `not_a_repo`) is a refusal naming the state and telling the user to sort it out in their own tools. Applies to workshop and external roots alike; renders nothing at all where the folder is not a repository, decided at first paint from a cheap stat walk carried on the root (`AgentRootDto.isGitRepo`) rather than from the panel's own query, so no settings row moves once the answer lands. Every command runs at the **repository root**, which may be an ancestor of the registered folder, so the panel names the repository and the refusals blame it rather than "this folder". See [Agents Folder Updates](agents/local_agents/folder_updates.md) |
| **Agents Home** | The one registered agents root marked default — `~/Documents/CinnaAgents` unless the `localAgentsHome` setting overrides it. Where the New Agent button scaffolds. Can be moved (only through the OS picker behind `local-agent:home-choose`), never removed. On macOS its **first** creation is a write into a TCC-guarded folder, so it is gated on an in-app explainer — see Home Access below |
| **Home Access** | Whether the Agents Home can be used: `ready`, `needs_consent` (nothing has touched it and macOS is about to ask), `denied` (refused). Only ever anything but `ready` on macOS. The gate lives in `agentsHomeService.ensureHome`, which **refuses** rather than writing — because the alternative was the system's *"would like to access files in your Documents folder"* prompt arriving mid sign-in, raised by a hook whose entire output was a sentence naming the folder. There is no way to ask macOS whether a prompt is pending, so the app answers from its own record: the acknowledgement in `localAgentsHomeAcknowledged`, a root row plus the folder on disk, or the path not being guarded at all. A refusal is held **in memory for the process and never stored** — macOS remembers it, a retry costs one failed `mkdir`, and a stored "denied" would keep reporting a problem already fixed. What is withheld is the **home row**, never the roots list. See [The Agents Folder Question](agents/local_agents/home_access.md) |
| **Folder Agent** | An agent that *is* a folder on disk (`agents.source = 'folder'`, row id `folder:<manifest uuid>`, protocol `local-folder`). Machine-local, default/settings scope. Distinct from `'local'` (a hand-added A2A URL) and `'remote'` (Cinna-synced). See [Agents Home, Scanner & Folder Index](agents/local_agents/folder_index.md) |
| **Folder Index** | The `agents` rows derived from scanning the roots, plus the `agent_roots` rows saying where to look. A rebuildable cache over the files, with exactly four values a rebuild cannot recover: `enabled` (the one column it owns), and a bare agent's `displayName`, `hidden` and `runtime`, which live in that agent's desktop state because its folder may not be written to |
| **Readiness** | How ready an agent folder is to run: `ok`, `credentials_needed`, `invalid`, `contract_too_new`. Always a renderable *state*, never an exception — a manifest is briefly unparseable every time an assistant saves it |
| **Turn Lock** | Per-agent, in-process lock. The turn holds it for its streaming half; page editors refuse to save while held; the folder watcher defers its rescan (both the per-agent and the whole-root branch) until release. `anyHeld()` — the global predicate — no longer gates anything about an engine: since every agent has its own process there is nothing shared to restart underneath a streaming turn |
| **Desktop State** | One agent's per-machine state: local API base URL, agent token, engine sessions, permission grants, the Claude engine's **Approvals** setting, last status — plus, for a bare agent, the name the user gave it, whether it is in the list, and the runtime it was given, none of which any file in its folder can state. Two locations, and the **root** decides which: `app-data/desktop.json` inside a kit folder (the one file in it the desktop owns), and `<userData>/external-agents/<name>-<hash of realpath>.json` for a bare one, whose folder is never written into. Never probed from the folder — a `cinna-agent.json` can arrive with one `git pull`, and an agent's sessions and grants must not move when it does. The token never leaves the main process |
| **Permission Profile** | The `permission` block written onto every folder agent's entry in the generated OpenCode config — an agent on the [Claude engine](agents/local_agents/claude_engine.md) has no such entry; there, the agent's **Approvals** setting decides whether Claude Code's own reviewer answers first (the default), with that SDK's ask-callback and the same standing grants behind it. An agent works freely **inside its own folder** (`read`/`edit`/`write`/`bash` allow); what asks is what the folder does not cover — `external_directory`, `webfetch`, the agent's own manifest and workflow prompt, secret files, `sudo` / `rm -r`. Identical for every agent unless its manifest's `runtime.permissions` replaces an entry. **Not a sandbox:** the shell is gated on command *text*, so a command can reach anything the user can. See [Local Agent Permissions](agents/local_agents/permissions.md) |
| **Standing Grant** | One remembered *Always allow*: `{action, pattern, scope, decidedAt}` in that agent's **Desktop State**, shared by both engines and stored under the action **the engine that raised the ask actually named** (`bash` on OpenCode, `Bash` on Claude) — the two vocabularies are never mapped onto each other, so a rule written on one engine cannot silently authorise the other — `app-data/desktop.json` inside a kit folder, and a file under `<userData>/external-agents/` for a bare one, whose folder the desktop writes nothing into. A bare agent's are therefore keyed on where its folder sits: moving it starts a new agent, which is asked again. The desktop is the authoritative store — OpenCode's own `always` writes a **user-global** row naming no directory, session or agent — measured again over ACP, where one `allow_always` silenced every later ask in that folder including in a new session in the same process — so `allow_always` is **filtered out of the agent's options before an answer is chosen**; a covered ask is answered `once` automatically with **no block written to the transcript at all** |
| **Grant Scope** | `exact` \| `origin` \| `action` — how widely a grant's pattern reaches, **recorded rather than inferred from its characters**. Matching is string work with no regular expression anywhere, because `rm -rf build/*` stored as a wildcard also covered `rm -rf build/../../Documents` |
| **Status Refresh Command** | `status_refresh_command` in a folder agent's manifest: how the desktop asks that agent to *recompute* its status. Only the `/run:<name>` form executes — a reference into the agent's own command catalog — and it runs under the agent's turn lock. Distinct from a **re-read**, which just reads `app-data/storage/STATUS.md` off disk. See [Agent Status](agents/agent_status/agent_status.md) |
| **Counterparty** | An agent the user picks and then expects an answer from. Every **enabled** agent is one, whatever its source: the composer `@`-list, the `[+]` capability picker and the Job agent picker all filter on `enabled` and nothing else, and `enabled` means only the user's own choice. A folder agent was excluded by a separate predicate — never by that column — until the local runner could serve one. See [Folder Agents as Counterparties](agents/local_agents/counterparty.md) |
| **Kit Contract** | The pinned, machine-readable half of the cinna-core agent start-kit bundled with the desktop (`resources/cinna-kit-contract/`): the manifest schema, the folder model (`layout.json`), and the root/agent templates. Lets the desktop scaffold, validate and export agent folders offline. See [Kit Contract](agents/local_agents/kit_contract.md) |
| **Agent Manifest** | `cinna-agent.json` at a local agent folder's root — the one file the desktop, a coding assistant and cinna-core all agree on. Unknown keys survive a read/write round trip untouched |
| **Contract Version** | Semver recorded on both the folder and the tool, and the **compatibility gate**: newer folder major → refuse and ask the user to update the app; older major → migratable; same major → run as-is. Distinct from `kit_version`, which is informational and never a gate |
| **Content Hash** | Stable SHA-256 over the files that would travel to a Cinna instance (sorted `path\0sha256(content)` lines, no mtime or inode, symlinks excluded). Answers "has this agent changed since it was pushed to that instance?" |
| **Legacy Manifest** | A `cinna-agent.json` carrying the retired integer `schema_version` and neither `contract_version` nor `id`. Read and warned about, never rejected — the one exemption from the identity requirement, encoded in the schema, the validator and the contract CHANGELOG together |
| **File Stamp** | `{mtimeMs, size, hash}` for a file an agent page can edit. Taken by the read that produced the rendered text and handed back at save time, so a write over a file an assistant changed underneath is refused. Metadata is a pre-check; the SHA-256 decides |
| **Identity State** | Where a folder agent's row id comes from: `manifest` (a UUID in `cinna-agent.json`), `legacy` (parsed, no `id` — indexed positionally), `unresolved` (unreadable manifest — listed, never indexed), `external` (a bare folder, positional by root-relative path). A folder that loses an id collision gets a fifth, *duplicate*, list id: selectable but not indexed. `external` is deliberately not `legacy` even though both are positional: the fix offered for a legacy folder is **Stamp identity**, and a bare folder has no manifest to write a UUID into |
| **Stamp Identity** | The offered — never automatic — write of a fresh UUID `id` into a legacy manifest. Re-keys the `agents` row and repoints everything that names it, rather than letting a rescan prune and re-insert |
| **Local Agent Outcome** | `LocalAgentOutcome<T>`: a failure **code** returned as data instead of thrown, because `ipcMain.handle` and `contextBridge` each drop an error's own properties. Used by `local-agent:get` and `:update-field`, whose codes drive renderer behaviour. See [Agents Tab & Agent Page](agents/local_agents/agents_tab.md) |
| **Tray Popup** | Menu-bar (status-bar) popover window listing agent statuses; opens from the macOS menu-bar tray icon, shows a worst-severity dot, and redirects the main window on click |
| **Engine** (a.k.a. **Local Engine**) | What actually runs a folder agent's turn. **Two of them** (`AgentEngine`), and a folder agent's runtime says which: `opencode` — the default, and what every agent naming no engine gets — or `claude`, the Claude Code the user already installed, under that install's own login with no credential held here (see [The Claude Engine](agents/local_agents/claude_engine.md)). Both are run by **one driver over one protocol**: a child process per agent speaking the [Agent Client Protocol](agents/local_agents/acp_contract.md) over stdio, started by the turn that needs it and reaped two minutes after it goes idle. So the engine is not an identity but a **launcher** — what to spawn, what to declare, what to say to the session before the first prompt. There is no shared server: the one desktop-managed `opencode serve` behind every folder agent, and every rule that existed because it was shared, went in phase 3 of the agent runtime plan. See [The Local Engine](agents/local_agents/engine.md) |
| **Claude Engine** | The second engine: a folder agent running **Claude Code**, through the ACP adapter in a child process, driving the `claude` binary the user already installed under that install's own login. **The desktop is an orchestrator and never becomes an authentication provider** — no login, no stored token, no brokered session, and nothing ever read from or written to `~/.claude/`. It is one environment variable from being untrue in either direction, so the child environment is *constructed*: narrowed to the shared child allowlist (which is where `USER` comes from — without it the CLI reports "Not logged in" on a logged-in machine), then stripped by name of every key, auth token, base URL, third-party-provider switch and `CINNA_ENGINE_KEY_*`, then audited on the value actually handed over, because a turn billed to the wrong account looks exactly like a turn billed to the right one. Isolation takes three options, not one: `settingSources: []` alone left the user's own MCP connectors attached. **No `allowedTools`** is passed, since a bare name there shadows the permission request the desktop's grants run through. The adapter's own `claude` is never run — `CLAUDE_CODE_EXECUTABLE` names the user's — and `session/set_mode` is applied after every `new` and `load`, because the adapter honours a `defaultMode` from the user's own settings even under `settingSources: []`. Moving out of process is what fixed the background-subagent stdin bug the in-process SDK carried. Readiness costs nothing: `claude auth status` says whether that install is logged in without running a turn, and of what it answers the panel names the **account and the plan** while **the organisation id and name are never read out of it at all**. Contract 1.2.0's `runtime.engine`. See [The Claude Engine](agents/local_agents/claude_engine.md) and [the ACP contract](agents/local_agents/acp_contract.md) |
| **Approvals** (Claude engine) | Who answers a Claude agent's permission asks *before* the desktop does — `ClaudeApproval`, `auto` \| `ask`, per agent. **Automatic** (the default) puts Claude Code's own reviewer in front, the classifier a terminal `claude` runs with auto mode on; **Ask every time** brings every command, edit, write and fetch to the desktop's permission block. Chosen on the agent page's Permissions tab, stored in Desktop State beside the grants for either kind of folder and never in a manifest; null is *no choice made*. The reviewer was watched and **declined nothing across seven probes** — a force push, a global git config rewrite — so on Automatic the block is a backstop rather than a gate, and every surface says so. The SDK's `bypassPermissions` / `dontAsk` are deliberately unreachable. A model without a reviewer (`haiku`) runs *Ask every time* regardless, and the transcript carries a notice saying so. See [Local Agent Permissions](agents/local_agents/permissions.md) and [the contract, §10](agents/local_agents/claude_contract.md#10-auto-mode--the-classifier-in-front-of-canusetool-and-what-it-approved) |
| **Engine Config** | The OpenCode configuration generated for **one agent**, into `<userData>/acp/opencode/<hash of agent id>/opencode.json` — never into an agent folder, and written temp-file-then-rename because the engine reads it at start. It carries the provider entry for that agent's credential (an **active** one: a credential the user switched off is left out, because that switch is a statement about spending), that agent's entry with its system prompt inlined, the permission profile, and a top-level `model` — stated there *as well as* on the session, because the agent entry's own model is ignored over ACP. API keys are never in it: each is an `{env:CINNA_ENGINE_KEY_…}` reference resolved from the process environment (Invariant 4). A keyless credential names a variable too, carrying the public literal `keyless` |
| **Launch Spec** | What one agent's process was started with: command, arguments, the **whole** child environment (nothing is inherited), cwd, and a `key` that moves whenever any of those do. The pool replaces a process whose key moved before the next turn — which is how a rotated API key, an edited prompt or a changed model reaches an agent, and why a running turn keeps the process it started with. The key is a **digest, never the values**: the environment carries credentials and the key is logged |
| **Agent Key** | The OpenCode agent-entry name a folder agent becomes (`<slug>-<hash of agent id>`, always hash-suffixed so it never depends on which other agents exist). Selected on the session as the `mode` config option, which is what makes a turn run *that* agent rather than the engine's stock coding assistant in the user's folder |
| **Generated Prompt** | The per-agent system prompt assembled from the agent's own files (workflow prompt, scripts and credentials READMEs, the `knowledge/` topic *list*, handovers) plus a desktop context block. **Inlined into the agent's config entry** — the engine's v2 config reader resolves no `{file:…}` and would hand the model the placeholder instead — and never written into the agent folder. The readable copy the shared server used to write beside its config is gone with it |
| **Runtime** | What a folder agent runs on: `{engine, credential, model}`. The **engine** is `opencode` unless the agent's own declaration names another — and it is a *launcher*, not a driver: both engines run through the one ACP driver, so an agent written before the axis existed is unchanged; an agent on `claude` has no credential and no catalogue at all, resolves its model to a plan **alias** (`haiku` / `sonnet` / `opus`) and leaves the ladder below before its first step, because every branch of it is written about a credential row with a key, an `enabled` flag and a model list. An unrecognised engine reads as **none** rather than bricking the folder, and `engine: "claude"` together with a `credential` is refused on write and ignored on read. The credential and model are resolved from the agent's own declaration first, then the Default runtime — but the **model** only where it can run: the config names a runtime as `<credential>/<model>` verbatim, so a model borrowed by a credential that cannot serve it is an entry that saves cleanly and fails on the agent's first turn. The declaration stores a credential **name** and *either* a model id *or* a Work Complexity — never a key, and never both of the two. A kit agent declares it in its manifest, under the file's stamp; a bare agent has no manifest, so the same three values go into its Desktop State through `local-agent:set-runtime` — unstamped, because the write touches no file in the folder — and both arrive on `LocalAgentDto.runtime`, so resolution has no branch for the second kind. One shared validator (`runtimeService.validate`) refuses a key-shaped credential on either path |
| **Work Complexity** | `simple` \| `medium` \| `complex` in a manifest's `runtime.complexity`, in place of a model id: how hard the agent's work is, left for the host to resolve. It exists because a model id is the least portable thing `cinna-agent.json` can carry — the file is committed, read by a coding assistant and uploaded to a Cinna instance on publish, and an id means something only to the catalogue that lists it, while `medium` means the same thing on another machine, another credential and after the next model release. Resolved against the **live** catalogue by model *family* (`src/shared/modelFamilies.ts`), not a table of ids, so a new release joins its tier with no app update. A **local** model is tiered by parameter count instead of by product name — Ollama has no line-up, only whatever the user pulled, and `qwen2.5-coder:1.5b` and `:32b` are the same product in different tiers; an unsized `:latest` tag resolves to Medium rather than to nothing, because null would leave every tier empty on a machine that pulled only defaults. On the [Claude engine](agents/local_agents/claude_engine.md) it is a **small table to a plan alias** (`haiku`/`sonnet`/`opus`) instead, and deliberately not the classifier: there is no credential and no catalogue on that path, so classifying against nothing would answer null for every agent. Contract 1.1.0, mutually exclusive with `runtime.model`. See [The Local Engine](agents/local_agents/engine.md#how-a-tier-becomes-a-model) |
| **Default Runtime** | The fallback runtime, derived from the user's default chat mode. There is deliberately no third fallback **for the credential** — an agent never runs on a key the user did not choose, because that is a billing surprise — and still no "first model in the catalogue". The **model** chain does have a floor below the Default runtime: the Medium tier of the credential the agent was already given. A *tier* is a class the user can choose and hold an opinion about, which is why the floor is not the arbitrary pick the rule forbids; what it replaced was a dead end where an agent named no model, could not run, and said so only on a panel the user had to go and find |
| **Medium Floor** | The last step of model resolution: Medium, resolved on the chosen credential, for an agent nothing above answered for. Medium and not Simple because an agent silently downgraded to the cheapest model does poor work and gives no clue why; Medium and not Complex because that failure is a bill. Never applied to the Default runtime itself — flooring twice would resolve against the *default* credential's catalogue and lend that model to an agent on a different key |
| **Inherited Model** | Which model a runtime that names none gets: the default runtime's when the credential is the default's own row → that credential's own default model (this is what covers a default chat mode left on *First available*) → the default's again when the two credentials share a provider *type*, `openai_compatible` and `ollama` excepted (two gateways, or two Ollama hosts, are two catalogues) → the **Medium floor** on that credential → nothing. One function in `src/shared/runtimeDefaults.ts` (`resolveRuntimeModel`), called by the main process **and** by the "Runs with" panel, so the `Default (…)` label and the generated config cannot name different models — an invariant three latent divergences were found under while the floor was being added |
| **Agent Turn** | One agent turn over one transport: the shared `RunAgentTurnInput` → `RunAgentTurnResult` signature, which **never throws** (a failed turn is a result carrying `error`, because an exception loses its code across IPC). Implemented by the two **Agent Drivers**, not by a separate runner seam — the three runners that used to sit behind that seam (A2A, OpenCode over HTTP, Claude in process) became two drivers when the local ones collapsed onto ACP. See [The Agent Turn](agents/local_agents/agent_turn.md) |
| **Agent Driver** | `AgentDriver` (`src/main/agents/drivers/`) — everything kind-specific about running an agent, behind one interface: `capabilities`, `readiness`, `run`, `respond`. There are **two** — `a2a` and `acp` — stored on `agents.driver`. **`source` still says who owns a row; `driver` says how it runs.** `driverFor(agent)` reads only the row and serves the direct-chat handler, the orchestrator's agent tool and the answer path. Which engine an ACP agent runs is a **launcher** in `driver_config`, and the row is only a cache of it: the driver re-reads the folder on every turn and takes the launcher from what it says then. This used to be a hand-off between *two folder drivers*, and while that hand-off was missing a Claude agent on a stale row answered "try again in a moment" for ever. Outside the drivers folder (and sync, which reads `source` for ownership) nothing branches on kind, and a ratchet test holds the remaining count exactly — `engine` comparisons are now at **zero**. See [Agent Drivers & Readiness](agents/drivers/drivers.md). Unknown/null stored driver IDs remain visible with inert capabilities and explicit refusal; only migrations backfill legacy nulls. |
| **Agent Capabilities** | `AgentCapabilities` — what an agent's driver can do for its row, computed with no I/O and the same on every call: streaming, cancel, sessions, which asks it raises and how they are answered (`inputResume`), `attachments` (`cinna` only for a Cinna-synced agent), `auth` (`cinna` \| `token` \| `cli` \| `none`), `commands` (`catalog` \| `card` \| `none`), `mcpInjection`, `cwd`. Carried on every agent DTO, so a screen asks "does this agent take a file?" instead of comparing `source`. One driver still gives two answers for the two engines, because a capability is about what the *engine* can do: Claude has a question path (its adapter enables `AskUserQuestion` when the client declares `elicitation.form`) and OpenCode has none (its `question` tool is not registered under ACP). It must not change between the list and the send, or the composer and the turn would disagree. Not the picker's **Capability** above |
| **Agent Readiness** | Whether an agent can take a turn **right now**, as its driver last answered: `ok`, a folder state, `not_installed` / `not_logged_in`, or `unreachable`, with a short `reason` and an optional raw `detail`. A folder's scan-time **Readiness** above is only its first rung. `agentReadinessService` keeps the answers in main's memory and merges them into the agent list; a list never waits for a check, and **`null` — never checked, or could not tell — never refuses anything**. The composer refuses a direct send to a refused agent, shows the reason and offers **Check again**, which runs fresh past every cache. A bare `/run:<name>` to a catalog agent always runs, because it is a script on this machine, not a turn. See [Agent Drivers & Readiness](agents/drivers/drivers.md) |
| **Engine Session** | An ACP session id created against a folder agent's directory, one per (chat, agent). Stored in `a2a_sessions.context_id` — the A2A-named column is reused deliberately, since that is what `agent:get-session` reads — with a durable copy in that agent's **Desktop State** — in the folder for a kit agent, under `<userData>` for a bare one. That copy is what `restoreHiddenAgents` re-seeds `a2a_sessions` from when an agent removed from the list is put back, so a bare agent's survives a removal precisely *because* it is not in the folder. Verified rather than trusted on resume: the engine's own storage can be cleared |
| **Parked Ask** (ACP) | A permission ask or question a local agent is blocked on mid-turn. Over ACP the agent is blocked on a **JSON-RPC request**, so the park *is* the unresolved response: there is no reply endpoint and no id for the agent to correlate. The desktop mints its own id (`per_acp_…` / `que_acp_…`) for the transcript and the out-of-band answer, and every exit from a turn releases what it parked — an unanswered ask is a turn that never ends |
| **Process Pool** | One ACP process per agent id (`acpProcessPool`): started lazily by the first turn that needs it, **held** for the length of a turn — idle time is the wrong signal for "in use" when a turn can be parked on a human — reaped two minutes after the last hold releases, replaced when its launch spec's key moves, and killed at app quit, as a **process group**, because an agent is rarely one process. A process that exits stays exited and is restarted by the next turn, never by a supervisor. The two minutes are measured, not guessed: an idle `opencode acp` holding a session is 311 MB of physical footprint, and a cold start is about a second |
| **Parked Request** | A permission ask or ask-user question a local agent is blocked on **mid-turn**. Rendered as a `tool` part (there is no `permission` part kind), answered out of band by request id while the turn streams, and released on every exit from the turn — an unanswered one is a turn that never ends. A release is settled as `rejected`, which is also what an expiry looks like, so the transcript distinguishes "No answer — the request expired." from "Not answered — the turn was stopped.": a decision nobody made must not be recorded as one |
| **Connect Intent** | The `cinna://connect?server=<origin>` deep link as it crosses into the renderer: an origin and when it arrived, and nothing else. Validated and reduced to an origin in main, buffered one at a time, and never acted on without the confirm step. See [The `cinna://connect` Link](auth/onboarding/connect_link.md) |
| **Confirm Step** | `ConnectIntentPanel` — the one screen a `cinna://connect` link is allowed to reach, and **the deep link's security boundary**. The URL validation is not: it narrows what a link can express, while a human reading the host is what decides whether it is acted on |
| **Local Development** | The desktop preparing *this machine* for agent work on a Cinna account: a managed toolchain under `<userData>/localdev`, a cinna-cli account workspace under the Agents Home, and the opencode engine pre-fetched so a first turn does not start with a download. The desktop is installer and orchestrator; cinna-cli owns setup, tokens, workspace layout and sync. See [Local Development](agents/local_dev/local_dev.md) |
| **Managed Toolchain** | uv, Mutagen and cinna-cli installed into `<userData>/localdev/` and nowhere else, version-stamped so an upgrade never swaps a running binary's file. Uninstalling Cinna takes it with it |
| **Account Workspace** | `<AgentsHome>/Cloud/<host>/` — a cinna-cli-owned directory holding the account token and context package for one Cinna instance. The desktop looks at exactly one file in it, `.cinna/account.json`, and only to answer "has cinna-cli set this up" |
| **Setup Token** | The single-use, fifteen-minute setup command the desktop mints with its own OAuth bearer (`POST /api/v1/cli/account/setup-tokens`) and hands to cinna-cli. It is what removes the second browser login. **Argv-only** — never logged, never in an error detail, never in a state the renderer can read |
| **Local Dev Consent** | A per-host yes/no, remembered — including the no. Stored as JSON in the default-scoped `localDevConsent` setting; an absent host means never asked, and `false` is what stops the prompt returning every launch. Asked as a checkbox on the `cinna://connect` confirm screen (ticked only where this machine holds no answer for that host), as the `localdev` onboarding step otherwise, and by a modal on an install that gains the feature later |
| **Managed Asset** | A pinned, checksum-verified install into a directory this app owns (`src/main/managed/managedAsset.ts`), shared by the local engine and the local-dev toolchain. **The presence of the install directory is the proof its bytes were verified** — everything is staged and published by one atomic rename |

- [The `cinna://connect` Link](auth/onboarding/connect_link.md) — A landing page on a self-hosted instance hands a freshly installed desktop the one thing the download cannot carry: which server it was for. The whole subprocess tree is killed on cancel or timeout, not just the shell that launched it: a real defect, found by running the code rather than reasoning about it, where a killed shell still left its already-forked grandchild running and the lock held for the timeout's full duration regardless. Also flips on the agent page's **Start chat** button — hard-coded disabled since Phase 3, never turned on when Phase 6 shipped a runner able to serve a folder-agent turn, so this closes Phase 6's debt rather than being new scope of its own — and gives the composer's pre-existing `/` command popup a folder branch so it reaches a folder agent with no change of its own, the same dead-branch-until-a-phase-adds-it shape `agentStatusService.list`'s remote-only filter had. - [Bare Agents & External Roots](agents/local_agents/bare_agents.md) — Any folder holding an `AGENT.md` can be adopted as an agent, without being converted first. The folder is registered as an **external** root and **nothing is ever written into it** — no templates, no `.cinna-kit/`, no `Local/`, no `app-data/` — which is why a bare agent's name, its removed-from-the-list flag, the runtime it was given and all its machine-local state live under `<userData>` instead, at a location the *root* decides rather than a probe of the folder (a `cinna-agent.json` is one `git pull` away, and an agent's sessions must not move when it arrives). The root is walked two levels deep, never into a folder that is already an agent and never into a dependency tree, so "one agent folder" and "a repository of them" are the same walk. Identity is positional, and deliberately a different identity *state* from `legacy`, because the fix offered there — Stamp identity — needs a manifest to write into. Its prompt is `AGENT.md` and nothing else the folder contains: `README.md` is excluded because it is written for whoever *builds* the agent, and is instead the first document of the init prompt — and, for the same reason, it is read on the page's **Overview** tab, rendered and read-only and absent where the folder has none, rather than beside `Instructions` on Prompts where it read as a second thing the agent is told. Adoption is two IPC calls with the picked path recorded in main, the whole picked folder becomes the root whatever was ticked (unticked folders are *hidden*, not omitted — one state, two histories), overlap with a registered root is refused first because that is the security rule, and an adopt that indexes nothing drops the root **it** created rather than closing on an empty one. Re-picking a folder already registered is a **re-selection**, not a refusal: the ticked set becomes the whole list, so unticking removes and ticking puts back — which is what makes this the only surface where a sixteenth agent can be added after fifteen were, since ⋯ takes one out at a time and Settings puts all of them back at once. Every removal's turn lock is checked before anything is written (taking them one at a time left an agent hidden under a dialog reporting that nothing had changed), a `name` reaches only an agent being added (it is prefilled from the folder, so sending it back renamed one silently), an agent put back gets its engine sessions again, and anything leaving is confirmed by name first. A bare agent also picks its **own runtime** on the same "Runs with" panel a kit agent uses, stored in its desktop state rather than in the folder and validated by the same checks as a manifest's, because an agent adopted from the user's own repository is not a lesser agent and "which credential pays for this" is the question they most need answered. Removal asks: "remove from the list only" is the default, both routes back are named, and restoring re-seeds the engine sessions (`job_agents` cannot come back, and the dialog says so). Ten surfaces on the reused agent page asserted files this folder shape never had, which is where [UX rules 9 and 10](development/ui_guidelines/ux_rules.md) came from. - [Agents Folder Updates](agents/local_agents/folder_updates.md) — A registered agents folder that is a git working tree can be checked for updates and fast-forwarded from Settings → Local Agents. `merge --ff-only` is the only update it performs and **it never resolves a conflict**: dirty, diverged, no upstream, unreachable remote and a refused merge are each reported as a named reason ending in "sort it out in your own tools, or ask an agent in this folder to". `dirty` counts tracked changes only, because a folder of agents always has untracked caches; a refusal is only stated when there is something to apply, because a repository that is up to date does not need to be told to commit. The status is read without fetching (it renders once per root) and an update re-reads *with* a fetch rather than trusting the last snapshot, then rescans the root so a pulled-in agent appears. `execFile` with no shell, bounded timeouts, the narrowed child environment so `SSH_AUTH_SOCK` survives, `GIT_TERMINAL_PROMPT=0`, and a **root id** rather than a renderer-supplied path
- [Local Agents Are Not Synced](agents/local_agents/local_only.md) — **The governing product position for anything a folder agent touches across machines.** A folder agent is a directory; the desktop's sync never carries one; a job bound to one is a **local-only job**. The `source: 'folder'` job-dependency descriptor exists so an unresolvable dependency is **visible and blocking**, not so the job runs elsewhere — the app refuses the run and the blocked-job panel deliberately offers **no repair instruction** (not "copy the folder here", which promises an unshipped workflow, and not "it will run on a device where that agent is set up", which names a device that need not exist — this state is reachable by one user on one machine who has never enabled sync). The one legitimate re-resolve is the **same machine** after a re-auth or reinstall; resolving on a peer holding the same manifest id is a **mechanism, not a supported workflow**, and the matching question is undesigned. Also names a documentation failure mode in the docs' own terms: **a sentence can be mechanically accurate and become an overclaim when someone decides what the feature is for** — no commit to notice, no symbol to grep, no test that can fail.
- [Folder Agents as Counterparties](agents/local_agents/counterparty.md) — Phase 7c of Local Agents: a folder agent becomes something the user can **pick and expect an answer from**, everywhere the app offers a choice. The temporary exclusion that kept folder agents out of the composer `@` picker and the Jobs agent picker is gone, along with both call sites — a deletion rather than a migration, because it was never expressed by clearing `enabled`. It changed **three** surfaces, not one: the third is that for a user whose only agents are folder agents the filtered list was empty, so the `@` popup and the `[+]` menu did not render **at all** — the gate did not hide rows, it removed the surface that would have shown them. `remoteMetadata` on a folder row is now **synthesized locally** from its `cinna-agent.json`, which lights up `#` prompts in the composer, the new-chat tag cloud, the hint context and the "Example tasks" clause of the description an orchestrating model reads — one field, four surfaces, three of which were visibly inert and one invisibly thinner. The column name is accurate for only half its rows now: **every sentence about it must say which kind of row it means.** A sweep of all 11 non-test read sites found no consumer testing the column for *presence*, so that is debt, not a live bug. **No `cinna_mcp` descriptor is emitted, deliberately** — the provider already prefers `fallbackDescription()`, which frames the agent for the model and then appends its description and examples, and a descriptor's `description` wins the `||`; building the thing the plan asked for would have degraded a working path. A `source: 'folder'` job-dependency descriptor keyed on the **manifest id** is now emitted, where before a folder row (both URL columns null) produced no descriptor at all, was dropped from the manifest, and let the job be reported fully set up, derive the plain-LLM pattern from an empty agent list, run, and record a **success with the agent silently absent**. **The descriptor is not a passport** — local agents are not synced and a job bound to one is local-only; it exists so an unresolvable dependency is visible and blocking (see [Local Agents Are Not Synced](agents/local_agents/local_only.md)). Of the three descriptor kinds that resolve against **this machine's** own resources — MCP, hand-added local A2A agent, folder agent — it is the **only one that does not auto-create a shell on a miss**, because a folder agent *is* a directory and a row without one would assert it exists here (a remote agent resolves against a server account instead, and never auto-created either) — which is why a missing workshop is `unavailable` (nothing to open) while a present-but-switched-off row stays `needs-setup`, and why "Set up" is gated on `localId !== null` and routed on `isFolderAgentId(localId)` to Settings → **Local Agents**. **That decision has since been taken and the run is now blocked**: `executeLocal` recomputes the unresolvable-agent set from the manifest and throws `JobError('incomplete_setup', …)` naming the missing agents, with `JobData.incompleteSetup` disabling the Run button and marking the sidebar row before the click. A `source: 'local'` shell the user *deletes* still reproduces the same agentless success and is knowingly outside the gate. The "Stamp identity" repair (a stamp used to orphan every dependent job permanently) is **outbound only**: a peer holding the stale manifest keeps it until the job is next edited, and can send the ghost back. - [Agent Status](agents/agent_status/agent_status.md) — Sidebar-footer activity indicator, frosted-glass modal and menu-bar popup surfacing per-agent self-reported status (severity, summary, markdown body) with one-click "Start chat", for **both** agent kinds. - [Local Development](agents/local_dev/local_dev.md) — Getting one Cinna profile from "signed in" to "this machine can do agent work" with no terminal: a **managed toolchain** (uv, Mutagen, cinna-cli) under `<userData>/localdev`, a cinna-cli **account workspace** at `<AgentsHome>/Cloud/<host>/` bootstrapped from a single-use setup token the desktop mints with its own OAuth bearer — which is what removes the second browser login — and the **opencode engine pre-fetched** as a sixth checklist row, because left alone it downloads lazily at the moment someone presses send. That row resolves through the engine's ordinary three sources, so a developer's own `opencode` answers it instantly and downloads nothing, and it is best effort: a pre-fetch that did not happen leaves the row **`pending`** — *not cached*, not failed, because nothing is broken and a red row under a green "ready" would be contradicted by an app that works — and `ready` is still reached. **`reconcile` is the only door**: idempotent, single-flight, and Repair *is* `reconcile(force)`, so there is no second path to drift from the first. It fires on every Cinna activation, after a re-auth, on OS resume and on the button. What it deliberately does not do: clone an agent, start a Mutagen session, run `cinna dev`, or reimplement anything cinna-cli owns — the desktop is installer and orchestrator, and the seam is a subprocess plus an **exit code** (`10` token rejected → `token_expired`, `11` account mismatch → `workspace`, `12` unreachable → `network`), never a message-string match. `LocalDevState` carries **six** phases, not the four the design named: `idle` ("we have not looked") is distinct from `unsupported` ("this server does not offer it") and `declined` ("asked, and no") from `consent` ("never asked"), because Settings has to offer different things for each and a screen that guesses will eventually guess wrong. **A `403` on the setup-token mint is the `agent-developer`/`admin` role gate, not a dead session** — `unsupported/role`, a supported state the UI explains and offers nothing to press. uv's version is the desktop's own pin; **Mutagen's version comes from the server and its bytes from a table in source**, so a version this build has no digest for is "update Cinna Desktop" rather than an unverified download — the deliberate trade, since an attacker who can name the version could otherwise name the bytes. cinna-cli is version-pinned over TLS from PyPI and knowingly not hash-pinned. `setup_command` is **argv-only** and `runCinnaCli` demands a separate `logArgs`, so logging a command is a decision someone takes rather than a default someone forgets. Consent is per host, `false` is remembered, and `~/.local/bin/cinna` is an opt-in symlink that refuses to replace anyone's real install. A `cinna://connect` link answers that consent on its **confirm screen**, as a checkbox beside Connect — ticked only where this machine holds no answer, since **Switch to it** must not reverse a deliberate decline — so it is no longer a step of its own after sign-in; and recording an answer waits for the reconcile activation already started, which read the consent before the answer was written. The install runs **concurrently** (only cinna-cli needs uv), so the bar is a weighted aggregation of per-component progress rather than fixed stage ranges, completion is **reported rather than inferred** from a later component starting, a failure is attributed by the **component the error names** (asking which row is active stopped meaning anything once several are), and only the current run may narrate — a claim released when a run *ends*, since a sibling download outlives the failure that stopped the others. `setState` broadcasts the state **with its checklist attached**: pushing the pre-checklist object is why the per-component list existed in main and never reached a window. ## Architecture

```
+------------------------------------------------+
|                 MAIN PROCESS                   |
|                                                |
|  SQLite (Drizzle)  LLM SDKs  MCP Clients  A2A |
|  User accounts (PBKDF2)  Session management    |
|  API keys & tokens encrypted via safeStorage   |
|                                                |
|  IPC Handlers (ipcMain.handle / .on)           |
|  + MessagePort for streaming                   |
+------------------+-----------------------------+
                   |  contextBridge (typed window.api)
+------------------+-----------------------------+
|              RENDERER (sandboxed)              |
|  contextIsolation: true, nodeIntegration: false|
|  React + Zustand + TanStack Query              |
|  window.api.auth.* / .chat.* / .providers.*    |
|  window.api.agents.* / .mcp.* / .llm.*        |
+------------------------------------------------+
```

**Security model**: API keys and OAuth tokens are encrypted at rest using Electron's `safeStorage` (OS keychain) and stored as blobs in SQLite. They are decrypted only in the main process. User passwords are hashed with PBKDF2-SHA512 (100k iterations). All data is user-scoped — every IPC query filters by the active user ID. The renderer is fully sandboxed — it can only access the typed `window.api.*` methods exposed via contextBridge.
