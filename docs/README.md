# Cinna Desktop

Desktop client for remote agents (MCP, A2A, OpenCinna).

## Glossary

| Term | Definition |
|------|-----------|
| **Chat** | A conversation with an LLM, persisted in SQLite with messages and model/provider binding |
| **Chat Mode** | A named preset bundling an LLM provider/model, MCP servers, and a color — used to quickly start configured chats |
| **Provider** (a.k.a. **LLM Provider**) | An LLM service (Anthropic, OpenAI, Gemini, OpenAI-compatible) configured with an encrypted API key. **UI naming:** surfaced to users as **"AI Credentials"** (the sidebar section, page title, "Add AI Credentials" button, and the chat-mode field). "LLM Provider" remains the canonical/technical name in code and these docs; "AI Credentials" is purely the friendlier user-facing label, matching CinnaCore. The two terms refer to the same thing |
| **Managed Provider / Chat Mode** | An LLM provider / default chat mode auto-materialized from a Cinna admin-provisioned credential (`managed = true`). Profile-scoped, sync-owned, read-only (local enable/disable only). See [Account Provisioning](llm/account_provisioning/account_provisioning.md) |
| **Adapter** | Implementation of the `LLMAdapter` interface that translates between our chat system and a provider's SDK |
| **MCP Server** | A Model Context Protocol server (local stdio or remote HTTP) that exposes tools to the LLM |
| **MCP Connection** | A live client session to an MCP server, managed by MCPManager |
| **On-Demand MCP** | An MCP server the user `@-mentions` into a chat so its tools are available only for that chat — tracked separately from the chat mode's baseline MCP set |
| **Baseline MCP** | The chat-mode-owned MCP set of a chat (`chat_mcp_providers`). Exactly the mode's list — empty means none. Unioned with the on-demand set at stream time; rendered as locked chips (no `×`) in the composer, since it's managed on the mode |
| **Tool Call** | LLM requests a tool -> main process calls MCP server -> result fed back to LLM |
| **MessagePort** | Electron's streaming channel used to send LLM response chunks from main to renderer |
| **safeStorage** | Electron's OS-keychain encryption used for API keys and OAuth tokens at rest |
| **Agent** | An external AI service (e.g. A2A agent) registered by the user, communicating via a standardized protocol |
| **A2A** | Agent-to-Agent Protocol v1.0 — open standard for AI agent interoperability (discovery, messaging, streaming) |
| **Agent Card** | A2A discovery metadata (JSON) fetched from a well-known URL, describing agent capabilities and endpoint |
| **Message Part** | A typed segment of an assistant message (`kind: 'text' \| 'thinking' \| 'tool' \| 'tool_result' \| 'command_result'`) — A2A messages may persist a structured `parts[]` list driven by the Cinna `cinna.content_kind` metadata convention. The sibling `'notice'` kind bypasses `parts[]` and lands on its own `agent_transition` row (agent-side system notice). The `'command_result'` kind carries the synchronous output of a platform slash-command and IS the assistant turn for that user message |
| **@-mention** | Typing `@` in the new-chat input to open a popup for selecting references (agents, and extensible for future types) |
| **Composer Menu** | The single left-side `[+]` button on the chat composer (`ComposerPlusMenu`) that consolidates attach-files, chat-mode, and add-agents/MCP into one menu — the mouse-driven sibling of the `@` / `~` triggers |
| **Capability** | A polymorphic chat tool source — an agent or an MCP server — surfaced uniformly as a selectable card in the `[+]` Add-agents/MCP picker |
| **Capability Picker** | The search-and-cards modal opened by the `[+]` menu's "Add agents / MCP" (`AgentPickerModal`, `activeFirst` multi-select): selected cards float to the top and hold position while toggling |
| **Communication Pattern** | How a new chat will route, derived from the current selection: **A2A** (one agent, no on-demand MCPs → direct agent connection) or **AI** (anything else → local model orchestrates). Surfaced as a badge left of the composer Cog |
| **Orchestrated Mode** | An LLM-root chat where the local model is the conductor and each attached agent is exposed to it as an emulated MCP tool, unioned with the real MCP tools. The "AI" communication pattern |
| **On-Demand Agent** | An agent `@-mentioned` into a chat so the orchestrator can call it as a tool. Mirrors On-Demand MCP exactly (`chat_on_demand_agents`, sticky chips, one-shot announce) |
| **Tool Provider** | Polymorphic tool source the orchestrator unions — an MCP provider (`McpToolProvider`) or an agent provider (`A2AAsMcpProvider`). Tool calls route by provider type |
| **Agent Sub-thread** | An agent-backed tool call rendered as an expandable nested thread showing the agent's own parts (thinking/tool/tool_result/text) rather than an opaque result string |
| **cinna.mcp Descriptor** | Optional backend-supplied shape (tool name, description, input schema) describing how an agent appears as an emulated MCP tool. Synthesized from agent fields when absent |
| **Note Attachment** | A profile note attached to a user message via the composer's `?` mention popup. Materialized at send time into a synthetic `.md` riding the standard file-attachment pipeline |
| **Attachment** | A file attached to a single user turn. Three sources: `cinna` (bytes on the Cinna backend, A2A-referenced), `local` (bytes in `userData/files/<userId>/<chatId>/`, used for raw-LLM chats), or `pending` (composer-only, paths held on disk for the new-chat flow until scope is known) |
| **Media Part** (file) | Resolver output handed to an LLM adapter: `image`, `document` (native non-image bytes like PDF), or `text` (UTF-8 from extraction). Adapters translate to provider-native content blocks |
| **Path Guard** | TTL-based allowlist of OS paths the renderer is permitted to reference. Populated by file dialogs and `webUtils.getPathForFile` so a compromised renderer can't synthesize arbitrary absolute paths |
| **User Account** | A local profile (username + optional password) that scopes all data — chats, providers, agents, settings |
| **Default User** | Built-in guest account (`__default__`) with no password, always present |
| **Cinna Account** | A user account linked to a remote Cinna server (cloud or self-hosted) via OAuth 2.0 + PKCE |
| **Cinna Server** | Remote service (cloud at `opencinna.io` or self-hosted) providing agent orchestration and future features |
| **Default Scope** | Shared storage under `__default__` user id — LLM providers, MCP servers, chat modes, and local agents live here and are visible from every profile |
| **Profile Scope** | Per-account storage under the active user id — chats, remote agents, agent overrides, and Cinna tokens live here and swap on user switch |
| **Agent Override** | Per-profile boolean (`agent_overrides` table) that overlays a synced agent's `enabled` flag so user toggles survive resync |
| **Job** | A reusable, profile-scoped saved spec (title, prompt, execution config). Two execution types: `local` (spawns a chat) or `cinna_task` (creates a remote cinna-core task) |
| **Job Folder** | User-defined sidebar grouping for jobs (profile-scoped, name + collapsed-state + sort position). Thin collapsible separator — owns ordering, not execution config. A job lives in exactly one folder or at the root |
| **Job Run** | One execution of a Job. Local runs reference the spawned `chatId`; Cinna runs reference the remote task; status flips via stream completion (local) or polling (cinna) |
| **Cinna Task Job** | Job variant that calls cinna-core's `POST /api/v1/tasks/`. Only available on Cinna-linked profiles; conversation lives on cinna-core, desktop keeps a pointer |
| **Task Comment** | Authored content on a cinna task (`comment_type = message \| result`); see also Activity for system-generated entries |
| **Task Attachment** | A file attached to a cinna task or one of its comments. Distinct from `FileUpload` (chat attachments) — uses a task-scoped download URL (`/api/v1/tasks/{taskId}/attachments/{id}/download`) |
| **Task Activity** | UI grouping for system-generated comment types (`status_change`, `assignment`, `system`) — shown as a compact collapsible log separate from authored comments |
| **Note** | A profile-scoped markdown document (title + body) the user inline-edits in the Notes tab. Autosaves on debounce; rendered with the same `react-markdown` stack used for chat bubbles |
| **Note Folder** | User-defined sidebar grouping for notes (profile-scoped, name + collapsed-state + sort position). Mirrors Job Folder semantics — a thin collapsible separator that owns ordering, not content |
| **Hint** | One line of shortcut-teaching copy shown in the new-chat screen's bottom bar. Either **ambient** (enters a shuffled rotation) or **contextual** (preempts the rotation when a matching user action fires). Gated on being actionable, and retired once the user has used what it teaches. See [Hints](ui/hints/hints.md) |
| **Login-Shell Environment** | The environment a user's shell produces after sourcing its profile. A Dock-launched macOS app inherits `launchd`'s bare environment instead, so the app resolves the login shell's once per lifetime and takes `PATH` from it. See [Shell Environment Resolution](development/shell_environment/shell_environment.md) |
| **Child Inherit Set** | The narrow, fixed allowlist a spawned third-party process (today: a stdio MCP server) receives — the MCP SDK's list valued from the login shell, plus session and proxy/CA variables — with the caller's own `env` map merged on top and always winning |
| **Detected Tool** | A developer tool the desktop probes for on the login-shell `PATH` (`claude`, `codex`, `opencode`, `code`, `cursor`, `uv`, `git`, `make`, `python3`), offered as a `cli-assistant`, an `editor`, or a feature-gating `runtime` |
| **Agents Root** (a.k.a. **workshop**) | A registered folder that local agent folders live under. May carry its own `.cinna-kit/` copy of the contract. Every "Open in…" target must `realpath` to a directory at or under one — see [Open in Tools](agents/local_agents/open_in_tools.md) |
| **Agents Home** | The one registered agents root marked default — `~/Documents/CinnaAgents` unless the `localAgentsHome` setting overrides it. Where the New Agent button scaffolds. Can be moved, never removed |
| **Folder Agent** | An agent that *is* a folder on disk (`agents.source = 'folder'`, row id `folder:<manifest uuid>`, protocol `local-folder`). Machine-local, default/settings scope. Distinct from `'local'` (a hand-added A2A URL) and `'remote'` (Cinna-synced). See [Agents Home, Scanner & Folder Index](agents/local_agents/folder_index.md) |
| **Folder Index** | The `agents` rows derived from scanning the roots, plus the `agent_roots` rows saying where to look. A rebuildable cache over the files — `enabled` is the one column it owns |
| **Readiness** | How ready an agent folder is to run: `ok`, `credentials_needed`, `invalid`, `contract_too_new`. Always a renderable *state*, never an exception — a manifest is briefly unparseable every time an assistant saves it |
| **Turn Lock** | Per-agent, in-process lock. The runner holds it for a turn; page editors refuse to save while held; the folder watcher defers its rescan (both the per-agent and the whole-root branch) until release |
| **Desktop State** | `app-data/desktop.json` — the one file inside an agent folder the desktop owns: local API base URL, agent token, engine sessions, permission grants, last status. The token never leaves the main process |
| **Counterparty** | An agent the user picks and then expects an answer from. `canBeCounterparty()` temporarily excludes folder agents (no runner yet) from the composer `@`-list and the Job agent picker — deliberately *not* by clearing `enabled`, which means only the user's choice |
| **Kit Contract** | The pinned, machine-readable half of the cinna-core agent start-kit bundled with the desktop (`resources/cinna-kit-contract/`): the manifest schema, the folder model (`layout.json`), and the root/agent templates. Lets the desktop scaffold, validate and export agent folders offline. See [Kit Contract](agents/local_agents/kit_contract.md) |
| **Agent Manifest** | `cinna-agent.json` at a local agent folder's root — the one file the desktop, a coding assistant and cinna-core all agree on. Unknown keys survive a read/write round trip untouched |
| **Contract Version** | Semver recorded on both the folder and the tool, and the **compatibility gate**: newer folder major → refuse and ask the user to update the app; older major → migratable; same major → run as-is. Distinct from `kit_version`, which is informational and never a gate |
| **Content Hash** | Stable SHA-256 over the files that would travel to a Cinna instance (sorted `path\0sha256(content)` lines, no mtime or inode, symlinks excluded). Answers "has this agent changed since it was pushed to that instance?" |
| **Legacy Manifest** | A `cinna-agent.json` carrying the retired integer `schema_version` and neither `contract_version` nor `id`. Read and warned about, never rejected — the one exemption from the identity requirement, encoded in the schema, the validator and the contract CHANGELOG together |
| **File Stamp** | `{mtimeMs, size, hash}` for a file an agent page can edit. Taken by the read that produced the rendered text and handed back at save time, so a write over a file an assistant changed underneath is refused. Metadata is a pre-check; the SHA-256 decides |
| **Identity State** | Where a folder agent's row id comes from: `manifest` (a UUID in `cinna-agent.json`), `legacy` (parsed, no `id` — indexed positionally), `unresolved` (unreadable manifest — listed, never indexed). A folder that loses an id collision gets a fourth, *duplicate*, list id: selectable but not indexed |
| **Stamp Identity** | The offered — never automatic — write of a fresh UUID `id` into a legacy manifest. Re-keys the `agents` row and repoints everything that names it, rather than letting a rescan prune and re-insert |
| **Local Agent Outcome** | `LocalAgentOutcome<T>`: a failure **code** returned as data instead of thrown, because `ipcMain.handle` and `contextBridge` each drop an error's own properties. Used by `local-agent:get` and `:update-field`, whose codes drive renderer behaviour. See [Agents Tab & Agent Page](agents/local_agents/agents_tab.md) |
| **Tray Popup** | Menu-bar (status-bar) popover window listing agent statuses; opens from the macOS menu-bar tray icon, shows a worst-severity dot, and redirects the main window on click |
| **Engine** (a.k.a. **Local Engine**) | The one desktop-managed `opencode serve` process every folder agent runs on. Loopback-only, on a port the desktop picks, behind a per-start Basic-auth password. **One process serves them all**, so anything that restarts it ends *every* streaming turn — which is why `turnLock.anyHeld()`, not the per-agent `isLocked`, is the engine-level guard. See [The Local Engine](agents/local_agents/engine.md) |
| **Engine Config** | The OpenCode configuration generated into `<userData>/engine/opencode.json` — never into an agent folder. One provider entry per usable AI credential, one agent entry per runnable folder agent, plus the permission profile. API keys are never in it: each is an `{env:CINNA_ENGINE_KEY_…}` reference resolved from the engine process's environment (Invariant 4) |
| **Loaded Config** | The record carried on the *running* engine process — a digest of its config and prompt bytes, a digest of its credential environment, and the agent keys and skips **that process actually loaded**. Dies with the process. "Does the engine need restarting" is a comparison against this, never against a remembered flag or the bytes on disk |
| **Agent Key** | The OpenCode agent-entry name a folder agent becomes (`<slug>-<hash of agent id>`, always hash-suffixed so it never depends on which other agents exist). Engine sessions bind to it |
| **Generated Prompt** | The per-agent system prompt assembled from the agent's own files (workflow prompt, scripts and credentials READMEs, the `knowledge/` topic *list*, handovers) plus a desktop context block. Written beside the engine config, never into the agent folder |
| **Runtime** | What a folder agent runs on, reduced to `{credential, model}` because the engine is always OpenCode. Resolved manifest-first, then the Default runtime. The manifest stores a credential **name** and a model id — never a key |
| **Default Runtime** | The fallback runtime, derived from the user's default chat mode. There is deliberately no third fallback: an agent never runs on a credential the user did not choose |
| **Agent Turn Runner** | `AgentTurnRunner` — one agent turn, whatever kind of agent it is: the shared `RunAgentTurnInput` → `RunAgentTurnResult` signature, which **never throws** (a failed turn is a result carrying `error`, because an exception loses its code across IPC). Two implementations, A2A and local; `resolveTurnRunner(agent)` picks between them on `agents.source` and is the one dispatch point both call sites use. See [The Agent Turn Runner](agents/local_agents/agent_turn.md) |
| **Engine Session** | An OpenCode `ses_…` created against a folder agent's directory and its agent key, one per (chat, agent). Stored in `a2a_sessions.context_id` — the A2A-named column is reused deliberately, since that is what `agent:get-session` reads — with a durable copy in the folder's `app-data/desktop.json`. Verified rather than trusted on resume: the engine's own storage can be cleared |
| **Admission Ack** | What `POST /api/session/{id}/prompt` answers with: a receipt (`SessionInputAdmitted`, carrying `admittedSeq`) saying the input was accepted — **not** the answer. The answer arrives on a separate SSE subscription, which is why a turn must subscribe *before* it prompts |
| **Hole** (engine stream) | The events lost between a dropped socket and the next one. Unrecoverable from the global stream, which takes no cursor — so a reconnect is reported as a hole (`disconnect` then `reconnect`) and **healed** by replaying the durable per-session stream from the last `durable.seq`. An engine *stop* is reported as a close instead: no reconnect is coming |
| **Parked Request** | A permission ask or ask-user question a local agent is blocked on **mid-turn**. Rendered as a `tool` part (there is no `permission` part kind), answered out of band by request id while the turn streams, and rejected on every exit from the turn — an unanswered one is a session that never goes idle |

## Feature Registry

### Core
- [Resource Activation](core/resource_activation/resource_activation.md) — Account-scoped resource lifecycle: services only run after user authentication
- [Settings Scope](core/settings_scope/settings_scope.md) — Default (shared) vs Profile (per-account) scope: which settings follow the user across profiles, which stay account-bound
- [Boot Resilience](core/boot_resilience/boot_resilience.md) — Fatal-startup dialog instead of ghost windows, renderer-crash detection, migration ordering safety for fresh installs

### Auth
- [User Accounts](auth/user_accounts/user_accounts.md) — Local user profiles with optional password auth, user-scoped data isolation, session management
- [Cinna Accounts](auth/cinna_accounts/cinna_accounts.md) — OAuth 2.0 + PKCE connection to remote Cinna servers (cloud or self-hosted), token rotation
- [Cinna Token Lifecycle](auth/cinna_accounts/token_lifecycle.md) — Token refresh/rotation between login and re-auth: silent near-expiry refresh, per-account dedup mutex, and orphan-refresh safeguards (pausing autonomous background refreshes around OS suspend/resume, foreground-only run polling) that prevent an interrupted refresh from becoming a rotation-replay self-logout
- [Cinna Re-authentication](auth/cinna_accounts/reauthentication.md) — In-place re-auth when a Cinna session expires. Four entry points (the Cinna account's card in Settings → User Accounts, settings banner, agent-status overlay, chat error chip) re-run OAuth against the stored server URL, verify the OAuth-returned email matches the local user, and overwrite only the token columns — local data is preserved
- [Onboarding](auth/onboarding/onboarding.md) — First-launch welcome screen: pick API key (validate + auto-create default chat mode) or Cinna Server (reuses self-hosted OAuth flow); force-on-restart toggle in Development settings for QA

### Chat
- [Messaging](chat/messaging/messaging.md) — Chat CRUD, MessagePort streaming, multi-provider tool-call loop
- [Conversation UI](chat/conversation_ui/conversation_ui.md) — Message rendering: user bubbles, assistant plain text, tool blocks, system errors
- [Chat Modes](chat/chat_modes/chat_modes.md) — Named presets bundling LLM provider/model, MCP servers, and color scheme for one-click chat setup. The mode's MCP list is the chat's complete baseline: an empty list attaches **nothing** (no "all enabled providers" fallback), and switching mode on an active chat replaces the baseline verbatim
- [Example Prompts](chat/example_prompts/example_prompts.md) — Remote-agent starter prompts shown as an animated tag cloud and surfaced via `#` in the chat input
- [CLI Commands](chat/cli_commands/cli_commands.md) — `/` picker surfacing an agent's `cinna.run.*` shell commands; selecting one inserts the `/run:<slug>` invocation string
- [Mention Popups](chat/mention_popups/mention_popups.md) — Shared trigger-driven listbox primitive (`@`, `#`, `/`) backing the agent, example-prompt, and CLI-command pickers
- [Composer `[+]` Menu](chat/composer_menu/composer_menu.md) — Single left-side `[+]` button consolidating attach-files / chat-mode (sub-menu) / add-agents+MCP (search-cards modal) into one mouse-driven menu; the agent/MCP picker uses active-first ordering (selected float to top, hold on toggle) and drives the same engage/detach routing as the `@` mention. Keeps `@` / `~` / `#` / `/` / `?` as keyboard equivalents
- [Orchestrated Agents](chat/orchestrated_agents/orchestrated_agents.md) — Agents-as-MCP, the engine for multi-counterparty chats: when a chat mixes ≥2 counterparties (LLM + agent, two agents, or agents + MCPs) the local model conducts and calls each agent as an emulated MCP tool, rendering each as an expandable sub-thread; a lone agent still talks direct A2A. Bringing a 2nd counterparty into a one-on-one chat promotes it in-chat (with agent-attributed history handoff). `A2A`/`AI` badge on the composer
- [Agent Attachments](chat/agent_attachments/agent_attachments.md) — Files a remote agent attaches to its reply (`<cinna_attach>` → A2A `FilePart` with `cinna.content_kind: 'file'`). The streaming accumulator routes each to a `file`-kind `MessagePart` (deduped by `file_id`), persisted on the assistant `parts[]` and rendered inline as a downloadable badge — the mirror of user file attachments. Download goes through the Cinna OAuth bearer path (`GET /files/{id}/download`), never the signed `?token=` URI; preview is out of scope (download-only)
- [File Attachments](chat/file_attachments/file_attachments.md) — `[+]` menu + drag-drop with deferred ingest on new-chat; per-model capability picks native pass-through (images, PDF on Anthropic/Gemini) vs text extraction (CSV/JSON/code via UTF-8, DOCX/XLSX/PPTX/PDF-on-OpenAI via `officeparser`); local store under `userData/files/<userId>/<chatId>/` for raw-LLM chats, Cinna backend for remote agents; path-guard allowlist + chat-ownership check + `basename` filename sanitization
- [File Preview](chat/file_preview/file_preview.md) — Click a `txt`/`csv`/`md`/`json`/`yaml` attachment badge (user or agent) to open a read-only modal that renders the decoded content (markdown render, JSON pretty-print, CSV table, wrapped text) with icon-only header actions (Download; CSV adds a Filter toggle for per-column substring filters + click-to-sort); other formats download on click as before. Separate `files:read-preview` IPC reads bytes into memory capped at 512 KB; single global modal driven by `useFilePreviewStore`, routed by `useAttachmentOpen`
- [Note Attachments](chat/note_attachments/note_attachments.md) — `?` mention popup attaches profile notes as composer badges (click to preview); at send time each note's live body is materialized as a `<safe-title>.md` routed through the existing file-attachment pipeline (`fileService.ingestSyntheticContent` → `fileService.ingest`). Double-Enter shortcut: picking a note then pressing Enter on an empty composer expands the note body inline as text instead of sending — prompt-template paste without leaving the keyboard.
- [Agent Notices](chat/agent_notices/agent_notices.md) — Agent-side system messages (`cinna.content_kind: 'notice'` TextParts) stream live as muted system pills, then collapse to a clickable accent dot once persisted as `agent_transition` rows. Excluded from LLM history rebuilds
- [Command Results](chat/command_results/command_results.md) — Synchronous platform slash-command output (`cinna.content_kind: 'command_result'` TextParts from `/files`, `/agent-status`, `/run:*` variants, …) renders as a bordered terminal-style "Command output" block. The agent stream never runs — the part IS the assistant turn and persists into the message's `parts[]` so chat previews and titles work
- [Ask User Question](chat/ask_user_question/ask_user_question.md) — Renders a remote agent's `AskUserQuestion` tool (`cinna.tool_name=askuserquestion`) as an interactive prompt instead of an opaque tool dot. An accent block with an "Answer" button opens a modal (single/multi-select options, per-question "Other" free-text, progress counter, Send gated until complete); answers are formatted to plain text and sent through the normal composer (`useChatComposer`), auto-threading onto the agent's context so it resumes. Active only on the last turn when idle — historical prompts render muted/read-only. Renderer-only: no DB column, IPC channel, or answer-status flag (state derived from message ordering)
- [Apply-Patch Diff](chat/apply_patch_diff/apply_patch_diff.md) — Renders the OpenCode/Codex `apply_patch` tool as a git-style diff (per-file op badge, path, `+N −M` tally, colorized lines) instead of a raw `patch_text` dump. A single `parsePatch()` doubles as the render guard (null → generic renderer); composes the shared `DisclosureBlock` collapsible shell extracted from the thinking/tool/result blocks
- [Auto Chat Titles](chat/auto_titles/auto_titles.md) — Opt-in background AI function: on the first user message in a new chat, generates a concise (≤ 40 char) title via the user's default chat mode LLM provider; replaces the renderer's truncated-message fallback. Fire-and-forget, fully fail-tolerant, no UI surface beyond a Settings → Features toggle

### Agents
- [Agents](agents/agents/agents.md) — A2A protocol agent management, card discovery, streaming chat via external agents
- [A2A Streaming Pipeline](agents/agents/streaming_pipeline.md) — Per-part delta computation, `cinna.content_kind` / `cinna.tool_name` metadata contract (text, thinking, tool, tool_result, notice, command_result), structured `parts[]` persistence
- [Remote Agents](agents/remote_agents/remote_agents.md) — Auto-sync agents from Cinna backend, categorized display, JWT-based A2A communication
- [Bundles Catalog](agents/bundles_catalog/bundles_catalog.md) — Settings → Profile → Catalog: browse cinna-server agent bundles, one-click Quick Install, post-install setup modal that deep-links missing credentials to the cinna-server web pages and polls until the runtime gate clears. Sub-docs: [Inline Catalog Install](agents/bundles_catalog/inline_install.md) — a **Catalog** section in the chat composer's add-agents picker that quick-installs a bundle and auto-selects the resulting agent in one click (no Settings detour; skips the setup gate); [Bundle Updates (tech)](agents/bundles_catalog/bundle_updates_tech.md) — detecting an outdated install via the sync's `bundle_version` and applying the latest revision in-app from the Catalog card or Agents list
- [Open in… (Local Agent Tools)](agents/local_agents/open_in_tools.md) — Hand a local agent's folder to the user's own tools: run Claude Code / Codex / OpenCode in a system terminal at the folder, open it in VS Code or Cursor, reveal it in the file manager, or open a bare terminal. Detection is one cached pass over the login-shell `PATH` (plus macOS `.app` bundles for editors, since many people never install the CLI shim), with an explicit Refresh. Every request is re-validated in main: absolute path, no control characters, `realpath`, must be a directory at or under a registered agents root on a separator boundary, and the *resolved* path is what launches. The guard is **closed by default** — with no roots provider registered every request is refused with `no_roots`, so a wiring gap fails safe. macOS terminal launches are Apple Events, so the signed build ships the automation entitlement + usage description and maps error `-1743` to `automation_denied`. Sub-doc: [Technical Details](agents/local_agents/open_in_tools_tech.md)
- [Kit Contract & Manifest Layer](agents/local_agents/kit_contract.md) — The bundled, pinned copy of the cinna-core start-kit *contract* (manifest schema, `layout.json` folder model, root/agent templates) plus the TypeScript reader, validator and exporter over it, so the desktop can scaffold, validate and export kit-shaped agent folders offline — no Python, no network. Governing principle: **files are the truth, the database is an index** — this layer never writes to SQLite. Three versions answer three separate questions (`contract_version` gates compatibility, `kit_version` is informational, `content_hash` detects drift against a publication); a legacy manifest is exempt from the identity requirement by a conditional `allOf` the schema, the validator and the CHANGELOG must change together; secret-bearing files (`credentials.json`, any `.env` but `.env.example`, `*.pem`/`*.key`/`*.p12`) are excluded at four independent layers while `credentials/README.md` and `.env.example` deliberately travel; manifest writes are content-hash guarded (mtime+size loses to `cp -p` / `rsync -t` / `git checkout`); and the hand-rolled YAML reader flags the three shapes it mis-reads and drops those command entries rather than executing a silently-truncated command. Sub-doc: [Technical Details](agents/local_agents/kit_contract_tech.md)
- [Agents Home, Scanner & Folder Index](agents/local_agents/folder_index.md) — Phase 2 of Local Agents: how agent *folders on disk* become `agents` rows. The agents home (`~/Documents/CinnaAgents`) plus adopted roots, the TypeScript port of `kit.py new`, the scanner that derives readiness (`ok` / `credentials_needed` / `invalid` / `contract_too_new`) and rebuilds each root's index in one transaction, the debounced `fs.watch` per root, `app-data/desktop.json`, the per-agent turn lock, and the IPC surface over all of it. Governing rule: **a scan can only speak for the folder it walked** — it never prunes a folder it could not parse, nor rows at a location the root has moved away from, because `a2a_sessions` and `job_agents` cascade from `agents.id` and a manifest is unparseable for a moment every time an assistant saves it. An unreadable folder therefore adopts the id of the row already at its path and changes **readiness, never identity**. Watch events are a three-way `ignore` / `root` / `agent` result (collapsing them made `app-data/` — the one directory deliberately not watched — trigger a full rescan), both rescan branches honour the turn lock, and rescans must be idempotent because macOS FSEvents replays pre-arm changes on every watcher arm. `enabled` means only the user's choice and survives every rescan; the temporary no-runner restriction is the separate `canBeCounterparty()` predicate. Roots may not nest — every root widens the "Open in…" path guard — and `local-agent:root-add` takes no renderer-supplied path, only a native dialog's. Sub-doc: [Technical Details](agents/local_agents/folder_index_tech.md)
- [Agents Tab & Agent Page](agents/local_agents/agents_tab.md) — Phase 3 of Local Agents: the user-facing surface. An **Agents** tab whose rows are folders grouped by root, a per-agent page that is a **viewer over the folder** (every card names the file it reads; Description, example prompts and the three prompt documents edit in place), a one-sentence New-agent flow, and Settings → Local Agents. The editor state machine is **pure and lives outside React** (`src/renderer/src/utils/localAgents.ts`): the stamp handed back on save is the one taken by the read the UI rendered, a reload pairs text and stamp from the *same* read, a refused save is never retried, and a "my slice didn't move" branch lets three cards share one `cinna-agent.json` without false conflicts. There are **three** save outcomes, not two — a conflict (`manifest_modified`/`file_modified`) is terminal, a blocked write (`turn_in_progress`) is retryable and re-arms a longer debounce. IPC error codes cannot survive a thrown rejection (two boundaries strip them), so the two channels whose codes drive behaviour return `LocalAgentOutcome<T>` data unwrapped renderer-side. Identity is a three-way union plus a *duplicate* list id that is selectable but not indexed (sharing one id previously opened the **wrong agent's editable page**). "Stamp identity" **re-keys** the row across nine tables in one transaction — including the three `messages.*_agent_id` columns no cascade touches, which don't disappear, they stop resolving. The AI draft runs in main, timeout-bounded, only ever fills a blank, takes its stamps before the model runs, and is double-guarded against StrictMode's second effect. Chat controls render **disabled** until the runner lands (Phase 6), via `canBeCounterparty()` rather than the `enabled` column. Sub-doc: [Technical Details](agents/local_agents/agents_tab_tech.md)
- [The Local Engine, Runtimes & Prompt Assembly](agents/local_agents/engine.md) — Phase 5 of Local Agents: what actually runs a folder agent. One desktop-managed `opencode serve` bound to loopback (a port the desktop picks — `--port 0` really binds 4096, and a second `serve` against a taken 4096 comes up *silently* on an unpredictable port), behind a fresh 32-byte password per start; `--mdns` must never be passed, since it defaults the hostname to `0.0.0.0`. **One process backs every folder agent**, so `turnLock.anyHeld()` — never the per-agent `isLocked` — gates a restart; the wrong predicate looks correct and is a live Invariant 3 violation that was found and fixed in this tree. `ensureRunning` is the **config choke point**: it re-derives the config at the moment of use rather than hooking the five-and-counting sites that invalidate one (a credential change, the background account-config sync materialising managed providers on a timer **with no IPC call to hook at all**, a managed mode's model, the default chat mode, a per-agent runtime write) — do not add per-site `applyConfigChange` calls. A change that arrives mid-turn is deferred **and writes nothing at all**, which closes the hazard of swapping a streaming agent's prompt or deleting it mid-reply. The manager records **facts about the running process, not the last config generated**: `agentKey()` and `lastSkips()` answer from a digest-and-keys record taken at spawn, which is load-bearing because Phase 6 binds engine sessions to `agentKey`. Two digests, because a **rotated key leaves the config bytes identical** (it lives only in `built.env`); both length-prefixed, since a delimiter collision would be a *false negative* — the engine keeps serving the old prompt with every test still passing. API keys reach the engine only as process environment, so OpenCode's `/config` endpoint, which returns the **resolved** config, must never be logged or forwarded. `refreshModels: false` on the reconcile path (one network round trip per credential); a turn that restarts refreshes, one that does not never does. Also: runtimes (`{credential, model}`, manifest → Default runtime, a **name** in the manifest and never a key), the assembled per-agent prompt (HTML comments stripped, knowledge listed not inlined, "do not switch to the Builder role"), the permission profile (explicit `'*': 'ask'`, `credentials/.env` **deny**), and binary resolution (configured path → login-shell PATH → pinned SHA-256-verified download, published only by an atomic rename). Sub-doc: [Technical Details](agents/local_agents/engine_tech.md)
- [The OpenCode Engine Contract](agents/local_agents/opencode_contract.md) — **What is verified about the engine, how, and under what conditions.** Every test in `agentTurn/**` and `engine/**` runs against a fake at the HTTP boundary, so a wrong assumption here passes the whole suite and fails in the app — this file is the record of what was actually watched against `opencode` 1.18.27 (`darwin-arm64`, digest matched), with a runbook to re-verify. **Verified:** loopback + Basic auth on every endpoint; `{data:…}` envelopes; `POST /api/session` takes `location.directory` **in the body**; `POST …/prompt` returns an *admission ack* (`admittedSeq`), not the answer; deltas are **true deltas** while `text.ended` is **cumulative**; `admittedSeq` equals `prompt.admitted`'s `durable.seq`; tool execution and the `permission.v2.asked` flow both work headless. **Disproven, and each one is in the schema so a fake implements it faithfully:** `session.idle` is **never emitted**, `POST …/wait` answers **503 “not available yet”** (declared, unimplemented), and `GET /api/event` takes **no parameters** so it cannot resume. The only real completion signal is `step.ended` — and **not** `finish === 'stop'`, because `finish` is an unconstrained string in the schema, so the rule inverts: terminate by default, continue only on the enumerated `'tool-calls'`. `step.ended` **is** one of the 28 durable variants, so a single `?after=` replay recovers both the missed content and the end of the turn. **The permission scoping defect is proven end to end:** one *Always* click produces `{projectID:'global', action, resource:'*'}` in a **user-global** SQLite store shared with the user's own OpenCode install, and a second, never-granted agent folder was then written to with **zero** permission events — which is why `ALWAYS_GRANTS_ENABLED` is `false`. Per-folder permissions **are** achievable, because the *ask* is per-session even though the *saved grant* is global: reply only `once`/`reject` and hold durable grants desktop-side. Also records the beliefs that were held and turned out false, and what remains **unverified** — chiefly whether a global `durable.seq` is a valid `?after=` cursor on the per-session stream, which is silent when wrong
- [The Agent Turn Runner](agents/local_agents/agent_turn.md) — Phase 6 of Local Agents: how a chat message addressed to a **folder agent** becomes a streaming turn against the local OpenCode engine, at parity with a remote A2A agent. A **lift, not a rewrite**: `runAgentTurn` was already the port-free single-turn primitive serving both direct chat and orchestrated mode, so `AgentTurnRunner` is that same signature over a widened input, `resolveTurnRunner(agent)` is the one dispatch point both call sites use, and every consumer downstream (parts accumulator, delta sink, `messageRepo`, `a2aSessionRepo`) is reused verbatim — the A2A body was not touched. **Dispatch is on `agents.source`, never on a missing card URL**, which is a symptom several unrelated states share: the combined `!agent || !agent.cardUrl` guard that stood at the seam matched every folder agent (they are inserted with a null card) and made the friendlier local branch below it unreachable code for the whole of Phase 5. The local runner inverts the A2A shape because `POST …/prompt` returns an **admission ack** (`admittedSeq`), not the answer — so the turn is assembled from a *separate* subscription, and **subscribing before prompting is a correctness rule**: the global stream takes no cursor, so anything emitted before the socket is live is gone. One `EngineEventBus` serves every turn (one `opencode serve` backs every folder agent), and a dropped socket is reported as a **hole** — `disconnect` then `reconnect` — so the turn heals from the *durable* per-session stream, while an engine stop is an `onClosed` instead, because the session id died with the process and a turn waiting for a reconnect that cannot come holds its lock for the life of the app. `TurnStream` maintains the **cumulative** message and hands the whole thing back, since the accumulator computes `text.slice(prior.length)` itself — feeding it a raw engine delta duplicates every character from the second chunk on, and passed 19/19 assertions when it was wrong; `text.ended` is idempotent (set, never append, never shrink), which is what makes a replay safe. Termination is the **default** and `'tool-calls'` the only enumerated continuation, because `finish` is an unconstrained string and a hang is invisible where an early end is not. **There is no `permission` or `question` part kind and none is to be added** (seam 7): both ride the existing `tool`-part convention — questions under `askuserquestion`, permissions under the reserved, un-model-emittable `cinna_permission_request` — with the engine's request id in `cinna.tool_id` as the reply address, answered **out of band** while the turn streams, because the MessagePort exists only for a direct chat. Also: the **`enabled` gate lives only in the runner** (`collectEngineAgents` does not consult it, so deleting the check makes a disabled agent chattable), reconcile-before-lock, session continuity through `a2a_sessions.context_id` plus a durable copy in `app-data/desktop.json`, a turn ceiling that caps every unsettling door not yet found, and Invariant 4 held by keeping the engine's base URL and password inside `engineManager` and never logging a response body. Sub-doc: [Technical Details](agents/local_agents/agent_turn_tech.md)

## Architecture

```
+------------------------------------------------+
|                 MAIN PROCESS                   |
|                                                |
|  SQLite (Drizzle)  LLM SDKs  MCP Clients  A2A |
|  User accounts (PBKDF2)  Session management    |
|  API keys & tokens encrypted via safeStorage   |
|                                                |
|  IPC Handlers (ipcMain.handle / .on)           |
|  + MessagePort for streaming                   |
+------------------+-----------------------------+
                   |  contextBridge (typed window.api)
+------------------+-----------------------------+
|              RENDERER (sandboxed)              |
|  contextIsolation: true, nodeIntegration: false|
|  React + Zustand + TanStack Query              |
|  window.api.auth.* / .chat.* / .providers.*    |
|  window.api.agents.* / .mcp.* / .llm.*        |
+------------------------------------------------+
```

**Security model**: API keys and OAuth tokens are encrypted at rest using Electron's `safeStorage` (OS keychain) and stored as blobs in SQLite. They are decrypted only in the main process. User passwords are hashed with PBKDF2-SHA512 (100k iterations). All data is user-scoped — every IPC query filters by the active user ID. The renderer is fully sandboxed — it can only access the typed `window.api.*` methods exposed via contextBridge.
