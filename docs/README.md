# Cinna Desktop

Desktop client for remote agents (MCP, A2A, OpenCinna).

## Glossary

| Term | Definition |
|------|-----------|
| **Chat** | A conversation with an LLM, persisted in SQLite with messages and model/provider binding |
| **Chat Mode** | A named preset bundling an LLM provider/model, MCP servers, and a color — used to quickly start configured chats |
| **Provider** (a.k.a. **LLM Provider**) | An LLM service (Anthropic, OpenAI, Gemini, OpenAI-compatible, Ollama) configured with an encrypted API key — or, for a **keyless** type, with a host and no key at all. **UI naming:** surfaced to users as **"AI Credentials"** (the sidebar section, page title, "Add AI Credentials" button, and the chat-mode field). "LLM Provider" remains the canonical/technical name in code and these docs; "AI Credentials" is purely the friendlier user-facing label, matching CinnaCore. The two terms refer to the same thing |
| **Managed Provider / Chat Mode** | An LLM provider / default chat mode auto-materialized from a Cinna admin-provisioned credential (`managed = true`). Profile-scoped, sync-owned, read-only (local enable/disable only). See [Account Provisioning](llm/account_provisioning/account_provisioning.md) |
| **Adapter** | Implementation of the `LLMAdapter` interface that translates between our chat system and a provider's SDK |
| **Keyless Credential** | An AI credential that authenticates with nothing — Ollama today (`KEYLESS_PROVIDER_TYPES` in `src/shared/credentials.ts`). It carries a **host** in the existing `base_url` column instead of a key, so it needed no migration. `isCredentialUsable` is the single predicate every layer must call in place of `hasApiKey && !unsupported`: main and renderer both import it, because the rule about which credentials can run must not be able to differ between the screen that offers one and the service that spends it. It says nothing about `enabled` — that is `isCredentialActive`, the `enabled && usable` conjunction under a name, for the callers that mean both — and nothing about **reachability** — whether the server is answering has a different answer every minute and belongs to the detection probe. Two write-path rules guard it: a renderer-supplied `baseUrl` is honoured **only** for keyless types (a keyed row pointed at an arbitrary URL is key exfiltration with extra steps), and a credential's `type` is immutable, since the repo preserves a stored key on update and re-typing a row would spend that key under another transport. See [Local Models & Keyless Credentials](llm/local_models/local_models.md) |
| **Ollama Detection** | The `provider:detect-ollama` probe: `GET /api/version` then `/api/tags` against `OLLAMA_HOST` and `127.0.0.1:11434`, or against one host the renderer names. It **reaches any http(s) host it is given, and that is inherent** — a user's Ollama may legitimately be a box on the LAN, so there is no host list to check against. What bounds it is the shape of the answer and the cost of asking: `{running, host, version, models, alreadyConfigured}` and nothing else, 5 s and 1.5 s ceilings, no retry, no port scan, no LAN sweep, and **no probe the user did not cause** by opening the AI Credentials screen or pressing Test. `http`/`https` only, userinfo dropped, so a pasted link cannot smuggle a credential into a stored host |
| **MCP Server** | A Model Context Protocol server (local stdio or remote HTTP) that exposes tools to the LLM |
| **MCP Connection** | A live client session to an MCP server, managed by MCPManager |
| **On-Demand MCP** | An MCP server the user `@-mentions` into a chat so its tools are available only for that chat — tracked separately from the chat mode's baseline MCP set |
| **Baseline MCP** | The chat-mode-owned MCP set of a chat (`chat_mcp_providers`). Exactly the mode's list — empty means none. Unioned with the on-demand set at stream time; rendered as locked chips (no `×`) in the composer, since it's managed on the mode |
| **Tool Call** | LLM requests a tool -> main process calls MCP server -> result fed back to LLM |
| **MessagePort** | Electron's streaming channel used to send LLM response chunks from main to renderer |
| **safeStorage** | Electron's OS-keychain encryption used for API keys and OAuth tokens at rest |
| **Agent** | An external AI service (e.g. A2A agent) registered by the user, communicating via a standardized protocol |
| **A2A** | Agent-to-Agent Protocol v1.0 — open standard for AI agent interoperability (discovery, messaging, streaming) |
| **Agent Card** | A2A discovery metadata (JSON) fetched from a well-known URL, describing agent capabilities and endpoint |
| **Message Part** | A typed segment of an assistant message (`kind: 'text' \| 'thinking' \| 'tool' \| 'tool_result' \| 'command_result'`) — A2A messages may persist a structured `parts[]` list driven by the Cinna `cinna.content_kind` metadata convention. The sibling `'notice'` kind bypasses `parts[]` and lands on its own `agent_transition` row (agent-side system notice). The `'command_result'` kind carries the synchronous output of a platform slash-command and IS the assistant turn for that user message |
| **Pinned** (transcript) | Whether the chat transcript is following the bottom of a streaming reply. Only the user changes it: scrolling up unpins, scrolling back into the bottom 64 px or clicking **Jump to latest** re-pins, and an arriving chunk never re-pins on its own. Unpinning requires the view to have actually moved *up* — not merely to be far from the bottom, since content growing opens up that distance with no gesture behind it. Following is instant and never animated; a smooth scroll restarted per chunk is what made a streaming table read as the window shaking. See [Transcript Scrolling](chat/conversation_ui/scroll_following.md) |
| **@-mention** | Typing `@` in the new-chat input to open a popup for selecting references (agents, and extensible for future types) |
| **Composer Menu** | The single left-side `[+]` button on the chat composer (`ComposerPlusMenu`) that consolidates attach-files, chat-mode, and add-agents/MCP into one menu — the mouse-driven sibling of the `@` / `~` triggers |
| **Capability** | A polymorphic chat tool source — an agent or an MCP server — surfaced uniformly as a selectable card in the `[+]` Add-agents/MCP picker |
| **Capability Picker** | The search-and-cards modal opened by the `[+]` menu's "Add agents / MCP" (`AgentPickerModal`, `activeFirst` multi-select): selected cards float to the top and hold position while toggling |
| **Communication Pattern** | How a new chat will route, derived from the current selection: **A2A** (one agent, no on-demand MCPs → direct agent connection) or **AI** (anything else → local model orchestrates). Surfaced as a badge left of the composer Cog |
| **Orchestrated Mode** | An LLM-root chat where the local model is the conductor and each attached agent is exposed to it as an emulated MCP tool, unioned with the real MCP tools. The "AI" communication pattern |
| **On-Demand Agent** | An agent `@-mentioned` into a chat so the orchestrator can call it as a tool. Mirrors On-Demand MCP exactly (`chat_on_demand_agents`, sticky chips, one-shot announce) |
| **Tool Provider** | Polymorphic tool source the orchestrator unions — an MCP provider (`McpToolProvider`) or an agent provider (`A2AAsMcpProvider`). Tool calls route by provider type |
| **Agent Sub-thread** | An agent-backed tool call rendered as an expandable nested thread showing the agent's own parts (thinking/tool/tool_result/text) rather than an opaque result string |
| **cinna.mcp Descriptor** | Optional backend-supplied shape (tool name, description, input schema) describing how an agent appears as an emulated MCP tool. Synthesized from agent fields when absent |
| **Note Attachment** | A profile note attached to a user message via the composer's `?` mention popup. Materialized at send time into a synthetic `.md` riding the standard file-attachment pipeline |
| **Attachment** | A file attached to a single user turn. Three sources: `cinna` (bytes on the Cinna backend, A2A-referenced), `local` (bytes in `userData/files/<userId>/<chatId>/`, used for raw-LLM chats), or `pending` (composer-only, paths held on disk for the new-chat flow until scope is known) |
| **Media Part** (file) | Resolver output handed to an LLM adapter: `image`, `document` (native non-image bytes like PDF), or `text` (UTF-8 from extraction). Adapters translate to provider-native content blocks |
| **Path Guard** | TTL-based allowlist of OS paths the renderer is permitted to reference. Populated by file dialogs and `webUtils.getPathForFile` so a compromised renderer can't synthesize arbitrary absolute paths |
| **User Account** | A local profile (username + optional password) that scopes all data — chats, providers, agents, settings |
| **Default User** | Built-in guest account (`__default__`) with no password, always present |
| **Cinna Account** | A user account linked to a remote Cinna server (cloud or self-hosted) via OAuth 2.0 + PKCE |
| **Cinna Server** | Remote service (cloud at `opencinna.io` or self-hosted) providing agent orchestration and future features |
| **Default Scope** | Shared storage under `__default__` user id — LLM providers, MCP servers, chat modes, and local agents live here and are visible from every profile |
| **Profile Scope** | Per-account storage under the active user id — chats, remote agents, agent overrides, and Cinna tokens live here and swap on user switch |
| **Agent Override** | Per-profile boolean (`agent_overrides` table) that overlays a synced agent's `enabled` flag so user toggles survive resync |
| **Job** | A reusable, profile-scoped saved spec (title, prompt, execution config). Two execution types: `local` (spawns a chat) or `cinna_task` (creates a remote cinna-core task) |
| **Job Folder** | User-defined sidebar grouping for jobs (profile-scoped, name + collapsed-state + sort position). Thin collapsible separator — owns ordering, not execution config. A job lives in exactly one folder or at the root |
| **Job Run** | One execution of a Job. Local runs reference the spawned `chatId`; Cinna runs reference the remote task; status flips via stream completion (local) or polling (cinna) |
| **Cinna Task Job** | Job variant that calls cinna-core's `POST /api/v1/tasks/`. Only available on Cinna-linked profiles; conversation lives on cinna-core, desktop keeps a pointer |
| **Task Comment** | Authored content on a cinna task (`comment_type = message \| result`); see also Activity for system-generated entries |
| **Task Attachment** | A file attached to a cinna task or one of its comments. Distinct from `FileUpload` (chat attachments) — uses a task-scoped download URL (`/api/v1/tasks/{taskId}/attachments/{id}/download`) |
| **Task Activity** | UI grouping for system-generated comment types (`status_change`, `assignment`, `system`) — shown as a compact collapsible log separate from authored comments |
| **Note** | A profile-scoped markdown document (title + body) the user inline-edits in the Notes tab. Autosaves on debounce; rendered with the same `react-markdown` stack used for chat bubbles |
| **Note Folder** | User-defined sidebar grouping for notes (profile-scoped, name + collapsed-state + sort position). Mirrors Job Folder semantics — a thin collapsible separator that owns ordering, not content |
| **Hint** | One line of shortcut-teaching copy shown in the new-chat screen's bottom bar. Either **ambient** (enters a shuffled rotation) or **contextual** (preempts the rotation when a matching user action fires). Gated on being actionable, and retired once the user has used what it teaches. See [Hints](ui/hints/hints.md) |
| **Login-Shell Environment** | The environment a user's shell produces after sourcing its profile. A Dock-launched macOS app inherits `launchd`'s bare environment instead, so the app resolves the login shell's once per lifetime and takes `PATH` from it. See [Shell Environment Resolution](development/shell_environment/shell_environment.md) |
| **Child Inherit Set** | The narrow, fixed allowlist a spawned third-party process (today: a stdio MCP server) receives — the MCP SDK's list valued from the login shell, plus session and proxy/CA variables — with the caller's own `env` map merged on top and always winning |
| **Detected Tool** | A developer tool the desktop probes for on the login-shell `PATH` (`claude`, `codex`, `opencode`, `code`, `cursor`, `uv`, `git`, `make`, `python3`), offered as a `cli-assistant`, an `editor`, or a feature-gating `runtime` |
| **Default Tool** | The one `cli-assistant` or `editor` a local agent folder opens in with a single click — the agent page's **Open in <tool>** button and the New-agent flow's "Build it with…" step. Stored as a `LocalToolId` in the `localAgentsDefaultTool` setting, **rewritten by the last pick** from either surface, set or cleared explicitly in Settings → Local Agents, and resolved against the detected list on every read so an uninstalled tool degrades to "ask". `localAgentsAutoOpen` lets a new agent open there without the step. See [Open in Tools](agents/local_agents/open_in_tools.md) |
| **Init Prompt** | The paste-anywhere briefing for one local agent folder — its path, the agent's name, and the first entry document the folder actually has (`AGENTS.md` → `CLAUDE.md` → `README.md`, else the manifest plus `Local/<slug>/docs/WORKFLOW_PROMPT.md`; a **bare** folder uses `README.md` → `AGENT.md`, the builder's document first). Built in main from the **index row**, copied to the clipboard by the Open-in menu's "Copy prompt for another tool". It is how an assistant the desktop cannot *launch* — one already running elsewhere, one in a browser, one with no launcher — is pointed at the same folder. See [Open in Tools](agents/local_agents/open_in_tools.md) |
| **Agents Root** | A registered folder local agent folders live under. Two kinds (`agent_roots.kind`): **workshop** — the kit shape, which may carry its own `.cinna-kit/` copy of the contract and is where new agents are scaffolded — and **external**, a folder the user pointed at that is only ever read. Every "Open in…" target must `realpath` to a directory at or under one, which is why overlap between roots is refused — see [Open in Tools](agents/local_agents/open_in_tools.md) |
| **External Root** | An `agent_roots` row with `kind = 'external'`: a folder adopted for the agents already in it. **Cinna installs nothing into it** — no templates, no `.cinna-kit/`, no `Local/`, no `app-data/`; the only file ever written there is an agent's own `AGENT.md`, and only when the user edits it on the agent page — and it is walked two levels deep for folders holding an `AGENT.md`. Registered by a two-call adopt (`local-agent:folder-pick`, then `:folder-add`, which refuses any path but the one just picked). See [Bare Agents & External Roots](agents/local_agents/bare_agents.md) |
| **Bare Agent** | A folder that is an agent because it holds an `AGENT.md` — singular, and deliberately not `AGENTS.md` — and for no other reason (`LocalAgentDto.kind = 'bare'`). No manifest, so no commands, credential slots, example prompts or publications; its system prompt is `AGENT.md` alone, and its identity is **positional** (`folder:external:<rootId>:<relPath>`) because there is no file to state a durable one. It **does** choose its own runtime, from the same "Runs with" panel a kit agent gets — but the answer is kept in that agent's Desktop State rather than in the folder, since the desktop writes nothing there; with no choice made it runs on the Default runtime. Adopted by path, never scaffolded. See [Bare Agents & External Roots](agents/local_agents/bare_agents.md) |
| **Agents Folder Update** | The git check on a registered root that is a working tree: is it behind, what are the missing commits, and one action — `merge --ff-only`. **It never resolves a conflict and never tries**; every state it cannot handle (`dirty`, `diverged`, `no_upstream`, `fetch_failed`, `not_fast_forward`, `git_missing`, `not_a_repo`) is a refusal naming the state and telling the user to sort it out in their own tools. Applies to workshop and external roots alike; renders nothing at all where the folder is not a repository, decided at first paint from a cheap stat walk carried on the root (`AgentRootDto.isGitRepo`) rather than from the panel's own query, so no settings row moves once the answer lands. Every command runs at the **repository root**, which may be an ancestor of the registered folder, so the panel names the repository and the refusals blame it rather than "this folder". See [Agents Folder Updates](agents/local_agents/folder_updates.md) |
| **Agents Home** | The one registered agents root marked default — `~/Documents/CinnaAgents` unless the `localAgentsHome` setting overrides it. Where the New Agent button scaffolds. Can be moved (only through the OS picker behind `local-agent:home-choose`), never removed. On macOS its **first** creation is a write into a TCC-guarded folder, so it is gated on an in-app explainer — see Home Access below |
| **Home Access** | Whether the Agents Home can be used: `ready`, `needs_consent` (nothing has touched it and macOS is about to ask), `denied` (refused). Only ever anything but `ready` on macOS. The gate lives in `agentsHomeService.ensureHome`, which **refuses** rather than writing — because the alternative was the system's *"would like to access files in your Documents folder"* prompt arriving mid sign-in, raised by a hook whose entire output was a sentence naming the folder. There is no way to ask macOS whether a prompt is pending, so the app answers from its own record: the acknowledgement in `localAgentsHomeAcknowledged`, a root row plus the folder on disk, or the path not being guarded at all. A refusal is held **in memory for the process and never stored** — macOS remembers it, a retry costs one failed `mkdir`, and a stored "denied" would keep reporting a problem already fixed. What is withheld is the **home row**, never the roots list. See [The Agents Folder Question](agents/local_agents/home_access.md) |
| **Folder Agent** | An agent that *is* a folder on disk (`agents.source = 'folder'`, row id `folder:<manifest uuid>`, protocol `local-folder`). Machine-local, default/settings scope. Distinct from `'local'` (a hand-added A2A URL) and `'remote'` (Cinna-synced). See [Agents Home, Scanner & Folder Index](agents/local_agents/folder_index.md) |
| **Folder Index** | The `agents` rows derived from scanning the roots, plus the `agent_roots` rows saying where to look. A rebuildable cache over the files, with exactly four values a rebuild cannot recover: `enabled` (the one column it owns), and a bare agent's `displayName`, `hidden` and `runtime`, which live in that agent's desktop state because its folder may not be written to |
| **Readiness** | How ready an agent folder is to run: `ok`, `credentials_needed`, `invalid`, `contract_too_new`. Always a renderable *state*, never an exception — a manifest is briefly unparseable every time an assistant saves it |
| **Turn Lock** | Per-agent, in-process lock. The runner holds it for a turn; page editors refuse to save while held; the folder watcher defers its rescan (both the per-agent and the whole-root branch) until release |
| **Desktop State** | One agent's per-machine state: local API base URL, agent token, engine sessions, permission grants, last status — plus, for a bare agent, the name the user gave it, whether it is in the list, and the runtime it was given, none of which any file in its folder can state. Two locations, and the **root** decides which: `app-data/desktop.json` inside a kit folder (the one file in it the desktop owns), and `<userData>/external-agents/<name>-<hash of realpath>.json` for a bare one, whose folder is never written into. Never probed from the folder — a `cinna-agent.json` can arrive with one `git pull`, and an agent's sessions and grants must not move when it does. The token never leaves the main process |
| **Permission Profile** | The `permission` block written onto every folder agent's entry in the generated engine config. An agent works freely **inside its own folder** (`read`/`edit`/`write`/`bash` allow); what asks is what the folder does not cover — `external_directory`, `webfetch`, the agent's own manifest and workflow prompt, secret files, `sudo` / `rm -r`. Identical for every agent unless its manifest's `runtime.permissions` replaces an entry. **Not a sandbox:** the shell is gated on command *text*, so a command can reach anything the user can. See [Local Agent Permissions](agents/local_agents/permissions.md) |
| **Standing Grant** | One remembered *Always allow*: `{action, pattern, scope, decidedAt}` in that agent's **Desktop State** — `app-data/desktop.json` inside a kit folder, and a file under `<userData>/external-agents/` for a bare one, whose folder the desktop writes nothing into. A bare agent's are therefore keyed on where its folder sits: moving it starts a new agent, which is asked again. The desktop is the authoritative store — OpenCode's own `always` writes a **user-global** row naming no directory, session or agent, so `always` is never posted to the engine; a covered ask is answered `once` automatically with **no block written to the transcript at all** |
| **Grant Scope** | `exact` \| `origin` \| `action` — how widely a grant's pattern reaches, **recorded rather than inferred from its characters**. Matching is string work with no regular expression anywhere, because `rm -rf build/*` stored as a wildcard also covered `rm -rf build/../../Documents` |
| **Status Refresh Command** | `status_refresh_command` in a folder agent's manifest: how the desktop asks that agent to *recompute* its status. Only the `/run:<name>` form executes — a reference into the agent's own command catalog — and it runs under the agent's turn lock. Distinct from a **re-read**, which just reads `app-data/storage/STATUS.md` off disk. See [Agent Status](agents/agent_status/agent_status.md) |
| **Counterparty** | An agent the user picks and then expects an answer from. Every **enabled** agent is one, whatever its source: the composer `@`-list, the `[+]` capability picker and the Job agent picker all filter on `enabled` and nothing else, and `enabled` means only the user's own choice. A folder agent was excluded by a separate predicate — never by that column — until the local runner could serve one. See [Folder Agents as Counterparties](agents/local_agents/counterparty.md) |
| **Kit Contract** | The pinned, machine-readable half of the cinna-core agent start-kit bundled with the desktop (`resources/cinna-kit-contract/`): the manifest schema, the folder model (`layout.json`), and the root/agent templates. Lets the desktop scaffold, validate and export agent folders offline. See [Kit Contract](agents/local_agents/kit_contract.md) |
| **Agent Manifest** | `cinna-agent.json` at a local agent folder's root — the one file the desktop, a coding assistant and cinna-core all agree on. Unknown keys survive a read/write round trip untouched |
| **Contract Version** | Semver recorded on both the folder and the tool, and the **compatibility gate**: newer folder major → refuse and ask the user to update the app; older major → migratable; same major → run as-is. Distinct from `kit_version`, which is informational and never a gate |
| **Content Hash** | Stable SHA-256 over the files that would travel to a Cinna instance (sorted `path\0sha256(content)` lines, no mtime or inode, symlinks excluded). Answers "has this agent changed since it was pushed to that instance?" |
| **Legacy Manifest** | A `cinna-agent.json` carrying the retired integer `schema_version` and neither `contract_version` nor `id`. Read and warned about, never rejected — the one exemption from the identity requirement, encoded in the schema, the validator and the contract CHANGELOG together |
| **File Stamp** | `{mtimeMs, size, hash}` for a file an agent page can edit. Taken by the read that produced the rendered text and handed back at save time, so a write over a file an assistant changed underneath is refused. Metadata is a pre-check; the SHA-256 decides |
| **Identity State** | Where a folder agent's row id comes from: `manifest` (a UUID in `cinna-agent.json`), `legacy` (parsed, no `id` — indexed positionally), `unresolved` (unreadable manifest — listed, never indexed), `external` (a bare folder, positional by root-relative path). A folder that loses an id collision gets a fifth, *duplicate*, list id: selectable but not indexed. `external` is deliberately not `legacy` even though both are positional: the fix offered for a legacy folder is **Stamp identity**, and a bare folder has no manifest to write a UUID into |
| **Stamp Identity** | The offered — never automatic — write of a fresh UUID `id` into a legacy manifest. Re-keys the `agents` row and repoints everything that names it, rather than letting a rescan prune and re-insert |
| **Local Agent Outcome** | `LocalAgentOutcome<T>`: a failure **code** returned as data instead of thrown, because `ipcMain.handle` and `contextBridge` each drop an error's own properties. Used by `local-agent:get` and `:update-field`, whose codes drive renderer behaviour. See [Agents Tab & Agent Page](agents/local_agents/agents_tab.md) |
| **Tray Popup** | Menu-bar (status-bar) popover window listing agent statuses; opens from the macOS menu-bar tray icon, shows a worst-severity dot, and redirects the main window on click |
| **Engine** (a.k.a. **Local Engine**) | The one desktop-managed `opencode serve` process every folder agent runs on. Loopback-only, on a port the desktop picks, behind a per-start Basic-auth password. **One process serves them all**, so anything that restarts it ends *every* streaming turn — which is why `turnLock.anyHeld()`, not the per-agent `isLocked`, is the engine-level guard. See [The Local Engine](agents/local_agents/engine.md) |
| **Engine Config** | The OpenCode configuration generated into `<userData>/engine/opencode.json` — never into an agent folder. One provider entry per **active** AI credential — a credential the user switched off is left out, because that switch is a statement about spending and no runner gate would honour it (an *agent*'s own `enabled` is a different, still-open question) — one agent entry per runnable folder agent, plus the permission profile. API keys are never in it: each is an `{env:CINNA_ENGINE_KEY_…}` reference resolved from the engine process's environment (Invariant 4). A keyless credential names a variable too, carrying the public literal `keyless` — the placeholder is emitted rather than omitted because an entry with an `env` is the availability branch every working entry takes, and it contradicts nothing, since no key exists on that path |
| **Loaded Config** | The record carried on the *running* engine process — a digest of its config and prompt bytes, a digest of its credential environment, and the agent keys and skips **that process actually loaded**. Dies with the process. "Does the engine need restarting" is a comparison against this, never against a remembered flag or the bytes on disk |
| **Agent Key** | The OpenCode agent-entry name a folder agent becomes (`<slug>-<hash of agent id>`, always hash-suffixed so it never depends on which other agents exist). Engine sessions bind to it |
| **Generated Prompt** | The per-agent system prompt assembled from the agent's own files (workflow prompt, scripts and credentials READMEs, the `knowledge/` topic *list*, handovers) plus a desktop context block. Written beside the engine config, never into the agent folder |
| **Runtime** | What a folder agent runs on, reduced to `{credential, model}` because the engine is always OpenCode. Resolved from the agent's own declaration first, then the Default runtime — but the **model** only where it can run: the config names a runtime as `<credential>/<model>` verbatim, so a model borrowed by a credential that cannot serve it is an entry that saves cleanly and fails on the agent's first turn. The declaration stores a credential **name** and *either* a model id *or* a Work Complexity — never a key, and never both of the two. A kit agent declares it in its manifest, under the file's stamp; a bare agent has no manifest, so the same three values go into its Desktop State through `local-agent:set-runtime` — unstamped, because the write touches no file in the folder — and both arrive on `LocalAgentDto.runtime`, so resolution has no branch for the second kind. One shared validator (`runtimeService.validate`) refuses a key-shaped credential on either path |
| **Work Complexity** | `simple` \| `medium` \| `complex` in a manifest's `runtime.complexity`, in place of a model id: how hard the agent's work is, left for the host to resolve. It exists because a model id is the least portable thing `cinna-agent.json` can carry — the file is committed, read by a coding assistant and uploaded to a Cinna instance on publish, and an id means something only to the catalogue that lists it, while `medium` means the same thing on another machine, another credential and after the next model release. Resolved against the **live** catalogue by model *family* (`src/shared/modelFamilies.ts`), not a table of ids, so a new release joins its tier with no app update. A **local** model is tiered by parameter count instead of by product name — Ollama has no line-up, only whatever the user pulled, and `qwen2.5-coder:1.5b` and `:32b` are the same product in different tiers; an unsized `:latest` tag resolves to Medium rather than to nothing, because null would leave every tier empty on a machine that pulled only defaults. Contract 1.1.0, mutually exclusive with `runtime.model`. See [The Local Engine](agents/local_agents/engine.md#how-a-tier-becomes-a-model) |
| **Default Runtime** | The fallback runtime, derived from the user's default chat mode. There is deliberately no third fallback **for the credential** — an agent never runs on a key the user did not choose, because that is a billing surprise — and still no "first model in the catalogue". The **model** chain does have a floor below the Default runtime: the Medium tier of the credential the agent was already given. A *tier* is a class the user can choose and hold an opinion about, which is why the floor is not the arbitrary pick the rule forbids; what it replaced was a dead end where an agent named no model, could not run, and said so only on a panel the user had to go and find |
| **Medium Floor** | The last step of model resolution: Medium, resolved on the chosen credential, for an agent nothing above answered for. Medium and not Simple because an agent silently downgraded to the cheapest model does poor work and gives no clue why; Medium and not Complex because that failure is a bill. Never applied to the Default runtime itself — flooring twice would resolve against the *default* credential's catalogue and lend that model to an agent on a different key |
| **Inherited Model** | Which model a runtime that names none gets: the default runtime's when the credential is the default's own row → that credential's own default model (this is what covers a default chat mode left on *First available*) → the default's again when the two credentials share a provider *type*, `openai_compatible` and `ollama` excepted (two gateways, or two Ollama hosts, are two catalogues) → the **Medium floor** on that credential → nothing. One function in `src/shared/runtimeDefaults.ts` (`resolveRuntimeModel`), called by the main process **and** by the "Runs with" panel, so the `Default (…)` label and the generated config cannot name different models — an invariant three latent divergences were found under while the floor was being added |
| **Agent Turn Runner** | `AgentTurnRunner` — one agent turn, whatever kind of agent it is: the shared `RunAgentTurnInput` → `RunAgentTurnResult` signature, which **never throws** (a failed turn is a result carrying `error`, because an exception loses its code across IPC). Two implementations, A2A and local; `resolveTurnRunner(agent)` picks between them on `agents.source` and is the one dispatch point both call sites use. See [The Agent Turn Runner](agents/local_agents/agent_turn.md) |
| **Engine Session** | An OpenCode `ses_…` created against a folder agent's directory and its agent key, one per (chat, agent). Stored in `a2a_sessions.context_id` — the A2A-named column is reused deliberately, since that is what `agent:get-session` reads — with a durable copy in that agent's **Desktop State** — in the folder for a kit agent, under `<userData>` for a bare one. That copy is what `restoreHiddenAgents` re-seeds `a2a_sessions` from when an agent removed from the list is put back, so a bare agent's survives a removal precisely *because* it is not in the folder. Verified rather than trusted on resume: the engine's own storage can be cleared |
| **Admission Ack** | What `POST /api/session/{id}/prompt` answers with: a receipt (`SessionInputAdmitted`, carrying `admittedSeq`) saying the input was accepted — **not** the answer. The answer arrives on a separate SSE subscription, which is why a turn must subscribe *before* it prompts |
| **Hole** (engine stream) | The events lost between a dropped socket and the next one. Unrecoverable from the global stream, which takes no cursor — so a reconnect is reported as a hole (`disconnect` then `reconnect`) and **healed** by replaying the durable per-session stream from the last `durable.seq`. An engine *stop* is reported as a close instead: no reconnect is coming |
| **Parked Request** | A permission ask or ask-user question a local agent is blocked on **mid-turn**. Rendered as a `tool` part (there is no `permission` part kind), answered out of band by request id while the turn streams, and rejected on every exit from the turn — an unanswered one is a session that never goes idle |
| **Connect Intent** | The `cinna://connect?server=<origin>` deep link as it crosses into the renderer: an origin and when it arrived, and nothing else. Validated and reduced to an origin in main, buffered one at a time, and never acted on without the confirm step. See [The `cinna://connect` Link](auth/onboarding/connect_link.md) |
| **Confirm Step** | `ConnectIntentPanel` — the one screen a `cinna://connect` link is allowed to reach, and **the deep link's security boundary**. The URL validation is not: it narrows what a link can express, while a human reading the host is what decides whether it is acted on |
| **Local Development** | The desktop preparing *this machine* for agent work on a Cinna account: a managed toolchain under `<userData>/localdev`, a cinna-cli account workspace under the Agents Home, and the opencode engine pre-fetched so a first turn does not start with a download. The desktop is installer and orchestrator; cinna-cli owns setup, tokens, workspace layout and sync. See [Local Development](agents/local_dev/local_dev.md) |
| **Managed Toolchain** | uv, Mutagen and cinna-cli installed into `<userData>/localdev/` and nowhere else, version-stamped so an upgrade never swaps a running binary's file. Uninstalling Cinna takes it with it |
| **Account Workspace** | `<AgentsHome>/Cloud/<host>/` — a cinna-cli-owned directory holding the account token and context package for one Cinna instance. The desktop looks at exactly one file in it, `.cinna/account.json`, and only to answer "has cinna-cli set this up" |
| **Setup Token** | The single-use, fifteen-minute setup command the desktop mints with its own OAuth bearer (`POST /api/v1/cli/account/setup-tokens`) and hands to cinna-cli. It is what removes the second browser login. **Argv-only** — never logged, never in an error detail, never in a state the renderer can read |
| **Local Dev Consent** | A per-host yes/no, remembered — including the no. Stored as JSON in the default-scoped `localDevConsent` setting; an absent host means never asked, and `false` is what stops the prompt returning every launch. Asked as a checkbox on the `cinna://connect` confirm screen (ticked only where this machine holds no answer for that host), as the `localdev` onboarding step otherwise, and by a modal on an install that gains the feature later |
| **Managed Asset** | A pinned, checksum-verified install into a directory this app owns (`src/main/managed/managedAsset.ts`), shared by the local engine and the local-dev toolchain. **The presence of the install directory is the proof its bytes were verified** — everything is staged and published by one atomic rename |

- [Kit Contract & Manifest Layer](agents/local_agents/kit_contract.md) — The bundled, pinned copy (contract `1.1.0`) of the cinna-core start-kit *contract* (manifest schema, `layout.json` folder model, root/agent templates) plus the TypeScript reader, validator and exporter over it, so the desktop can scaffold, validate and export kit-shaped agent folders offline — no Python, no network. Governing principle: **files are the truth, the database is an index** — this layer never writes to SQLite. Three versions answer three separate questions (`contract_version` gates compatibility, `kit_version` is informational, `content_hash` detects drift against a publication); a legacy manifest is exempt from the identity requirement by a conditional `allOf` the schema, the validator and the CHANGELOG must change together; secret-bearing files (`credentials.json`, any `.env` but `.env.example`, `*.pem`/`*.key`/`*.p12`) are excluded at four independent layers while `credentials/README.md` and `.env.example` deliberately travel; manifest writes are content-hash guarded (mtime+size loses to `cp -p` / `rsync -t` / `git checkout`); and the hand-rolled YAML reader flags the three shapes it mis-reads and drops those command entries rather than executing a silently-truncated command. **Reading is tolerant where writing is strict**: what a newer *minor* adds is graded a warning and given defined behaviour, never an error — an error makes the scanner mark the folder `invalid` and the engine drop it entirely, which would brick a folder a future 1.x tool wrote and break the "minor bumps are additive and safe to ignore" promise the compatibility gate rests on — while this desktop still refuses to *write* either shape. Sub-doc: [Technical Details](agents/local_agents/kit_contract_tech.md)
- [Agents Home, Scanner & Folder Index](agents/local_agents/folder_index.md) — Phase 2 of Local Agents: how agent *folders on disk* become `agents` rows. The agents home (`~/Documents/CinnaAgents`) plus adopted roots, the TypeScript port of `kit.py new`, the scanner that derives readiness (`ok` / `credentials_needed` / `invalid` / `contract_too_new`) and rebuilds each root's index in one transaction, the debounced `fs.watch` per root, `app-data/desktop.json`, the per-agent turn lock, and the IPC surface over all of it. Governing rule: **a scan can only speak for the folder it walked** — it never prunes a folder it could not parse, nor rows at a location the root has moved away from, because `a2a_sessions` and `job_agents` cascade from `agents.id` and a manifest is unparseable for a moment every time an assistant saves it. An unreadable folder therefore adopts the id of the row already at its path and changes **readiness, never identity**. Watch events are a three-way `ignore` / `root` / `agent` result (collapsing them made `app-data/` — the one directory deliberately not watched — trigger a full rescan), both rescan branches honour the turn lock, and rescans must be idempotent because macOS FSEvents replays pre-arm changes on every watcher arm. `enabled` means only the user's choice and survives every rescan — it was never borrowed to express "no runner exists yet", which is why nothing had to be turned back on when one arrived. Roots may not nest — every root widens the "Open in…" path guard — and `local-agent:root-add` takes no renderer-supplied path, only a native dialog's. A root now also has a **kind**: `scanRoot` dispatches to the external walk for an adopted folder ([Bare Agents](agents/local_agents/bare_agents.md)), and everything downstream — the DTO, the index transaction, the prune, the turn lock — is shared. Sub-doc: [Technical Details](agents/local_agents/folder_index_tech.md)
- [The Agents Folder Question](agents/local_agents/home_access.md) — Asking about `~/Documents/CinnaAgents` before macOS does: the consent gate in front of the first write into a TCC-guarded folder, the `AgentsHomeModal` explainer and its refusal follow-up, the recovery affordances in the sidebar and Settings, and why a refusal is remembered for the process and never on disk
- [Agents Tab & Agent Page](agents/local_agents/agents_tab.md) — Phase 3 of Local Agents: the user-facing surface. An **Agents** tab whose rows are folders grouped by root — each with a chat button beside it (shown on hover or keyboard focus, withheld from an `invalid` folder) that starts a chat with the agent and moves the sidebar to Chats without opening its page — a per-agent page that is a **control surface first** — Open in <default tool>, Start chat, a ⋯ menu (Rescan, Reveal, Terminal, Stamp identity, **Delete agent…**) and a "Runs with" panel above the fold whose many possible warnings share **one reserved, prioritised, fixed-height line** (stacked conditional rows changed the panel's height on a credential change and moved the tab strip under the pointer) and whose second control asks **how hard the work is** rather than which model runs it, with an **Advanced** checkbox for the raw model list — a remembered preference that only breaks a tie, since the agent's own runtime decides which picker it opens on and ticking the box therefore *converts* that runtime and says so; a conversion that cannot be made honestly is never approximated, and a pinned model no tier describes leaves the checkbox ticked and **disabled** with the reason standing beside it rather than springing back under the pointer, five tabs (Overview, Prompts, Commands, **Permissions** — with a standing-grant count badge — and Folder) below, and a readiness strip that renders only when something needs attention — and a **viewer over the folder** underneath (every card names the file it reads; Description, example prompts and the three prompt documents edit in place); a name-only New-agent flow (description optional — the name stands in, since the kit schema needs one, and the AI draft runs only when a sentence was given) that ends by handing the folder to the user's tool; and Settings → Local Agents — three titled sections (Agent Folders, Engine Settings, Developer Tools) built from the shared `SettingsLayout` primitives, where each status line sits in the section holding the control that resolves it (the engine's state directly above the field deciding which binary starts, rather than in a Readiness card of its own) and a stopped engine is reported neutrally, since the first local turn starts it. **Delete is the OS Trash, never `rm -rf`, and goes through the ordinary rescan prune** rather than a row delete, under the turn lock (a mid-turn agent refuses with `turn_in_progress`, which the dialog explains as busy — the third channel to return a `LocalAgentOutcome`); the chat rows survive with a binding that stops resolving, and a job bound to the agent is **blocked**, not run agentless, because the run gate reads the stored manifest. The ⋯ menu — not the dismissable dialog — owns the delete mutation and clears the selection from a hook-level `onSuccess` (a mutate-level one dies with the unmounted caller), and the composer/Jobs pickers' `['agents']` query is invalidated on create, stamp, delete and every watcher push, where before only a remote sync refreshed it. The secrets line's "Add them in `credentials/.env`" opens that **file**, not the folder around it, and **creates it** when it is missing — owner-only, declared names commented out, since the scaffold writes only `.env.example` and an uncommented placeholder reads to the scanner as every credential already satisfied; that seed is the one write the desktop makes into the file it otherwise only reads names from. The editor state machine is **pure and lives outside React** (`src/renderer/src/utils/localAgents.ts`): the stamp handed back on save is the one taken by the read the UI rendered, a reload pairs text and stamp from the *same* read, a refused save is never retried, and a "my slice didn't move" branch lets three cards share one `cinna-agent.json` without false conflicts. There are **three** save outcomes, not two — a conflict (`manifest_modified`/`file_modified`) is terminal, a blocked write (`turn_in_progress`) is retryable and re-arms a longer debounce. IPC error codes cannot survive a thrown rejection (two boundaries strip them), so the two channels whose codes drive behaviour return `LocalAgentOutcome<T>` data unwrapped renderer-side. Identity is a three-way union plus a *duplicate* list id that is selectable but not indexed (sharing one id previously opened the **wrong agent's editable page**). "Stamp identity" **re-keys** the row across nine tables in one transaction — including the three `messages.*_agent_id` columns no cascade touches, which don't disappear, they stop resolving. - [The Local Engine, Runtimes & Prompt Assembly](agents/local_agents/engine.md) — Phase 5 of Local Agents: what actually runs a folder agent. - [The OpenCode Engine Contract](agents/local_agents/opencode_contract.md) — **What is verified about the engine, how, and under what conditions.** Every test in `agentTurn/**` and `engine/**` runs against a fake at the HTTP boundary, so a wrong assumption here passes the whole suite and fails in the app — this file is the record of what was actually watched against `opencode` 1.18.27 (`darwin-arm64`, digest matched), with a runbook to re-verify. **Verified:** loopback + Basic auth on every endpoint; `{data:…}` envelopes; `POST /api/session` takes `location.directory` **in the body**; `POST …/prompt` returns an *admission ack* (`admittedSeq`), not the answer; deltas are **true deltas** while `text.ended` is **cumulative**; `admittedSeq` equals `prompt.admitted`'s `durable.seq`; tool execution and the `permission.v2.asked` flow both work headless. **Disproven, and each one is in the schema so a fake implements it faithfully:** `session.idle` is **never emitted**, `POST …/wait` answers **503 “not available yet”** (declared, unimplemented), and `GET /api/event` takes **no parameters** so it cannot resume. The only real completion signal is `step.ended` — and **not** `finish === 'stop'`, because `finish` is an unconstrained string in the schema, so the rule inverts: terminate by default, continue only on the enumerated `'tool-calls'`. `step.ended` **is** one of the 28 durable variants, so a single `?after=` replay recovers both the missed content and the end of the turn. **The permission scoping defect is proven end to end:** one *Always* click produces `{projectID:'global', action, resource:'*'}` in a **user-global** SQLite store shared with the user's own OpenCode install, and a second, never-granted agent folder was then written to with **zero** permission events — so the desktop never sends `always` at all. Per-folder permissions **are** achievable, because the *ask* is per-session even though the *saved grant* is global: reply only `once`/`reject` and hold durable grants desktop-side — which is what [Local Agent Permissions](agents/local_agents/permissions.md) now does. Also read out of the binary and load-bearing for anyone editing the profile: the pattern matcher is **not a glob** (there is no `**`, and a missed pattern fails **open**), `evaluate` is a `findLast` so the *last* matching rule wins rather than the most specific, and the shell tool is gated on the **full command text** while `external_directory` fires only for path arguments of a fixed command list — so the folder is a boundary for the file tools, not for the shell. Also records the beliefs that were held and turned out false, and what remains **unverified** — chiefly whether a global `durable.seq` is a valid `?after=` cursor on the per-session stream, which is silent when wrong
- [The Agent Turn Runner](agents/local_agents/agent_turn.md) — Phase 6 of Local Agents: how a chat message addressed to a **folder agent** becomes a streaming turn against the local OpenCode engine, at parity with a remote A2A agent. A **lift, not a rewrite**: `runAgentTurn` was already the port-free single-turn primitive serving both direct chat and orchestrated mode, so `AgentTurnRunner` is that same signature over a widened input, `resolveTurnRunner(agent)` is the one dispatch point both call sites use, and every consumer downstream (parts accumulator, delta sink, `messageRepo`, `a2aSessionRepo`) is reused verbatim — the A2A body was not touched. **Dispatch is on `agents.source`, never on a missing card URL**, which is a symptom several unrelated states share: the combined `!agent || !agent.cardUrl` guard that stood at the seam matched every folder agent (they are inserted with a null card) and made the friendlier local branch below it unreachable code for the whole of Phase 5. The local runner inverts the A2A shape because `POST …/prompt` returns an **admission ack** (`admittedSeq`), not the answer — so the turn is assembled from a *separate* subscription, and **subscribing before prompting is a correctness rule**: the global stream takes no cursor, so anything emitted before the socket is live is gone. One `EngineEventBus` serves every turn (one `opencode serve` backs every folder agent), and a dropped socket is reported as a **hole** — `disconnect` then `reconnect` — so the turn heals from the *durable* per-session stream, while an engine stop is an `onClosed` instead, because the session id died with the process and a turn waiting for a reconnect that cannot come holds its lock for the life of the app. `TurnStream` maintains the **cumulative** message and hands the whole thing back, since the accumulator computes `text.slice(prior.length)` itself — feeding it a raw engine delta duplicates every character from the second chunk on, and passed 19/19 assertions when it was wrong; `text.ended` is idempotent (set, never append, never shrink), which is what makes a replay safe. Termination is the **default** and `'tool-calls'` the only enumerated continuation, because `finish` is an unconstrained string and a hang is invisible where an early end is not. **There is no `permission` or `question` part kind and none is to be added** (seam 7): both ride the existing `tool`-part convention — questions under `askuserquestion`, permissions under the reserved, un-model-emittable `cinna_permission_request` — with the engine's request id in `cinna.tool_id` as the reply address, answered **out of band** while the turn streams, because the MessagePort exists only for a direct chat. Also: the **`enabled` gate lives only in the runner** (`collectEngineAgents` does not consult it, so deleting the check makes a disabled agent chattable), reconcile-before-lock, session continuity through `a2a_sessions.context_id` plus a durable copy in `app-data/desktop.json`, a turn ceiling that caps every unsettling door not yet found, and Invariant 4 held by keeping the engine's base URL and password inside `engineManager` and never logging a response body. - [Local Agent Permissions](agents/local_agents/permissions.md) — What a folder agent may do on the user's machine, who decides, and where the decision is kept. Two mechanisms answering two questions: a **static profile** in the generated engine config, and **standing grants** stored beside the agent. The profile widened deliberately — an agent now reads, writes, edits and runs commands **inside its own folder** outright, because the previous profile (writes only under `app-data/`, three shapes of command) asked about nearly every step of ordinary work, and **a prompt that fires constantly is not a control, it is a thing users learn to click through**. What still asks is what the folder does not cover: `external_directory`, `webfetch`, the agent's own `cinna-agent.json` and `docs/WORKFLOW_PROMPT.md`, secret files (`deny` for writes as well as reads, now that the folder is writable), and `sudo` / `rm -r` as an *accident* boundary rather than a security one. Three engine facts read out of the pinned 1.18.27 binary govern every pattern in it and each fails toward **allow**: the matcher is **not a glob** — `*` crosses `/`, there is no `**`, and `**/.env` therefore never matches a root-level `.env`, which is exactly what a resource is; resolution is **`findLast`**, so the *last* matching rule wins and our block merges after OpenCode's allow-everything base (which is why `'*': 'ask'` must be written, and why `read: {'*': 'allow'}` switches the engine's own `.env` protection off and leaves ours the only defence); and the shell tool is gated on the **full command text** while `external_directory` fires only for path arguments of a fixed command list — so **the folder is a boundary for the file tools, not for the shell**, and the Permissions card says so in the user's own words rather than describing a fence that is not there. **"Always allow" is answered by the desktop and never sent to the engine:** one engine-side `always` writes `{projectID:'global', resource:'*'}` into a store shared with the user's personal OpenCode install, so the grant is written to that agent folder's `app-data/desktop.json` while the user waits, the engine is told `once`, and a later ask a grant covers is answered `once` automatically with **no block written to the transcript at all** — a widget that appeared and answered itself mid-stream is one the user cannot act on. A grant carries an explicit **scope** and is matched by string work with no regex anywhere, because the first cut compiled the pattern and `rm -rf build/*` silently also covered `rm -rf build/../../Documents`; every resource of an ask must be covered, not any; a missing scope reads as the narrowest; and "remembered for this agent" is claimed **only** where the write reached disk, because the action goes ahead either way. `always` has two locks (converted on the answer path, downgraded again at the engine door), the automatic reply retries once and then **rejects** rather than parking a turn to the 20-minute ceiling, and a refused answer now leaves the buttons where they were instead of greying out a block nothing else could answer. Surfaced as the agent page's **Permissions** tab with a count badge. Deliberately does **not** prune OpenCode's own store, so a grant made outside this app still allows without asking. - [Bare Agents & External Roots](agents/local_agents/bare_agents.md) — Any folder holding an `AGENT.md` can be adopted as an agent, without being converted first. The folder is registered as an **external** root and **nothing is ever written into it** — no templates, no `.cinna-kit/`, no `Local/`, no `app-data/` — which is why a bare agent's name, its removed-from-the-list flag, the runtime it was given and all its machine-local state live under `<userData>` instead, at a location the *root* decides rather than a probe of the folder (a `cinna-agent.json` is one `git pull` away, and an agent's sessions must not move when it arrives). The root is walked two levels deep, never into a folder that is already an agent and never into a dependency tree, so "one agent folder" and "a repository of them" are the same walk. Identity is positional, and deliberately a different identity *state* from `legacy`, because the fix offered there — Stamp identity — needs a manifest to write into. Re-picking a folder already registered is a **re-selection**, not a refusal: the ticked set becomes the whole list, so unticking removes and ticking puts back — which is what makes this the only surface where a sixteenth agent can be added after fifteen were, since ⋯ takes one out at a time and Settings puts all of them back at once. Every removal's turn lock is checked before anything is written (taking them one at a time left an agent hidden under a dialog reporting that nothing had changed), a `name` reaches only an agent being added (it is prefilled from the folder, so sending it back renamed one silently), an agent put back gets its engine sessions again, and anything leaving is confirmed by name first. A bare agent also picks its **own runtime** on the same "Runs with" panel a kit agent uses, stored in its desktop state rather than in the folder and validated by the same checks as a manifest's, because an agent adopted from the user's own repository is not a lesser agent and "which credential pays for this" is the question they most need answered. Removal asks: "remove from the list only" is the default, both routes back are named, and restoring re-seeds the engine sessions (`job_agents` cannot come back, and the dialog says so). Ten surfaces on the reused agent page asserted files this folder shape never had, which is where [UX rules 9 and 10](development/ui_guidelines/ux_rules.md) came from. - [Local Agents Are Not Synced](agents/local_agents/local_only.md) — **The governing product position for anything a folder agent touches across machines.** A folder agent is a directory; the desktop's sync never carries one; a job bound to one is a **local-only job**. The `source: 'folder'` job-dependency descriptor exists so an unresolvable dependency is **visible and blocking**, not so the job runs elsewhere — the app refuses the run and the blocked-job panel deliberately offers **no repair instruction** (not "copy the folder here", which promises an unshipped workflow, and not "it will run on a device where that agent is set up", which names a device that need not exist — this state is reachable by one user on one machine who has never enabled sync). - [Adapters](llm/adapters/adapters.md) — Custom LLM abstraction layer with Anthropic, OpenAI, Gemini and Ollama adapters

- [Local Models & Keyless Credentials](llm/local_models/local_models.md) — Ollama as a first-class AI credential, for chat and for folder agents. **Keyless credentials** are the architecture: one shared `isCredentialUsable` in place of a hand-written `hasApiKey && !unsupported` at every call site, and a host in the existing `base_url` column instead of a key, so no migration. The adapter lists over the native `/api/tags` (only that surface returns the parameter size a local tier is made of) and streams by delegating to the OpenAI adapter on `<host>/v1`; the engine gets a custom provider entry with a public `keyless` placeholder, `{32768, 4096}` limits and no `tool_call` claim (`capabilities.tools: false` is catalogue metadata — the runner sends all 12 tools regardless, measured on the wire); the reconcile re-asks the **local** credentials only, and a refresh never shrinks a provider to nothing, which is what stopped an agent hanging for twenty minutes when Cinna started before Ollama. The detection probe reaches any host the renderer names — inherent, since an Ollama may be on the LAN — and is bounded by its answer shape, its ceilings and the fact that only a user action causes one
- [Switching an AI Credential Off](llm/adapters/credential_enablement.md) — A credential's `enabled` switch is a statement about **spending**, so it now means off everywhere: `collectEngineProviders` no longer hands the local engine a disabled credential, which for a canonical type had been carrying a working key into the config and letting a folder agent bill after the user turned it off. Switching one off asks first **only when something depends on it**, and the confirm names the chat modes and agents that stop rather than counting them; the card then keeps a counted line for as long as it is off, because the dialog is gone by tomorrow. `isCredentialUsable` stays a test of the key alone — the "Runs with" panel must list a disabled credential for an agent pointing at one to say so — and `isCredentialActive` is the `enabled && usable` conjunction under a name. Credential-reference resolution (id → name → type, tie-broken toward a credential that can run) moved into `src/shared/credentials.ts` after the renderer's hand-written copy drifted from main's the moment main's learned about `enabled`. Every surface reports it in its own words: a red dot and `AI credential switched off` in the agents sidebar (outranking the folder's own `credentials needed`), an `Inactive` badge with a visible cause on both kinds of chat-mode card, and a select that no longer claims "None (use default)" over a mode that names a credential
- [AI Functions](llm/ai_functions/ai_functions.md) — Shared primitive for one-shot LLM calls (Auto Chat Titles today; chat-summary and similar utilities in the future) — adapter resolution + `runSingleShot`
- [Account-Provisioned Providers & Chat Modes](llm/account_provisioning/account_provisioning.md) — "Ready on login": a Cinna admin provisions AI credentials centrally; the desktop auto-materializes read-only, profile-scoped **managed providers** + a default **managed chat mode** per credential from cinna-core's `GET /external/account-config` (decrypted key delivered to the trusted client, re-encrypted locally). ## Architecture

```
+------------------------------------------------+
|                 MAIN PROCESS                   |
|                                                |
|  SQLite (Drizzle)  LLM SDKs  MCP Clients  A2A |
|  User accounts (PBKDF2)  Session management    |
|  API keys & tokens encrypted via safeStorage   |
|                                                |
|  IPC Handlers (ipcMain.handle / .on)           |
|  + MessagePort for streaming                   |
+------------------+-----------------------------+
                   |  contextBridge (typed window.api)
+------------------+-----------------------------+
|              RENDERER (sandboxed)              |
|  contextIsolation: true, nodeIntegration: false|
|  React + Zustand + TanStack Query              |
|  window.api.auth.* / .chat.* / .providers.*    |
|  window.api.agents.* / .mcp.* / .llm.*        |
+------------------------------------------------+
```

**Security model**: API keys and OAuth tokens are encrypted at rest using Electron's `safeStorage` (OS keychain) and stored as blobs in SQLite. They are decrypted only in the main process. User passwords are hashed with PBKDF2-SHA512 (100k iterations). All data is user-scoped — every IPC query filters by the active user ID. The renderer is fully sandboxed — it can only access the typed `window.api.*` methods exposed via contextBridge.
