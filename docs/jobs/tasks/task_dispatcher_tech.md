## Database Schema

All added idempotently by `migrateTasks` (`src/main/db/migrations/tasks.ts`). All are device-local: none is a synced collection, and neither task column is in the device-sync payload.

- **`agent_task_dispatch`** — primary key `(user_id, agent_id)`; `mode` (`manual` default), `max_runs` (N of `up_to`, null in the other modes), `paused_reason`, `paused_task_id`, `paused_at` (ms), `updated_at`. **No row means Manual, not paused.** `agentTaskDispatchRepo.patch` nulls `max_runs` outside `up_to` and deletes a row that has returned to those defaults, so that rule keeps holding. A table of its own, not columns on `agent_overrides`, because an override row carries `enabled`, the same reason `agent_colors` is separate. No FK to `agents`. An install from before `up_to` still has `active_task_id` / `active_chat_id`; the migration copies a run recorded there into `agent_task_dispatch_runs` once, empties them, deletes a row left manual and unpaused, and nothing writes them again. `agentRepo` rewrites `agent_id` on an agent id rename. `userRepo` deletes the rows with the profile.
- **`agent_task_dispatch_runs`** — primary key `(user_id, agent_id, task_id)`; `chat_id` (null until the run is accepted), `started_at` (ms). Every dispatched run in flight, one row each, so that boot finds each run Cinna quit under — one pair of columns could hold only one, and an `up_to` queue has several. `setActive(taskId, null)` writes it just before the start, `setActive(taskId, chatId)` once accepted, `clearActive` on settle, a failed start or boot recovery. No FK. `agentRepo` rewrites `agent_id` on rename; `userRepo` deletes with the profile.
- **`task_dispatch_gates`** — `id` (`dgate_…`), `user_id`, `task_id` (FK `ON DELETE CASCADE`), `agent_id`, `digest`, `title`, `file_path`, `body` (the prompt as it would be sent), `status` (`open` | `approved` | `skipped` | `superseded`), `created_at`, `settled_at`. Unique `(user_id, task_id, digest)`: one card per content. Index `(user_id, status)`. `taskDispatchGateRepo.open` supersedes, in one transaction, every open card of the task for another digest. `reopen` reopens a card (and refreshes `created_at`). `userRepo` deletes gates explicitly, since the cascade fires only with FK enforcement on.
- **`task_input_requests.queued_answer` / `queued_at` / `queued_error`** — an Inbox answer to a dispatch-owned task's `next_message` ask, stored for the queue to send, and why the last one could not be. Added after the table's rebuild, which would drop them. `queueAnswer` sets the answer only on an open ask holding none (and clears `queued_error`); `dropQueuedAnswer(requestId, queuedAt, error)` clears only the answer stored at that time, so a newer one stays; `settle` clears the answer with every settlement, which is how a typed message supersedes it. `listQueued(userId)` — open asks of live tasks holding an answer, oldest answer first.
- **`tasks.dispatch_note`** — `DISPATCH_NOTE_UNREPORTED` or `DISPATCH_NOTE_INTERRUPTED`, written only with a `blocked` status (`taskService.setStatus` `opts.dispatchNote`). `statusPatch` clears it on every other status.
- **`tasks.dispatch_agent_id`** — the queue that owns how the task settles. Set by `taskRepo.setDispatchAgent` in the run's `onRunAccepted`. Cleared by `release` (the dispatcher settled it, or boot recovery), by `statusPatch` for any status other than `in_progress` or `blocked`, by `taskService.takeOver` and `handOffToRemote`, and by a device-sync apply that changes `status`, `executor` or `executorDevice` (`taskMapper` in `sync/collections.ts` compares the row before and after, because that write skips `statusPatch`). `setDispatchAgent` and `setTrustedDigest` leave `updatedAt` alone, so the task list does not reorder for bookkeeping.
- **`tasks.started_by_user`** — the user started the task's current run, so its turns may raise a [desktop notification](../../ui/desktop_notifications/desktop_notifications_tech.md#database-schema). Written by `taskExecutionService.start` inside the run's acceptance from `options.startedBy`: `taskDispatch:run-next` passes `{ startedBy: 'user' }` to `runNext`, which carries it on the flight (`Flight.startedByUser`, the last `launch` argument) into `deps.start`. The queue's own `launch(…, 'queue')` and a gate's Approve and run (`runNext` without it) clear it. A `resume` flight goes through `deps.resume`, not `start`, and leaves it as it was — so does a Run next that sends a stored answer. `setStartedByUser` leaves `updatedAt` alone like `setDispatchAgent`.

## IPC Channels

All require activation and resolve the profile in main. Refusals come back as data with a `code`, because a thrown `DomainError.code` does not survive the bridge.

| Channel | Request → response |
|---|---|
| `taskDispatch:list` | → `AgentDispatchState[]`, one per dispatchable agent (enabled local folder agents with a path, bare and kit) |
| `taskDispatch:get` | agent id → `AgentDispatchState`, or null for an agent that cannot work a queue |
| `taskDispatch:set-mode` | agent id, mode, maxRuns? → `TaskDispatchUpdateResult`. A mode that fails `isTaskDispatchMode`, or `up_to` with an N that fails `isTaskDispatchMaxRuns`, is `invalid_input` (checked in the handler and again in `setMode`); maxRuns is ignored for the other modes. A tighter mode (Manual, or a smaller count) aborts the queue's own slot waits for that agent |
| `taskDispatch:resume` | agent id → `TaskDispatchUpdateResult`. Clears the pause only |
| `taskDispatch:run-next` | agent id, task id? → `TaskDispatchRunResult` (the handler passes `{ startedBy: 'user' }`, marking a task it starts `started_by_user`): `{ok, taskId, chatId}` (a stored answer sent answers with its task), `{ok, gate}` (the card to open), or `{ok: false, code}` with `not_dispatchable`, `live_turn` (the task's own chat, or a stored answer's, is running a turn), `slot`, `not_eligible`, `nothing_eligible`, `start_failed`, `invalid_input` |
| `inbox:dispatch-gate` | gate id, `approve` \| `skip` → `TaskDispatchGateResult`: `{ok, started, reason?, mode?}` (`reason`: `live_turn`, `slot`, `not_eligible`) or `{ok: false, code}` with `no_longer_waiting`, `already_answered`, `changed`, `unavailable`. In `task.ipc.ts` beside the other Inbox answers |
| `taskDispatch:changed` (push) | `{agentId \| null}`, sent through `publishEvent` on every change of a queue's state, including the ones the queue did not cause (see `announceChanges`). The renderer invalidates on it and has no poll. `window.api.taskDispatch.onChanged` returns an unsubscribe |

`inbox:list`'s `InboxSnapshot` gains `dispatch: TaskDispatchInboxItem[]` (optional in the type only so older surfaces still compile; main always fills it). An entry holding a stored answer carries `queuedAnswer`, `queuedAt` and `queuedFor` (the agent's name, and N in `up_to` else null, from `dispatchQueuesFor`, read only when some entry has a stored answer); `queuedError` is the last send's failure. `inbox:answer` answers `{ok: true, queued: true}` for a stored answer, and `already_answered` when one is already waiting.

## Services & Key Methods

### `taskDispatchService.ts`

Hub core: it imports no Electron. Everything it needs from the app is a `TaskDispatchDeps` seam that the tests replace: `agents`, `start`, `resume`, `chatRunning`, `withSlot`, `slotFree`, `trust`, `refreshTask`, `liveAgentIds` (now `activeAgentSessions.liveAgentIds`, read by boot recovery only), `publish`. `productionDeps` wires them to `localAgentService.list` (filtered by path and the profile's `agentOverrideRepo` enabled value), `taskExecutionService.start`, `inboxService.startNextMessageTurn`, `runExecutionService.isRunning`, `withRuntimeAgent`, `runtimeAgentSlotFree`, `taskSyncService.trustLocalContent`, `taskSyncService.pullFresh`, `activeAgentSessions.liveAgentIds`, and `publishEvent(TASK_DISPATCH_CHANGED_CHANNEL)`.

- **State in memory.** `flights`, keyed by profile, agent **and task** (`taskFlightKey`), so an agent can have several and two never hold one task: `phase` `slot` → `starting` → `running`, `launchedAt` (launch order; `flightsOf` lists oldest first), `origin` `queue` | `manual` | `resume`, `explicit` (the user asked: skips the count, the pause and the settle checks), `answer` (`{requestId, queuedAt}` for `resume`), the run once accepted, an `AbortController`. `settlingOwned` (agents whose owned turn is being settled, with a count) and `settlingTasks` (the same by `taskSettleKey(user, task)`; `refusal` returns *"This task is still being wrapped up. Try again in a moment."* for such a task, for every start). `announced` (each agent's state as last published). There is no folder identity: nothing compares folders.
- `limitOf(row)` — N for `up_to` (falling back to the default for a bad stored value), else 1. `held(userId, taskId)` — a flight of any agent holds the task; `candidates` leaves held tasks out. `chatBusy(task)` — the task's chat runs a turn now (the only running-turn check left).
- `refusal(userId, task, agentId)` — the eligibility sentence, or null. Ends with the `blocked_by` check over `task.blockedBy`. `candidates` filters `taskService.list({statuses: ['open']})` through it, sorts by `TASK_PRIORITIES` rank desc, `createdAt` asc, then id, and marks `gated` from `task.fromOutside`.
- `pass(scope, epoch)` — reads `storedAnswers` first (clearing, with a sentence, any whose task lost its `dispatchAgentId`) and clears with `NOT_DISPATCHABLE_ANSWER` the answers of agents no longer listed. Then per agent, skipping one that is `settling`: an `up_to` agent goes to `passWide`; any other agent with no flight sends its oldest stored answer (`launchAnswer`, unless its chat is running — and then nothing else starts for it) in any mode and while paused; failing that, in `one` mode and not paused, walk the candidates, call `gateFor` on each gated one, skip a `chatBusy` one, and `launch` the first other. Last, `announceChanges`.
- `passWide(scope, agent, row, answers)` — fills free runs while `room()`: fewer than N flights, none of them in its slot phase, no settle, same epoch (a Run next beyond N keeps `room()` false). Stored answers first (any mode, while paused; skipping a held task or a running chat), then, unless paused, candidates (gating gated ones, skipping held and `chatBusy` ones). After each launch it yields a `setImmediate` so the flight can take a free slot; while one still waits it stops, so N waits never queue for one agent.
- `announceChanges(userId, agents)` — serializes `stateFor` per agent and publishes only those that differ from `announced`. Every wake runs a pass, and every pass ends here, so a task made Ready, a file saved or a turn opening or closing in a folder reaches the renderer without a poll. `stop` clears `announced`. `wake()` debounces by `WAKE_DEBOUNCE_MS` and chains passes on one promise, so two wakes never start two runs. An `epoch` bump (`stop`) voids passes already queued.
- **Wakes**: `setMode`, `resume`, any `taskRunnerBridge.taskChanged` (an `installTaskRunnerHooks(…, 'task-dispatch')` listener), `onRunClosed`, `onRunOpened` (a turn taking a chat may take a Ready task's chat, which moves the announced state), `wakeDispatcher` (an answer was stored; registered through `setDispatchWake` for the import cycle), the end of a flight or an owned settle, `start` (profile ready), and the `TICK_MS` interval.
- `launch(scope, agent, task, origin, answer?)` — registers the flight synchronously (so a second wake sees the agent and the task taken). `options` carries `answer`, `startedByUser` and `explicit`, then `withSlot`. Inside the slot: abandon on quit or abort; for a non-`explicit` flight only, against the agent's row as it is now, `AgentFullError` when the agent's other non-waiting flights (explicit ones too) already fill `limitOf`, `AbandonedError` for a `queue` flight whose queue paused meanwhile, and `AgentFullError` while the agent is `settling`. Then `sendAnswer` for a `resume` flight, else `startTask`. `startTask` runs `recheck` (re-reads the task, applies `refusal`, opens the gate of one that became `fromOutside`; `NoLongerEligibleError`), throws `LiveTurnError` while the task's chat is running, `setActive(taskId, null)`, then `deps.start(…, {continueInChat: !!task.chatId, onRunAccepted})`. `accepted` (the `onRunAccepted`) runs inside the run's acceptance, before any event: it stores `flight.run`, calls `markDispatchedRun`, and sets `dispatch_agent_id`. Then `setActive(taskId, chatId)`, awaits `completed`, and calls `settle`. `finally` clears the run mark, drops the flight, publishes and wakes. A start that never got going goes to `startFailed`: `clearActive`, then a pause with `error` only for `origin: 'queue'`, never for `LiveTurnError`, `AgentFullError`, `NoLongerEligibleError` or an abandoned wait; a `resume` flight's answer is dropped with the error's message.
- `recheckAnswer(flight)` / `sendAnswer` — the stored answer as it is now: gone, settled or re-stored → `NoLongerEligibleError`; task not `blocked` / `in_progress` → the ask is settled `expired`; `dispatchAgentId` changed, not run here, or the chat not visible → `dropAnswer` with a sentence; chat running → `LiveTurnError` (the answer stays for a later pass). An `explicit` resume flight (Run next) skips the count checks. Then `setActive` and `deps.resume`, which calls `inboxService.startNextMessageTurn` with the same `accepted`.
- `settleTask(userId, agentId, taskId, outcome, afterRead)` — the report rule. Returns at once while `quitting`. For a file task it awaits `deps.refreshTask` first, then reads the row. A deleted or `archived` task → `release` and return, no status and no pause. `completed` / `needs_input` with an open input request → return (still owned). Otherwise `release`, then: `canceled` → `cancelled` if still `in_progress`, pause `stopped`; `failed` / `budget` → `error` with the message, pause `error`; not `reported` (category from `folderCategoryForStatus(parseTaskStatus(status))` is not done, failed, waiting or cancelled) → via `in_progress` if needed, then `blocked` with `DISPATCH_NOTE_UNREPORTED`, pause `unreported`. Status writes go through `taskService.setStatus` and a failure is only logged.
- `settleOwnedTurn(end)` — the registered `setDispatchOwnedTurnSettler`. It ignores a task whose `dispatchAgentId` is no longer `end.agentId`. It increments `settlingOwned` synchronously, before the turn's close wakes a pass, then runs `settleTask`, and decrements, publishes and wakes in `finally`.
- `pause(userId, agentId, reason, taskId)` — a no-op (logged) on a queue already paused: the first pause stays.
- `runNext(scope, agentId, taskId?)` — `invalid_input` for a bad id. It does not check the agent's count, its folder or its settling: every launch is `explicit`. `not_eligible` for a named task a flight already holds or whose own last turn is being settled (`refusal`). With no task named, the agent's first stored answer not held is sent first (`live_turn` while its chat runs, `slot` with no free slot; a task being settled is skipped; a `NoLongerEligibleError` falls through to the tasks). Then the named task, or the first ungated candidate whose chat is free, else the first ungated, else the first gated; an ungated choice whose chat is busy → `live_turn`; a gated choice → `gateFor(…, reopenSkipped: true)` → `{gate}`; `slot` when `!deps.slotFree()` (no queueing); else `launch(…, 'manual')` and wait for acceptance.
- `gateFor(userId, agentId, task, reopenSkipped)` — the card for the row's current `localFile.digest`. An existing card for that digest that is `approved` or `superseded` (the content is untrusted again) is reopened, and so is a `skipped` one when `reopenSkipped`. Otherwise `taskDispatchGateRepo.open` with `taskContinuationPrompt(task)` as the body.
- `answerGate(scope, gateId, action)` — `no_longer_waiting` / `already_answered`; a deleted task or a changed digest supersedes the card (`changed`); `skip` → settle `skipped`; `approve` → settle `approved`, `deps.trust` (on failure the card is reopened and the answer is `unavailable`), then `runNext(…, gate.taskId)`; a refusal is mapped to a `TaskDispatchGateDeferral` (`live_turn`, `slot` or `not_eligible`) and the agent's `mode` is returned with it.
- `stateFor` — builds `AgentDispatchState`: `maxRuns` (N in `up_to`, else null), `running` (every flight with a chat, oldest first — an array now). `waiting` is `slot` for a flight in its slot phase, and `gate` only when every candidate is gated and `hasOpenGate` finds an open card for one at its current digest. With no open card, `next` is the top gated task with `needsApproval: true`.
- `recoverInterrupted()` — boot, from `initializeHubCore` before any profile activates. For every `agentTaskDispatchRepo.listActive()` row (`agent_task_dispatch_runs`, oldest first): `blocked` + `DISPATCH_NOTE_INTERRUPTED` when still `in_progress`, `release`, `clearActive`, then `pause` `interrupted` — so the oldest run keeps the pause. Then for every `taskRepo.listDispatchOwned()` task still `in_progress` with no open input request and no live turn: the same note, `release`, pause `interrupted`.
- `setMode(scope, agentId, mode, maxRuns?)` — `invalid_input` for `up_to` without a valid N; aborts the queue's own slot waits when the new mode is tighter than the old (Manual, a smaller `limitOf`, or leaving `up_to`).
- `start(scope)` / `stop()` / `shutdown()` — `stop` bumps the epoch, clears the timers and `announced`, and aborts the slot waits of `queue` and `resume` flights (a Run next keeps its own; a stored answer stays stored). `shutdown` also sets `quitting` and aborts every slot wait. From then on nothing is settled, so each in-flight row stays for the next boot.

### Elsewhere

- `inboxService.endTurn` — after the ask bookkeeping, `isDispatchedRun(chatId, turnId)` returns without settling. A task with `dispatchAgentId` whose `chatId` is this chat is handed to `settleDispatchOwnedTurn` (`completed` / `failed` / `canceled`, with the error event's message). Both come before the job-run, handover and ordinary branches. `settleDispatchOwnedTurn` answers true even while quitting, so the ordinary branch never completes the task on the way out.
- `taskExecutionService.start` — `continueInChat` uses `ownChat`: the task's chat if it is still visible (else a new chat), refused when it is not `direct` to the same agent or is already running. The re-check inside acceptance passes the accepted chat id to `assertTask`, so the run being accepted — already registered on that chat — does not count as a turn running there; any other running turn in the task's chat still refuses. It cannot be combined with `reuseChatId`, and it lifts the "already has a conversation" refusal. `onRunAccepted` is called from `onAccepted` with `ctx.turnId`.
- `taskService.taskBlockers(row)` — resolves `localFile.blockedBy` through `taskRepo.listFileTasksByKey` (live tasks with a `local_file` whose `remoteKey` is one of the ids), kept to files in the same directory. Each blocker carries the task's `title` and parsed `status`, so the task page lists its blockers without a fetch each (as fresh as the page's own read of the task); `done` is `completed` only, and a missing id is `{taskId: null, title: null, status: null, done: false}`. Exposed as `TaskDto.blockedBy` by `toTaskDto`.
- `taskSyncService.trustLocalContent(userId, taskId, digest)` — queued behind the task's pushes (`pushesInFlight`). It bumps the binding revision, calls `localHome.trust` and stores the returned binding through `markRemoteSynced`, bumps again, then `taskRepo.setTrustedDigest`. The bumps keep a pull that read the old binding from storing it back.
- `taskSyncService.pullFresh(userId, taskId)` — waits out any read already in flight for the task, then starts its own, retrying once if the revision check discards it.
- `jobService.reportRunCompletion` — when `takeAgentStatusReportInChat(run.taskId, chatId)` finds a report: `blocked` returns with the attempt still running; `completed` / `error` set the outcome (`succeeded` / `failed`, with the task's error) and skip `applyRunState`.
- `runExecutionService` calls `runOpened(chatId)` whenever a turn takes a chat and `runClosed(chatId)` whenever it lets go, and the dispatcher wakes on both.
- `inboxService.answer` — for a task with `dispatchAgentId` whose agent `isDispatchableAgent` (unregistered or unreadable counts as yes; a wrong yes is cleared by the next pass), `queueAnswer` and `wakeDispatcher` instead of starting the turn, before the `isRunning` check. `startNextMessageTurn(scope, row, content, onAccepted?)` — the turn that answers a `next_message` ask, shared with the dispatcher's `resume`: `resumeChat` settles the ask inside acceptance, then `onAccepted`; a nested ask continues in its wrapper's tool call.

## Renderer Components

- `useTaskDispatch.ts` — `useTaskDispatchList` / `useAgentDispatch` (the push alone plus `refetchOnWindowFocus`, no poll; `retry: 1`), `useDispatchControls(agentId, {onStarted})`, which owns `setMode(mode, maxRuns?)`, `resume`, `runNext`, `pending`, `pendingMode`, `pendingMaxRuns`, and an `error` tagged with action and agent. Its owner is the surface, never a menu, so a result is not lost when a popover closes. `useOpenInboxGate` sets `revealInboxGateId` and switches to the Inbox. `useAnswerDispatchGate`. The shared words are `DISPATCH_MODE_LABELS`, `dispatchModeLabel(mode, n)` ("Up to 3"), `DISPATCH_MAX_RUNS_CHOICES`, `dispatchPausedParts` / `dispatchPausedText`, `dispatchStatusParts` ("Running 2 of 3", "Running <task> · 1 of 3", "· waiting for a runner slot") and `dispatchGateSettledText(action, result)` (a sentence per deferral reason: *Approved. … the task’s conversation finishes its turn* / *a task runner slot is free*). `dispatchStatusParts` says `Running N tasks` when a Run next took the agent past its N. `refreshAfterDispatch` invalidates `['task-dispatch']`, `['tasks']`, `['task']` and the Inbox.

## Configuration

- Run mode and its N are per profile and per device (`agent_task_dispatch`). There is no app setting. N is 2–8 (`TASK_DISPATCH_MAX_RUNS`), and every dispatched turn still needs a runner slot, so `taskRunnerConcurrency` caps what Up to N can actually run.
- `taskRunnerConcurrency` (`app_settings`, default 2, 1–8) bounds dispatched turns together with autonomous and script runs. See [Autonomous Tasks (tech)](autonomous_tasks_tech.md#configuration).

## Security

- **Outside content never runs unapproved.** Only `answerGate` calls `trust`, and only for the digest the card showed and the file still has. A Cinna write onto untrusted content stays untrusted (see [Folder Tasks (tech)](folder_tasks_tech.md)).
- **The renderer decides nothing.** It sends an agent id, an optional task id, a mode and N, or a gate id. Main resolves the profile, re-derives eligibility, and rechecks after every wait.
- **No digest or binding state reaches the renderer.** A gate item carries the title, the path and the body that would be sent.
- **Run marks are keyed by chat and run id**, so a user's own turn on the same task is never settled by the report rule.
