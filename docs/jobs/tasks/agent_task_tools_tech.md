## Database Schema

Added idempotently by `migrateTasks` (`src/main/db/migrations/tasks.ts`):

- `tasks.created_by_agent_id`, `tasks.created_by_chat_id` (text, null) and `tasks.chain_depth` (integer, default 0), indexed by `idx_tasks_created_by_chat (user_id, created_by_chat_id)` for the cap count. Null/0 for any task a person, a job or a pull created. Not in the device-sync payload (`src/main/sync/collections.ts` lists task fields explicitly).
- Own-queue creates set all three. A kit/cloud delegation's task gets `created_by_agent_id` and `chain_depth` (the delegation depth) at `createWithTask`; a bare delegation's task is made by the file intake, so `delegationService.create` stamps it afterwards through `taskRepo.setProvenance`, which writes only where `created_by_agent_id` is still null and leaves `updatedAt` alone. Delegated tasks get no `created_by_chat_id`: their cap share is counted from `delegations.origin_chat_id`.
- `task_comments`: `id`, `task_id` (`ON DELETE CASCADE`; a soft-deleted task keeps its comments until hard delete), `user_id`, `author_kind` (`agent` | `user`), `author_agent_id`, `body`, `remote_status` (`pending` | `sent` | `failed` | null), `created_at` (ms). Index `(user_id, task_id, created_at)`. Not a synced collection. `taskCommentRepo` is wrapped in `redactingRepository` on `create`, so credentials in a body are redacted on the way in.

## IPC Channels

| Channel | Request → response |
|---|---|
| `task:comments` | task id → `TaskCommentDto[]`, oldest first, in the active profile; rebuilt field by field so nothing beyond the DTO crosses. Empty for a missing or deleted task |

Every `tasks_*` operation is a session tool only; there is no renderer channel for any of them.

## Services & Key Methods

- `DelegationToolProvider.getTools` offers all eight schemas to every session it is built for; `conductorBridge` builds it for a folder agent's non-nested session, without asking whether the chat is an executor's. `callTool` refuses an unknown tool and unknown arguments ("The tool received an unknown argument.") before dispatch. `tasks_list` answers are digested per provider instance, and an answer equal to the previous one gains `notice: UNCHANGED_NOTICE`.
- `taskToolService.tasksTargets` is `delegationService.targets`: `{ protocol_version, targets }` with a `target` string per entry (see [the protocol tech doc](task_protocol_tech.md#targets)).
- `taskToolService.tasksCreate` runs `createTask` through `serializedInChat(chatId, …)`, a per-chat promise chain. `createTask` decodes `assignee` with `decodeTaskTarget` (null → refusal) and decides self (a non-`cloud` target with the caller's agent id) vs. delegation. A delegation (refusing `parent`) maps the decoded target to `target`, `description → brief`, `category → status` (`draft` / `ready`), `priority` and `custom_fields → customFields` (checked by the own-queue parsers first), calls `delegationService.create` with `beforeNew: () => assertChatCap(session)`, and puts the result's `taskId` in front as `ref`. `create` calls `beforeNew` only after the idempotency lookup and when `delegationBriefExists` says no bare brief is already written at that id, so repeats are answered at the cap.
- `delegationService.create` refuses `priority` / `customFields` for a non-bare target, an invalid priority, and custom fields that fail `validateTaskCustomFields` or are named like a `HANDOVER_BRIEF_KEYS` entry in any case (`briefCustomFields`); it passes them to `createDelegationBrief`. A decoded target that `targetEntries` does not list, or that does not accept delegations, is "That target is unavailable for delegation."
- Own queue: depth `(task ? depthOf(task) : 0) + 1` — 1 with no chat task, where `depthOf` is `max(delegationRepo.byTaskId(…).depth, task.chainDepth)`; `category` `ready` → `open`, `backlog` or absent → `new`, anything else refused; `taskAuthoringService.createRouted` with `assignee: { kind: 'agent', agentId }`, which picks the folder home or native through `localHomeFor`. `delegationService.create` computes its depth as `max(parent.depth, task.chainDepth) + 1` against `MAX_HANDOVER_DEPTH`.
- Titles are refused past 300 characters (`text(…, 'title', 300)` here and `requiredString(…, 300)` in `delegationService.create`), although the schema's `maxLength` is 500.
- `assertChatCap` = `taskRepo.countCreatedInChat` + `delegationRepo.countForOriginChat` (all delegation rows from the chat, settled and skipped included).
- `tasksList` walks `taskRepo.list`, tags relations (`delegationRepo.listByOriginAgent` for `delegated`), drops archived rows (no category) and closed ones unless `include_closed` or `category: done` (`fromProtocolCategory` → `closed`), sorts by `createdAt` desc and caps at 50 with `truncated` / `total`. Each entry is `summary(row, …)`: `ref`, `title`, `status`, `statusLabel`, `category` (protocol word), `priority`, `relations`, `assignee`, `parent`, `file`, and `delegation` (`id`, `state`, plus `resultStatus`, `summary`, `question` when set).
- `tasksGet`: the row through `requireTask` (`ref`, at most 128 characters), then `relationsOf`; no relation and not the chat's task is refused. The answer is built from `taskService.getById`: the summary fields plus `goal`, `description`, `blocked_by` (`id`, `ref`, `title`, `status`), `custom_fields`, the last ten `comments` (`author`, `at`, `body`), `report` (`note`, `artifacts`, `error`, or null when there is none of them), `delegation`, and `delegations` from `delegationRepo.listForOriginTask` (rows with a task only).
- `tasksUpdate`: permission (current task, assigned, or created with no `chatId`) → `delegatedRefusal` (a `delegationRepo` or `handoverRepo` row for the task; requester → `tasks_reply`, executor → `tasks_report`) → `ownedElsewhere` (`taskRuntimeRepo`, `scriptRuntimeRepo.owner`, or `activeChatRunId` in another chat) → field patch via `taskAuthoringService.update` → `category` through `resolveStatus`. A resolved move is refused when the word is in `REPORT_WORDS` (`completed`, `blocked`, `error`, `in_progress`, `failed`, compared through `normalizeStatusWord`), the status is in `REPORT_STATUSES` (`in_progress`, `blocked`, `error`), or it is `completed` on the chat's own task; then, for a status in `CLOSING_STATUSES` (`completed`, `error`, `cancelled`), when `worked(session, row)` is true — `dispatchAgentId` or `chatId` set, an open `taskInputRequestRepo` request, a delegation or handover row, a runner in `taskRunnersByChat` (by `taskId` or `controllerTaskId`), or a task/script runtime. What passes goes through `taskAuthoringService.setStatus`, i.e. the manual-move rules. `tasksUpdate` never sets the report mark.
- `tasksReport` takes the task from `ref` or the chat's own (`taskOrCurrent`). `delegatedRole` decides the path:
  - *requester* → refused with the `tasks_reply` pointer;
  - *executor* → refused unless it is the chat's own task; with a delegation row, `delegationService.report` (which parses with `parseTaskReport(input, 'requester')`, makes relative artifacts absolute against the executor's folder, passes `body` and `audience`, and calls `delegationLifecycle.applyResult`); with only a `handoverRepo` row, `parseTaskReport` then `handoverService.applyReport(scope, handover, { status, summary, question, artifacts, body })`, the file artifacts made relative to the handover folder and `http(s)` links appended to the body as `- <name>: <url>` lines. It returns `{ handoverId, ref, status }`;
  - *neither* → a non-current task must be assigned to the caller or created by it with no `chatId`, and pass `ownedElsewhere`; a runner in `taskRunnersByChat` refuses every task; `parseTaskReport(input, 'user')`, and `audience: requester` is refused. The status goes through `statusForReport` (`done` → `completed`, `failed` → `error`). The handoff note is the summary, `Question: <question>` and the body joined by blank lines (`taskService.setHandoffNote`); artifacts go through `artifactOf` (a URL is a `link`, a relative path is joined to the agent folder) to `taskService.setArtifacts`; `taskService.setStatus` only when the status differs; then `noteAgentStatusReport(taskId, chatId, activeChatRunId(chatId))` for the chat's own task. The answer is `{ ref, status, taskStatus, category }`.
- Idempotency on the own-task path: `lastReports` (module memory) keeps a sha256 of `[status, summary, question, body, artifacts]` and the answer per task. An equal digest with the task already at that status re-marks the turn and returns the stored answer without writing. The bus path is idempotent through `delegationLifecycle.applyResult`'s result digest.
- A `jobRunId` task is accepted: `jobService.reportRunCompletion` reads the mark with `takeAgentStatusReportInChat(taskId, chatId)` (it knows the chat, not the run id) and maps the attempt from the task's status — `blocked` leaves the run running, `completed` / `error` set its outcome and skip `applyRunState`. A dispatched turn's end is not read from the mark at all: the dispatcher reads the task's status (`taskDispatchService.settleTask`).
- `tasksReply` is `delegationService.reply`: `ref` is looked up as a delegated task id (`delegationRepo.byTaskId`) and otherwise used as the delegation's own id, then checked with `owned`; `message` at most 64 000 characters.
- `resolveStatus`: a canonical status passes; for a device-local task with an agent, a `folderBoard` column word or a default word becomes `{ status, label }`; otherwise a default word maps to its category's status.
- `inboxService.endTurn` returns early when `takeAgentStatusReport(task.id, ctx.turnId)` is true and the task is not `in_progress`. `takeAgentStatusReport` always clears the mark and is true only for the same run id; `runExecutionService` calls `forgetAgentStatusReports(chatId)` when it registers a new turn.
- `tasksComment` takes the task from `ref` or the chat's own, checks the relation, then checks `files` with `filesOf` (relative paths resolved inside the agent folder, each an existing regular file, at most 20) and `taskSyncService.canAttachFiles` (a bound task whose adapter is not a local home and lists `file` in `writeArtifactKinds`) — all before the row is written. It stores the row as `pending`, then `taskSyncService.copyComment(userId, taskId, { logEntry, remoteBody })`: a binding whose adapter has `localHome.appendLog` → `appendLog` (queued behind the task's push in `pushesInFlight`, revision bumped around the write, binding stored with `stateWhileOwed` so owed fields keep their base); else an adapter with `capabilities().comments` → `addComment` with `type: 'note'` and `**<agent>:** <body>`; else false. Result → `remote_status` `sent`, `failed` (on throw; logged) or null. Files then go through `taskSyncService.attachFiles` (`adapter.putArtifact` one by one); a throw is logged and becomes a warning. The answer is `{ commentId, ref, attached?, warning? }`.
- Folder adapter `localHome.appendLog` keeps `writtenDigest` at its prior value unless the file was Cinna's own before the append, so an entry never launders an outside edit into trusted content. Its `capabilities().comments` stays false.
- `formatFolderLogEntry` writes `**<author>** · YYYY-MM-DD HH:MM UTC` then the body, with `<!--` escaped so a body cannot close the log or the handoff section. `patchFolderTaskFile` with `appendLog` adds lines only; a file without a log gets one after the description and before the handoff section. `parseFolderTaskFile` excludes the log (last `LOG_CLOSE`, nearest `LOG_OPEN` before it) from the description, and `setDescription` rewrites the description while keeping the log and handoff section byte for byte.
- `taskToolService.comments` resolves agent author names through `localAgentService.get` (null when the agent is gone).

## Renderer Components

- `TaskView` reads `useTaskComments(task.id)` (polled on `POLL_MS`, `retry: 1`) and renders `TaskComments` last, after `TaskList` (Subtasks) and outside the Goal/Details grid, which is unchanged by comments. `TaskComments` returns null with no comments; a failed first read (`errorUpdateCount > 0 && !data`, so a refetch does not hide it) keeps the section with Try again.
- `TaskComments` anchors its window at the first comment id shown on first data (`COMMENTS_SHOWN` = 5), offers "Show earlier comments (N)", which with `showAll` becomes "Show fewer comments" (same button element, `aria-expanded`; collapsing re-anchors at the latest `COMMENTS_SHOWN`), and renders `CommentItem`s: Bot/User icon, author (button to the agent page via `hasAgentPage` / `useOpenAgentPage`), `Timestamp`, an `AlertTriangle` with an aria-label when `remoteStatus === 'failed'` (file / connected service / plain "Not copied" by `home`), the body in `<Prose compact>` (`.markdown-compact`: h1–h6 at 1em, body line height) clamped past 600 characters / 8 lines by `.comment-clamp` in `main.css` (six lines of `1.625em` on a `text-xs` wrapper, last line masked out).

## Configuration

None. The caps are constants in `taskToolService.ts`; the turn header line is wire-only and omitted at zero.

## Security

- Every call goes through `validateSession`; tool arguments cannot name a profile, chat or depth.
- Comment bodies are redacted on insert; folder writes go through the folder adapter's fresh-read, temp-file-and-rename path and its symlink refusals.
- Errors reach the agent as the refusing service's message (`plain` / `plainAsync`), never a stack.
