# Jobs — Technical Details

Task records and Inbox channels are documented in [Tasks: Technical Details](../tasks/tasks_tech.md); job attempts retain their own completion and refresh hooks.

The [script definition contract](../tasks/script_definitions_tech.md) covers nullable job router/script/budget columns, shared create/update DTOs, local validation and raw sync preservation. The dispatcher admits supported explicit routers through the matching main-owned engine; the legacy local executor still refuses them. The ordinary routing/execution flow below applies only when these fields are null. See [script execution details](../tasks/script_execution_tech.md) for both autonomous Job admission paths.

## File Locations

JobDetail uses an explicit coordinator/script router before ordinary newChatRouter inference. `src/renderer/src/components/chat/RouterBadge.tsx` accepts script only for display; it does not add script as a chat router.

### Main process
- `src/main/db/schema.ts` — `jobs` (with `folderId` / `position` columns; `agentId` now legacy/dormant), `jobFolders`, `jobMcpProviders`, `jobAgents` (multi-agent join table mirroring `jobMcpProviders`), `jobRuns` tables; `chats.originatingJobRunId` / `chats.router` columns
- `src/main/db/migrations/jobs.ts` — `migrateJobs()` — inline-SQL `CREATE TABLE IF NOT EXISTS` for the job tables (`jobs`, `job_folders`, `job_mcp_providers`, `job_agents`, `job_runs`), indexes on `jobs.user_id`, `job_folders.user_id` and `job_runs.job_id`, plus idempotent `ALTER TABLE` adds for `chats.originating_job_run_id`, `chats.hidden_from_list`, `jobs.folder_id`, and `jobs.position` (all guarded via `hasColumn`). The `job_agents` migration is a one-time backfill: copy each job's legacy `jobs.agent_id` into `job_agents` (guarded by `IN (SELECT id FROM agents)` so a dangling ref can't trip the FK insert — `foreign_keys` is ON), then `UPDATE jobs SET agent_id = NULL` so the backfill never re-runs and can't resurrect an agent the user later removed via the multi-agent UI
- `src/main/db/client.ts` — `migrateJobs(sqlite)` invoked from `runMigrations()` after chats + mcp_providers + chat_modes (FK dependencies)
- `src/main/db/jobs.ts` — `jobsRepo` (CRUD + soft delete + `minPositionInFolder` + `reorderInGroup` transaction that rewrites every passed id with the target group's `folderId` and a fresh `position = index`), `jobFoldersRepo` (CRUD + `reorder` transaction + `delete` transaction that detaches contained jobs to root before dropping the folder row), `jobMcpRepo` (`listProviderIds`, `setProviderIds` — dedups ids before the delete-then-insert), `jobAgentRepo` (`listAgentIds` — ordered `asc(agent_id)`, because `job_agents` records **no** order at all (composite PK, no timestamp) and there is therefore no "first agent the user picked"; the sort exists only so the same job runs the same way twice, which matters since a `human` run addresses the first of this list —, `setAgentIds` — same dedup-then-replace shape as `jobMcpRepo`), `jobRunsRepo` (`listByJob` — LEFT-joins `chats` and returns `JobRunRowWithMeta` with a derived `chatHidden` boolean —, `countInProgressByJob` — single `GROUP BY job_id` aggregate over rows with `status IN ('pending','running')`, used by the sidebar spinner —, `getById`, `getByLocalChatId`, `create`, `updateStatus`, `createLocalChatAndRun` router-aware transaction: sets `hiddenFromList = true`, writes the spawned chat's `router`, and either the bound root agent (`agentId`) or the `chat_on_demand_agents` + `chat_on_demand_mcps` rows). New jobs land at `position = min(position) - 1` of the root group so they appear at the top of the ungrouped list.
- `src/main/db/chats.ts` — extended `chatRepo.create()` accepts `init?` (title/modelId/providerId/modeId/agentId/originatingJobRunId/`hiddenFromList`); `chatRepo.setOriginatingJobRunId(userId, chatId, runId)` back-pointer setter; `chatRepo.list(userId)` filters out hidden-from-list chats; `chatRepo.showInList(userId, chatId)` clears the flag (promotes a hidden chat to the main list)
- `src/main/services/jobService.ts` — profile-scoped CRUD, dependency DTOs, folders/history, completion hooks and public execution/refresh facade. `execute` selects the owning executor; `executeLocal` and `executeCinnaTask` retain their signatures and require the selected capability. `refreshRun` follows current task metadata; `refreshCinnaRun` delegates for compatibility. `adoptRemoteRun` handles legacy associations and `enrichRun` supplies chat visibility plus refresh metadata. See [execution and refresh](execution_tech.md).
- `src/main/services/jobExecution/contract.ts`, `index.ts`, `desktop.ts`, `remote.ts` — typed captured scope, executor selection, actual preparation/dispatch bodies and their separate transaction boundaries.
- `src/main/services/jobExecution/dependencies.ts` — `unresolvableAgentLabels`, shared by the list/detail dependency indicators and desktop admission; portable folder/account ownership stays here.
- `src/main/tasks/jobDefinitionPolicy.ts`, `jobRuntimeDefinition.ts` — pure stored-schema policy and autonomous definition validation.
- `src/main/db/jobRunRefresh.ts` — pure current-task/receipt/legacy refresh projection; `src/shared/jobs.ts` supplies required result disposition and ephemeral run refresh mode.
- `src/main/services/cinnaApiService.ts` — `cinnaApiService` — handwritten REST client for cinna-core: `listAgents`, `createTask`, `getTaskDetail`, `getTaskView` (full `InputTaskDetailPublic` with comments + attachments — see [Cinna Task Run View tech](../cinna_task_view/cinna_task_view_tech.md)), `getServerUrl`. Internal `cinnaFetch()` helper centralizes auth-header + `net.fetch` + error mapping; raises `CinnaApiError('reauth_required')` on 401/403.
- `src/main/services/chatStreamingService.ts` — the three guards at the top of `stream` (no chat, no provider/model, no adapter) each post an error, save it to the transcript, close the port, **report the run as `failed`** and then throw. They report because `runExecutionService.ts`'s `handOff` swallows that throw by design — a service that owns the port owns its ending — so before this nothing downstream heard about the refusal and the run sat `running` for the life of the app. Pinned by `chatStreamingService.refusal.test.ts`. `_runStreamLoop` calls `jobService.reportRunCompletion(chatId, 'succeeded' | 'failed' | 'cancelled', errorMessage?)` from **two** further places: the success line, as `aborted ? 'cancelled' : 'succeeded'`, and the `catch`, where an abort reports `cancelled` (no error message) and anything else `failed`. The success line is reachable on a stop through the three `if (aborted) break` statements between tool rounds. The abort branch of the `catch` first saves the round's unsaved `partial` as an assistant message and posts `done { stopReason: 'canceled' }`, then reports — see [Messaging tech — Cancellation](../../chat/messaging/messaging_tech.md#cancellation)
- `src/main/services/a2aStreamingService.ts` — `streamToAgent` reports a stop from **two** places, each on the same `aborted` test: its success line and the `catch`. The `result.error` branch runs only when the turn was *not* stopped: it posts and persists the error and reports `failed`. A stopped turn whose result also carries an error falls through to the success line, so it keeps its notices and parts, posts `done { stopReason: 'canceled' }` and reports `cancelled` — returning from the error branch instead finalized the run but posted no `done`, leaving the chat streaming. The `catch` posts `done { stopReason: 'canceled' }` after a stop too, with nothing to keep. The error branches once suppressed the finalization along with the error surface, because one `if (!signal.aborted)` guard was doing both jobs. Covered by `a2aStreamingService.test.ts`, including a runner cancelled cleanly and a stopped turn whose result also carries an error
- `src/main/services/a2aStreamingService.ts` — same hook at the agent stream's `done` / catch path
- `src/main/ipc/job.ipc.ts` — `registerJobHandlers()` — all `job:*` and `jobFolder:*` channels wrapped via `ipcHandle()`, each calls `userActivation.requireActivated()` then delegates to `jobService`. Includes `job:set-agents` (replaces the job's agent set, mirroring `job:set-mcp-providers`), `job:run-origin` (run id → `JobRunOrigin | null` for the chat-page banner), folder channels `jobFolder:list/create/update/delete/reorder`, and `job:reorder` (for moving + reordering jobs across groups).
- `src/main/services/runExecutionService.ts` — `reportRefusal(chatId, message)` records ordinary setup failures before/around stream ownership. `preserveOnRefusal` skips pre-acceptance job finalization for a pending next-message answer; its failed transaction leaves the request retryable. Activated IPC setup stays in `src/main/ipc/run.ipc.ts`. See [execution lifetime and acceptance](../../chat/chat_routing/chat_routing_tech.md#shared-turn-lifetime-and-acceptance).
- `src/main/ipc/cinna.ipc.ts` — `registerCinnaHandlers()` — `cinna:list-agents`, `cinna:get-task-view` delegating to `cinnaApiService`
- `src/main/ipc/app.ipc.ts` — `app:open-external` handler — restricts to `http:` / `https:` before `shell.openExternal`
- `src/main/ipc/index.ts` — `registerJobHandlers()` and `registerCinnaHandlers()` registered in `registerAllIpcHandlers()`
- `src/main/errors.ts` — `JobError` + `JobErrorCode` (`not_found | not_activated | unsupported_type | missing_dependency | invalid_input`); `CinnaApiError` + `CinnaApiErrorCode` (`not_cinna_user | missing_server_url | reauth_required | request_failed | invalid_response`)

### Shared
- `src/shared/jobs.ts` — `JobData` (carries `folderId: string | null`, `position: number`, `needsSetup: boolean` and `incompleteSetup: boolean` — the last of these true when the synced manifest names an **agent** that resolves to nothing on this device, which blocks the run; deliberately not folded into `needsSetup`, which is also true for a disabled MCP shell, so a surface gating "can't run here" on `needsSetup` would refuse jobs that run fine), `JobRunData` (its `taskId: string | null` is the task the run produced — the column has crossed IPC since `enrichRun` spread the row, and the declaration only caught up later), `JobRunOrigin` (`{ jobId, jobTitle }` — minimal job pointer resolved from a run id, powers the chat-page job-origin banner), `JobDetailData` (now carries `agentIds: string[]`), `JobCreateInputDto`, `JobPatchDto`, `JobType`, `JobRunStatus`, `JobFolderData`, `JobFolderCreateInputDto`, `JobFolderPatchDto` — imported by both preload and renderer (the preload `.ts` is not exposed to the renderer compiler, so DTOs live in `shared/`)
- `src/shared/chatRouting.ts` — `ChatRouter` + `newChatRouter(...)` / `routingOf(...)`. Single source of truth shared by the new-chat composer (`useNewChatFlow` / `RouterBadge`), main's send path and the job runner (`jobService.executeLocal`): no agent or one agent alone → `'direct'`, several agents → `'human'`, any agent with an MCP server → `'coordinator'`. See [Chat Routing](../../chat/chat_routing/chat_routing_tech.md)

- `src/renderer/src/hooks/useSystem.ts` — `useOpenExternal()` returns a stable callback wrapping `window.api.system.openExternal` so components don't reach into the contextBridge surface directly. The `code` is kept beside the sentence for a caller that ever needs to branch. Both sentences are short **by constraint**: the task page reserves exactly one line for this message, and a wrap there moves the page under the click that produced it.

- `src/renderer/src/components/layout/SidebarTabs.tsx` — Icon-only book-tab rail (`MessageSquare` for Chats, `Briefcase` for Jobs). Buttons carry `aria-pressed` for the active-tab CSS hook. Re-clicking the active tab is a no-op **unless a tabless view is in the centre**: `TABLESS_VIEWS` (`'inbox' | 'task' | 'cinna-task-run'`) are the views that belong to no tab, and pressing the already-selected tab while one of them is open realigns the centre to `VIEW_FOR_TAB[tab]` and keeps the tab's own selection — dropping it would send a user who answered an ask back to a different conversation than the one they left. The cinna run screen had the same trap and was simply the exception nobody had written down.

- `src/renderer/src/hooks/useTasks.ts` — `useTask(taskId)` (`['task', taskId]`, five-second poll that stops on a settled status — `blocked` keeps polling, because the ask it waits on is answered on another surface entirely; one retry, since the poll is the retry), `useOpenTask()` (sets `activeTaskId` + `activeView: 'task'` and deliberately leaves the sidebar tab where it was), and `useRerunTask()` (re-sends the last user message of the task's chat). It sets the task `in_progress` **before** the send, so a task that cannot be re-opened stops the run instead of leaving a turn streaming into a task that disowns it, and navigates to the chat before calling `startRun`, because the optimistic user bubble is global rather than per chat

- `src/renderer/src/components/jobs/JobItem.tsx` — Single row. Active state is `activeJobId === job.id && (activeView === 'job-detail' || 'job-edit' || 'chat')` — also highlights while the user is viewing one of this job's spawned chats (because the open-chat flows preserve `activeJobId`). **No delete button** — delete now lives on the edit screen. **Two warnings share the trailing slot and only one may be hidden by a hover** (`:145`): the amber `needsSetup` glyph is advisory and keeps its original rule (`job.needsSetup && !hovering`, and suppressed while running); the red `incompleteSetup` marker is shown **unconditionally**, because the run-now button is the thing it is warning about and suppressing it on hover hid it at the moment the user reached for that button. Both icons are pinned to `w-4 h-4` so the row height never shifts between idle, hover, and running states. Row is also `draggable` (drag source for job reorder/move); accepts drops of kind `job` from a different row via an optional `onDropJob(draggedJobId, beforeJobId)` callback that the parent (JobsList for root, JobFolderRow for folder bodies) wires up. ## Database Schema

### `jobs` table
- `id` TEXT PK
- `user_id` TEXT NOT NULL — profile scope key (per-account)
- `type` TEXT NOT NULL DEFAULT `'local'` — `'local' | 'cinna_task'`
- `title` TEXT NOT NULL
- `description` TEXT
- `prompt` TEXT NOT NULL
- `agent_id` TEXT — **legacy/dormant**. Replaced by the `job_agents` join table; the migration backfills it into `job_agents` then nulls it. Kept only so the column drop isn't needed.
- `mode_id` TEXT — optional chat-mode reference (no FK)
- `cinna_agent_id`, `cinna_priority` TEXT — populated for `cinna_task` jobs only
- `color_preset`, `icon_name` TEXT — visual customization (reserved; not wired into the sidebar yet)
- `folder_id` TEXT — optional sidebar folder reference (no FK; folder delete sets this to null manually in the same transaction). Null = job sits at the root level.
- `position` INTEGER NOT NULL DEFAULT 0 — sort key within the parent group (folder or root). Lower = top. New jobs land at `min(position) - 1` of the root group; drag-drop rewrites every id in the affected group with `position = index`.
- `deleted_at` INTEGER — soft delete timestamp
- `created_at`, `updated_at` INTEGER NOT NULL
- Index: `idx_jobs_user_id`

### `job_folders` table
- `id` TEXT PK
- `user_id` TEXT NOT NULL — profile scope key (per-account)
- `name` TEXT NOT NULL — trimmed, non-empty (validated in the service)
- `position` INTEGER NOT NULL DEFAULT 0 — sort key for the folder list. New folders land at `max(position) + 1`.
- `collapsed` INTEGER NOT NULL DEFAULT 0 — persisted expand/collapse state, toggled by a single click on the folder header.
- `created_at`, `updated_at` INTEGER NOT NULL
- Index: `idx_job_folders_user_id`
- **No FK from `jobs.folder_id`**: folder delete detaches contained jobs by SQL UPDATE inside the same transaction as the folder drop (see `jobFoldersRepo.delete`), so adding a FK would only constrain the cleanup the service is already doing explicitly.

### `job_mcp_providers` table
- `job_id` TEXT NOT NULL → `jobs(id)` ON DELETE CASCADE
- `mcp_provider_id` TEXT NOT NULL → `mcp_providers(id)` ON DELETE CASCADE
- PRIMARY KEY (`job_id`, `mcp_provider_id`)

### `job_agents` table
- `job_id` TEXT NOT NULL → `jobs(id)` ON DELETE CASCADE
- `agent_id` TEXT NOT NULL → `agents(id)` ON DELETE CASCADE
- PRIMARY KEY (`job_id`, `agent_id`)
- Mirrors `job_mcp_providers`. Replaces the single `jobs.agent_id` so a job can attach any number of agents. The cascade means a deleted agent silently drops out of the job's set (no dangling refs to validate at run time).

### `job_runs` table

`JobRunData.refreshMode` is derived, required DTO metadata rather than a stored or synced column. List joins are scoped to the profile and use the same pure policy as single-row responses. A partial nested task join starts with nonnullable executor so a live row with null deletedAt is not mistaken for an absent task.
- `id` TEXT PK
- `job_id` TEXT NOT NULL → `jobs(id)` ON DELETE CASCADE
- `user_id` TEXT NOT NULL — included for scope filtering even though `job_id` is sufficient
- `type` TEXT NOT NULL — `'local' | 'cinna_task'`
- `local_chat_id` TEXT → `chats(id)` ON DELETE SET NULL — spawned chat, only for local runs
- `cinna_task_id` TEXT — remote task UUID, only for cinna runs
- `cinna_short_code` TEXT — remote task short code, only for cinna runs
- `status` TEXT NOT NULL DEFAULT `'pending'` — `'pending' | 'running' | 'succeeded' | 'failed' | 'cancelled'`
- `task_id` TEXT — the task this run produced. Added by `src/main/db/migrations/tasks.ts` (an idempotent `ALTER TABLE job_runs ADD COLUMN task_id TEXT` guarded by `hasColumn`), **not** by `migrations/jobs.ts`, because the column points at a table that migration does not own. Nullable for legacy runs; every new local or remote run has one. A legacy remote run is adopted on its next eligible refresh. `cinna_task_id` / `cinna_short_code` remain compatibility pointers filled from the task’s binding
- `error_message` TEXT
- `started_at`, `finished_at`, `created_at` INTEGER (`created_at` NOT NULL)
- Index: `idx_job_runs_job_id`

### `chats` table additions
- `originating_job_run_id` TEXT — set by `jobRunsRepo.createLocalChatAndRun` so the stream completion hook can resolve back to its run without renderer cooperation. Also surfaced to the renderer via `ChatData` (preload) so the chat-page `JobOriginBanner` can resolve it (run id → job) via `job:run-origin`.
- `router` TEXT — the spawned chat's router, written by `createLocalChatAndRun` from `newChatRouter`. The legacy orchestrated column is removed after migration backfill; Job chat creation writes only router. See [Chat Routing](../../chat/chat_routing/chat_routing_tech.md) and [Orchestrated Agents](../../chat/orchestrated_agents/orchestrated_agents.md)
- `hidden_from_list` INTEGER NOT NULL DEFAULT 0 — when `1`, the chat is excluded from `chatRepo.list` (the main Chats sidebar). Set to `1` for every job-spawned chat; cleared by `chatRepo.showInList` when the user clicks "Move to Chats" on a run row. Migration is an idempotent `ALTER TABLE chats ADD COLUMN hidden_from_list INTEGER NOT NULL DEFAULT 0` guarded by `hasColumn`.

## IPC Channels

- `job:list` — `JobData[]` for the active profile (excludes soft-deleted). Each row carries `inProgressRunsCount` (count of `pending` + `running` job_runs) so the sidebar can render a per-row spinner without a follow-up call.
- `job:get(jobId)` — `JobDetailData` (job + `mcpProviderIds` + last 10 runs)
- `job:create(input)` — Returns the new `JobData`. Renderer defaults: `type: 'local'`, `title: 'New Job'`, `prompt: 'Describe the task here…'`.
- `job:update(jobId, patch)` — Returns the updated `JobData`. Patch is a partial DTO.
- `job:delete(jobId)` — `{ success: true }`. Soft delete.
- `job:set-mcp-providers(jobId, mcpProviderIds[])` — `{ success: true }`. Replaces the job's MCP attachments.
- `job:set-agents(jobId, agentIds[])` — `{ success: true }`. Replaces the job's agent set (`job_agents`); stale ids are filtered server-side.
- `job:list-runs(jobId)` — `JobRunData[]` newest-first.
- `job:run-origin(runId)` — `JobRunOrigin | null` (`{ jobId, jobTitle }`). Resolves a run id back to its originating job for the chat-page banner; null when the run/job is missing or the job is soft-deleted. Both reads are `userId`-scoped.
- `job:execute(jobId)` — Rejects with `JobError('incomplete_setup', …)` when the job's manifest names an agent that resolves to nothing here; the renderer reads the **message** (via `unwrapIpcError`), never the code, which two boundaries strip. Otherwise a discriminated union:
  - `disposition: 'accepted'`, local provenance, chat/run/task ids — main has admitted coordinator/script work; invalidate queries and optionally navigate without sending.
  - `disposition: 'renderer_turn'`, local provenance, chat/run/task ids, prompt/agentId/modeId — perform the existing renderer configuration and send once. Missing or unknown disposition refuses before dispatch.
  - `disposition: 'accepted'`, remote provenance, run/task ids and legacy remote pointers — remote work is accepted; remain on the current view.
- `job:cancel-run(runId)` — Flips a run to `'cancelled'`. **Nothing in the renderer calls it**: the preload exposes `window.api.jobs.cancelRun`, and no component or hook reaches for it, so the only gesture that produces a `cancelled` run today is stopping the chat, which reaches the same status through the streaming services' abort branches. The channel is wired end to end and unused, not dead code with a caller somewhere off-screen
- `job:delete-run(runId)` — Hard-deletes a run row. For local runs, the originating chat is hard-deleted alongside via the same transaction so neither orphans. Response: `{ success: true, chatDeleted: boolean, chatId: string | null }` — the renderer uses `chatDeleted` + `chatId` to invalidate `['chats']` / `['trash']` and reset `activeChatId` when the deleted chat was open.
- `job:refresh-run(runId, options?: { force?: boolean })` — `JobRunData`, including main-derived `refreshMode`. Refreshes the current remotely executing bound task regardless of run origin, or adopts an eligible legacy remote run. Force bypasses the terminal read short-circuit, never the current-attempt projection guard. Pending handoffs require Task-page review.
- `job:cinna-server-url` — Resolved Cinna server URL for the active profile (used to build `/tasks/{short_code}` deep links).
- `job:reorder(targetFolderId: string | null, orderedJobIds: string[])` — `{ success: true }`. Rewrites the destination group's `(folderId, position)` pairs in a single transaction. Pre-validates ownership of the target folder (when non-null) and every submitted job id. Logs `jobs reordered { targetFolderId, count }`.
- `jobFolder:list` — `JobFolderData[]` for the active profile, ordered by `(position ASC, createdAt ASC)`.
- `jobFolder:create({ name })` — `JobFolderData`. New folder lands at the bottom of the folder list (`position = max + 1`).
- `jobFolder:update(folderId, { name?, collapsed? })` — `JobFolderData`. Trims name; either field may be patched independently (e.g. the collapse toggle only sends `collapsed`).
- `jobFolder:delete(folderId)` — `{ success: true }`. Detaches contained jobs to root (`folderId = null`) in the same transaction as the folder drop — no orphan rows on crash.
- `jobFolder:reorder(orderedIds: string[])` — `{ success: true }`. Rewrites folder positions in a single transaction. Logs `folders reordered { count }`.
- `cinna:list-agents` — `CinnaAgentDto[]` (id, name, description)
- `cinna:get-task-view(taskId)` — `CinnaTaskViewDto` (task detail + comments + standalone attachments) — see [Cinna Task Run View tech](../cinna_task_view/cinna_task_view_tech.md)
- `files:download-task-attachment({ taskId, attachmentId, filename })` — save-as for a `TaskAttachment`; distinct from `files:download` because the URL is task-scoped
- `chat:show-in-list(chatId)` — `{ success: true }`. Promotes a hidden (job-spawned) chat into the main Chats list by clearing `chats.hidden_from_list`.
- `app:open-external(url)` — `{ success: true } | { success: false, error: 'unsupported_protocol' | 'invalid_url' }`. Restricted to `http:` / `https:`.

## Services & Key Methods

- `src/main/db/jobs.ts`:
  - `jobsRepo.list/getById/create/update/touch/softDelete` — CRUD with `userId` in WHERE. `list` orders by `(position ASC, updatedAt DESC)` so legacy rows with identical zeros still sort sensibly.
  - `jobsRepo.minPositionInFolder(userId, folderId | null)` — `SELECT min(position)` filtered by group; used by `create` to land new jobs at the top of the root group with `position = min - 1`.
  - `jobsRepo.reorderInGroup(userId, targetFolderId, orderedJobIds)` — single transaction; writes every passed id with `folderId = targetFolderId` and `position = index`. Caller must submit the full ordering of the destination group.
  - `jobFoldersRepo.list/getById/create/update/delete/maxPosition/reorder` — CRUD with `userId` in WHERE. `delete` is a transaction: detach contained jobs (`UPDATE jobs SET folder_id = NULL WHERE folder_id = ?`) → drop the folder row. `reorder` rewrites `position = index` for every id in a single transaction.
  - `jobRunsRepo.createLocalChatAndRun(input)` — single `db.transaction(...)`, router-aware. Inserts the chat row (with `agentId = rootAgentId`, `router`), the `job_runs` row, back-fills `chats.originating_job_run_id`, and inserts `chat_on_demand_agents` + `chat_on_demand_mcps` rows (each with `pendingAnnounce = true`, inlined rather than calling the on-demand repos so the inserts share the job's transaction). Returns `{ chatId, runId }`. Note: job MCPs land in `chat_on_demand_mcps`, NOT the chat-mode baseline `chat_mcp_providers`, so they count toward the routing decision and the conductor unions them.
  - `jobMcpRepo.listProviderIds(jobId)` / `setProviderIds(jobId, ids)` — `setProviderIds` dedups then transactionally deletes-all + inserts.
  - `jobAgentRepo.listAgentIds(jobId)` / `setAgentIds(jobId, ids)` — mirror of `jobMcpRepo`; `setAgentIds` dedups then transactionally deletes-all + inserts.
  - `jobRunsRepo.listByJob/getById/create/updateStatus` — standard repo shape.
  - `jobRunsRepo.getByLocalChatId(chatId)` — lookup used by `reportRunCompletion`. Not scoped by user — the caller (stream layer) already has chat-level authorization.
- `src/main/services/jobService.ts` — scoped public facade:
  - `listFolders(userId)` / `createFolder(userId, { name })` / `updateFolder(userId, folderId, patch)` / `deleteFolder(userId, folderId)` / `reorderFolders(userId, orderedIds)` — folder CRUD + reorder. All raise `JobError('not_found' | 'invalid_input', ...)` on validation failures. Mutating ops log via `createLogger('job')`.
  - `reorderJobs(userId, targetFolderId, orderedJobIds)` — validates target folder ownership (when non-null) and pre-walks `orderedJobIds` asserting each maps to a non-deleted job in scope (raises `JobError('not_found', 'Job not found: ' + id)` on the first bad id, before any write). Calls `jobsRepo.reorderInGroup`. Logs `jobs reordered { targetFolderId, count }`.
  - `execute(userId, jobId, settingsUserId)` — captures scope and delegates actual admission/dispatch to `executorFor(job)`; its result disposition owns renderer behavior. See [executor contract](execution_tech.md#services-and-key-methods).
  - `setAgents(userId, jobId, agentIds)` — `requireJob`, then `filterExistingAgents` drops stale ids (logs a warn on any dropped), then `jobAgentRepo.setAgentIds` + `jobsRepo.touch`.
  - `executeLocal(userId, jobId)` — synchronous compatibility entry requiring `prepareRendererTurn`; the desktop executor validates portable dependencies, attached agents, mode and MCPs before atomically creating chat/run/task and starting task bookkeeping. It returns the ordinary initial-turn payload; no stream starts in the transaction.
  - `executeCinnaTask(userId, jobId)` — asynchronous compatibility entry requiring `executeRemote`; the remote executor validates configuration, rechecks Job/connection after availability, and uses the shared durable handoff. Accepted work is retained if the later transactional run/link write fails.
  - `refreshRun(userId, runId, options)` — follows derived refresh metadata, rechecks scoped run and connection after waits, and trusts atomic task projection. `refreshCinnaRun` is a compatibility alias. Legacy adoption is transactionally linked and rereads deletion/pointer/terminal policy after availability. See [refresh modes and ownership](execution_tech.md#refresh-modes-and-ownership).
  - `adoptRemoteRun(userId, run)` — uses the registry’s available adapter, re-reads the run after awaiting availability to avoid duplicate adoption, and reuses a task already bound to that remote id. Reuse fills the task’s run provenance only when it has none; it never replaces a prior attempt link. Otherwise creates an `origin: remote`, `executor: remote` replica from the job’s title and prompt, binds the existing id and links the run. It returns null when there is no remote id or usable adapter.

  - `reportRunCompletion(chatId, outcome, errorMessage?)` — `outcome` is `'succeeded' | 'failed' | 'cancelled'`. Looks up the run by chat id, defers every outcome while an open next-message request remains, then flips status if still non-terminal (so a late stop cannot rewrite a recorded outcome). **Four call sites can produce `'cancelled'`, across four branches**, and the count is worth stating because two of them were found by counting: `chatStreamingService.ts` success + `catch`, and `a2aStreamingService.ts` success + `catch`. A stopped A2A turn whose result also carries an error is deliberately not a fifth: that branch handles failures only, and the stop falls through to the success line, because returning from the branch posted no `done` and left the chat streaming. The two success lines are the exit a stop *usually* takes — a cancelled runner returns what it streamed with no error, so it never reaches an error branch — and they were the last to be covered. Pinned by `jobService.reportRunCompletion.test.ts` for the status write and by each streaming service's own test for the branch that produces it. Pinned by `src/main/services/jobService.reportRunCompletion.test.ts`, which drives it against a real in-memory database and asserts on `countInProgressByJob` — the sidebar's own question — rather than on the status column alone. It also writes the outcome onto `run.taskId` when there is one, through `taskService.applyRunState` (the run vocabulary, not a status derived here) plus a `setStatus(..., 'error')` when a failure carries a message. That write is **best-effort inside a try/catch**: a run that has genuinely finished must be recorded as finished even if the task write throws, or the sidebar counts it as busy for ever. A caller outside the two streaming services now produces `'failed'` as well — `runExecutionService.ts`'s `reportRefusal`, for a turn refused before either service owned it.
  - `setRunStatus(userId, runId, status, errorMessage?)` — manual cancel path.
- `src/main/services/cinnaApiService.ts`:
  - Internal `cinnaFetch<T>(userId, path, opts)` — bearer auth header, JSON encode/decode, 401/403 → `CinnaApiError('reauth_required', ...)`, network errors → `'request_failed'`, non-JSON → `'invalid_response'`.
  - `listAgents` — paginated response unwrapper; throws `CinnaApiError('invalid_response', ...)` if the response shape is unexpected.
  - `getTaskView(userId, taskId)` — single `GET /api/v1/tasks/{id}/detail` call; tolerant parsers map `TaskCommentPublic` and `TaskAttachmentPublic` to the desktop's `CinnaTaskCommentDto` / `CinnaTaskAttachmentDto`. See [Cinna Task Run View tech](../cinna_task_view/cinna_task_view_tech.md).

## Explicit Terminal Writes

`taskService.setStatus` expires next-message requests when a task becomes completed, error, cancelled or archived. If its linked attempt is pending/running, it records succeeded, failed, or cancelled respectively (archive cancels an active attempt); already terminal attempts keep their outcome. This matters after a next-message turn ended: no live stream remains to finish the idle job later.

`jobService.setRunStatus` leaves terminal attempts unchanged. A requested terminal result on an active attempt first updates its desktop-owned task through `applyRunState`, including claim validation and request expiry, then writes the job result. A task still claimed by another device refuses before the attempt is changed. This bookkeeping does not introduce a new cancel button or remotely cancel a service task.

`useJobList` and `useJobRuns` in `src/renderer/src/hooks/useJobs.ts` refetch every five seconds while cached data includes an active attempt, then stop when all attempts settle. Remote projection therefore updates the sidebar count and history for a local job handed to a service, without relying on a Cinna-only refresh control. See [remote status projection](../tasks/remote_sync.md#remote-status-finishes-the-current-attempt).

## Configuration

- Legacy adoption: `POLL_INTERVAL_MS = 5_000` in `useCinnaRunPoll.ts`, only while visible and only for active `legacy_adoption` rows. Bound task reads belong to `taskSyncScheduler`; Job queries separately poll saved rows while attempts remain active.
- Auto-save debounce: `DEBOUNCE_MS = 600` in `JobEditForm.tsx`.
- Recent runs limit: `RECENT_RUNS_LIMIT = 10` returned by `jobService.getDetail` (history view uses the full `listRuns`).
- Cinna server URL query stale time: `5 * 60_000` in `useCinnaServerUrl`.
- Minimum refresh-spin animation: `MIN_SPIN_MS = 500` in `JobRunRow.tsx` — keeps the spinner visible even when the cinna refresh IPC roundtrip resolves sub-frame.
- Task-view polling: `ACTIVE_REFETCH_MS = 5_000`, badge stale time: `BADGE_STALE_MS = 60_000` in `useCinnaTaskView.ts`.

## Security

- **Profile scope.** Every `jobsRepo` / `jobFoldersRepo` / `jobRunsRepo` query filters by `userId` (the active profile). Cross-profile access requires guessing both the entity id AND owning the right session — defense-in-depth even though all ids are already opaque.
- **Reorder authorization.** `jobService.reorderJobs` walks the submitted `orderedJobIds` and refuses the batch if any id is missing from the active profile or soft-deleted — a malicious renderer can't trip the transaction into touching another user's row even by guessing an id.
- **Cinna tokens.** `cinnaApiService` resolves tokens inside the main process via `getCinnaAccessToken(userId)`; the renderer never sees them. `CinnaReauthRequired` is mapped to `CinnaApiError('reauth_required', ...)` so the IPC boundary carries a stable code.
- **External URL open.** `app:open-external` validates `protocol === 'http:' || 'https:'` before invoking `shell.openExternal`, mirroring the renderer's `setWindowOpenHandler` policy.
- **Logger discipline.** `createLogger('job')` and `createLogger('cinna-api')`. Prompts and Cinna task bodies are NOT logged; only IDs, status, and timing. Network errors include URL + status code, not response bodies beyond the first 200 chars.
- **Transactional execution.** Ordinary desktop preparation includes chat, attachments, run, task and association/start writes. Remote acceptance cannot be rolled back; local run/link failure preserves the accepted task and receipt. See [transaction boundaries](execution_tech.md).

## Local schedule integration

[Local schedules](../tasks/local_schedules_tech.md) creates one-step script Jobs and admits them through scriptRuntimeService.prepareJob, linking its durable occurrence in the same transaction before launch. jobService.deleteRun notifies taskRunnerBridge.chatRemoved after the repository actually deletes the owned chat, so waiting gates/reservations are cancelled rather than stranded after Job-history deletion.
