# The Tasks View

## Purpose

One place to see every root task the profile has — whoever runs it, wherever it came from — as a card per agent with its work inside (**Agents**, the default), as one list by last change (**Recent**), as a board or as a list grouped by where the work stands, to write a new task down by hand and to move work that nobody is running between Backlog, Ready and Done. It sits beside the [Inbox](../tasks/inbox.md): the Inbox is what is waiting on the user, the Tasks view is all the work.

## Core Concepts

- **Status category** — the coarse place a task sits, and the only status vocabulary the user reads. Five categories, in lifecycle order: **Backlog** (`new`, `refining`), **Ready** (`open`), **In progress** (`in_progress`), **Waiting** (`blocked`), **Done** (`completed`, `error`, `cancelled`). `archived` has no category: it is the filed-away pile and the view leaves it out. Where a single task's status is named — the status pill, a row's spoken name, the dialogs — Done splits back into **Done**, **Failed** and **Cancelled**, because those are three different answers, and an archived task reads **Archived**.
- **User columns** — Backlog, Ready and Done: the categories a person may put a task in. In progress and Waiting are put there by a run or a question, never by a drag.
- **Manual move** — a status a person sets by hand, from the board or Edit task. It follows the [shared transition table](../tasks/tasks.md#business-rules) plus a small overlay for tasks bound to no service (below).
- **Custom field** — a named value the user attaches to a task (`estimate: 3`, `area: billing`, `labels: ui, docs`): text, a number, true/false or a flat list of those. Shown under **Fields** in the task page's Details.
- **Status word** — a [folder task](../tasks/folder_tasks.md)'s own word for its status (`doing`, `Up Next`), from its file. Wherever a status is named for such a task the word is shown as written, in the tone of the category it maps to; the category still decides everything else.
- **Folder board** — the board filtered to a bare agent whose tasks live in its folder: one column per status word instead of the five categories.
- **Agent card** — one agent's place in the Agents layout: the agent's icon (in its chosen colour) and name, a count of its open work, and its tasks as rows, on a plain frosted-glass card.
- **Period** — the Filters form's **Changed in**: **Last week** (the default), **Last month** or **All time**. It reaches only Backlog and Done, by last change; Waiting, In progress and Ready show whatever it says. It applies in every layout.
- **Filters block** — one bordered field in the header, left of New task: a pill per applied filter (the period unless it is All time, the agent, the search), each with an **×**, then the **Filters** button that opens the form. With nothing applied it is the Filters button alone.
- **Unassigned** — a task whose assignee is the default chat model and which has no conversation yet. Main stores "nobody yet" and "the default model" the same way, so until a chat runs it the task has nobody on it, and that is the word the page and the dialogs use. The Agent filter's **No agent**, and the Agents layout's **No agent** card, are wider: every task with no agent on it, including one the default model has already run.

## User Stories / Flows

1. **Open the view.** Click the **Tasks** button in the top bar, between the sidebar toggle and Agent Status. The view opens with no sidebar tab selected, like the Inbox; the button stays pressed while it is open.
2. **Read by agent.** The view opens on **Agents** unless the user chose another layout before. One card per agent that has a task the filters let through, A→Z by name; then **No agent**, when tasks with no agent pass. The card shows the agent's icon in its chosen colour; its name, underlined, opens the agent's page. The header counts open work as the rows' own status glyphs with a number each — Waiting, In progress, Ready — and its tooltip and accessible name say it as a sentence (*"1 waiting, 2 ready"*); a card with only Backlog and Done work shows its total as a bare number in a small badge, named *N tasks*. Rows are the shared task rows, Waiting first and Done last as in the list, the last changed first within each. A card shows six; **Show more tasks**, centred under them, slides the rest open as one unbroken list and becomes **Show less** at its foot.
3. **Read the list.** Switch to **List**: sections in the order the user acts on them: **Waiting**, **In progress**, **Ready**, **Backlog**, **Done**, each with its count. Every section is always there, even at zero. Done shows ten rows and **Show more tasks** for the rest; the other sections show everything. Rows are the same task rows a task page's Subtasks and the chat's Tasks badge use, and name each row's agent while the filter is **All agents**.
4. **See what changed lately.** Switch to **Recent**: one section, every task the filters let through, the last changed first, ten rows and then **Show more tasks**. The chat Tasks badge's **Open Tasks** opens the view here.
5. **Use the board.** Switch **Agents | Recent | Board | List** — the choice is remembered. Five columns in lifecycle order: Backlog, Ready, In progress, Waiting, Done. A card shows its status icon, title, agent and a mark for high or urgent priority. Filtered to a bare agent that keeps its tasks in `.cinna/tasks/`, the board is that folder's own words instead — see [the folder board](../tasks/folder_tasks.md#the-folder-board); until the agent's columns are read the board shows the loading line rather than five columns it would then replace.
6. **Narrow it.** **Filters**, the last part of the filters block, opens a small form with the search focused: the title search, **Agent** (**All agents**, then every agent that has a task, A→Z, then **No agent**) and **Changed in** (Last week, Last month, All time), with the note *Waiting, In progress and Ready always show.* Every change applies at once; there is no Apply. Escape closes the form and puts focus back on Filters; a click outside it or a scroll of the view closes it too. What is applied shows as pills inside the block, to the left of Filters: the period (*Last week* to begin with; none for All time), the agent, the search in quotes. A pill's **×** clears its filter — **Remove Last week** sets the period to All time, **Remove the <agent> filter**, **Clear the search** — and focus moves to Filters. Pills slide open and shut rather than appearing. When the filters leave nothing, one line says why: **No tasks match.** for a search, or for an agent with no task at all; else the period's words — *No tasks in the last week.*
7. **Write a task down.** **New task** asks for a title and nothing else; Enter creates it and the user lands on its page. **More options** holds the goal (defaults to the title), priority, Backlog or Ready (Backlog by default — named in the assignee folder's own words when it keeps a task folder), the assignee (Unassigned or an enabled agent) and custom fields. A task for an enabled bare agent is written into that agent's `.cinna/tasks/` as a file; every other task is stored here only.
8. **Move a task.** Drag a card to Backlog, Ready or Done, or use the card's **⋯ → Move to…** — the same moves, reachable by keyboard. The card moves at once; if main refuses, it goes back and the reason appears in one line under the header.
9. **Edit a task.** On the task page, **⋯ → Edit task…** opens every field: title, description, priority, status (the manual targets only — a folder task's in its folder's words), assignee and custom fields. A field that cannot change says why in one line under it. A folder task's nested or long custom fields are listed under **Read-only fields**, to be edited in the file.
10. **Run the agent's queue.** Filtered (**Filters → Agent**) to one folder agent whose queue Cinna works, the controls row gains a split button right after the layout switch: **Run next** starts that agent's next Ready task, and the chevron opens the run mode (**Manual**, **One at a time**, **Up to N** with **−** / **+** on its line) with the current one checked. A started task stays where it is in the view: its row moves to In progress by itself. A task whose file needs approval opens the Inbox on its card. When the queue is paused, the left half becomes **Resume** in the warning tone, and its tooltip says what paused it. The menu then also offers the task it paused on and Run next. See [the task dispatcher](../tasks/task_dispatcher.md).
11. **Go back.** A task page opened from the Tasks view — or reached from such a page through its parent or a subtask — shows **Back to Tasks**, which returns to the same layout, agent and period; the search starts empty again.
12. **Turn it off.** Settings → Features → Interface → **Tasks button** (on by default) removes the button; turning it off while the view is open returns to the chats.

## Business Rules

### Categories, not raw statuses

- **The user reads categories.** `in_progress` is a column name, and `refining` and `new` mean the same thing to someone looking at their work. Every surface that names a status — the pill, the page's status icon tooltip, a row's accessible name, a card, the dialogs — uses the same words, so a task is not "Backlog" on the board and "new" on its page. A folder task names its status by its file's word on every one of those surfaces alike, for the same reason: the word the agent and the file use is the one the user reads.
- **A status this build does not know prints itself.** The run screen's pill can carry a value an older server sends (`succeeded`); it reads as words, never guessed into a category.
- **Archived is not on the view.** The root query excludes it, in every layout.

### Manual moves

- **Only from a user column, only to a user column (or Cancelled).** A task In progress or Waiting belongs to a run or a question: closing it by hand would settle a run that is still working. Main refuses with *"This task is in progress — let its run finish it, or stop the run."* or the Waiting equivalent, and the board offers no drag or ⋯ for such a card. **One exception: a task the [dispatcher](../tasks/task_dispatcher.md) flagged** (Waiting with *Ended without reporting* or *Interrupted when Cinna quit*) waits on no one, so it moves by hand like a task in a user column — refused still while a question is open for it, a turn is live in its chat or a runtime owns it.
- **The overlay exists for work no service judges.** The pinned table cannot send a task back from Ready to Backlog, nor close one that never started. For a task that lives only here that is bookkeeping, so three moves the table lacks are added: Ready → Backlog, Backlog → Done and Ready → Done. A task **bound** to a service keeps the table unchanged, because its status goes up as a path of legal steps and these pairs have none — the board offers that task only what the service would accept. A [folder task](../tasks/folder_tasks.md) is bound too, but a file keeps no transition table (`transitionTable: false`), so it moves by the overlay like an unbound task.
- **Done is where finished work stays.** Done, Failed and Cancelled have nowhere to go by hand, except that a Failed task may go back to Backlog (the table's `error → new`). Archiving and reopening are not manual moves.
- **Refused while something else owns the status.** A coordinator or script runtime ends its task and keeps a checkpoint for it; a turn live in the task's chat is about to write the status itself. A manual move is refused in both cases, with the reason.
- **A manual close does not invent a job result.** Closing a task by hand when its job run is still pending or running is refused: settling that run as succeeded would record work that never happened. A task whose run already finished is closed alone.
- **The task must be held here.** Like every status write, the device claim decides: a task another device holds or a remote service runs has no moves on the board.
- **Refusals are sentences.** Main words a refused move in category words — *"This task can't move from Ready to Done: it is tracked on the connected service, which doesn't allow that step."* — and never names the service, which is the adapters' business.
- **A folder board adds Cancelled and its own words.** Its droppable columns are every column whose status is `new`, `open`, `completed` or `cancelled` — never Active, Waiting, Failed, Hidden or an unmapped word. A drop of a file task sends the column's word with its status, and main refuses a word that does not mean that status in that folder, or any word for a task with no file. The rules are in [Folder Tasks](../tasks/folder_tasks.md#the-folder-board).
- **A drop does not flicker back.** The board shows the moved card in its new column until a read confirms the write, or shows any status other than the one the move left — something newer has spoken, and the read is the truth again. A second move of the same card keeps its own pending state.

### Writing and editing tasks

- **New task asks for one thing.** Everything main can default, it defaults: the goal is the title, it starts in Backlog, it is local, run by this desktop (claimed by this device once the profile has a sync identity) and routed directly. A new task can start only in Backlog or Ready.
- **The assignee is fixed once a run could have started from it.** It can change only while the task has no conversation, this device holds the claim, no service is bound (the remote assigns its own), it does not live in an agent's folder (the folder is the assignee), it is not a script (its steps name their agents) and no runtime owns it. The dialog disables the control with the reason; main refuses the write regardless. Title, description, priority and custom fields stay writable when the assignee is not.
- **Only an enabled agent can be chosen.** An agent missing from the profile, or switched off in it, is refused with *"That agent is unavailable. Choose another agent."*
- **Edit task writes the status first.** It is the write main is likelier to refuse, and when it is refused nothing has been saved. If the status saves and the rest is refused, the dialog says exactly that and keeps the other edits in the form.
- **Dialogs close on success only.** A refusal stays in the dialog. Escape and an outside click close an untouched form; once the user has typed, Cancel is the only way to discard it.

### Custom fields

- **Scalars and flat lists, named like identifiers.** A key starts with a letter, then letters, digits, `-` or `_`, at most 64 characters; at most 50 fields; text at most 2000 characters. Nested values are refused because the task file format keeps them as frontmatter, where a nested value would not survive a line-level edit. A nested value a task file already holds is shown read-only and never written.
- **Built-in names are reserved.** `status`, `title`, `priority`, `assignee`, `goal`, `description`, `id`, `parent`, `blocked_by`, `origin`, `created`, `updated` and `cinna_task` belong to the task file format; a custom `status` would be read back as the task's status.
- **Edited values are text.** A value the user types is stored as text; a number or a list the user did not touch keeps its type.
- **Shown as written.** Under their own **Fields** heading in Details, keys in the user's own case rather than the built-in rows' small capitals, so a field called "Status" cannot be mistaken for the task's status. An empty value has no row; no non-empty field, no heading.
- **They travel to the user's other devices, and to a task file — not to a service.** A bound task's custom-field edit carries a remote dirty marker like any field; a [folder task](../tasks/folder_tasks.md) writes it into its file's frontmatter, and a service with no field for them (cinna-core) drops the marker on the next push. On device sync, a payload from an older build that does not carry the key keeps this device's fields; an explicit null clears them; a value this build refuses is left alone rather than half-applied. See [A Task on the User's Other Devices](../tasks/cross_device.md).

### Agents and the period

- **A card is an agent with work to show.** Only an agent that has a task the current filters let through gets a card, and **No agent** only while tasks with no agent do; a card comes and goes with its agent's tasks. The Agent filter likewise offers only agents that have a task. A search or an agent filter therefore narrows the cards by itself — to the agents it finds something for, or to the one agent.
- **Cards are A→Z by name, No agent last.** A fixed order, so a poll never reorders the cards.
- **The period never hides open work.** Waiting, In progress and Ready are held by a question, a run or the queue, and a stuck task is exactly the one that must not drop out of sight for having sat still. The period reaches only Backlog and Done, by when they last changed; in every layout, the board's columns and Recent included.
- **The period lasts the window, starting at Last week.** It is kept while the window lives, like the agent filter, so Back to Tasks finds it unchanged; every launch starts at Last week. A boundary crossed while the view is open is applied at the next poll.
- **The header counts open work first.** Waiting, In progress and Ready, as glyphs and numbers, with the words in the tooltip and the accessible name, so a screen reader hears what a sighted user decodes from the icons. Backlog and Done are not counted; a card with only those shows its total as a bare number, the words again in its name and tooltip.
- **The agent's colour is on its icon, not on the card.** Cards are plain frosted glass, lighter than a popover so the page shows through; the chosen colour stays where it is everywhere else, on the agent's type icon.
- **A card pages in place, and trades the lists' Show more rule for it.** Six rows, then **Show more tasks**; the rest slides open below the first six, flush with them, and the button becomes **Show less** at the foot, so the card reads as one list that can fold again. This is a deliberate exception, by user decision, to the lists' rule below: opening carries the button down while rows slide in under the pointer. A card that falls back to six rows folds itself, so a seventh task arriving later shows **Show more**, not **Show less**.
- **The filters block grows leftwards.** It sits at the row's right end beside New task, and its pills open into the free space to its left, so the Filters button — and the form anchored under it — never moves, and typing a search moves nothing the user is looking at. That is also why Run next sits left of the gap rather than beside Filters: a growing block must not push it about. Every pill is always there and opens and closes by animation, so a filter change resizes the block smoothly whether it came from an × or from the form. A pill's × hands focus to Filters, because the pill it was on goes inert as it closes.

### Layout

- **Nothing moves under the user.** Every list section and board column is always present; rows keep the order they were first seen for as long as the view is open, so a poll cannot move a row under the pointer — in Recent, in List and in each agent card, where a task an agent is writing to keeps its place instead of jumping to the top, and a task new to the list joins at the end. Changing the agent or the period takes the order again, since those rows were never seen there, and so does starting or clearing a search — rows first seen through a search would otherwise keep their places above a card's Waiting rows once it is cleared — but a keystroke does not. A refused move's sentence is laid over the gap under the header rather than inserted above the content; the drop highlight is an outline, not a border, so a column never resizes.
- **The Agents grid does reflow, as list sections do.** A card that grows lowers the cards below it, and a card comes and goes with its agent's tasks; no row moves inside a card.
- **Show more leaves nothing clickable under the pointer that pressed it** — in the lists. It reveals every remaining row at once, below its own slot, and the slot keeps its line as an inert **All N shown**. The pointer rests on text and nothing above it moved. Pushing the button down and putting a task row where it was would have made a second click open a task nobody chose. Done, Recent, the board's Done column, a task page's Subtasks and a job's Tasks history all page this way; the agent cards do not (above).
- **Controls first, in one row.** Title, Agents | Recent | Board | List, Run next when there is a queue, the gap, the filters block and New task stay on one line down to the 800 px minimum beside the sidebar: the layout switch drops its words for icons, Filters and New task keep only their glyphs (the names stay in their tooltips and accessible names), and the pills truncate to a few letters and their × — the agent and search pills first, the period's last. The search, the agent and the period sit behind Filters, so the row holds the same controls at every width; the form is a popover over the page, so typing in it moves nothing behind it. Every layout shares one width, so switching between them moves no control.
- **The queue control follows the agent filter, never the search.** It appears only when the agent filter names a folder agent with a queue, so typing in the search moves nothing. At narrow widths Run next drops its word for its icon. A pause changes the control in place and adds no row above the list, so a poll that pauses the queue moves nothing; the Inbox card is what asks for attention. Its actions belong to the view, not to the menu, so a result outlives the menu closing. A refusal shows in the same overlay slot as a refused move, right-aligned. It is secondary-styled, so New task stays the row's one primary action.
- **A refusal belongs to the filter it was made under.** Changing the agent or the period clears a refused move's or the queue's sentence, so a stale reason never outlives the board it was about.
- **The view polls, like the Inbox.** The root list re-reads every five seconds, and opening the view nudges device sync as the Inbox and task page do — the rows read local SQLite, so without it a task another device finished would read In progress until the next sync cycle. A failed read keeps the rows and shows **Try again** below them. A failed **first** read draws no cards and no empty line, only that line: nothing is known yet, and *No tasks yet.* would be a claim.

### Where the work is happening

- **A task with a chat says so on its row.** A task bound to a conversation visible here shows, on a regular row (the Tasks view's lists and Agents cards, and the agent page's task list), "in <chat name>" after the title in the muted small size. The title wins the width: the name gives way, down to nothing, before the title loses a character. A chat with no name worth showing — blank, or the default "New Chat" — adds nothing, and a compact row (a task page's Subtasks) has no room for the name at all.
- **A pulsing dot says a turn is live in that chat.** It is the accent colour and pulses like the app's other live dots (the sidebar's session status). It is drawn for every task that has a chat and made invisible while the chat is idle, so a poll that flips it moves nothing beside it (`ux_rules.md` rule 1). It is decorative; the row's accessible name says ", running" and the chat's name, since a screen reader should hear what a sighted user sees. A compact row keeps the dot even where the name is dropped.
- **On the board the dot is a badge on the status icon,** pinned to its corner and out of the flow, so a card never gains a line and a flip moves nothing. The card's accessible name says ", running" too.
- **The chat's own Tasks popover hides both.** The popover under the composer lists the chat's tasks inside the chat that already shows its own turn live; a dot and a name there would repeat the surface they sit on. (`hideChat` on the row. A task page's Subtasks, each in a chat of its own, keep the dot.)
- **A task without a visible chat shows nothing.** No chat, a chat this profile cannot see, or one in the Trash: the row is as it was. The task page's **Chat** row follows the same rule ([Tasks and the Inbox](../tasks/tasks.md)).
- **Why it is there.** An agent can take a task on in its own conversation ([Agent Task Tools](../tasks/agent_task_tools.md#taking-a-task-on-attach)), and such a task is not settled by a turn ending. "In progress" alone would not tell the user whether anything is happening or where; the name and the dot do.

## Architecture Overview

```
Top bar Tasks button / chat Tasks badge's Open Tasks (mode 'recent') → ui.store activeView 'tasks' → TasksView (Agents | Recent | Board | List)
TasksView → useTaskList({rootOnly}) → task:list → taskService.list → period, agent and search filters in the renderer (ui.store: agent, period; view state: search)
Agents layout → agentCards(filtered tasks) → one card per agent with a task → TaskRow
Board drop / ⋯ Move to / Edit task status → task:set-status (status, folder word?) → taskAuthoringService.setStatus → taskService.setStatus(…, {manual: true, bound, label})
Folder board → task:folder-board → taskSyncService.folderBoard → folder adapter localHome.board
Filtered to one folder agent → taskDispatch:list / run-next / set-mode / resume → taskDispatchService
New task → task:create → taskAuthoringService.createRouted → taskService.create | taskSyncService.createInHome (bare agent: writes the file)
Edit task fields → task:update → taskAuthoringService.update → taskService.update
Task write → device sync (custom fields travel; folder tasks never do) / bound push (custom fields to a task file only)
```
